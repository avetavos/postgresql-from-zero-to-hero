When many transactions run at once, they can interfere with each other in ways that produce surprising results. An **isolation level** is the dial that controls how much one transaction is protected from the in-progress work of others. Turning the dial up prevents more anomalies but makes conflicts more likely to fail and need a retry.

Everything below was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). Each concurrency example is a real run of two `psql` processes started at the same moment, printed as they came back. A line `\o /dev/null` around `pg_sleep(n)` just hides the empty result of the sleep, so a session can wait while the other one works.

Two tables are used: `accounts` for reads and updates, and `doctors` for the classic write-skew story (a hospital rule says at least one doctor must stay on call).

```sql
-- sql/setup.sql
CREATE TABLE accounts (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner   text NOT NULL,
  balance numeric NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts (owner, balance) VALUES ('Ada', 500), ('Linus', 100);

CREATE TABLE doctors (name text PRIMARY KEY, on_call boolean NOT NULL);
INSERT INTO doctors VALUES ('alice', true), ('bob', true);
```

## The anomalies

The SQL standard names a set of phenomena that weaker isolation allows. PostgreSQL's levels are defined by which of these they forbid ([docs, table 13.1](https://www.postgresql.org/docs/18/transaction-iso.html)).

- **Dirty read** — reading a row another transaction has changed but not yet committed. PostgreSQL never allows this at any level.
- **Non-repeatable read** — reading the same row twice in one transaction and getting different committed values because another transaction changed it in between.
- **Phantom read** — running the same search twice and finding rows that were not there the first time because another transaction inserted them.
- **Serialization anomaly (write skew is the classic one)** — two transactions each read an overlapping set of rows, then each writes based on what it read, producing a result no single serial order could have created.

This is what PostgreSQL allows at each level, straight from the documentation. The last column says how this lesson reproduces the cell:

| Level | Dirty read | Non-repeatable read | Phantom read | Serialization anomaly | Proved here |
|---|---|---|---|---|---|
| Read Uncommitted | not possible (behaves as Read Committed) | possible | possible | possible | dirty-read run |
| Read Committed (default) | not possible | possible | possible | possible | Ada 500 then 600; count 2 then 3 |
| Repeatable Read | not possible | not possible | not possible in PostgreSQL | possible | 500 and 500; write skew commits both |
| Serializable | not possible | not possible | not possible | not possible | write skew raises `40001` |

Read Uncommitted is accepted as a name but internally it is Read Committed, because PostgreSQL never shows uncommitted data. Repeatable Read is stronger than the SQL standard requires: phantoms cannot happen either.

## Read Committed: a fresh snapshot per statement

Read Committed is the default. Each statement sees a snapshot of everything committed before that statement began, which is why two reads in the same transaction can disagree. Session A reads Ada's balance and counts the accounts with at least 100, waits two seconds, and reads again. One second in, session B adds 100 to Ada and inserts a new account, both committed at once:

```text
-- session A: script
BEGIN;
SELECT balance AS ada_first FROM accounts WHERE owner = 'Ada';
SELECT count(*) AS rich_first FROM accounts WHERE balance >= 100;
\o /dev/null
SELECT pg_sleep(2);
\o
SELECT balance AS ada_second FROM accounts WHERE owner = 'Ada';
SELECT count(*) AS rich_second FROM accounts WHERE balance >= 100;
COMMIT;
-- session A: psql output
BEGIN
 ada_first 
-----------
       500
(1 row)

 rich_first 
------------
          2
(1 row)

 ada_second 
------------
        600
(1 row)

 rich_second 
-------------
           3
(1 row)

COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance + 100 WHERE owner = 'Ada';
INSERT INTO accounts (owner, balance) VALUES ('Grace', 300);
-- session B: psql output
UPDATE 1
INSERT 0 1
```

The second read sees Ada's new balance (a **non-repeatable read**: 500 became 600) and a new row (a **phantom**: the count went from 2 to 3). Both changes were committed by B between A's two statements.

## Repeatable Read: one snapshot per transaction

At Repeatable Read the first query takes a snapshot and every later statement in the transaction uses it. The very same script, with only the first line changed:

```text
-- session A: script
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance AS ada_first FROM accounts WHERE owner = 'Ada';
SELECT count(*) AS rich_first FROM accounts WHERE balance >= 100;
\o /dev/null
SELECT pg_sleep(2);
\o
SELECT balance AS ada_second FROM accounts WHERE owner = 'Ada';
SELECT count(*) AS rich_second FROM accounts WHERE balance >= 100;
COMMIT;
-- session A: psql output
BEGIN
 ada_first 
-----------
       500
(1 row)

 rich_first 
------------
          2
(1 row)

 ada_second 
------------
        500
(1 row)

 rich_second 
-------------
           2
(1 row)

COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance + 100 WHERE owner = 'Ada';
INSERT INTO accounts (owner, balance) VALUES ('Grace', 300);
-- session B: psql output
UPDATE 1
INSERT 0 1
```

Ada is still 500 and the count is still 2, although B had committed both changes long before A's second read. The snapshot is the reason reads are stable; the price is that A is now working with data it knows may be stale, which matters as soon as A wants to write.

## Dirty reads never happen

Asking for `READ UNCOMMITTED` is allowed, and `SHOW` confirms the level was accepted. Session B updates Ada but does not commit; A, one second later, still sees the committed value:

```text
-- session A: script
BEGIN ISOLATION LEVEL READ UNCOMMITTED;
SHOW transaction_isolation;
\o /dev/null
SELECT pg_sleep(1);
\o
SELECT balance AS ada_sees FROM accounts WHERE owner = 'Ada';
COMMIT;
-- session A: psql output
BEGIN
 transaction_isolation 
-----------------------
 read uncommitted
(1 row)

 ada_sees 
----------
      500
(1 row)

COMMIT

-- session B: script
BEGIN;
UPDATE accounts SET balance = balance + 100 WHERE owner = 'Ada';
\o /dev/null
SELECT pg_sleep(2);
\o
ROLLBACK;
-- session B: psql output
BEGIN
UPDATE 1
ROLLBACK
```

## Setting the level

You choose the level for one transaction, either with `BEGIN ISOLATION LEVEL ...` or with `SET TRANSACTION ISOLATION LEVEL ...` as the first statement after `BEGIN`. The default for new transactions is `default_transaction_isolation`.

```sql
-- sql/set-level.sql
SHOW default_transaction_isolation;

BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SHOW transaction_isolation;
COMMIT;

-- the same thing in one line
BEGIN ISOLATION LEVEL SERIALIZABLE;
SHOW transaction_isolation;
ROLLBACK;
```

```text
 default_transaction_isolation 
-------------------------------
 read committed
(1 row)

BEGIN
SET
 transaction_isolation 
-----------------------
 repeatable read
(1 row)

COMMIT
BEGIN
 transaction_isolation 
-----------------------
 serializable
(1 row)

ROLLBACK
```

Once any query has run, the level can no longer change ([docs](https://www.postgresql.org/docs/18/sql-set-transaction.html)):

```sql
-- @expect-error 25001
BEGIN;
SELECT 1;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

```text
BEGIN
 ?column? 
----------
        1
(1 row)

ERROR:  SET TRANSACTION ISOLATION LEVEL must be called before any query
```

## How a level decides what to allow

The decision is the same shape every time: when a statement reads data, the level determines which snapshot it sees and whether a conflicting commit by someone else can affect the outcome.

export const isoFlow = `flowchart TD
  A[Statement reads data] --> B{Isolation level}
  B -->|Read Committed| C[Fresh snapshot per statement]
  B -->|Repeatable Read| D[One snapshot for the whole transaction]
  B -->|Serializable| E[Snapshot plus conflict tracking]
  C --> F[Same row may differ on a second read]
  D --> G[Repeated reads are stable]
  E --> H[Abort if the result could not occur serially]`;

## Writing under Repeatable Read

The snapshot that makes reads stable also means A may try to change a row that has changed since its snapshot. The two levels behave differently. At Read Committed, an `UPDATE` waits for the other writer, re-reads the newest version of the row, and applies its change to that (so a relative update like `balance - 50` does not lose B's +100):

```text
-- session A: script
BEGIN;
SELECT balance AS a_snapshot_sees FROM accounts WHERE owner = 'Ada';
\o /dev/null
SELECT pg_sleep(2);
\o
UPDATE accounts SET balance = balance - 50 WHERE owner = 'Ada';
COMMIT;
-- session A: psql output
BEGIN
 a_snapshot_sees 
-----------------
             500
(1 row)

UPDATE 1
COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance + 100 WHERE owner = 'Ada';
-- session B: psql output
UPDATE 1

-- afterwards:
SELECT owner, balance FROM accounts WHERE owner = 'Ada';
 owner | balance 
-------+---------
 Ada   |     550
(1 row)
```

At Repeatable Read, A's snapshot still says 500 while the row now says 600, so applying A's update would silently overwrite something A never saw. PostgreSQL refuses instead:

```text
-- session A: script
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance AS a_snapshot_sees FROM accounts WHERE owner = 'Ada';
\o /dev/null
SELECT pg_sleep(2);
\o
UPDATE accounts SET balance = balance - 50 WHERE owner = 'Ada';
COMMIT;
-- session A: psql output
BEGIN
 a_snapshot_sees 
-----------------
             500
(1 row)

ERROR:  could not serialize access due to concurrent update
ROLLBACK

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance + 100 WHERE owner = 'Ada';
-- session B: psql output
UPDATE 1

-- afterwards:
SELECT owner, balance FROM accounts WHERE owner = 'Ada';
 owner | balance 
-------+---------
 Ada   |     600
(1 row)
```

A must roll back and start again on a fresh snapshot. Whenever you use Repeatable Read or Serializable for a writing transaction, this error is an expected outcome, not a bug.

## Write skew: what Repeatable Read cannot see

Two doctors, alice and bob, are both on call. The rule: at least one must stay. Each checks that two are on call, thinks about it, and takes themself off. They write to different rows, so there is no write conflict, and each snapshot said 2. At Repeatable Read both commit:

```text
-- session A: script
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) AS on_call_now FROM doctors WHERE on_call;
\o /dev/null
SELECT pg_sleep(2);
\o
UPDATE doctors SET on_call = false WHERE name = 'alice';
COMMIT;
-- session A: psql output
BEGIN
 on_call_now 
-------------
           2
(1 row)

UPDATE 1
COMMIT

-- session B: script
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) AS on_call_now FROM doctors WHERE on_call;
\o /dev/null
SELECT pg_sleep(2);
\o
UPDATE doctors SET on_call = false WHERE name = 'bob';
COMMIT;
-- session B: psql output
BEGIN
 on_call_now 
-------------
           2
(1 row)

UPDATE 1
COMMIT

-- afterwards:
SELECT name, on_call FROM doctors ORDER BY name;
 name  | on_call 
-------+---------
 alice | f
 bob   | f
(2 rows)
```

Nobody is on call. This is **write skew**, and it is allowed at Read Committed and Repeatable Read.

## Serializable and retries

Serializable is the strongest level: PostgreSQL guarantees the outcome is as if the concurrent transactions had run one after another in some order. It tracks which transactions read what the others wrote, and when it finds a dangerous pattern it aborts one of them with a **serialization failure** (SQLSTATE `40001`). The same two-doctor script at Serializable:

```text
-- session A: script
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) AS on_call_now FROM doctors WHERE on_call;
\o /dev/null
SELECT pg_sleep(2);
\o
UPDATE doctors SET on_call = false WHERE name = 'alice';
COMMIT;
-- session A: psql output
BEGIN
 on_call_now 
-------------
           2
(1 row)

UPDATE 1
COMMIT

-- session B: script
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) AS on_call_now FROM doctors WHERE on_call;
\o /dev/null
SELECT pg_sleep(2);
\o
UPDATE doctors SET on_call = false WHERE name = 'bob';
COMMIT;
-- session B: psql output
BEGIN
 on_call_now 
-------------
           2
(1 row)

UPDATE 1
ERROR:  could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during commit attempt.
HINT:  The transaction might succeed if retried.

-- afterwards:
SELECT name, on_call FROM doctors ORDER BY name;
 name  | on_call 
-------+---------
 alice | f
 bob   | t
(2 rows)
```

One doctor stays on call. The loser gets `40001` at `COMMIT` with a `HINT` that says exactly what to do: retry. That is not a bug; it is the level doing its job. Which of the two transactions loses is not predictable, so the application must catch the error and run the whole transaction again ([docs](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE)). The retry must re-run the reads too, because the second attempt should see the first doctor already gone.

      for (let attempt = 1; attempt <= 5; attempt++) {
        const client = await pool.connect();
        try {
          await client.query('BEGIN ISOLATION LEVEL SERIALIZABLE');
          const { rows } = await client.query('SELECT count(*)::int AS n FROM doctors WHERE on_call');
          await client.query('SELECT pg_sleep(2)'); // stands in for slow application logic
          if (rows[0].n >= 2) {
            await client.query('UPDATE doctors SET on_call = false WHERE name = $1', [name]);
          }
          await client.query('COMMIT');
          console.log(`${name}: attempt ${attempt} committed (saw ${rows[0].n} on call)`);
          return;
        } catch (e) {
          await client.query('ROLLBACK').catch(() => {});
          if (e.code !== '40001' || attempt === 5) throw e; // retry only serialization failures
          console.log(`${name}: attempt ${attempt} failed with ${e.code}, retrying`);
        } finally {

        }
      }
    }

    	conn, err := pgx.Connect(ctx, dsn)
    	if err != nil {
    		return err
    	}
    	defer conn.Close(ctx)
    	for attempt := 1; attempt <= 5; attempt++ {
    		var n int
    		err = pgx.BeginTxFunc(ctx, conn, pgx.TxOptions{IsoLevel: pgx.Serializable}, func(tx pgx.Tx) error {
    			if err := tx.QueryRow(ctx, "SELECT count(*) FROM doctors WHERE on_call").Scan(&n); err != nil {
    				return err
    			}
    			if _, err := tx.Exec(ctx, "SELECT pg_sleep(2)"); err != nil { // stands in for slow application logic
    				return err
    			}
    			if n >= 2 {
    				_, err := tx.Exec(ctx, "UPDATE doctors SET on_call = false WHERE name = $1", name)
    				return err
    			}
    			return nil
    		})

    		return err
    	}
    	return nil
    }

    fn is_serialization_failure(e: &sqlx::Error) -> bool {
        e.as_database_error().and_then(|d| d.code()).as_deref() == Some("40001")
    }

    async fn go_off_call_once(pool: &sqlx::PgPool, name: &str) -> Result<i64, sqlx::Error> {
        let mut tx = pool.begin().await?;
        sqlx::query("SET TRANSACTION ISOLATION LEVEL SERIALIZABLE").execute(&mut *tx).await?;
        let n: i64 = sqlx::query_scalar("SELECT count(*) FROM doctors WHERE on_call")

        if n >= 2 {

        }
        tx.commit().await?;
        Ok(n)
    }

    async fn go_off_call(pool: &sqlx::PgPool, name: &str) -> Result<(), sqlx::Error> {

                Err(e) => return Err(e),
            }
        }
        Ok(())

Two details are easy to miss. First, retry only `40001` (and `40P01`, the deadlock error from the locking lesson): other errors are bugs and retrying them hides them. Second, the failure can arrive from any statement, including the `UPDATE`, not just from `COMMIT`; that is why each snippet keeps the whole transaction inside the loop.

## Reading AI-generated code

An assistant is asked to fix the hospital race. It knows Serializable prevents write skew, switches the level, and leaves a confident comment:

<SpotTheBug lang="js" code={`// AI comment: "SERIALIZABLE prevents write skew, so this is safe"
async function goOffCall(pool, name) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN ISOLATION LEVEL SERIALIZABLE');

    throw e;
  } finally {
    client.release();
  }

The isolation level is right and the code is still broken: it has no retry. Serializable does not make the conflict disappear, it turns a silent data error into a `40001` that someone has to handle. Calling the function for alice and bob at the same moment (pg 8.23.0):

```text
$ node serializable-no-retry.js   # alice and bob call goOffCall at the same moment
alice fulfilled 
bob rejected 40001 could not serialize access due to read/write dependencies among transactions
afterwards alice=false, bob=true
```

The rule is preserved (bob is still on call), but bob's request fails and the user sees an error for something the application could have handled. Under real load a large share of requests would fail this way. The fix is the retry loop above: run the whole transaction again on `40001`, capped at a few attempts. The `goOffCall` in the Node.js tab is that fix, and its run is the Node.js block of the retry output.

## Mental Model

Think of each level as a different promise about what you can see. Read Committed says "each statement sees the world as of the moment it started". Repeatable Read says "your whole transaction sees the world as of your first query". Serializable says "and I will also make sure your result matches some order in which you ran one at a time, or I will cancel you". A higher level never makes the database wait more; it makes a transaction more likely to be told to try again.

## Tips / gotchas

- Read Committed is the right default for most workloads; only raise the level when you have a real anomaly to prevent.
- At Serializable (and Repeatable Read for write conflicts), always wrap the transaction in a retry loop that re-runs it on SQLSTATE `40001`. The hint in the error even tells you so.
- Set the isolation level at the very start of the transaction. Once data has been accessed, you cannot change it (`25001`).
- A higher level is not "more correct" for free. It trades a higher chance of aborts for stronger guarantees, so measure before reaching for Serializable everywhere.
- Long transactions at Repeatable Read or Serializable hold a snapshot that keeps dead row versions alive (see the MVCC lesson).

<Callout title="Pick the weakest level that is still correct">
Isolation is about ruling out specific anomalies, not about being maximally strict. Identify which anomaly would actually break your logic, choose the lowest level that forbids it, and add a retry loop if that level can abort. Correct and cheap beats strict and slow.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| Serializable (strictest) | Prevents every anomaly, including write skew (one doctor stayed on call) | Some transactions abort with `40001` and must be retried; the retry has a cost |
| Repeatable Read | Stable snapshot for reports and multi-statement reads (500 and 500) | Write skew still commits (nobody on call); concurrent updates fail with `could not serialize access due to concurrent update` |
| Read Committed (the default) | High throughput, almost no aborts from isolation conflicts | Non-repeatable reads and phantoms happen (500 then 600, 2 then 3) |

## Common Misconceptions

- **"Serializable means transactions run one at a time."** They still run concurrently; PostgreSQL only cancels the ones that could not have been run serially.
- **"Repeatable Read prevents all anomalies."** It prevents non-repeatable reads and phantoms but not write skew: both doctors went off call.
- **"A 40001 is an application bug."** It is the documented, expected answer; the fix is a retry loop, not a lower isolation level.
- **"READ UNCOMMITTED lets you see dirty data."** In PostgreSQL it behaves as Read Committed, as the dirty-read run shows.
- **"Choosing Serializable without a retry loop is safe."** The data stays correct, but requests fail.
