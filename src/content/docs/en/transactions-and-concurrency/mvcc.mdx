The isolation levels in the previous lesson all rest on one engine: **Multi-Version Concurrency Control**, or MVCC. Its promise is simple to state and powerful in practice — writers do not block readers, and readers do not block writers. A long report can keep reading while updates pour in, and neither side waits on the other ([docs](https://www.postgresql.org/docs/18/mvcc-intro.html)).

Everything below was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). Transaction ids and page numbers are different on every cluster, so read the numbers for their relationships (this one is one higher than that one), not for their values. The `pageinspect` extension is used to look at raw heap pages; it is a contrib module that only a superuser can install, so it belongs in a lab, not in production.

```sql
-- sql/setup.sql
CREATE EXTENSION pageinspect;  -- a contrib extension for looking inside pages; needs a superuser

CREATE TABLE accounts (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner   text NOT NULL,
  balance numeric NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts (owner, balance) VALUES ('Ada', 500), ('Linus', 100);
```

## The core idea: never overwrite in place

When you `UPDATE` a row, PostgreSQL does not change the existing bytes. It writes a **new version** of the row and marks the old version as superseded. For a moment both versions exist on disk. Which one a given transaction sees depends on when that transaction started.

Each row version carries hidden system columns that record its lifetime:

- `xmin` — the id of the transaction that created this version.
- `xmax` — the id of the transaction that deleted or replaced it (zero while the version is live).
- `ctid` — where this version physically lives: (page number, line pointer).

A transaction sees a version only if it was created by a transaction that had committed before the reading transaction's snapshot, and not yet replaced as far as that snapshot is concerned.

## Each transaction reads a snapshot

A **snapshot** is the set of committed data a transaction is allowed to see. Under Read Committed each statement takes a new snapshot; under Repeatable Read and Serializable the whole transaction shares one. Because reads are answered from the snapshot, an ordinary `SELECT` never needs to lock anything and never waits for a writer.

A's second read shows the old version with its `xmax` already filled in (B's transaction id), yet A still sees it, because B's commit is not part of A's snapshot. After A's `COMMIT`, a new snapshot sees only the new version at (0,3). Nobody waited for anybody.

## Dead tuples and VACUUM

The old versions left behind by updates and deletes are called **dead tuples**. Once no running transaction's snapshot could possibly need a version any more, it is just wasted space. PostgreSQL reclaims that space with **VACUUM**, which runs automatically in the background (autovacuum) and can also be run by hand. The statistics view counts them; `pg_stat_force_next_flush()` publishes this session's pending counters so the view is current:

```sql
-- sql/dead-tuples.sql
SELECT pg_stat_force_next_flush();  -- publish this session's pending counters now
SELECT n_tup_upd, n_tup_hot_upd, n_live_tup, n_dead_tup
FROM pg_stat_user_tables WHERE relname = 'accounts';
```

```text
 pg_stat_force_next_flush 
--------------------------
 
(1 row)

 n_tup_upd | n_tup_hot_upd | n_live_tup | n_dead_tup 
-----------+---------------+------------+------------
         1 |             1 |          2 |          1
(1 row)
```

One update, one dead tuple, and `n_tup_hot_upd` says it was a **HOT** (heap-only tuple) update: the new version fit on the same page and no indexed column changed, so PostgreSQL did not have to touch any index. Now vacuum it:

A non-HOT update leaves a different trail. When the update changes an indexed column, the new version needs new index entries, so the old one cannot be a simple redirect. After `VACUUM` its line pointer is freed (`lp_flags = 0`, unused) and can be reused by the next insert:

```sql
-- sql/non-hot.sql
CREATE TABLE tagged (id int PRIMARY KEY, label text);
CREATE INDEX tagged_label_idx ON tagged (label);
INSERT INTO tagged VALUES (1, 'a');
UPDATE tagged SET label = 'b' WHERE id = 1;   -- changes an indexed column: not a HOT update
SELECT pg_stat_force_next_flush();
SELECT relname, n_tup_upd, n_tup_hot_upd, n_dead_tup
FROM pg_stat_user_tables WHERE relname IN ('accounts', 'tagged') ORDER BY 1;
VACUUM tagged;
SELECT lp, lp_flags, lp_off, t_xmin, t_xmax, t_ctid
FROM heap_page_items(get_raw_page('tagged', 0));
```

## The visibility map: why counting is not free

Every row version has to be checked against the reader's snapshot, which is why `count(*)` in PostgreSQL reads the table. An index-only scan can skip the table only for pages the **visibility map** marks all-visible, and `VACUUM` is what sets those bits. The plans below count 100 000 rows through the primary key index (the planner would pick a sequential scan here, so `enable_seqscan = off` forces the index-only plan for teaching only):

```sql
-- sql/visibility-map.sql
CREATE TABLE big AS SELECT g AS id, md5(g::text) AS payload FROM generate_series(1, 100000) g;
ALTER TABLE big ADD PRIMARY KEY (id);
ANALYZE big;
SET enable_seqscan = off;  -- teaching switch only: force the index-only plan
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF, BUFFERS OFF) SELECT count(*) FROM big;
VACUUM big;
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF, BUFFERS OFF) SELECT count(*) FROM big;
UPDATE big SET payload = payload WHERE id <= 1000;
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF, BUFFERS OFF) SELECT count(*) FROM big;
```

```text
SELECT 100000
ALTER TABLE
ANALYZE
SET
                                 QUERY PLAN                                  
-----------------------------------------------------------------------------
 Aggregate (actual rows=1.00 loops=1)
   ->  Index Only Scan using big_pkey on big (actual rows=100000.00 loops=1)
         Heap Fetches: 100000
         Index Searches: 1
(4 rows)

VACUUM
                                 QUERY PLAN                                  
-----------------------------------------------------------------------------
 Aggregate (actual rows=1.00 loops=1)
   ->  Index Only Scan using big_pkey on big (actual rows=100000.00 loops=1)
         Heap Fetches: 0
         Index Searches: 1
(4 rows)

UPDATE 1000
                                 QUERY PLAN                                  
-----------------------------------------------------------------------------
 Aggregate (actual rows=1.00 loops=1)

         Heap Fetches: 2120
         Index Searches: 1
(4 rows)
```

Fresh from `CREATE TABLE AS`, nothing is marked all-visible, so all 100 000 index entries need a heap fetch (`Heap Fetches: 100000`). After `VACUUM` none do (`Heap Fetches: 0`). After 1 000 rows are updated, the pages they touched lose their bit again and about 2 000 fetches come back. This is also why vacuum matters for read speed, not only for space.

## Long transactions hold back cleanup

An old version can only be removed when **no** snapshot in the database can still need it. The oldest running snapshot therefore sets the cleanup horizon. Two runs of the same job: a worker updates one row 1 000 times and runs `VACUUM (VERBOSE)`, while another session holds a Repeatable Read transaction open. In run 1 that session is connected to a different database; in run 2 to the same one:

```text
-- run 1: the open transaction is in ANOTHER database
-- session holder (b3_h2): script
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM t;
\! sleep 5
COMMIT;
-- session worker (b3_h1): script
\! sleep 1
SELECT 'UPDATE t SET n = n + 1 WHERE id = 1;' FROM generate_series(1, 1000) \gexec
VACUUM (VERBOSE, INDEX_CLEANUP OFF) t;
-- session worker: VACUUM output (three summary lines of the VERBOSE report)
pages: 0 removed, 1 remain, 1 scanned (100.00% of total), 0 eagerly scanned
tuples: 187 removed, 1 remain, 0 are dead but not yet removable
removable cutoff: 428058, which was 0 XIDs old when operation ended

-- run 2: the open transaction is in the SAME database
-- session holder (b3_h1): script
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM t;
\! sleep 5
COMMIT;
-- session worker (b3_h1): script
\! sleep 1
SELECT 'UPDATE t SET n = n + 1 WHERE id = 1;' FROM generate_series(1, 1000) \gexec
VACUUM (VERBOSE, INDEX_CLEANUP OFF) t;
-- session worker: VACUUM output (three summary lines of the VERBOSE report)
pages: 0 removed, 5 remain, 5 scanned (100.00% of total), 0 eagerly scanned
tuples: 0 removed, 1001 remain, 1000 are dead but not yet removable
removable cutoff: 428065, which was 1000 XIDs old when operation ended
```

In run 1 the worker's vacuum removes what it can and finds nothing it must keep; in run 2 all 1 000 dead versions are "dead but not yet removable" and five pages have been consumed instead of one. The horizon is per database (plus the shared catalogs), so a forgotten transaction in another database is harmless to this one — but a forgotten transaction here holds everything. A replication slot can hold it back too: the documentation describes a slot's `xmin` as "the oldest transaction that this slot needs the database to retain. `VACUUM` cannot remove tuples deleted by any later transaction" ([docs](https://www.postgresql.org/docs/18/view-pg-replication-slots.html)), and the replication lesson shows one in a live lab.

## Bloat: what an open snapshot costs

Table bloat is dead space that stays in the file. It is easy to produce: keep one snapshot open while a hot row is updated over and over. This is a one-row counter table updated 50 000 times with `pgbench` (the `UPDATE` script is `UPDATE page_views SET views = views + 1 WHERE page = '/home';`), measured on this Mac:

```text

tps = 5220.507993 (without initial connection time)

(1 row)

-- session H: script
```

Run 1 and run 3 finish with **one** 8 kB page: HOT pruning cleans the page as it goes. Run 2 has an old snapshot open the whole time, so nothing can be pruned: the table grows to hundreds of pages holding one live row and about 50 000 dead ones, `VACUUM` reports `50000 are dead but not yet removable`, and even the throughput is about a third. When the snapshot ends, `VACUUM` reclaims the dead versions for reuse, but a file rarely shrinks back: only completely empty pages at the end are truncated.

## Reading AI-generated code

An assistant is asked for a nightly export of the counters and wants it consistent, so it opens one `REPEATABLE READ` transaction around everything:

<SpotTheBug lang="python" code={`# AI comment: "one REPEATABLE READ transaction gives the export a consistent snapshot"
conn.isolation_level = psycopg.IsolationLevel.REPEATABLE_READ
with conn.transaction():
    rows = conn.execute("SELECT page, views FROM page_views").fetchall()
    for page, views in rows:
        upload_to_warehouse(page, views)  # slow network call, once per row`}>

The snapshot is held from the `SELECT` until the last upload finishes, and the network calls can take minutes. For all of that time nothing in this database can be cleaned up: that is run 2 above, with the counters table growing to hundreds of pages and every update slowing down. The fix is to keep the transaction as short as the read (run 3 above): fetch the rows inside the transaction, close it, and upload afterwards. `idle_in_transaction_session_timeout` is the safety net for code that does not.

```python
with conn.transaction():
    rows = conn.execute("SELECT page, views FROM page_views").fetchall()
# the snapshot is gone here; do the slow work outside the transaction
for page, views in rows:
    upload_to_warehouse(page, views)
```

</SpotTheBug>

## Freezing and transaction id wraparound

`xmin` and `xmax` are 32-bit counters, so ids eventually wrap around; PostgreSQL compares them modulo 2^31, which means a row created "too long ago" would suddenly look like it is in the future. To prevent that, `VACUUM` **freezes** old row versions, marking them as visible to everyone forever ([docs](https://www.postgresql.org/docs/18/routine-vacuuming.html#VACUUM-FOR-WRAPAROUND)). The documentation states that every table must be vacuumed at least once every two billion transactions, that autovacuum forces a freeze pass at `autovacuum_freeze_max_age` (200 million by default), and that the server starts warning 40 million transactions before wraparound and refuses to assign new ids at 3 million. The age of the oldest unfrozen id is visible:

```sql
-- sql/freeze.sql
SELECT age(datfrozenxid) AS database_age FROM pg_database WHERE datname = current_database();
SHOW autovacuum_freeze_max_age;
SELECT relname, age(relfrozenxid) FROM pg_class WHERE relname = 'accounts';
VACUUM (FREEZE) accounts;
SELECT relname, age(relfrozenxid) FROM pg_class WHERE relname = 'accounts';
SELECT lp, t_xmin, combined_flags
FROM heap_page_items(get_raw_page('accounts', 0)),
     LATERAL heap_tuple_infomask_flags(t_infomask, t_infomask2)
WHERE lp = 2;
```

The database's age is large on this scratch cluster because of all the earlier runs, and far below the 200 million limit. `VACUUM (FREEZE)` brought the table's age to 0 and the row's flags to `HEAP_XMIN_FROZEN`: its `t_xmin` is still stored but is now ignored. `pg_current_xact_id()` returns the 64-bit `xid8`, which does not wrap, while `xmin` is the 32-bit `xid`.

## Mental Model

Think of a table as a ledger where nothing is ever erased. An update strikes a line through the old entry (sets its `xmax`) and writes a new one below. A reader looks at the ledger as of one moment and simply ignores entries that were written later or struck through earlier. Someone has to come back and remove the struck-through lines nobody can be looking at any more: that is VACUUM, and the oldest reader anywhere in the database decides how far it may go.

## Tips / gotchas

- Ordinary reads take no row locks under MVCC. If you need a read to also reserve a row for a coming write, that is what the locking lesson's `SELECT ... FOR UPDATE` is for.
- Long-running transactions are the enemy of vacuuming. While a transaction stays open, its snapshot may still need old versions, so dead tuples cannot be removed and tables bloat (271 pages instead of one above).
- `VACUUM` reclaims space for reuse within the table; it does not normally shrink the file on disk (only empty pages at the end are truncated). `VACUUM FULL` rewrites the table, but locks it while it runs.
- Frequent updates to the same rows create many versions. Watch `n_dead_tup` in `pg_stat_user_tables` and let autovacuum keep up, or tune it for hot tables.
- Updating an indexed column defeats HOT and costs index maintenance; avoid indexing columns that change constantly.

<Callout title="Why your SELECTs never wait">
The reason a slow analytics query and a flood of updates can run together happily is MVCC. The reader sees a frozen snapshot; the writers append new versions beside the old ones. Nobody blocks anybody. The price is the dead tuples left behind, which is exactly why VACUUM exists.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| MVCC (readers do not block writers, writers do not block readers) | Very high concurrency; a long query runs alongside write load with neither waiting (A read the old version while B updated) | Must retain old row versions as dead tuples, needing `VACUUM` and monitoring; one old snapshot can bloat a table about 270-fold (271 pages instead of one) |
| HOT updates | No index maintenance, and pages can be pruned in place (8 kB after 50 000 updates) | Only when no indexed column changes and the new version fits on the same page |
| Lock-based concurrency control (used by some other databases) | No accumulating dead tuples, no vacuum needed | Readers and writers block each other, lowering throughput under a mixed workload |

## Common Misconceptions

- **"UPDATE overwrites the row in place."** It writes a new version at a new `ctid` (0,1 became 0,3) and leaves the old one behind.
- **"A long-running transaction stalls vacuuming system-wide."** The cleanup horizon is per database: run 1 above was unaffected by a transaction in another database. It does stall the whole database it lives in.
- **"VACUUM shrinks the file."** It frees space for reuse; the 271-page file stayed 271 pages.
- **"count(*) should be instant."** Every version must be checked against your snapshot; only pages the visibility map marks all-visible can be skipped.
- **"A SELECT sees the latest data."** It sees its snapshot, which can be older than the latest commit (Repeatable Read showed 500 while the row already said 400).
