So far every statement you wrote ran on its own. In real applications, though, a single business action often needs several statements that must all succeed together or not at all. Moving money between two accounts is the classic case: one row goes down, another goes up, and you can never afford to apply only half of that.

A **transaction** is the tool for exactly this. It groups one or more statements into a single all-or-nothing unit of work. Either every statement takes effect, or none of them do. On top of that, a busy database has many transactions running at the same time, which is what we mean by **concurrency**. This module is about both: how to define units of work, and how PostgreSQL keeps them from corrupting each other's data.

Every lesson in this module was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). The concurrency examples are not described, they are reproduced: two or three real `psql` sessions started together, with the output printed as it came back.

## The four guarantees: ACID

A transaction in PostgreSQL gives you four guarantees, remembered by the acronym **ACID** ([docs](https://www.postgresql.org/docs/18/tutorial-transactions.html)).

| Letter | Property    | What it promises                                                        |
|--------|-------------|-------------------------------------------------------------------------|
| A      | Atomicity   | All statements commit together or roll back together; never half-done   |
| C      | Consistency | The database moves from one valid state to another, honouring constraints |
| I      | Isolation   | Concurrent transactions do not see each other's unfinished work         |
| D      | Durability  | Once committed, the change survives a crash or power loss               |

Atomicity is the part you feel most directly when you type `COMMIT` or `ROLLBACK`. Isolation is the part that gets interesting once more than one client is connected, and it is where most of this module's depth lies.

## How the pieces fit together

The next four lessons build on each other. You start a transaction, you choose how isolated it should be, and underneath both of those PostgreSQL uses two mechanisms to make concurrency safe: keeping multiple versions of each row, and taking locks when it must.

## What this module covers

- **Transaction basics** — `BEGIN`, `COMMIT`, `ROLLBACK`, what happens when a statement fails inside a transaction (`25P02`), `SAVEPOINT` for partial rollbacks, and a connection leak you can see in `pg_stat_activity`.
- **Isolation levels** — Read Committed, Repeatable Read, and Serializable, with each anomaly reproduced (a balance that changes mid-transaction, write skew that commits, `40001` and the retry loop that handles it).
- **MVCC** — Multi-Version Concurrency Control, where writers do not block readers and readers do not block writers because each transaction reads a consistent snapshot. You look at `xmin`, `xmax` and `ctid` and at a raw heap page, and see why one forgotten transaction bloats a table.
- **Locking and deadlocks** — explicit row locks with `SELECT ... FOR UPDATE`, the lost update they prevent, the four lock modes, a real deadlock with its server log, `NOWAIT`, `SKIP LOCKED` and advisory locks.

## Mental Model

Hold two ideas at once. A transaction is *your* boundary — you decide when work begins and ends. Concurrency control is *PostgreSQL's* job — it decides how your transaction coexists with everyone else's, using snapshots (so readers never wait) and locks (so writers take turns). The rest of this module shows where those two responsibilities meet, and what your code must do when PostgreSQL says "try again".

## Tips / gotchas

- A connection that is not inside an explicit transaction runs each statement in its own implicit transaction, committed immediately. This is called auto-commit.
- Isolation is a spectrum, not a switch. Higher levels prevent more anomalies but make conflicts more likely to abort.
- PostgreSQL never asks readers to wait for writers for ordinary `SELECT` queries; that is the headline benefit of MVCC.
- Deadlocks and serialization failures are a normal possibility in any concurrent system, not a bug; well-written applications expect them and retry.

<Callout title="The mental model for the module">
A transaction defines what must happen together. Isolation defines what it may see. MVCC and locks are how PostgreSQL delivers both without making everybody wait. Learn the error codes that mean "retry" (`40001`, `40P01`) and you know most of what an application has to handle.
</Callout>

## Common Misconceptions

- **"Transactions make my code slower."** A transaction costs almost nothing when it is short; a *long* one is what hurts (see the MVCC lesson).
- **"Higher isolation is always safer."** It is stricter, and it aborts more; without a retry loop that is an outage, not safety.
- **"Reads and writes block each other."** Not in PostgreSQL: ordinary reads use a snapshot and take no row locks.
