MVCC removes the need for read locks, but writes still have to be coordinated. When two transactions want to change the same row, one must wait for the other to finish. Most of the time PostgreSQL takes the necessary **row locks** for you during an `UPDATE` or `DELETE`. Sometimes, though, you want to lock a row at the moment you read it, so that nobody else can change it before you do ([docs](https://www.postgresql.org/docs/18/explicit-locking.html)).

Everything below was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). The single-session fences are `sql` fences run in one empty database; every lock wait, deadlock and queue example is a real run of two or three `psql` processes started together, printed as they came back. `\o /dev/null` around `pg_sleep(n)` hides the empty result of the sleep, and `\! sleep n` (a shell command) pauses a session without a query running, so that it shows up as `idle in transaction`. Process ids and timings are from this Mac and differ on every run.

Three tables: `accounts` and `ledger_entries` (with a foreign key to it) for row locks, and a `jobs` table for a work queue.

```sql
-- sql/setup.sql
CREATE TABLE accounts (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner   text NOT NULL,
  balance numeric NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts (owner, balance) VALUES ('Ada', 500), ('Linus', 100);

CREATE TABLE ledger_entries (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  account_id bigint NOT NULL REFERENCES accounts (id),
  amount     numeric NOT NULL
);

CREATE TABLE jobs (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  status  text NOT NULL DEFAULT 'pending',
  payload text NOT NULL
);
INSERT INTO jobs (payload) SELECT 'job-' || g FROM generate_series(1, 6) g;
```

## Lock waits, and how to see them

`SELECT ... FOR UPDATE` reads a row and locks it as if you were about to update it. Any other transaction that tries to update, delete, or also lock that row must wait until you commit or roll back. Session A locks Ada's row and holds it for three seconds; B asks for the same lock one second in; C looks at `pg_stat_activity` and `pg_locks` at two seconds:

```text
-- session A (holder): script
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
\! sleep 3
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
-- session A (holder): psql output
BEGIN
 balance 
---------
     500
(1 row)

UPDATE 1
COMMIT

-- session B (waiter): script
\o /dev/null
SELECT pg_sleep(1);
\o
\timing on
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- session B (waiter): psql output
Timing is on.
 balance 
---------
     400
(1 row)

Time: 2008.066 ms (00:02.008)

-- session C (observer): script
\o /dev/null
SELECT pg_sleep(2);
\o
SELECT pid, state, wait_event_type, wait_event, pg_blocking_pids(pid) AS blocked_by, left(query, 44) AS query
FROM pg_stat_activity
WHERE datname = current_database() AND backend_type = 'client backend' AND pid <> pg_backend_pid()
ORDER BY pid;
SELECT locktype, mode, granted, pid FROM pg_locks WHERE NOT granted;
-- session C (observer): psql output
  pid  |        state        | wait_event_type |  wait_event   | blocked_by |                    query                     
-------+---------------------+-----------------+---------------+------------+----------------------------------------------
 21999 | idle in transaction | Client          | ClientRead    | {}         | SELECT balance FROM accounts WHERE id = 1 FO
 22000 | active              | Lock            | transactionid | {21999}    | SELECT balance FROM accounts WHERE id = 1 FO
(2 rows)

   locktype    |   mode    | granted |  pid  
---------------+-----------+---------+-------
 transactionid | ShareLock | f       | 22000
(1 row)
```

B printed nothing for about two seconds, until A committed, and then it received the new balance (400, not 500). C shows why: A is `idle in transaction` doing nothing, while B is `active` with `wait_event_type = Lock` and `wait_event = transactionid`, and `pg_blocking_pids(pid)` names A's process. In `pg_locks`, B holds an ungranted `ShareLock` on A's transaction id: a row-level wait is implemented as a wait for the other transaction to end. Whenever an application "hangs", these two views tell you who waits for whom.

## The lost update, and FOR UPDATE

Here is the read-modify-write bug that motivates row locks. Both sessions read Ada's balance (500), compute the new value in the application, and write it back. Each was correct given what it read; together they lose one of the withdrawals:

```text
-- session A: script
BEGIN;
SELECT balance AS a_read FROM accounts WHERE id = 1;
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = 500 - 100 WHERE id = 1;  -- computed in the application
COMMIT;
-- session A: psql output
BEGIN
 a_read 
--------
    500
(1 row)

UPDATE 1
COMMIT

-- session B: script
BEGIN;
SELECT balance AS b_read FROM accounts WHERE id = 1;
\o /dev/null
SELECT pg_sleep(1.5);
\o
UPDATE accounts SET balance = 500 - 50 WHERE id = 1;   -- computed from the same stale read
COMMIT;
-- session B: psql output
BEGIN
 b_read 
--------
    500
(1 row)

UPDATE 1
COMMIT

-- afterwards:
SELECT balance FROM accounts WHERE id = 1;
 balance 
---------
     450
(1 row)
```

Ada should have 350 after withdrawing 100 and 50, but the table says 450: A's withdrawal vanished, overwritten by B's write, which was computed from a stale read. With `FOR UPDATE` on the read, B has to wait for A, and its read returns the value A wrote:

```text
-- session A: script
BEGIN;
SELECT balance AS a_read FROM accounts WHERE id = 1 FOR UPDATE;
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
-- session A: psql output
BEGIN
 a_read 
--------
    500
(1 row)

UPDATE 1
COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(0.3);
\o
BEGIN;
SELECT balance AS b_read FROM accounts WHERE id = 1 FOR UPDATE;
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
COMMIT;
-- session B: psql output
BEGIN
 b_read 
--------
    400
(1 row)

UPDATE 1
COMMIT

-- afterwards:
SELECT balance FROM accounts WHERE id = 1;
 balance 
---------
     350
(1 row)
```

The balance is 350. In the drivers the same pattern looks like this (each run once, starting from Ada 500):

When the change can be expressed as a single statement, you do not need `FOR UPDATE` at all: `UPDATE accounts SET balance = balance - 50` reads and writes the row under one lock. Under Read Committed a waiting `UPDATE` also **re-checks its WHERE clause** against the new version of the row once the other transaction commits (PostgreSQL calls this EvalPlanQual, [docs](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED)). A takes 100 from Ada and holds the transaction open; B tries to take 50 only `WHERE balance >= 450`:

```text
-- session A: script
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
\o /dev/null
SELECT pg_sleep(2);
\o
COMMIT;
-- session A: psql output
BEGIN
UPDATE 1
COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance - 50 WHERE id = 1 AND balance >= 450;
-- session B: psql output
UPDATE 0

-- afterwards:
SELECT balance FROM accounts WHERE id = 1;
 balance 
---------
     400
(1 row)
```

B waited, looked at the row A had left (400), found that the condition no longer held, and updated nothing: `UPDATE 0`, not an error.

## The four row-lock modes

`FOR UPDATE` is the strongest of four modes. Sessions can ask for weaker ones when they only need to keep a row from being deleted or from having its key changed:

- `FOR UPDATE` — I may delete this row or change any column.
- `FOR NO KEY UPDATE` — I will change the row but not its key columns. This is what an ordinary `UPDATE` takes.
- `FOR SHARE` — nobody may change or delete this row while I look at it, but others may share the lock.
- `FOR KEY SHARE` — nobody may delete it or change its key. This is what foreign-key checks take on the parent row.

Which pairs conflict? Every cell below is a real run: session A holds the row lock in the row's mode, session B tries the column's mode with `NOWAIT` half a second later:

| A holds \ B asks | FOR KEY SHARE | FOR SHARE | FOR NO KEY UPDATE | FOR UPDATE |
|---|---|---|---|---|
| FOR KEY SHARE | ok | ok | ok | conflict |
| FOR SHARE | ok | ok | conflict | conflict |
| FOR NO KEY UPDATE | ok | conflict | conflict | conflict |
| FOR UPDATE | conflict | conflict | conflict | conflict |

The practical effect is on foreign keys. A child insert takes `FOR KEY SHARE` on the parent row. If another transaction holds `FOR UPDATE` on that parent, the insert waits:

```text
-- session A: script
BEGIN;
SELECT id FROM accounts WHERE id = 1 FOR UPDATE;
\o /dev/null
SELECT pg_sleep(2);
\o
COMMIT;
-- session A: psql output
BEGIN
 id 
----
  1
(1 row)

COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(0.5);
\o
\timing on
INSERT INTO ledger_entries (account_id, amount) VALUES (1, 10);
-- session B: psql output
Timing is on.
INSERT 0 1
Time: 1513.899 ms (00:01.514)
```

but if the other transaction holds `FOR NO KEY UPDATE`, which is what a plain `UPDATE` of a non-key column takes, the insert goes straight through:

```text
-- session A: script
BEGIN;
SELECT id FROM accounts WHERE id = 1 FOR NO KEY UPDATE;
\o /dev/null
SELECT pg_sleep(2);
\o
COMMIT;
-- session A: psql output
BEGIN
 id 
----
  1
(1 row)

COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(0.5);
\o
\timing on
INSERT INTO ledger_entries (account_id, amount) VALUES (1, 10);
-- session B: psql output
Timing is on.
INSERT 0 1
Time: 8.963 ms
```

1.5 seconds versus 9 milliseconds. Prefer `FOR NO KEY UPDATE` over `FOR UPDATE` when you are not going to delete the row or change its key.

## When waiting becomes a deadlock

A **deadlock** happens when two transactions each hold a lock the other needs. Transaction A locks row 1 and then wants row 2; transaction B locked row 2 and now wants row 1. Neither can proceed, and neither will ever release first.

export const deadlockCycle = `flowchart LR
  A["Txn A holds lock on row 1"] -->|waits for row 2| B["Txn B holds lock on row 2"]
  B -->|waits for row 1| A`;

<Mermaid code={deadlockCycle} title="A deadlock cycle: each transaction waits on a lock the other holds" />

PostgreSQL runs a deadlock detector. A waiter checks for a cycle only after it has waited `deadlock_timeout`; the default is one second. When it finds one it aborts a transaction so the others can continue (which one is hard to predict, [docs](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-DEADLOCKS)). The two sessions below update the same two rows in opposite order:

```sql
-- sql/timeouts.sql
SHOW deadlock_timeout;
SHOW lock_timeout;
```

```text

------------------
 1s
(1 row)

 lock_timeout 
--------------
 0
(1 row)
```

```text
-- session A: script
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance + 10 WHERE id = 2;
COMMIT;
-- session A: psql output
BEGIN
UPDATE 1
ERROR:  deadlock detected
DETAIL:  Process 21947 waits for ShareLock on transaction 729227; blocked by process 21946.
Process 21946 waits for ShareLock on transaction 729228; blocked by process 21947.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,2) in relation "accounts"
ROLLBACK

-- session B: script
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 2;
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance + 10 WHERE id = 1;
COMMIT;
-- session B: psql output
BEGIN
UPDATE 1
UPDATE 1
COMMIT

-- afterwards:
SELECT id, balance FROM accounts ORDER BY id;
 id | balance 
----+---------
  1 |     510
  2 |      90
(2 rows)
```

Session A was chosen as the victim: it gets SQLSTATE `40P01` and must retry the whole transaction, while B's second update, freed by A's rollback, went through. The client message names process ids but not the statements. Those go to the server log, which is where you diagnose a deadlock afterwards:

```text
2026-09-30 07:52:51.275 UTC [21947] ERROR:  deadlock detected
2026-09-30 07:52:51.275 UTC [21947] DETAIL:  Process 21947 waits for ShareLock on transaction 729227; blocked by process 21946.
	Process 21946 waits for ShareLock on transaction 729228; blocked by process 21947.
	Process 21947: UPDATE accounts SET balance = balance + 10 WHERE id = 2;
	Process 21946: UPDATE accounts SET balance = balance + 10 WHERE id = 1;
2026-09-30 07:52:51.275 UTC [21947] HINT:  See server log for query details.
2026-09-30 07:52:51.275 UTC [21947] CONTEXT:  while updating tuple (0,2) in relation "accounts"
2026-09-30 07:52:51.275 UTC [21947] STATEMENT:  UPDATE accounts SET balance = balance + 10 WHERE id = 2;
```

**In pgAdmin:** to observe a live lock wait, run `BEGIN; SELECT ... FOR UPDATE` in one Query Tool tab without committing, then run the same in a second tab and watch it hang. The `pg_locks` view shows who holds what while you experiment.

## Choosing not to wait: NOWAIT, lock_timeout and SKIP LOCKED

Sometimes waiting is the wrong behaviour. `NOWAIT` makes a `SELECT ... FOR UPDATE` fail immediately if the row is locked. `lock_timeout` bounds the wait for any statement. Both raise SQLSTATE `55P03` (with different messages). `SKIP LOCKED` does not fail at all: it quietly steps over locked rows. A holds Ada's row; B tries three things:

```text
-- session A: script
BEGIN;
SELECT 1 FROM accounts WHERE id = 1 FOR UPDATE;
\o /dev/null
SELECT pg_sleep(3);
\o
COMMIT;
-- session A: psql output
BEGIN
 ?column? 
----------
        1
(1 row)

COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
SET lock_timeout = '500ms';
UPDATE accounts SET balance = balance WHERE id = 1;
SELECT * FROM accounts WHERE id = 2 FOR UPDATE NOWAIT;
-- session B: psql output
ERROR:  could not obtain lock on row in relation "accounts"
SET
ERROR:  canceling statement due to lock timeout
CONTEXT:  while updating tuple (0,1) in relation "accounts"
 id | owner | balance 
----+-------+---------
  2 | Linus |     100
(1 row)
```

`NOWAIT` on the locked row fails at once with `could not obtain lock on row in relation "accounts"`. With `lock_timeout = '500ms'` the `UPDATE` waits half a second and is cancelled with `canceling statement due to lock timeout`. And the same `NOWAIT` on a different, unlocked row (Linus) simply succeeds.

`SKIP LOCKED` is the backbone of work queues where many workers each take the next free job; the PostgreSQL documentation describes it as a way to avoid lock contention with multiple consumers of a queue-like table ([docs](https://www.postgresql.org/docs/18/sql-select.html#SQL-FOR-UPDATE-SHARE)). It gives an inconsistent view of the table on purpose, so it is wrong for anything that must see every row. Two workers each claim two pending jobs from a six-job table; worker 2 starts half a second after worker 1 while worker 1 still holds its rows:

```text
-- session worker 1: script
BEGIN;
SELECT id, payload FROM jobs WHERE status = 'pending' ORDER BY id LIMIT 2 FOR UPDATE SKIP LOCKED;
\o /dev/null
SELECT pg_sleep(2);
\o
UPDATE jobs SET status = 'done' WHERE id IN (1, 2);
COMMIT;
-- session worker 1: psql output
BEGIN
 id | payload 
----+---------
  1 | job-1
  2 | job-2
(2 rows)

UPDATE 2
COMMIT

-- session worker 2: script
\o /dev/null
SELECT pg_sleep(0.5);
\o
BEGIN;
SELECT id, payload FROM jobs WHERE status = 'pending' ORDER BY id LIMIT 2 FOR UPDATE SKIP LOCKED;
UPDATE jobs SET status = 'done' WHERE id IN (3, 4);
COMMIT;
-- session worker 2: psql output
BEGIN
 id | payload 
----+---------
  3 | job-3
  4 | job-4
(2 rows)

UPDATE 2
COMMIT

-- afterwards:
SELECT id, status FROM jobs ORDER BY id;
 id | status  
----+---------
  1 | done
  2 | done
  3 | done
  4 | done
  5 | pending
  6 | pending
(6 rows)
```

Worker 2 got jobs 3 and 4 instead of waiting for 1 and 2. The idiomatic form claims a job in one statement, so a crash between claim and update cannot leave a job locked forever:

## Table locks and advisory locks

Every statement also takes a table-level lock. Most are harmless, but `ACCESS EXCLUSIVE` (taken by `LOCK TABLE`, `DROP TABLE`, `VACUUM FULL` and many `ALTER TABLE` forms) conflicts with everything, including a plain `SELECT`. A holds it for two seconds; B's `count(*)` starts half a second in:

```text
-- session A: script
BEGIN;
LOCK TABLE accounts IN ACCESS EXCLUSIVE MODE;
\o /dev/null
SELECT pg_sleep(2);
\o
COMMIT;
-- session A: psql output
BEGIN
LOCK TABLE
COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(0.5);
\o
\timing on
SELECT count(*) FROM accounts;
-- session B: psql output
Timing is on.
 count 
-------
     2
(1 row)

Time: 1504.090 ms (00:01.504)
```

B waited 1.5 seconds for a query that reads one table. This is why schema changes on hot tables are dangerous.

**Advisory locks** are locks with no table behind them: you pick a number, the database keeps track of who holds it. They are for coordination the application owns, like "only one worker runs this nightly job". Session-level advisory locks last until unlocked or until the connection ends; the `xact` variants end with the transaction:

```text
-- session A: script
SELECT pg_try_advisory_lock(42) AS a_got_it;
\o /dev/null
SELECT pg_sleep(2);
\o
SELECT pg_advisory_unlock(42) AS a_released;
-- session A: psql output
 a_got_it 
----------
 t
(1 row)

 a_released 
------------
 t
(1 row)

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
SELECT pg_try_advisory_lock(42) AS b_got_it;
\o /dev/null
SELECT pg_sleep(2);
\o
SELECT pg_try_advisory_lock(42) AS b_got_it_later;
SELECT pg_advisory_unlock(42) AS b_released;
-- session B: psql output
 b_got_it 
----------
 f
(1 row)

 b_got_it_later 
----------------
 t
(1 row)

 b_released 
------------
 t
(1 row)
```

```sql
-- sql/advisory-xact.sql
BEGIN;
SELECT pg_advisory_xact_lock(7);
SELECT locktype, classid, objid, mode, granted
FROM pg_locks WHERE locktype = 'advisory' AND pid = pg_backend_pid();
COMMIT;
SELECT count(*) AS advisory_locks_left
FROM pg_locks WHERE locktype = 'advisory' AND pid = pg_backend_pid();
```

```text
BEGIN
 pg_advisory_xact_lock 
-----------------------
 
(1 row)

 locktype | classid | objid |     mode      | granted 
----------+---------+-------+---------------+---------
 advisory |       0 |     7 | ExclusiveLock | t
(1 row)

COMMIT

---------------------
                   0
(1 row)
```

B could not get lock 42 until A released it. Be careful with the session-level kind behind a transaction-mode connection pooler: the lock belongs to a server connection, not to your client (the pooling lesson shows what goes wrong). Prefer `pg_advisory_xact_lock` there.

## Reading AI-generated code

An assistant writes a money-transfer function and explains, correctly, that each `UPDATE` locks its row:

<SpotTheBug lang="sql" code={`-- AI comment: "debit first, then credit; both rows are locked by the UPDATEs"

  PERFORM 1 FROM accounts WHERE id IN (from_id, to_id) ORDER BY id FOR UPDATE;  -- always lock in id order
  UPDATE accounts SET balance = balance - amount WHERE id = from_id;

  UPDATE accounts SET balance = balance + amount WHERE id = to_id;

$$;

## Mental Model

A lock is a queue ticket on one thing. MVCC means readers never need a ticket; writers do, one per row they change, and the ticket is held until commit or rollback, not until the statement ends. Waiting is therefore always waiting for a transaction, which is why a forgotten transaction holds up everyone behind it. A deadlock is two people each holding a ticket the other needs; the database breaks the tie by cancelling one.

## Tips / gotchas

- Lock rows in a consistent order everywhere in your code. If every transaction touches row 1 before row 2, the cycle that causes a deadlock can never form.
- Treat deadlock errors (`40P01`) and serialization failures (`40001`) the same way: roll back and retry the whole transaction. Both are expected under concurrency.
- Keep the work between taking a lock and committing as short as possible. The longer you hold a lock, the longer others queue behind you.
- Prefer a single relative `UPDATE` to read-then-write. Use `FOR UPDATE` when you must read, decide, then write.
- `SKIP LOCKED` is ideal for queues but wrong for accounting; it deliberately ignores rows, so never use it where you must see every matching row.
- Set `lock_timeout` (and `idle_in_transaction_session_timeout`) so a stuck session cannot block a hot table indefinitely.

<Callout title="A consistent lock order prevents most deadlocks">
Deadlocks are not caused by locking too much, but by locking in conflicting orders. Decide one global order for acquiring locks, for example always by ascending primary key, and apply it in every transaction. PostgreSQL will still detect any deadlock that slips through, but you will rarely hand it one to find.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| Row-level lock | High concurrency, since other transactions can still edit other rows in the same table | Must design a consistent lock order yourself, or risk a deadlock |
| Table-level lock | Easy to write, guarantees nobody else touches the whole table while you work | Blocks even plain `SELECT`s (1.5 s wait above) |
| Explicit `SELECT ... FOR UPDATE` | Precise control over when the lock is taken, prevents lost updates (350, not 450) | More code to write, and you must think through the lock order yourself |
| Relying on the implicit lock from a single relative `UPDATE` | Shorter code, no need to think about locking up front | Only works when the change fits in one statement |
| `NOWAIT` / `lock_timeout` | Fail fast instead of queueing | The caller must handle `55P03` |
| `SKIP LOCKED` | Many workers share a queue without blocking | Deliberately inconsistent view of the table |

## Common Misconceptions

- **"A deadlock means I locked too much."** It means two transactions locked in different orders; the same locks in one order never deadlock.
- **"The database picks the deadlock victim fairly."** It is not predictable: in the run above the transaction that happened to run the check was cancelled.
- **"SELECT FOR UPDATE and UPDATE are different kinds of lock."** A plain `UPDATE` takes `FOR NO KEY UPDATE`, which conflicts with `FOR UPDATE` and with itself.
- **"A lock is released at the end of the statement."** Row locks last until the transaction ends.
- **"Read Committed makes read-then-write safe."** Both sessions read 500 and one withdrawal was lost.
