A transaction turns several statements into one indivisible unit. You open it with `BEGIN`, run the statements you want grouped, and then close it with `COMMIT` to keep the work or `ROLLBACK` to discard it. Nothing inside the transaction is visible to other connections until you commit ([docs](https://www.postgresql.org/docs/18/tutorial-transactions.html)).

Everything below was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). The single-session examples are `sql` fences run top to bottom in one empty database; the two-session example is a real run of two `psql` processes; the driver snippets were each run once (pg 8.23.0, psycopg 3.3.6, pgx v5.11.0, sqlx 0.9.0).

We use one small `accounts` table for every example. The `CHECK` constraint matters: it is how we will make statements fail on purpose.

```sql
-- sql/setup.sql
CREATE TABLE accounts (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner   text NOT NULL,
  balance numeric NOT NULL CHECK (balance >= 0)
);

INSERT INTO accounts (owner, balance) VALUES ('Ada', 500), ('Linus', 100);
```

## The classic transfer

Moving 100 from Ada to Linus is two updates that must happen together. If the server crashed between them, atomicity guarantees neither change survives, so money is never created or destroyed.

## Choosing to abandon the work

If anything looks wrong before you commit, `ROLLBACK` discards every change made since `BEGIN`, as if the transaction never ran. Notice that inside the transaction you can see your own uncommitted change (Ada shows 300); after the rollback it is gone.

    ```sql
    BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE owner = 'Ada';
    SELECT owner, balance FROM accounts ORDER BY id;
    -- on reflection, cancel everything:
    ROLLBACK;
    SELECT owner, balance FROM accounts ORDER BY id;
    ```

## The life of a transaction

Every transaction follows the same path: it begins, runs its statements, and ends in exactly one of two ways. There is no in-between state once you decide.

  A[BEGIN] --> B[Run statements]
  B --> C{"Everything correct?"}
  C -->|Yes| D[COMMIT: changes become permanent]
  C -->|No| E[ROLLBACK: changes discarded]
  D --> F[Transaction ends]
  E --> F`;

## Without BEGIN, nothing is atomic

By default a connection is in **auto-commit** mode: each lone statement is its own transaction, committed the moment it finishes. Here we move 500 from Linus (who only has 200) to Ada with two separate statements. The credit succeeds and is committed immediately; the debit then fails the `CHECK`:

```sql
-- @expect-error 23514
-- move 500 from Linus (who has 200) to Ada, WITHOUT BEGIN: each statement is its own transaction
UPDATE accounts SET balance = balance + 500 WHERE owner = 'Ada';
UPDATE accounts SET balance = balance - 500 WHERE owner = 'Linus';
```

```text
UPDATE 1
ERROR:  new row for relation "accounts" violates check constraint "accounts_balance_check"
DETAIL:  Failing row contains (2, Linus, -300).
```

```sql
-- sql/half-done.sql
SELECT owner, balance, sum(balance) OVER () AS total FROM accounts ORDER BY id;
```

```text
 owner | balance | total 
-------+---------+-------
 Ada   |     900 |  1100
 Linus |     200 |  1100
(2 rows)
```

Ada gained 500 that nobody lost: the total went from 600 to 1100. That is exactly the half-done state a transaction exists to prevent. Take the 500 back out by hand:

```sql
-- sql/repair.sql
UPDATE accounts SET balance = balance - 500 WHERE owner = 'Ada';
```

Now the same two statements inside `BEGIN` ... `COMMIT`. The debit fails, and PostgreSQL puts the transaction into an **aborted** state: every later command is refused with SQLSTATE `25P02` until you end the transaction. Even `COMMIT` cannot save it, and it answers with the command tag `ROLLBACK`, not `COMMIT`:

```sql
-- @expect-error 23514
BEGIN;
UPDATE accounts SET balance = balance + 500 WHERE owner = 'Ada';
UPDATE accounts SET balance = balance - 500 WHERE owner = 'Linus';
SELECT 1;
COMMIT;
```

```text
BEGIN
UPDATE 1
ERROR:  new row for relation "accounts" violates check constraint "accounts_balance_check"
DETAIL:  Failing row contains (2, Linus, -300).
ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK
```

```sql
-- sql/atomic-check.sql
SELECT owner, balance, sum(balance) OVER () AS total FROM accounts ORDER BY id;
```

```text
 owner | balance | total 
-------+---------+-------
 Ada   |     400 |   600
 Linus |     200 |   600
(2 rows)
```

Nothing changed: Ada 400, Linus 200, total 600. The credit that ran before the failure was thrown away with everything else.

## Partial rollback with SAVEPOINT

Sometimes you want to undo only part of a transaction without abandoning the rest. A `SAVEPOINT` is a named marker inside the transaction; `ROLLBACK TO` rewinds to that marker, keeping everything before it and discarding everything after. It is also the only way to recover from an error and keep going: `ROLLBACK TO` takes the transaction out of the aborted state ([docs](https://www.postgresql.org/docs/18/sql-savepoint.html)).

The statement that fails has to really fail, so this one drives Ada's balance negative and trips the `CHECK`. (An `UPDATE` that matches no rows, such as `WHERE owner = 'Nobody'`, raises no error at all — it just reports `UPDATE 0` — so there is nothing to roll back to.)

<Tabs syncKey="lang">
  <TabItem label="psql">
    ```sql
    -- @expect-error 23514
    BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE owner = 'Ada';
    SAVEPOINT after_debit;
    UPDATE accounts SET balance = balance - 1000 WHERE owner = 'Ada';  -- violates the CHECK
    -- the transaction is now aborted; undo just the failed part:
    ROLLBACK TO after_debit;
    UPDATE accounts SET balance = balance + 100 WHERE owner = 'Linus';
    COMMIT;
    ```
  </TabItem>
  <TabItem label="Node.js">
    ```js
    const client = await pool.connect();
    try {
      await client.query('BEGIN');
      await client.query("UPDATE accounts SET balance = balance - 100 WHERE owner = 'Ada'");
      await client.query('SAVEPOINT after_debit');
      try {
        await client.query("UPDATE accounts SET balance = balance - 1000 WHERE owner = 'Ada'");
      } catch (e) {
        console.log('rolling back to the savepoint:', e.code);
        await client.query('ROLLBACK TO after_debit');
      }
      await client.query("UPDATE accounts SET balance = balance + 100 WHERE owner = 'Linus'");
      await client.query('COMMIT');
    } catch (e) {
      await client.query('ROLLBACK');
      throw e;
    } finally {
      client.release();
    }
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    with conn.transaction():
        cur.execute("UPDATE accounts SET balance = balance - 100 WHERE owner = 'Ada'")
        try:
            with conn.transaction():  # a nested block is a SAVEPOINT
                cur.execute("UPDATE accounts SET balance = balance - 1000 WHERE owner = 'Ada'")
        except psycopg.errors.CheckViolation:
            print("rolling back to the savepoint: 23514")
        cur.execute("UPDATE accounts SET balance = balance + 100 WHERE owner = 'Linus'")
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    tx, err := conn.Begin(ctx)
    if err != nil {
        return err
    }
    defer tx.Rollback(ctx)
    tx.Exec(ctx, "UPDATE accounts SET balance = balance - 100 WHERE owner = 'Ada'")
    tx.Exec(ctx, "SAVEPOINT after_debit")
    if _, err := tx.Exec(ctx, "UPDATE accounts SET balance = balance - 1000 WHERE owner = 'Ada'"); err != nil {
        var pgErr *pgconn.PgError
        if errors.As(err, &pgErr) {
            fmt.Println("rolling back to the savepoint:", pgErr.Code)
        }
        tx.Exec(ctx, "ROLLBACK TO after_debit")
    }
    tx.Exec(ctx, "UPDATE accounts SET balance = balance + 100 WHERE owner = 'Linus'")
    return tx.Commit(ctx)
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    let mut tx = pool.begin().await?;
    sqlx::query("UPDATE accounts SET balance = balance - 100 WHERE owner = 'Ada'")
        .execute(&mut *tx).await?;
    sqlx::query("SAVEPOINT after_debit").execute(&mut *tx).await?;
    if let Err(e) = sqlx::query("UPDATE accounts SET balance = balance - 1000 WHERE owner = 'Ada'")
        .execute(&mut *tx).await
    {
        println!("rolling back to the savepoint: {}", e.as_database_error().unwrap().code().unwrap());
        sqlx::query("ROLLBACK TO after_debit").execute(&mut *tx).await?;
    }
    sqlx::query("UPDATE accounts SET balance = balance + 100 WHERE owner = 'Linus'")
        .execute(&mut *tx).await?;
    tx.commit().await?;
    ```
  </TabItem>
</Tabs>

## What a rollback does not undo

A rollback discards row changes and, in PostgreSQL, also schema changes: DDL is transactional. It does not give back sequence values, so identity ids have gaps after a rollback (the same reason as the upsert lesson):

```sql
-- sql/side-effects.sql
CREATE TABLE ledger (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, note text);

BEGIN;
INSERT INTO ledger (note) VALUES ('rolled back') RETURNING id;
ROLLBACK;

INSERT INTO ledger (note) VALUES ('kept') RETURNING id;

BEGIN;
CREATE TABLE scratch (x int);
INSERT INTO scratch VALUES (1);
ROLLBACK;
SELECT to_regclass('scratch') AS scratch_exists;
```

```text
CREATE TABLE
BEGIN
 id 
----
  1
(1 row)

INSERT 0 1
ROLLBACK
 id 
----
  2
(1 row)

INSERT 0 1
BEGIN
CREATE TABLE
INSERT 0 1
ROLLBACK
 scratch_exists 
----------------
 
(1 row)
```

The rolled-back insert consumed id 1, so the next row got 2. And the `CREATE TABLE` inside the rolled-back transaction left no table behind (`to_regclass` returns NULL).

Every transaction that writes gets a transaction id. `pg_current_xact_id()` returns it, and it is the same all the way through one transaction but a fresh one for every auto-committed statement (your numbers will differ; the pattern will not):

```sql
-- sql/xid.sql
BEGIN;
SELECT pg_current_xact_id() = pg_current_xact_id() AS same_xid_in_tx;
COMMIT;
SELECT pg_current_xact_id() AS first_autocommit;
SELECT pg_current_xact_id() AS second_autocommit;
```

```text
BEGIN
 same_xid_in_tx 
----------------
 t
(1 row)

COMMIT
 first_autocommit 
------------------
           324811
(1 row)

 second_autocommit 
-------------------
            324812
(1 row)
```

## A forgotten transaction is not free

An open transaction holds its locks and its snapshot. A session that ran `BEGIN` and then went quiet shows up in `pg_stat_activity` as `idle in transaction`, and anyone who needs the rows it touched has to wait. Session A updates Ada and then does nothing for 3 seconds; session B, one second in, looks at `pg_stat_activity` and tries to update the same row:

```text
-- session A: script
BEGIN;
UPDATE accounts SET balance = balance WHERE owner = 'Ada';
\! sleep 3
ROLLBACK;
-- session A: psql output
BEGIN
UPDATE 1
ROLLBACK

-- session B: script
\! sleep 1
SELECT state, wait_event_type, query
FROM pg_stat_activity
WHERE datname = current_database() AND pid <> pg_backend_pid() AND backend_type = 'client backend';
\timing on
UPDATE accounts SET balance = balance WHERE owner = 'Ada';
-- session B: psql output
        state        | wait_event_type |                           query                            
---------------------+-----------------+------------------------------------------------------------
 idle in transaction | Client          | UPDATE accounts SET balance = balance WHERE owner = 'Ada';
(1 row)

Timing is on.
UPDATE 1
Time: 1997.304 ms (00:01.997)
```

B waited about two seconds — until A finished — for a change that A never even needed. The server can end such sessions for you with `idle_in_transaction_session_timeout`; the connection is closed with a `FATAL`, and the client has to reconnect:

```text
-- session A: script
SET idle_in_transaction_session_timeout = '1s';
BEGIN;
SELECT 1 AS still_alive;
\! sleep 2
SELECT 2 AS after_the_nap;
-- session A: psql output
SET
BEGIN
 still_alive 
-------------
           1
(1 row)

FATAL:  terminating connection due to idle-in-transaction timeout
server closed the connection unexpectedly
	This probably means the server terminated abnormally
	before or while processing the request.
connection to server was lost
```

## Reading AI-generated code

An assistant is asked for an atomic transfer with `node-postgres` and writes the happy path, with a comment that says exactly what we want:

<SpotTheBug lang="js" code={`// AI comment: "transfer money atomically inside a transaction"
async function transfer(pool, from, to, amount) {
  const client = await pool.connect();
  await client.query('BEGIN');
  await client.query('UPDATE accounts SET balance = balance - $1 WHERE owner = $2', [amount, from]);
  await client.query('UPDATE accounts SET balance = balance + $1 WHERE owner = $2', [amount, to]);
  await client.query('COMMIT');
  client.release();
}`}>

It is atomic only while nothing goes wrong. When the second `UPDATE` (or the first, if Ada is short) throws, control leaves the function before `COMMIT` and before `client.release()`. There is no `ROLLBACK`, so the connection stays in the aborted transaction, and it is never returned to the pool. Run it three times with an amount Ada cannot cover (pg 8.23.0, pool of 5, `amount = 1000`):

```text

call failed: 23514 new row for relation "accounts" violates check constraint "accounts_balance_check"
call failed: 23514 new row for relation "accounts" violates check constraint "accounts_balance_check"
after 3 failed calls: [{"state":"idle in transaction (aborted)","n":3}]
pool: total 3 idle 0 waiting 0

$ node transfer.js fixed
call failed: 23514 new row for relation "accounts" violates check constraint "accounts_balance_check"
call failed: 23514 new row for relation "accounts" violates check constraint "accounts_balance_check"
call failed: 23514 new row for relation "accounts" violates check constraint "accounts_balance_check"
after 3 failed calls: []
pool: total 1 idle 1 waiting 0
```

Three backends are stuck as `idle in transaction (aborted)` and the pool has lost three of its five clients. After five such failures every request waits forever for a connection. You would find them with a query like this one:

```sql
SELECT state, count(*) FROM pg_stat_activity WHERE datname = current_database() AND pid <> pg_backend_pid() AND state <> 'idle' GROUP BY state;
```

The fix is the try / catch / finally shape from the transfer tab: `ROLLBACK` on the error path and `release()` in `finally`, so the connection is always returned. The same three failing calls leave nothing open (the second run above):

```js
async function transfer(pool, from, to, amount) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    await client.query('UPDATE accounts SET balance = balance - $1 WHERE owner = $2', [amount, from]);
    await client.query('UPDATE accounts SET balance = balance + $1 WHERE owner = $2', [amount, to]);
    await client.query('COMMIT');
  } catch (e) {
    await client.query('ROLLBACK');
    throw e;
  } finally {
    client.release();
  }
}
```

</SpotTheBug>

## Mental Model

A transaction is a private scratchpad. Everything you do lands on your pad first, invisible to others; `COMMIT` publishes the whole pad in one instant, `ROLLBACK` tears it up. Outside a `BEGIN`, PostgreSQL wraps each statement in its own tiny pad. Errors inside a pad do not just fail one statement — they spoil the pad, and only `ROLLBACK` (or `ROLLBACK TO` a savepoint) lets you write on it again.

## Tips / gotchas

- Keep transactions short. A transaction that stays open holds locks (B waited two seconds above) and, as the MVCC lesson shows, holds back cleanup of old row versions.
- An error inside a transaction puts it into an aborted state (`25P02` for every later command); `COMMIT` on an aborted transaction silently becomes a rollback.
- An `UPDATE` that matches nothing is not an error. Check the row count (`UPDATE 0`) if you need to know.
- In application code, always pair `BEGIN` with a `ROLLBACK` on the error path and release the connection in `finally`. The driver examples above show the shape; the bug above shows what happens without it.
- Set `idle_in_transaction_session_timeout` in production as a backstop for code that forgets.
- Sequences and `nextval` are not rolled back; never rely on gapless ids.

<Callout title="Commit is the point of no return">
Before `COMMIT`, your changes live only in your transaction and can vanish with a single `ROLLBACK`. After `COMMIT`, durability takes over and the change is written to survive a crash. Treat the commit as the moment you are sure.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| Wrap related statements in `BEGIN...COMMIT` | Atomicity — the whole thing succeeds or nothing happens (the 600 total above) | You must handle the error path (`ROLLBACK`) yourself, and an open transaction holds locks longer |
| Let each statement auto-commit | Simpler code, no transaction to manage | An error partway through leaves half the work committed (the 1100 total above) |
| `SAVEPOINT` around risky statements | Recover from one failure without losing the rest | Each savepoint starts a subtransaction; use them where you expect an error, not around every statement |

## Common Misconceptions

- **"Several statements are automatically atomic."** Without a `BEGIN`, each statement commits on its own; a failure between them leaves the data half-done (Ada +500 with no matching debit).
- **"COMMIT always commits."** On an aborted transaction it rolls back and says so with the tag `ROLLBACK`.
- **"An error only fails that statement."** Inside a transaction it fails the rest too, until `ROLLBACK` or `ROLLBACK TO`.
- **"ROLLBACK undoes everything."** It does not return sequence values (id 1 was burned), and it is not a substitute for closing connections properly.
- **"Forgetting to close a transaction is harmless."** It blocks other writers and holds back vacuum; it is one of the most common production incidents.
