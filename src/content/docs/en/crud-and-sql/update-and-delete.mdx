The last two CRUD verbs change existing data. `UPDATE` sets new column values on rows that match a condition, and `DELETE` removes matching rows. Both lean heavily on the `WHERE` clause you learned for `SELECT` — and both become destructive mistakes if you forget it.

Everything below is real output from **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026), run top to bottom in one empty database that starts with the course's canonical dataset. Most changes are wrapped in `BEGIN ... ROLLBACK` so that every example starts from the same rows; the command tags (`UPDATE 1`, `DELETE 2`) are what a real run prints.

## Updating columns

`UPDATE` names the table, lists `SET column = value` pairs, and uses `WHERE` to pick the rows. Without `WHERE`, every row is changed. The new value can reference the old one, as `copies_sold + 500` shows.

## Confirming a change with RETURNING

Just like `INSERT`, both `UPDATE` and `DELETE` accept `RETURNING`. This is the cleanest way to see exactly which rows changed and what their new values are.

    UPDATE books
    SET published = 2019
    WHERE title = 'The Glass Orchard'
    RETURNING id, title, published;
    ROLLBACK;

PostgreSQL 18 adds `old` and `new` aliases to `RETURNING`, so one statement can report both the value before and the value after ([release notes](https://www.postgresql.org/docs/18/release-18.html)). Before PostgreSQL 18 this needed a `SELECT` first or a trigger:

```sql
-- sql/update-returning-old-new.sql
BEGIN;
UPDATE books
SET copies_sold = copies_sold + 5
WHERE id = 2
RETURNING id, title, old.copies_sold AS was, new.copies_sold AS now;
ROLLBACK;
```

```text
BEGIN
 id |       title       | was  | now  
----+-------------------+------+------
  2 | The Glass Orchard | 1250 | 1255
(1 row)

UPDATE 1
ROLLBACK
```

### UPDATE ... FROM

To set values from another table, add a `FROM` clause and join in `WHERE`. Here each book's `copies_sold` is recomputed from its `sales` rows. Books 1 and 3 already agree with their sales; book 2 has 200 copies unaccounted for in `sales` (1250 vs 1050), and the statement would silently overwrite them:

```sql
-- sql/update-from.sql
BEGIN;
UPDATE books b
SET copies_sold = s.total
FROM (SELECT book_id, sum(copies) AS total FROM sales GROUP BY book_id) s
WHERE s.book_id = b.id
RETURNING b.id, b.title, old.copies_sold AS was, new.copies_sold AS now;
ROLLBACK;
```

```text
BEGIN
 id |       title       | was  | now  
----+-------------------+------+------
  1 | Quiet Harbors     |  450 |  450
  2 | The Glass Orchard | 1250 | 1050
  3 | Tidal Notes       |  600 |  600
(3 rows)

UPDATE 3
ROLLBACK
```

The `FROM` list is a join, and the `WHERE` is the join condition. That is powerful and easy to get wrong (see the last section).

## The danger of a missing WHERE

`UPDATE` and `DELETE` apply to every row that matches the condition — and if there is no condition, every row matches. `DELETE FROM books;` would empty the table, and `UPDATE books SET copies_sold = 0;` zeroes every record. The command tag is the only warning: `UPDATE 4` where you expected `UPDATE 1`.

A safe habit is to run the same `WHERE` as a `SELECT` first, confirm the row count, then switch the verb. Wrapping risky changes in a transaction gives you an escape hatch, as here (the whole table zeroed, then undone):

```sql
-- sql/missing-where.sql
SELECT count(*) AS rows_that_match FROM books WHERE author_id = 1;
BEGIN;
UPDATE books SET copies_sold = 0;
SELECT sum(copies_sold) AS total_after FROM books;
ROLLBACK;
SELECT sum(copies_sold) AS total_after_rollback FROM books;
```

```text
 rows_that_match 
-----------------
               2
(1 row)

BEGIN
UPDATE 4
 total_after 
-------------
           0
(1 row)

ROLLBACK
 total_after_rollback 
----------------------
                 2300
(1 row)
```

The same pattern from psql and the drivers — inspect inside the transaction, then decide:

## TRUNCATE

To remove every row, `TRUNCATE` is the tool: it is much faster than `DELETE FROM` on a big table and it is transactional in PostgreSQL. It refuses when a foreign key points at the table, unless you truncate the referencing table too or say `CASCADE` (which also empties tables you may not have intended):

```sql
-- sql/truncate.sql
BEGIN;
TRUNCATE sales;
SELECT count(*) AS sales_rows FROM sales;
ROLLBACK;
SELECT count(*) AS sales_rows_after_rollback FROM sales;
```

```text
BEGIN
TRUNCATE TABLE
 sales_rows 
------------
          0
(1 row)

ROLLBACK
 sales_rows_after_rollback 
---------------------------
                         6
(1 row)
```

```sql
-- @expect-error 0A000
TRUNCATE books;
```

```text
ERROR:  cannot truncate a table referenced in a foreign key constraint
DETAIL:  Table "sales" references "books".
HINT:  Truncate table "sales" at the same time, or use TRUNCATE ... CASCADE.
```

```sql
-- sql/truncate-cascade.sql
BEGIN;
TRUNCATE books CASCADE;
SELECT (SELECT count(*) FROM books) AS books, (SELECT count(*) FROM sales) AS sales, (SELECT count(*) FROM authors) AS authors;
ROLLBACK;
```

```text
BEGIN
NOTICE:  truncate cascades to table "sales"
TRUNCATE TABLE
 books | sales | authors 
-------+-------+---------
     0 |     0 |       3
(1 row)

ROLLBACK
```

## What DELETE and UPDATE leave behind

PostgreSQL never overwrites a row in place. An `UPDATE` writes a new version of the row and leaves the old one as a **dead tuple** until `VACUUM` reclaims it, and a `DELETE` just marks the row dead. Proof on 100,000 rows: one full-table `UPDATE` doubles the heap file; `VACUUM` makes the dead space reusable (it does not shrink the file), and a second full-table `UPDATE` then fits in the same space. `pg_stat_force_next_flush()` is a testing helper that publishes this session's statistics immediately; normally they show up about a second later:

```sql
-- sql/dead-tuples.sql
CREATE TABLE counters (id int PRIMARY KEY, n int NOT NULL);
INSERT INTO counters SELECT g, 0 FROM generate_series(1, 100000) g;
VACUUM (ANALYZE) counters;
SELECT pg_size_pretty(pg_relation_size('counters')) AS fresh_heap;
UPDATE counters SET n = n + 1;
SELECT pg_size_pretty(pg_relation_size('counters')) AS after_one_full_update;
SELECT pg_stat_force_next_flush();
SELECT n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname = 'counters';
VACUUM counters;
SELECT pg_stat_force_next_flush();
SELECT n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname = 'counters';
UPDATE counters SET n = n + 1;
SELECT pg_size_pretty(pg_relation_size('counters')) AS after_second_update_with_reuse;
```

## Reading AI-generated code

The task was "sync `books.copies_sold` from the East region sales". The assistant writes an `UPDATE ... FROM`, and it even reads well:

<SpotTheBug lang="sql" code={`-- migration: sync books.copies_sold from the East region sales
-- AI comment: "pull the East figures into the books table"
UPDATE books
SET copies_sold = s.copies
FROM sales s
WHERE s.region = 'East';`}>

The bug is the missing join condition. The `WHERE` filters `sales` to the East rows but never ties a sale to its book, so every book is joined with every East sale, and PostgreSQL applies one arbitrary match to each. It runs without error and touches every row, including the book that has no sales at all (`UPDATE 4`):

```sql
-- sql/update-from-bug.sql
BEGIN;
UPDATE books
SET copies_sold = s.copies
FROM sales s
WHERE s.region = 'East'
RETURNING books.id, books.title, old.copies_sold AS was, new.copies_sold AS now;
ROLLBACK;
```

```text
BEGIN
 id |       title       | was  | now 
----+-------------------+------+-----
  1 | Quiet Harbors     |  450 | 900
  2 | The Glass Orchard | 1250 | 900
  3 | Tidal Notes       |  600 | 900
  4 | Unlinked Draft    |    0 | 900
(4 rows)

UPDATE 4
ROLLBACK
```

Every book now claims 900 copies (the value of the first East sale the join happened to pick). The fix joins on the key and aggregates first, so each book gets one value and only books with East sales are touched:

```sql
-- sql/update-from-fixed.sql
BEGIN;
UPDATE books b
SET copies_sold = e.total
FROM (SELECT book_id, sum(copies) AS total FROM sales WHERE region = 'East' GROUP BY book_id) e
WHERE e.book_id = b.id
RETURNING b.id, b.title, old.copies_sold AS was, new.copies_sold AS now;
ROLLBACK;
```

```text
BEGIN
 id |       title       | was  | now 
----+-------------------+------+-----
  1 | Quiet Harbors     |  450 |  50
  2 | The Glass Orchard | 1250 | 900
  3 | Tidal Notes       |  600 | 200
(3 rows)

UPDATE 3
ROLLBACK
```

`RETURNING old.x, new.x` is what made the bug obvious. Use it (or a preceding `SELECT count(*)`) for every data fix.

## Mental Model

`UPDATE` and `DELETE` are `SELECT` plus an action: the `WHERE` (and `FROM`/`USING` join) selects a set of rows, and the action applies to that set. If the set is wrong, the action is wrong, silently. So every safe workflow is about checking the set before acting: `SELECT count(*)` first, `RETURNING` after, a transaction around it. Inside, MVCC means neither statement is in place; both create dead row versions that vacuum cleans up later.

## Tips / gotchas

- Always include a `WHERE` clause on `UPDATE` and `DELETE` unless you genuinely intend to touch every row. A forgotten `WHERE` rewrites or empties the whole table.
- Preview destructive statements by running the matching `SELECT count(*) ... WHERE ...` first to confirm how many rows you are about to affect.
- Wrap risky or multi-step changes in a transaction so you can `ROLLBACK` if the result is wrong.
- Use `RETURNING` (with `old`/`new` in PostgreSQL 18) to verify exactly which rows changed instead of trusting the row count alone.
- In `UPDATE ... FROM` and `DELETE ... USING`, always include the join condition in `WHERE`.
- A `DELETE` may fail if other tables reference the row through a foreign key (`23503`); `ON DELETE CASCADE` changes that, at the price of larger deletes.
- Use `TRUNCATE` (not `DELETE`) to empty a whole table.

<Callout title="WHERE is not optional in practice">
The single most common production accident with SQL is an `UPDATE` or `DELETE` that ran without its `WHERE` clause. Build the muscle memory: type the `WHERE` first, the values second. When in doubt, do it inside a transaction you can roll back.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| `UPDATE`/`DELETE` with a specific `WHERE` | Safe, only touches the rows you intended | Requires getting the condition fully right before running it |
| `UPDATE`/`DELETE` with no `WHERE` | Fast to write, no condition to think about | Hits every row immediately — a disaster if run against the wrong table or environment |
| Wrapped in a transaction you can `ROLLBACK` | An emergency exit before the real `COMMIT` | Have to remember to open/close the transaction and check the result every time |
| Run directly outside a transaction | Fast, no transaction to manage | No undo button if the result is wrong |
| `TRUNCATE` instead of `DELETE FROM` | Instant, no per-row work | Needs a strong lock, refused with foreign keys unless `CASCADE` |

## Common Misconceptions

- **"`DELETE` frees disk space."** It marks rows dead. Only `VACUUM` makes the space reusable, and only trailing empty pages are returned to the OS (the heap above did not shrink).
- **"An UPDATE changes the row in place."** It writes a new version (the heap doubled after one full-table update).
- **"`UPDATE ... FROM` without a join is a syntax error."** It is valid SQL and updates every row with an arbitrary match (proved above).
- **"The row count is enough to know it worked."** `UPDATE 4` looks fine until you expected 1; `RETURNING` shows which rows.
- **"`TRUNCATE` cannot be rolled back."** In PostgreSQL it can, inside a transaction.
