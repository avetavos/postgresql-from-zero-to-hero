Creating data means adding rows, and the statement for that is `INSERT`. You name a table, list the columns you are supplying, and give the values. PostgreSQL fills in anything you leave out — generated ids, columns with a `DEFAULT`, and any column that allows `NULL`.

This lesson builds the course's `authors`, `books` and `sales` dataset from scratch, one `INSERT` at a time, so by the end you have exactly the rows every later lesson starts with. Everything shown is real output from **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026), top to bottom in one empty database. Timings are from this Mac.

```sql
-- sql/setup.sql
CREATE TABLE authors (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  born int
);
CREATE TABLE books (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title       text NOT NULL,
  author_id   bigint REFERENCES authors (id),
  published   int,
  copies_sold int NOT NULL DEFAULT 0
);
CREATE TABLE sales (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  book_id bigint REFERENCES books (id),
  region  text NOT NULL,
  copies  int NOT NULL
);
```

## A single row

The most basic form lists the columns, then the matching values. The server answers with a command tag, `INSERT 0 1`: the `0` is a legacy object id field and the `1` is the number of rows inserted.

Notice the `psql` tab uses literal values, while every driver uses **placeholders** — `$1`, `$2` in PostgreSQL native style, or `%s` for psycopg — and passes the real values separately. Always supply user data this way; never glue values into the SQL string yourself (the last section of this lesson proves why, with a real payload).

**In pgAdmin:** paste the `psql` version into the Query Tool and run it; the message panel will report `INSERT 0 1`, meaning one row was added.

## Many rows at once

You can list several value tuples in one statement. This is far faster than running one `INSERT` per row, because it is a single round trip and a single transaction (measured below).

<Tabs syncKey="lang">
  <TabItem label="psql">
    ```sql
    -- sql/insert-many.sql
    INSERT INTO authors (name, born) VALUES
      ('Owen Pryce', 1975),
      ('Sela Vance',  1990);
    SELECT id, name, born FROM authors ORDER BY id;
    ```
  </TabItem>
  <TabItem label="Node.js">
    ```js
    await pool.query(
      'INSERT INTO authors (name, born) VALUES ($1, $2), ($3, $4)',
      ['Owen Pryce', 1975, 'Sela Vance', 1990],
    );
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    rows = [("Owen Pryce", 1975), ("Sela Vance", 1990)]
    cur.executemany("INSERT INTO authors (name, born) VALUES (%s, %s)", rows)
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    rows := [][]any{
        {"Owen Pryce", 1975},
        {"Sela Vance", 1990},
    }
    _, err := conn.CopyFrom(ctx,
        pgx.Identifier{"authors"},
        []string{"name", "born"},
        pgx.CopyFromRows(rows))
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    let names = ["Owen Pryce", "Sela Vance"];
    let years = [1975_i32, 1990];
    sqlx::query(
        "INSERT INTO authors (name, born) SELECT * FROM UNNEST($1::text[], $2::int[])",
    )
    .bind(&names[..])
    .bind(&years[..])
    .execute(&pool)
    .await?;
    ```
  </TabItem>
</Tabs>

```text
INSERT 0 2
 id |    name    | born 
----+------------+------
  1 | Mara Linde | 1968
  2 | Owen Pryce | 1975
  3 | Sela Vance | 1990
(3 rows)
```

The drivers each have an idiomatic bulk path: psycopg has `executemany`, pgx offers the very fast `CopyFrom` (the `COPY` protocol), and with sqlx you can unnest arrays so a single statement inserts many rows. The next three books go in as a multi-row insert too. Each has an `author_id`, which must match an existing author because of the foreign key:

```sql
-- sql/insert-books.sql
INSERT INTO books (title, author_id, published, copies_sold) VALUES
  ('Quiet Harbors',     1, 2003,  450),
  ('The Glass Orchard', 1, 2018, 1250),
  ('Tidal Notes',       2, 2011,  600);
```

## Letting columns take defaults

The `books` table has `copies_sold int NOT NULL DEFAULT 0`. If you simply omit that column, PostgreSQL uses the default. You can also write `DEFAULT` explicitly to be clear about your intent, and `NULL` is a legal value for a nullable column such as `author_id`. Same statement from every driver: leave the column out of the column list.

```sql
-- sql/insert-default.sql
INSERT INTO books (title, author_id, published, copies_sold)
VALUES ('Unlinked Draft', NULL, 2020, DEFAULT);
SELECT id, title, author_id, copies_sold FROM books ORDER BY id;
```

```text
INSERT 0 1
 id |       title       | author_id | copies_sold 
----+-------------------+-----------+-------------
  1 | Quiet Harbors     |         1 |         450
  2 | The Glass Orchard |         1 |        1250
  3 | Tidal Notes       |         2 |         600
  4 | Unlinked Draft    |           |           0
(4 rows)
```

`copies_sold` landed as `0` and `author_id` as NULL, and the identity gave the new row id 4. Omitting a column entirely is the usual approach; writing `DEFAULT` is handy when you are filling several rows and want every position spelled out.

## Getting the generated id back

The `id` column is `GENERATED ALWAYS AS IDENTITY`, so PostgreSQL assigns it. To learn the value without a second query, append `RETURNING`. The block below runs inside a transaction that is rolled back, so no extra author is left behind (but the identity value is used up: sequences never roll back, as the constraints lesson showed).

<Tabs syncKey="lang">
  <TabItem label="psql">
    ```sql
    -- sql/insert-returning.sql
    BEGIN;
    INSERT INTO authors (name, born)
    VALUES ('Temp Author', 2000)
    RETURNING id;
    ROLLBACK;
    ```
  </TabItem>
  <TabItem label="Node.js">
    ```js
    const res = await pool.query(
      'INSERT INTO authors (name, born) VALUES ($1, $2) RETURNING id',
      ['Temp Author', 2000],
    );
    console.log(res.rows[0].id);
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    cur.execute(
        "INSERT INTO authors (name, born) VALUES (%s, %s) RETURNING id",
        ("Temp Author", 2000),
    )
    new_id = cur.fetchone()[0]
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    var id int64
    err := conn.QueryRow(ctx,
        "INSERT INTO authors (name, born) VALUES ($1, $2) RETURNING id",
        "Temp Author", 2000).Scan(&id)
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    let id: i64 = sqlx::query_scalar(
        "INSERT INTO authors (name, born) VALUES ($1, $2) RETURNING id",
    )
    .bind("Temp Author")
    .bind(2000_i32)
    .fetch_one(&pool)
    .await?;
    ```

The statement both inserts the row and hands back the new id in one trip; here the next id is 4 because authors 1-3 exist. `RETURNING` works with multi-row inserts too and returns one row per inserted row, in insert order. This is also how the sales rows go in:

```sql
-- sql/insert-returning-many.sql
INSERT INTO sales (book_id, region, copies) VALUES
  (2, 'East', 900), (3, 'West', 400), (1, 'West', 400),
  (3, 'East', 200), (2, 'West', 150), (1, 'East',  50)
RETURNING id, book_id, region, copies;
```

```text
 id | book_id | region | copies 
----+---------+--------+--------
  1 |       2 | East   |    900
  2 |       3 | West   |    400
  3 |       1 | West   |    400
  4 |       3 | East   |    200
  5 |       2 | West   |    150
  6 |       1 | East   |     50
(6 rows)

INSERT 0 6
```

## When an insert is refused

An insert can fail in four ways you will meet in practice. Each is a different SQLSTATE class and message, real:

- Supplying a value for a `GENERATED ALWAYS` identity column (`428C9`). `OVERRIDING SYSTEM VALUE` is the deliberate escape hatch:

```sql
-- @expect-error 428C9
INSERT INTO authors (id, name, born) VALUES (10, 'Impostor', 1980);
```

```text
ERROR:  cannot insert a non-DEFAULT value into column "id"
DETAIL:  Column "id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.
```

- Leaving out a `NOT NULL` column that has no default (`23502`):

```sql
-- @expect-error 23502
INSERT INTO sales (book_id, copies) VALUES (1, 10);
```

```text
ERROR:  null value in column "region" of relation "sales" violates not-null constraint
DETAIL:  Failing row contains (7, 1, null, 10).
```

- Pointing at a row that does not exist (`23503`):

```sql
-- @expect-error 23503
INSERT INTO sales (book_id, region, copies) VALUES (99, 'East', 10);
```

```text
ERROR:  insert or update on table "sales" violates foreign key constraint "sales_book_id_fkey"
DETAIL:  Key (book_id)=(99) is not present in table "books".
```

## INSERT ... SELECT and DEFAULT VALUES

The source of an insert does not have to be a literal list. `INSERT ... SELECT` copies rows produced by any query, and `DEFAULT VALUES` inserts a row where every column takes its default:

```sql
-- sql/insert-select.sql
CREATE TABLE top_books (title text NOT NULL, copies_sold int NOT NULL);
INSERT INTO top_books
SELECT title, copies_sold FROM books WHERE copies_sold > 500 ORDER BY copies_sold DESC;

CREATE TABLE pings (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, at timestamptz NOT NULL DEFAULT now());
INSERT INTO pings DEFAULT VALUES RETURNING id;
SELECT * FROM top_books;
```

```text
(2 rows)
```

## How much faster is batching?

The claim "multi-row inserts and `COPY` are much faster than a loop of single inserts" is easy to check. The same 50,000 rows, four ways, into four tables, timed inside one psql session. The first two run 50,000 separate `INSERT` statements from the client (`\gexec`); this is over a local Unix socket, so the network cost you would pay in production is not even included:

```sql
-- sql/load-timing.sql
CREATE TABLE load_single (id int, label text);
CREATE TABLE load_tx     (id int, label text);
CREATE TABLE load_multi  (id int, label text);
CREATE TABLE load_copy   (id int, label text);

-- 1) one INSERT statement per row, each its own transaction (autocommit)
SELECT clock_timestamp() AS t0 \gset
\o /dev/null
SELECT format('INSERT INTO load_single VALUES (%s, %L);', g, 'row-' || g) FROM generate_series(1, 50000) g \gexec
\o
SELECT round(extract(epoch FROM clock_timestamp() - :'t0') * 1000) AS single_row_autocommit_ms;

-- 2) the same statements inside ONE transaction
SELECT clock_timestamp() AS t0 \gset
BEGIN;
\o /dev/null
SELECT format('INSERT INTO load_tx VALUES (%s, %L);', g, 'row-' || g) FROM generate_series(1, 50000) g \gexec
\o
COMMIT;
SELECT round(extract(epoch FROM clock_timestamp() - :'t0') * 1000) AS single_row_one_tx_ms;

-- 3) one multi-row statement
SELECT clock_timestamp() AS t0 \gset
INSERT INTO load_multi SELECT g, 'row-' || g FROM generate_series(1, 50000) g;
SELECT round(extract(epoch FROM clock_timestamp() - :'t0') * 1000) AS one_statement_ms;

-- 4) COPY from a file (\copy: the file is on the client side)
\copy (SELECT g, 'row-' || g FROM generate_series(1, 50000) g) TO '/tmp/load.csv' WITH (FORMAT csv)
SELECT clock_timestamp() AS t0 \gset
\copy load_copy FROM '/tmp/load.csv' WITH (FORMAT csv)
SELECT round(extract(epoch FROM clock_timestamp() - :'t0') * 1000) AS copy_ms;
SELECT (SELECT count(*) FROM load_single) AS single_rows, (SELECT count(*) FROM load_tx) AS tx_rows,
       (SELECT count(*) FROM load_multi) AS multi_rows, (SELECT count(*) FROM load_copy) AS copy_rows;
```

```text
CREATE TABLE

--------------------------

(1 row)

COMMIT
```

On this Mac: about 6.6 seconds when each row is its own transaction, about 3.4 seconds when the same statements share one transaction (the difference is 50,000 commits), and about 34 ms for one multi-row statement or 15 ms for `COPY`. That is a factor of several hundred between the naive loop and the batched forms, before adding network latency per statement. Use one multi-row `INSERT` for small batches (a single statement can carry at most 65,535 bound parameters, see the [protocol message formats](https://www.postgresql.org/docs/18/protocol-message-formats.html)) and `COPY` for large loads.

## Reading AI-generated code

An assistant asked for "a quick insert for the signup form" writes a helper. It works in every demo, including names with normal characters:

<SpotTheBug lang="js" code={`// signup.js  (AI comment: "quick insert for the signup form")
async function addAuthor(name, born) {
  await pool.query(
    \`INSERT INTO authors (name, born) VALUES ('\${name}', \${born})\`
  );
}`}>

The bug is that the values are pasted into the SQL text with a template string. With `pg`, a query without parameters is sent as a simple query, which may contain several statements, so a crafted `name` can end the INSERT and append its own. Proved with a real program against a scratch database (a table `sales` with 6 rows). First, what the server actually receives for the hostile name, built in SQL with `format`:

```sql
-- sql/injection-built-sql.sql
SELECT format($f$INSERT INTO authors (name, born) VALUES ('%s', %s)$f$,
              $p$x', 1); DELETE FROM sales; --$p$, 1990) AS what_the_server_receives;
```

```text
                            what_the_server_receives                             
---------------------------------------------------------------------------------
 INSERT INTO authors (name, born) VALUES ('x', 1); DELETE FROM sales; --', 1990)
(1 row)
```

The first statement inserts a harmless author `x`, the second deletes every sale, and `--` comments out the rest. Now the real program: even a legitimate name with an apostrophe breaks it (`42601`), the hostile one empties `sales`, and the placeholder version stores the same hostile text as plain data and leaves `sales` alone:

```text
$ node inj.mjs        # pg 8.23.0, scratch database with 6 rows in sales
sales rows before: 6
O'Brien -> 42601 syntax error at or near "Brien"
sales rows after unsafe insert: 0
sales rows restored: 6
sales rows after safe insert: 6
[
  { id: '1', name: 'x' },
  { id: '2', name: "x', 1); DELETE FROM sales; --" },
  { id: '3', name: "O'Brien" }
]
```

The fix is to pass the values separately from the SQL so the server never parses them as SQL:

```js
async function addAuthor(name, born) {
  await pool.query(
    'INSERT INTO authors (name, born) VALUES ($1, $2)',
    [name, born],
  );
}
```

In `psql` the same idea is `PREPARE` / `EXECUTE` (drivers use the protocol-level equivalent). The hostile string is stored verbatim and `sales` still has its 6 rows (rolled back to keep the dataset intact):

```sql
-- sql/injection-safe.sql
BEGIN;
PREPARE add_author (text, int) AS
  INSERT INTO authors (name, born) VALUES ($1, $2);
EXECUTE add_author($p$x', 1); DELETE FROM sales; --$p$, 1990);
SELECT name FROM authors WHERE born = 1990 ORDER BY id;
SELECT count(*) AS sales_rows FROM sales;
ROLLBACK;
DEALLOCATE add_author;
```

## Mental Model

An `INSERT` is a request to the server, and everything you leave out is decided by the schema: `DEFAULT`, identity generation, or `NULL`. The command you write picks the *cost profile*: every statement is a round trip, and every transaction is a commit. Batching, in one statement or in one transaction, changes those two numbers, and that is the whole speed story. Placeholders separate *code* from *data* so the server can never confuse them.

## Tips / gotchas

- Always pass values through driver placeholders (`$1`, `%s`). Building SQL with string concatenation invites SQL injection and breaks on quotes or special characters.
- With an `IDENTITY` (or `serial`) primary key, do not supply the id yourself — let PostgreSQL generate it and read it back with `RETURNING`.
- Multi-row inserts are one statement and one round trip; `COPY` is faster still for big loads (measured above).
- Failed and rolled-back inserts still consume identity values, so ids have gaps.
- A column with no value and no default must allow `NULL`, or the insert fails with a not-null violation.

<Callout title="RETURNING is your friend">
`RETURNING` turns a write into a write-plus-read in a single statement. It avoids a follow-up `SELECT` and avoids race conditions, since the values you get back are exactly the ones this insert produced.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| `RETURNING` after `INSERT` | Get generated values (like `id`) back in one round trip, no race condition | One more syntax to remember, and some drivers must read the result as a query instead of a plain exec |
| A separate `SELECT` afterwards | Simple and easy for beginners to follow | An extra round trip, and a race condition if another insert lands in between |
| Multi-row `INSERT` in one statement | Fast — a single round trip (34 ms for 50,000 rows above) | Longer statement, and one bad row can fail the whole statement |
| `COPY` / `\copy` | Fastest bulk path (15 ms for 50,000 rows above) | Needs a file or stream in CSV/text format; less flexible error handling |
| Looping single-row inserts | Easy to read, one step at a time | 6.6 s for the same 50,000 rows (autocommit), 3.4 s in one transaction |

## Common Misconceptions

- **"Batching only helps over a slow network."** It helped by a factor of hundreds over a local socket, because each statement also pays a commit (6.6 s vs 3.4 s vs 34 ms above).
- **"Escaping quotes is enough to be safe."** Placeholders are the fix; hand-escaping is where injection bugs come from (the `O'Brien` failure above is the friendly version).
- **"`RETURNING` needs a second query."** It is part of the same statement, even for many rows.
- **"A rolled-back insert leaves no trace."** The rows are gone, but the identity value is consumed (the temp author took 4).
- **"`DEFAULT` and omitting the column differ."** They are the same; `DEFAULT` just makes a full column list explicit.
