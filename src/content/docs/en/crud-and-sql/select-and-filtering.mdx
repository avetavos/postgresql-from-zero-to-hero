Reading is the most common thing you do with a database, and `SELECT` is how you do it. A `SELECT` describes which columns you want, which rows qualify, in what order, and how many. The server returns a result set — zero or more rows — without changing anything on disk.

## IN, BETWEEN, and pattern matching

`IN` checks membership in a list, `BETWEEN` is an inclusive range (both ends are included: 1968 and 1975 below), and `LIKE` matches text patterns.

```sql

SELECT name, born
FROM authors
WHERE born BETWEEN 1968 AND 1975;

SELECT title FROM books WHERE published IN (2003, 2011);
```

The rest of the three-valued logic, run on the same table. `= NULL` returns nothing. `<> 1` **also** drops the row with a NULL author, because `unknown <> 1` is unknown, not true; `IS DISTINCT FROM` treats NULL as an ordinary value. And `count(column)` skips NULLs while `count(*)` does not:

```sql
-- sql/select-null.sql
SELECT title FROM books WHERE author_id = NULL;
SELECT title FROM books WHERE author_id <> 1 ORDER BY id;
SELECT title FROM books WHERE author_id IS DISTINCT FROM 1 ORDER BY id;
SELECT count(*) AS all_rows, count(author_id) AS non_null_author_id FROM books;
```

### Deep OFFSET is slow, keyset paging is not

`OFFSET n` cannot skip rows without reading them: the server produces the first `n + limit` rows and throws `n` away. The cost grows with the page number. Keyset ("seek") paging asks for rows after the last key you saw instead. On 200,000 rows, page 15,001 both ways (the plan shows the rows actually read):

```sql
-- sql/offset-vs-keyset.sql
CREATE TABLE events (id int PRIMARY KEY, payload text);
INSERT INTO events SELECT g, md5(g::text) FROM generate_series(1, 200000) g;
ANALYZE events;
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, SUMMARY ON)
SELECT id FROM events ORDER BY id LIMIT 10 OFFSET 150000;
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, SUMMARY ON)
SELECT id FROM events WHERE id > 150000 ORDER BY id LIMIT 10;
```

```text
CREATE TABLE
INSERT 0 200000

------------------------------------------------------------------------------------------------------

   ->  Index Only Scan using events_pkey on events (actual time=0.012..15.379 rows=150010.00 loops=1)
         Heap Fetches: 150010
         Index Searches: 1
 Planning Time: 0.095 ms
 Execution Time: 19.118 ms
(6 rows)

                                           QUERY PLAN                                            
-------------------------------------------------------------------------------------------------
 Limit (actual time=0.004..0.006 rows=10.00 loops=1)
   ->  Index Only Scan using events_pkey on events (actual time=0.004..0.005 rows=10.00 loops=1)
```

`OFFSET 150000` read 150,010 rows and took about 19 ms; the keyset form read 10 rows and took a few microseconds. Deep pages are rarely needed by real users but constantly needed by crawlers and export jobs. The trade-off: keyset needs a unique, indexed sort key (`ORDER BY id`, or `(created_at, id)`) and cannot jump straight to "page 300".

### Pattern matching and indexes

The advice that `ILIKE '%text%'` "cannot use a plain index" is true, and the fix is a trigram index. On the same 200,000 rows, four hits out of 200,000 for an `ILIKE` on `'%A3F9C%'` (the data is lowercase hex, which is why `ILIKE` matters): even with a plain B-tree on the column, PostgreSQL reads the whole table; with a `pg_trgm` GIN index it reads five heap blocks:

```sql
-- sql/ilike-trigram.sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX events_payload_btree ON events (payload);
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, SUMMARY ON)
SELECT id FROM events WHERE payload ILIKE '%A3F9C%';
CREATE INDEX events_payload_trgm ON events USING gin (payload gin_trgm_ops);
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, SUMMARY ON)
SELECT id FROM events WHERE payload ILIKE '%A3F9C%';
```

## Mental Model

A `SELECT` is a pipeline: FROM (which rows exist) then WHERE (which qualify) then the select list then ORDER BY then LIMIT/OFFSET. Each stage only sees what the previous stage gave it. That is why NULL comparisons silently drop rows (the WHERE stage only keeps *true*), why an unordered LIMIT is arbitrary (no order was ever defined), and why a deep OFFSET is expensive (the earlier stages had to produce those rows before OFFSET could discard them).

## Tips / gotchas

- `NULL` uses three-valued logic: a comparison against `NULL` is neither true nor false but unknown, so such rows are excluded by `WHERE`. Always use `IS NULL` (or `IS DISTINCT FROM`) rather than `= NULL`.
- `LIMIT` without an `ORDER BY` returns an arbitrary subset — the server may return rows in any order, and that order can change between runs. Always pair `LIMIT` with a deterministic `ORDER BY`, with a unique tiebreaker.
- `ILIKE '%x%'` cannot use a plain B-tree; a `pg_trgm` GIN index makes it fast (about 100 ms down to 0.2 ms above). `lower(col) = ...` needs an expression index.
- Prefer keyset paging over deep `OFFSET` for large tables.
- Selecting only the columns you need keeps result sets small and your code resilient to schema changes.

<Callout title="Order before you page">
Pagination only makes sense on a stable sort. If two rows tie on your sort column, add a tiebreaker such as `ORDER BY born DESC, id` so the same row never appears on two pages.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| Explicit column list | Stable API, less data over the wire, no leaking of sensitive columns | Query needs an edit when the needed columns change |
| `SELECT *` | Fast to write, convenient for prototyping or exploring data | Breaks silently when someone adds/removes/renames a column later, and can leak columns that should not be exposed |
| Filter with `WHERE` in SQL | Pushed down to the database, can use an index, only the needed rows cross the wire | Requires understanding SQL and planning indexes that match the filter pattern |
| Fetch everything and filter in application code | Easy application-side logic, no complex SQL to write | Wastes bandwidth, misses the chance to use an index, and gets slower as the table grows |
| `LIMIT`/`OFFSET` paging | Simple, allows jumping to any page | Cost grows with the offset (19 ms at 150,000 rows) |
| Keyset paging | Constant cost per page | Needs a unique indexed sort key, no random page jumps |

## Common Misconceptions

- **"`WHERE col <> 1` returns every row that is not 1."** Not the rows where `col` is NULL (proved above).
- **"`LIMIT 10` gives me the first 10 rows."** It gives 10 rows. Which ones is unspecified without `ORDER BY`.
- **"`BETWEEN` excludes the upper bound."** It includes both ends.
- **"`ILIKE` is just a slower `LIKE`."** It also cannot use the same indexes; a trigram index makes both fast.
- **"Sorting is the same everywhere."** It follows the collation: `apple, Apple, Banana` in `en_US.utf8`, `Apple, Banana, apple` in `"C"`.
