When a query is slow, guessing is a waste of time. PostgreSQL will tell you exactly how it intends to run a query, and how it actually ran. The tool is `EXPLAIN`, and learning to read its output is the single most useful performance skill you can pick up.

Everything below was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). Every plan is pasted from `psql`, never typed, and timings are from this Mac (single runs, so small differences are noise).

## The planner chooses a plan

You write *what* you want; the **query planner** decides *how* to get it. For a given query there can be many possible plans (scan the whole table, use this index, use that one, combine two), and the planner estimates the cost of each, then picks the cheapest.

export const plannerFlow = `flowchart LR
  Q["Your SQL query"] --> P["Query planner"]
  P --> E1["Estimate: Seq Scan cost"]
  P --> E2["Estimate: Index Scan cost"]
  P --> E3["Estimate: Bitmap Scan cost"]
  E1 --> C["Pick the cheapest plan"]
  E2 --> C
  E3 --> C
  C --> X["Execute chosen plan"]`;

<Mermaid code={plannerFlow} title="How the planner chooses a plan" />

Those cost estimates depend on statistics about your data: how many rows the table has, how many distinct values a column holds, how common each value is. If the statistics are stale or too crude, the planner makes bad guesses; both cases appear below.

## The dataset

Plans are only meaningful on realistic volumes, so this lesson builds an `orders` table with 500 000 rows: 10 000 customers, three statuses (skewed on purpose), one order every 90 seconds since 1 January 2024, and a `city` that always determines its `country`. There are indexes on `customer_id`, `created_at` and `status`.

## EXPLAIN: the estimated plan

Plain `EXPLAIN` plans the query but does not run it, so it is instant and safe on anything:

```sql
-- sql/explain-estimate.sql
EXPLAIN SELECT * FROM orders WHERE customer_id = 42;
```

```text
                                      QUERY PLAN                                      
--------------------------------------------------------------------------------------
 Bitmap Heap Scan on orders  (cost=4.81..189.92 rows=50 width=39)
   Recheck Cond: (customer_id = 42)
   ->  Bitmap Index Scan on orders_customer_id_idx  (cost=0.00..4.80 rows=50 width=0)
         Index Cond: (customer_id = 42)
(4 rows)
```

Read a node like this: `cost=4.81..189.92` is the estimated cost to return the first row, then all rows, in arbitrary units (one sequential page read is 1.0, from `seq_page_cost`); `rows=50` is how many rows the planner expects to come out; `width=39` is the average row size in bytes. The plan is a tree, read from the inside out: the most indented node (`Bitmap Index Scan`) runs first and feeds its parent (`Bitmap Heap Scan`).

## EXPLAIN ANALYZE: what really happened

Line by line:

- `actual time=0.054..0.267`: milliseconds until the first row and until the last row, per loop. `rows=50.00` is the *actual* rows per loop, shown with decimals since PostgreSQL 18 (an average when a node loops); the estimate was `rows=50`, so this plan is well estimated.
- `loops=1`: how many times this node ran. In a nested loop the inner node's numbers are *per loop*, so multiply.
- `Recheck Cond` and `Heap Blocks: exact=50`: the bitmap said which pages hold matches; the executor re-applies the condition on those 50 pages.
- `Buffers: shared hit=50 read=3`: 8 kB blocks found in `shared_buffers` (hit) versus fetched from the operating system or disk (read). It is the honest measure of I/O.
- `Index Searches: 1`: PG 18 shows how many times the index was descended.
- `Planning: Buffers` and `Planning Time`: the cost of building the plan itself, separate from `Execution Time`.

Sending the same statement from application code returns the plan as ordinary rows, one text line each. Each driver ran it once against the dataset and reported the number of plan lines, the start of the first line and the last line:

### Other options

`EXPLAIN (COSTS OFF)` removes the cost numbers when you only care about the shape. `VERBOSE` adds the output column list and schema-qualified names, and `SETTINGS` lists any planner setting that differs from the default, which makes a pasted plan reproducible. Here a lowered `random_page_cost` (a value commonly suggested for SSDs, see the [planner settings](https://www.postgresql.org/docs/18/runtime-config-query.html)) flips the same query from a bitmap scan to a plain index scan:

```sql
-- sql/explain-options.sql
BEGIN;
SET LOCAL random_page_cost = 1.1;
EXPLAIN (COSTS OFF, SETTINGS, VERBOSE) SELECT id, amount FROM orders WHERE customer_id = 42;
ROLLBACK;
```

## Telling the scan types apart

The same table produces different scan nodes as the query changes. Four kinds to recognize:

**Seq Scan** reads the whole table and filters. It wins when most rows qualify. **Index Scan** walks the index and fetches each matching row from the table. **Bitmap Heap Scan** first collects all matching row locations from the index, then fetches the pages in physical order: the middle ground for hundreds to thousands of rows. **Index Only Scan** answers from the index alone, when the query needs nothing but the indexed columns.

An hour of orders and a day of orders both use an Index Scan; so, surprisingly, do 175 680 rows (six months, 35 % of the table) in 15 ms:

```sql
-- sql/scan-types.sql
-- the same table, three time windows: 1 hour, 1 day, about half of the table
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF)
SELECT * FROM orders WHERE created_at >= '2024-06-01 00:00+00' AND created_at < '2024-06-01 01:00+00';
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF)
SELECT * FROM orders WHERE created_at >= '2024-06-01 00:00+00' AND created_at < '2024-06-02 00:00+00';
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF)
SELECT * FROM orders WHERE created_at >= '2024-06-01 00:00+00' AND created_at < '2024-12-01 00:00+00';
```

Why does a scan of a third of the table still pick the index? Because `created_at` is perfectly correlated with the physical row order (the table was filled in time order), so the index scan reads the heap pages one after another. The planner knows this from the statistics:

```sql
-- sql/correlation.sql
SELECT attname, round(correlation::numeric, 3) AS correlation
FROM pg_stats
WHERE tablename = 'orders' AND attname IN ('created_at', 'customer_id', 'status')
ORDER BY attname;
```

```text
   attname   | correlation 
-------------+-------------
 created_at  |       1.000
 customer_id |       0.000
 status      |       0.842
(3 rows)
```

`created_at` has correlation 1.000; `customer_id` is 0.000, random. For a random column a thousand matching rows are spread over a thousand pages, and the planner chooses a Bitmap Heap Scan (2.4 ms below), until `VACUUM` builds the visibility map and the same query becomes an **Index Only Scan** with `Heap Fetches: 0` (0.044 ms):

```sql
-- sql/index-only-scan.sql
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF)
SELECT customer_id FROM orders WHERE customer_id BETWEEN 1 AND 20;
VACUUM orders;
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF)
SELECT customer_id FROM orders WHERE customer_id BETWEEN 1 AND 20;
```

```text

   Recheck Cond: ((customer_id >= 1) AND (customer_id <= 20))
   Heap Blocks: exact=1000

         Index Searches: 1

(8 rows)

An Index Only Scan needs the visibility map: before `VACUUM` the planner did not choose it because every entry would have needed a trip to the heap to check the row is visible. `Heap Fetches` counts those trips.

## Why the planner sometimes ignores an index

A common surprise: you create an index, but `EXPLAIN` still shows a `Seq Scan`. This is usually the planner being *right*, not wrong. The same `status` column, with an index on it, gives both answers:

```sql
-- sql/selectivity.sql
-- 0.5 % of the rows versus 91 % of the rows
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF) SELECT * FROM orders WHERE status = 'refunded';
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF) SELECT * FROM orders WHERE status = 'paid';
```

```text
                                 QUERY PLAN                                 
----------------------------------------------------------------------------
 Index Scan using orders_status_idx on orders (actual rows=2500.00 loops=1)
   Index Cond: (status = 'refunded'::text)
   Index Searches: 1
 Planning Time: 0.257 ms
 Execution Time: 3.280 ms
(5 rows)

                     QUERY PLAN                     
----------------------------------------------------
 Seq Scan on orders (actual rows=456667.00 loops=1)
   Filter: (status = 'paid'::text)
   Rows Removed by Filter: 43333
 Planning Time: 0.059 ms
 Execution Time: 22.528 ms
(5 rows)
```

- **The query is not selective.** `refunded` is 0.5 % of the table: Index Scan, 3.3 ms. `paid` is 91 %: Seq Scan, 22.5 ms. To prove the planner right, forbid the seq scan and index scans for `paid`. The index plan reads more buffers and is slower (51.4 ms against 43.7 ms for the default choice, single runs):

```sql
-- sql/forced-index.sql
-- diagnosis only: forbid the seq scan and see what the planner was avoiding
BEGIN;
SET LOCAL enable_seqscan = off;
SET LOCAL enable_bitmapscan = off;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE status = 'paid';
ROLLBACK;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE status = 'paid';
```

- **The table is tiny.** On 100 rows the planner does not use the primary-key index for `id = 7`, because reading the single page is cheaper:

CREATE TABLE colors (id int PRIMARY KEY, name text);

- **The condition cannot use the index.** A function or cast around the column, a leading-wildcard `LIKE`, or a type mismatch. That case is the *Reading AI-generated code* section below.

## When the estimate is wrong: correlated columns

The planner multiplies the selectivities of separate conditions as if the columns were independent. In `orders`, `city = 7` always implies `country = 7`, but the planner does not know. It estimates 487 rows; the actual is 5 000, ten times more. `CREATE STATISTICS` with `dependencies` tells it, and the estimate becomes 4 617:

```sql
-- sql/correlated-columns.sql
-- city 7 always lies in country 7, but the planner multiplies the two selectivities
EXPLAIN (ANALYZE, COSTS ON, BUFFERS OFF, TIMING OFF)
SELECT * FROM orders WHERE city = 7 AND country = 7;
CREATE STATISTICS orders_city_country (dependencies) ON city, country FROM orders;
ANALYZE orders;
EXPLAIN (ANALYZE, COSTS ON, BUFFERS OFF, TIMING OFF)
SELECT * FROM orders WHERE city = 7 AND country = 7;
```

```text

---------------------------------------------------------------------------------------------------------

   Workers Planned: 2
   Workers Launched: 2
   ->  Parallel Seq Scan on orders  (cost=0.00..7798.00 rows=203 width=39) (actual rows=1666.67 loops=3)
         Filter: ((city = 7) AND (country = 7))
         Rows Removed by Filter: 165000
 Planning Time: 0.240 ms
 Execution Time: 10.584 ms
(8 rows)

CREATE STATISTICS
ANALYZE
                                                QUERY PLAN

   Workers Planned: 2
   Workers Launched: 2
   ->  Parallel Seq Scan on orders  (cost=0.00..7798.00 rows=1924 width=39) (actual rows=1666.67 loops=3)

In a bigger query the wrong estimate decides the join order or the join algorithm, and *that* is where a factor of ten can turn milliseconds into minutes ([docs on extended statistics](https://www.postgresql.org/docs/18/planner-stats.html)).

## EXPLAIN on writes

`EXPLAIN ANALYZE` really runs an `UPDATE` or `DELETE`. To read the plan without keeping the change, wrap it in a transaction and roll back. The sums below prove it: 16999.50 before, 17049.50 inside the transaction (50 rows changed by +1), 16999.50 after the rollback:

```sql
-- sql/explain-update.sql
SELECT sum(amount) AS total_before FROM orders WHERE customer_id = 42;
BEGIN;
EXPLAIN (ANALYZE, BUFFERS)
UPDATE orders SET amount = amount + 1 WHERE customer_id = 42;
SELECT sum(amount) AS total_inside_transaction FROM orders WHERE customer_id = 42;
ROLLBACK;
SELECT sum(amount) AS total_after_rollback FROM orders WHERE customer_id = 42;
```

## Reading AI-generated code

An assistant is asked for the number of orders placed on 1 March 2024 and writes something readable, with a comment claiming it uses the index on `created_at`:

<SpotTheBug lang="sql" code={`-- AI comment: "orders placed on March 1st - uses the index on created_at"
SELECT count(*) FROM orders WHERE created_at::date = '2024-03-01';`}>

The result is right and the index is ignored. `created_at::date` wraps the indexed column in an expression, and the plain index is on the column itself, so the planner cannot use it. It scans all 500 000 rows (`Rows Removed by Filter: 166347` in each of three workers), 15.9 ms:

```sql
-- sql/stb-wrong.sql
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF)
SELECT count(*) FROM orders WHERE created_at::date = '2024-03-01';
```

```text
                                 QUERY PLAN                                 
----------------------------------------------------------------------------
 Finalize Aggregate (actual rows=1.00 loops=1)
   ->  Gather (actual rows=3.00 loops=1)
         Workers Planned: 2
         Workers Launched: 2
         ->  Partial Aggregate (actual rows=1.00 loops=3)
               ->  Parallel Seq Scan on orders (actual rows=320.00 loops=3)
                     Filter: ((created_at)::date = '2024-03-01'::date)
                     Rows Removed by Filter: 166347
 Planning Time: 0.271 ms
 Execution Time: 15.871 ms
(10 rows)
```

The fix is to compare the bare column with a half-open range, which is what "on that date" means. The same count is now an `Index Only Scan`: 0.69 ms, 23 times faster (and the gap grows with the table):

```sql
-- sql/stb-fixed.sql
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF)
SELECT count(*) FROM orders
WHERE created_at >= '2024-03-01 00:00+00' AND created_at < '2024-03-02 00:00+00';
```

```text
                                                                           QUERY PLAN                                                                           
----------------------------------------------------------------------------------------------------------------------------------------------------------------
 Aggregate (actual rows=1.00 loops=1)
   ->  Index Only Scan using orders_created_at_idx on orders (actual rows=960.00 loops=1)

         Heap Fetches: 0
         Index Searches: 1
 Planning Time: 0.465 ms
 Execution Time: 0.688 ms
(7 rows)

If the query must use the cast, index the expression (`CREATE INDEX ON orders ((created_at::date))`), which the next lesson covers. Beware that `::date` on a `timestamptz` depends on the session `TimeZone`.

## Mental Model

`EXPLAIN` is the planner's plan; `EXPLAIN ANALYZE` adds what the executor saw. The distance between the two `rows=` numbers is the health of the statistics. Almost every slow query is one of three things: a scan that reads far more than it returns, a wrong estimate that picked the wrong strategy, or a condition that hides the column from an index. The plan tells you which, if you read it inside-out and compare estimate against actual.

## Tips / gotchas

- `EXPLAIN ANALYZE` actually executes the query. For a `SELECT` that is harmless, but for an `UPDATE` or `DELETE` it will change your data: wrap it in a transaction you `ROLLBACK`.
- Plans are only meaningful on realistic data. A query that seq-scans a 100-row test table may index-scan the same table with a million rows. Test against representative volumes.
- Always compare estimated `rows` against actual `rows`. A big mismatch points to stale statistics (`ANALYZE`) or correlated columns (`CREATE STATISTICS`).
- Read plan trees inside-out and multiply per-loop numbers by `loops`.
- `SET enable_seqscan = off` (and friends) proves what the planner avoided; do not ship it.
- Do not compare plan `cost=` numbers across different queries: they are only meaningful for choosing between plans of the same query.

<Callout title="Let EXPLAIN replace guessing">
Before you add an index or rewrite a query, run `EXPLAIN (ANALYZE, BUFFERS)` (on PostgreSQL 18, `EXPLAIN ANALYZE` already includes buffers) and read what PostgreSQL actually does. The plan tells you the scan type, where the time goes, and whether your estimates match reality, turning performance work from guesswork into measurement.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| `EXPLAIN` | Runs instantly, safe on any query since nothing executes | Only statistics-based estimates, no real numbers |
| `EXPLAIN ANALYZE` | Real timing, real row counts, buffer usage (default in PG 18) | Actually runs the query: an `UPDATE`/`DELETE` really changes data |
| `EXPLAIN (ANALYZE, BUFFERS OFF)` | Less output when you only care about timing | You lose the cache-vs-disk information |
| `enable_*` switches | Show the alternative plan the planner rejected | Session-wide; hides the real problem if left on |
| `CREATE STATISTICS` | Fixes estimates for correlated columns | Extra work at `ANALYZE` time; only helps queries that filter those columns together |

## Common Misconceptions

- **"An index is always used if it exists."** `paid` (91 % of the rows) ignored its index, correctly: forcing it was slower (51.4 ms against 43.7 ms).
- **"A seq scan means a missing index."** Sometimes it is the cheapest plan (tiny tables, unselective conditions).
- **"Index scans are always fast."** 175 680 rows by index scan took 15 ms; whether it is cheap depends on the correlation between index order and heap order.
- **"`WHERE col::date = ...` uses the index on `col`."** It does not; a range on the bare column does (15.9 ms against 0.69 ms).
- **"EXPLAIN ANALYZE on an UPDATE is a dry run."** It really updates; only the rollback restores the data.
