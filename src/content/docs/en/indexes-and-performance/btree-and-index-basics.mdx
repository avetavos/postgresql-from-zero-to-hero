An index is a separate data structure that lets PostgreSQL find rows without reading the whole table. PostgreSQL supports several index types, but one is the default and the right answer for the vast majority of cases: the **B-tree**. This lesson creates one, shows the plan change, and is honest about the cost.

Everything below was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). The `sql` fences run top to bottom in one empty database, the plans are pasted from `psql`, and every timing is from this Mac (single runs, so treat small differences as noise).

## The dataset

This lesson needs a table big enough for an index to matter, so it generates its own: 200 000 books, each with a unique `isbn`, a `title`, one of 20 authors, a publication year between 1950 and 2024, and a sales count.

```sql
-- sql/setup.sql
CREATE TABLE books (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  isbn        text NOT NULL,
  title       text NOT NULL,
  author_id   int  NOT NULL,
  published   int  NOT NULL,
  copies_sold int  NOT NULL DEFAULT 0
);
INSERT INTO books (isbn, title, author_id, published, copies_sold)
SELECT md5(g::text),
       'The ' || substr(md5((g * 3)::text), 1, 12),
       1 + g % 20,
       1950 + ('x' || substr(md5((g * 5)::text), 1, 6))::bit(24)::int % 75,
       (g * 7919) % 5000
FROM generate_series(1, 200000) AS g;
ANALYZE books;
SELECT count(*) AS books, count(DISTINCT author_id) AS authors, pg_size_pretty(pg_table_size('books')) AS table_size
FROM books;
```

What did it cost? Space:

```sql
WHERE relname IN ('books', 'books_pkey', 'books_isbn_key')
```

```text
----------------+---------

(3 rows)
```

The `isbn` index is 11 MB: over half the size of the 19 MB table. Its keys are 32-character strings, so it is not small. An index is a copy of the indexed columns plus pointers, kept in sorted order, and it must be maintained on every write (measured below).

## What a B-tree can do

A B-tree keeps keys in sorted order in a balanced tree, so it serves anything that follows that order: equality, ranges (`<`, `<=`, `>`, `>=`, `BETWEEN`), `IN`, `IS NULL`, and, importantly, `ORDER BY` and `LIMIT`, because the rows come out already sorted. Add an index on `title` and ask for the five first titles:

```sql
-- sql/title-index.sql
CREATE INDEX books_title_idx ON books (title);
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM books ORDER BY title LIMIT 5;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM books WHERE title BETWEEN 'The 3f9' AND 'The 3fa';
```

```text
CREATE INDEX
                                                                QUERY PLAN                                                                
------------------------------------------------------------------------------------------------------------------------------------------
 Limit  (cost=0.42..0.84 rows=5 width=70) (actual time=0.034..0.044 rows=5.00 loops=1)
   Buffers: shared hit=5 read=3
   ->  Index Scan using books_title_idx on books  (cost=0.42..16860.37 rows=200000 width=70) (actual time=0.033..0.040 rows=5.00 loops=1)
         Index Searches: 1
         Buffers: shared hit=5 read=3
 Planning:
   Buffers: shared hit=119 read=1
 Planning Time: 0.330 ms
 Execution Time: 0.063 ms
(9 rows)

                                                         QUERY PLAN                                                         
----------------------------------------------------------------------------------------------------------------------------
 Index Scan using books_title_idx on books  (cost=0.42..8.44 rows=1 width=70) (actual time=0.036..0.109 rows=50.00 loops=1)
   Index Cond: ((title >= 'The 3f9'::text) AND (title <= 'The 3fa'::text))
   Index Searches: 1
   Buffers: shared hit=51 read=2
 Planning:
   Buffers: shared hit=6
 Planning Time: 0.057 ms
 Execution Time: 0.115 ms
(8 rows)
```

The `ORDER BY title LIMIT 5` plan has no `Sort` node: it reads the first five entries of the index and stops (0.06 ms; without the index PostgreSQL would have to read and sort all 200 000 rows). The range query (`BETWEEN 'The 3f9' AND 'The 3fa'`) is an `Index Scan` too: it descends to the first match, walks the sorted entries, and returns 50 rows in 0.1 ms.

| Operation | Served by a B-tree? |
|---|---|
| `=`, `IN`, `IS NULL` | Yes |
| `<`, `<=`, `>`, `>=`, `BETWEEN` | Yes |
| `ORDER BY` / `LIMIT` on the indexed column | Yes, no separate sort |
| `LIKE 'The 3f%'` (prefix) | Only with the right operator class or the `C` collation, see the *Reading AI-generated code* section below |
| `LIKE '%3f'` (suffix / contains), `ILIKE` | No: use a trigram (`pg_trgm`) GIN index, see the next lesson |
| `lower(title) = ...` | Not with an index on plain `title`; needs an expression index |

## Composite indexes and the left-prefix rule

An index can cover several columns, ordered. `(author_id, published)` is sorted by `author_id` first, and by `published` within each author. That is ideal for a query on both. First the baseline for a query on `published` alone (2 762 of the 200 000 rows), then the index:

```sql
-- sql/composite-baseline.sql
SELECT count(DISTINCT author_id) AS distinct_authors, count(DISTINCT published) AS distinct_years FROM books;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM books WHERE published = 2000;
```

```text
 distinct_authors | distinct_years 
------------------+----------------
               20 |             75
(1 row)

                                                 QUERY PLAN                                                 
------------------------------------------------------------------------------------------------------------
 Seq Scan on books  (cost=0.00..4970.00 rows=2647 width=70) (actual time=0.018..8.079 rows=2762.00 loops=1)
   Filter: (published = 2000)
   Rows Removed by Filter: 197238
   Buffers: shared hit=2470
 Planning:
   Buffers: shared hit=43
 Planning Time: 0.282 ms
 Execution Time: 8.181 ms
(8 rows)
```

```sql
-- sql/composite-index.sql
CREATE INDEX books_author_published_idx ON books (author_id, published);
-- both columns: the ideal case
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM books WHERE author_id = 6 AND published = 2000;
-- only the second column: PostgreSQL 18 skip scan
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM books WHERE published = 2000;
```

```text

(12 rows)

                                                                  QUERY PLAN

   Heap Blocks: exact=1673
   Buffers: shared hit=1702 read=23
   ->  Bitmap Index Scan on books_author_published_idx  (cost=0.00..106.04 rows=2647 width=0) (actual time=0.382..0.382 rows=2762.00 loops=1)
```

The first plan is the textbook case: both columns are equalities on the index, so it descends once (`Index Searches: 1`) and fetches 143 rows in 0.3 ms.

The second query filters only on the **second** column. The old rule of thumb said such a query cannot use the index; that changed in PostgreSQL 18. It now uses a **skip scan**: with only 20 distinct values of `author_id`, the executor searches the index once per author for `published = 2000` (`Index Searches: 22` for 20 distinct authors) and combines the results. 2.5 ms against the 8 ms `Seq Scan` above ([docs](https://www.postgresql.org/docs/18/indexes-multicolumn.html), [release notes](https://www.postgresql.org/docs/18/release-18.html)).

Skip scan pays off only when the leading column has **few distinct values**. Make the leading column `isbn`, with 200 000 distinct values, and the planner is back to the sequential scan:

```sql
-- sql/composite-high-cardinality.sql
-- same idea, but the leading column now has 200 000 distinct values
DROP INDEX books_author_published_idx;
CREATE INDEX books_isbn_published_idx ON books (isbn, published);
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM books WHERE published = 2000;
DROP INDEX books_isbn_published_idx;
```

```text
DROP INDEX
CREATE INDEX

------------------------------------------------------------------------------------------------------------
 Seq Scan on books  (cost=0.00..4970.00 rows=2647 width=70) (actual time=0.013..8.087 rows=2762.00 loops=1)
   Filter: (published = 2000)
   Rows Removed by Filter: 197238
   Buffers: shared hit=2470
 Planning:
   Buffers: shared hit=118 read=1
 Planning Time: 0.363 ms

(8 rows)

DROP INDEX
```

So the practical rule for PostgreSQL 18: put the columns you always filter with `=` first, and treat "second column only" queries as fast only when the first column has a small number of distinct values (a status, a type, a region). Before 18 they were always slow.

## Unique indexes

A unique index also enforces a rule. Inserting a second row with the same `isbn` fails:

```sql
-- @expect-error 23505
INSERT INTO books (isbn, title, author_id, published) VALUES (md5('12345'), 'A Duplicate Isbn', 1, 2000);
```

```text
ERROR:  duplicate key value violates unique constraint "books_isbn_key"
DETAIL:  Key (isbn)=(827ccb0eea8a706c4c34a16891f84e7b) already exists.
```

Multiple `NULL`s are allowed in a unique column by default, because `NULL` is not equal to `NULL`; `UNIQUE NULLS NOT DISTINCT` (PostgreSQL 15+) changes that:

```sql
-- sql/unique-nulls.sql
CREATE TABLE codes (code text UNIQUE);
INSERT INTO codes VALUES (NULL), (NULL);
SELECT count(*) AS null_rows FROM codes WHERE code IS NULL;
CREATE TABLE codes_strict (code text UNIQUE NULLS NOT DISTINCT);
INSERT INTO codes_strict VALUES (NULL);
```

```text
CREATE TABLE
INSERT 0 2
 null_rows 
-----------
         2
(1 row)

CREATE TABLE
INSERT 0 1
```

```sql
-- @expect-error 23505
INSERT INTO codes_strict VALUES (NULL);
```

```text
ERROR:  duplicate key value violates unique constraint "codes_strict_code_key"
DETAIL:  Key (code)=(null) already exists.
```

A `UNIQUE` or `PRIMARY KEY` constraint creates a unique index for you: that is what `books_pkey` in the size listing is.

## Building an index on a live table

A plain `CREATE INDEX` takes a lock that blocks writes to the table (reads still work) until the build finishes. On a big table that can be minutes. Here it is with two sessions: session A builds an index, session B tries an `UPDATE` 0.1 s later, and waits for the build to end:

```text
-- session A: script
\timing on
CREATE INDEX books_expr_plain ON books (md5(title || isbn || title));
-- session A: psql output
Timing is on.
CREATE INDEX
Time: 247.257 ms

-- session B (starts 0.1 s later): script
\o /dev/null
SELECT pg_sleep(0.1);
\o
\timing on
UPDATE books SET copies_sold = copies_sold + 1 WHERE id = 1;
-- session B: psql output
Timing is on.
UPDATE 1
Time: 145.352 ms
```

`CREATE INDEX CONCURRENTLY` does the build without blocking writes, at the price of more work and two table scans. The same `UPDATE`, run during a concurrent build, finishes in 2 ms ([docs](https://www.postgresql.org/docs/18/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY)):

```text
-- session A: script
\timing on
CREATE INDEX CONCURRENTLY books_expr_conc ON books (md5(title || isbn || title));
-- session A: psql output
Timing is on.
CREATE INDEX
Time: 272.840 ms

-- session B (same script as above): psql output
Timing is on.
UPDATE 1
Time: 1.990 ms
```

The catch: if a concurrent build fails, it leaves an **invalid** index behind. Here we add a row that duplicates an existing title, then try to build a unique index over `title`:

```sql
-- @expect-error 23505
INSERT INTO books (isbn, title, author_id, published) VALUES ('dup-title-isbn', (SELECT title FROM books WHERE id = 1), 1, 2000);
CREATE UNIQUE INDEX CONCURRENTLY books_title_uniq ON books (title);
```

```text
INSERT 0 1
ERROR:  could not create unique index "books_title_uniq"
DETAIL:  Key (title)=(The eccbc87e4b5c) is duplicated.
```

```sql
-- sql/invalid-index.sql
SELECT indexrelid::regclass AS index, indisvalid, indisready
FROM pg_index
WHERE indrelid = 'books'::regclass
ORDER BY 1;
DROP INDEX books_title_uniq;
DELETE FROM books WHERE isbn = 'dup-title-isbn';
```

```text
      index       | indisvalid | indisready 
------------------+------------+------------
 books_pkey       | t          | t
 books_isbn_key   | t          | t
 books_title_idx  | t          | t
 books_title_uniq | f          | f
(4 rows)

DROP INDEX
DELETE 1
```

`books_title_uniq` is there (it still costs write overhead!) but `indisvalid` is `f`, so queries never use it. Drop it and retry; `pg_index.indisvalid = false` is the query to remember after any failed `CONCURRENTLY`.

## What an index costs on writes

Every `INSERT` must add an entry to every index. The same 200 000 rows, inserted into three tables of the same shape with 0, 1 and 5 single-column indexes:

```sql
-- sql/write-cost.sql
CREATE TABLE w0 (a int, b int, c int, d text, e text);
CREATE TABLE w1 (a int, b int, c int, d text, e text);
CREATE TABLE w5 (a int, b int, c int, d text, e text);
CREATE INDEX ON w1 (a);
CREATE INDEX ON w5 (a);
CREATE INDEX ON w5 (b);
CREATE INDEX ON w5 (c);
CREATE INDEX ON w5 (d);
CREATE INDEX ON w5 (e);
\timing on
INSERT INTO w0 SELECT g, g % 1000, g % 77, md5(g::text), md5((g + 1)::text) FROM generate_series(1, 200000) g;
INSERT INTO w1 SELECT g, g % 1000, g % 77, md5(g::text), md5((g + 1)::text) FROM generate_series(1, 200000) g;
INSERT INTO w5 SELECT g, g % 1000, g % 77, md5(g::text), md5((g + 1)::text) FROM generate_series(1, 200000) g;
\timing off
```

```text
CREATE TABLE
CREATE TABLE
CREATE TABLE
CREATE INDEX
CREATE INDEX
CREATE INDEX
CREATE INDEX
CREATE INDEX
CREATE INDEX
Timing is on.
INSERT 0 200000
Time: 383.832 ms

```

384 ms with no index, 508 ms with one, **1 994 ms with five**: about 5.2 times slower for the same rows. Reads got faster; writes paid for it. Indexes that no query uses are pure cost, and PostgreSQL tells you which ones they are:

```sql
-- sql/index-usage.sql
CREATE INDEX books_copies_idx ON books (copies_sold);  -- nothing will ever use this one
SELECT pg_stat_force_next_flush();
SELECT indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE relname = 'books'
ORDER BY idx_scan, indexrelname;
```

```text
CREATE INDEX
 pg_stat_force_next_flush 
--------------------------
 
(1 row)

   indexrelname   | idx_scan |  size   
------------------+----------+---------
 books_copies_idx |        0 | 1400 kB
 books_pkey       |        1 | 4408 kB
 books_isbn_key   |        2 | 11 MB
 books_title_idx  |        2 | 7960 kB
(4 rows)
```

`idx_scan` counts how many times each index was used since statistics were last reset. `books_copies_idx` (never queried) has 0 scans and 1.4 MB of dead weight on every write. Before dropping anything, check a full business cycle of traffic and that the index does not back a constraint (`books_pkey` and `books_isbn_key` do).

## Reading AI-generated code

An assistant is asked for a title search endpoint that matches a prefix. It creates an index on `title` and writes a comment saying the index serves the search:

<SpotTheBug lang="sql" code={`-- AI comment: "title search endpoint: prefix match, served by the index on title"
CREATE INDEX books_title_idx ON books (title);

SELECT id, title FROM books WHERE title LIKE 'The 3f9a%';`}>

The index exists and the query is correct, but the plan says otherwise. This database uses the `en_US.utf8` collation, and a plain B-tree on `text` is sorted by that collation's rules, which do not line up with the character-by-character range that `LIKE 'The 3f9a%'` needs. So the planner cannot use it:

```sql
-- sql/stb-wrong.sql
EXPLAIN (ANALYZE, COSTS OFF)
SELECT id, title FROM books WHERE title LIKE 'The 3f9a%';
```

```text
                           QUERY PLAN                            
-----------------------------------------------------------------
 Seq Scan on books (actual time=6.720..10.741 rows=2.00 loops=1)
   Filter: (title ~~ 'The 3f9a%'::text)
   Rows Removed by Filter: 199998
   Buffers: shared hit=2470
 Planning:
   Buffers: shared hit=105 read=5
 Planning Time: 0.394 ms
 Execution Time: 10.781 ms
(8 rows)
```

`Seq Scan`, 10.8 ms, 199 998 rows removed to return 2. The fix is an index with the `text_pattern_ops` operator class, which sorts strictly by character; now `LIKE 'prefix%'` becomes a range (`Index Cond: ((title ~>=~ 'The 3f9a') AND (title ~<~ 'The 3f9b'))`) ([docs](https://www.postgresql.org/docs/18/indexes-opclass.html)):

```sql
-- sql/stb-fixed.sql
CREATE INDEX books_title_pattern_idx ON books (title text_pattern_ops);
EXPLAIN (ANALYZE, COSTS OFF)
SELECT id, title FROM books WHERE title LIKE 'The 3f9a%';
```

```text
CREATE INDEX
                                           QUERY PLAN                                           
------------------------------------------------------------------------------------------------
 Index Scan using books_title_pattern_idx on books (actual time=0.045..0.052 rows=2.00 loops=1)
   Index Cond: ((title ~>=~ 'The 3f9a'::text) AND (title ~<~ 'The 3f9b'::text))
   Filter: (title ~~ 'The 3f9a%'::text)
   Index Searches: 1
   Buffers: shared hit=2 read=3
 Planning:
   Buffers: shared hit=133 read=4
 Planning Time: 0.647 ms
 Execution Time: 0.084 ms
(9 rows)
```

The alternative is to declare the column (or index) with `COLLATE "C"`. Neither helps `ILIKE` or `%contains%`; those need a trigram index.

## Mental Model

An index is a sorted, second copy of some columns, each entry pointing at a table row. Anything that can be answered by "find this position in the sorted order, then walk along it" is fast: equality, ranges, prefixes (when the ordering matches), `ORDER BY`, `MIN`/`MAX`. Everything else falls back to reading the table. Every write must update every index, so an index is a trade: cheaper reads for slower writes and more disk.

## Tips / gotchas

- Index the columns you filter, join, and sort on, in that order of importance; primary keys and unique constraints are indexed already.
- Foreign-key columns are **not** indexed automatically: index them if you join on them or delete from the parent table ([docs](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-FK)).
- For a composite index, put the columns you always compare with `=` first. Since PostgreSQL 18, a query that skips the leading column can still use the index through a skip scan, but only when that column has few distinct values.
- Check `EXPLAIN` before and after; the planner ignores an index when a scan is cheaper (small tables, or a query that returns a large fraction of the rows).
- Build on live tables with `CREATE INDEX CONCURRENTLY`, and check `indisvalid` afterwards.
- Watch `pg_stat_user_indexes.idx_scan` for indexes that are never used; each one slows every write.

<Callout title="Indexes are not free">
An index speeds up reads on that column and slows down every write to it, and it takes disk space (here the `isbn` index is over half the size of its table; five indexes made bulk inserts about 5.2 times slower). Add indexes for queries you actually run, and remove the ones nothing uses.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| Add a B-tree index | 9.1 ms to 0.06 ms for the lookup; no sort for `ORDER BY ... LIMIT` | 11 MB for the `isbn` index; slower writes (5 indexes: 384 ms to 1 994 ms for 200 000 inserts) |
| Composite `(a, b)` instead of two indexes | One index serves `a`, `a AND b`, and (PG 18, few distinct `a`) `b` | Bigger index; useless for `b` alone when `a` has many distinct values |
| `text_pattern_ops` | Makes `LIKE 'prefix%'` indexable | A second index if you also need normal ordering/range on the same column |
| `CREATE INDEX CONCURRENTLY` | Does not block writes | Slower, two table scans, can leave an invalid index on failure |

## Common Misconceptions

- **"A B-tree always serves `LIKE 'prefix%'`."** Not under `en_US.utf8`: plain index gave a `Seq Scan`, `text_pattern_ops` gave an `Index Scan`.
- **"A composite index cannot help a query on the second column."** True before PostgreSQL 18. With few distinct leading values, skip scan makes it work (`Index Searches: 22`), and with many it does not.
- **"More indexes are always better."** Five indexes made the same insert 5.2 times slower.
- **"A failed CREATE INDEX CONCURRENTLY leaves nothing behind."** It leaves an invalid index that still costs writes.
- **"Primary keys need an extra index."** `PRIMARY KEY` and `UNIQUE` create one.
