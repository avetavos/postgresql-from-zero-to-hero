B-tree handles equality, ranges, sorting, and (with the right operator class) prefix matches, which covers most queries. But some data and some query shapes call for a different structure. PostgreSQL ships with several other index access methods, and a few index *variants* that apply to any access method. This lesson is a tour of them, and for each one it shows the size and the plan on real rows, so you can see when it earns its place.

Everything below was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). The `sql` fences run top to bottom in one empty database, every size and plan is pasted from `psql`, and timings are single runs from this Mac.

## The dataset

One table of 300 000 books with a JSON `metadata` document, an ISBN, a time-ordered `created_at`, and an `in_print` flag (5 % of the books are out of print). `autovacuum_enabled = off` is set on this table only so the visibility-map demonstration at the end behaves the same every time. The `btree_gist` extension is needed by the exclusion constraint later.

```sql
-- sql/setup.sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE books (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  isbn       text        NOT NULL,
  title      text        NOT NULL,
  author_id  int         NOT NULL,
  created_at timestamptz NOT NULL,
  in_print   boolean     NOT NULL,
  metadata   jsonb       NOT NULL
) WITH (autovacuum_enabled = off);  -- keeps the visibility-map demo repeatable
INSERT INTO books (isbn, title, author_id, created_at, in_print, metadata)
SELECT md5(g::text),
       (ARRAY['Amber', 'Birch', 'Cedar', 'Dune', 'Ember', 'Fjord', 'Glen', 'Harbor'])[1 + h % 8] || ' Notes ' || g,
       1 + g % 500,
       timestamptz '2020-01-01 00:00:00+00' + g * interval '5 minutes',
       g % 20 <> 0,
       jsonb_build_object(
         'genre',  (ARRAY['fiction', 'poetry', 'history', 'science', 'travel', 'cooking', 'art', 'sport'])[1 + (h / 8) % 8],
         'rating', 1 + (h / 64) % 5,
         'pages',  100 + (h / 320) % 700,
         'tags',   jsonb_build_array('t' || (h / 224000) % 50, 't' || h % 97))
FROM (SELECT g, ('x' || substr(md5(g::text || 'h'), 1, 7))::bit(28)::int AS h
      FROM generate_series(1, 300000) AS g) AS s;
ANALYZE books;
SELECT count(*) AS books,
       pg_size_pretty(pg_table_size('books')) AS table_size,
       count(*) FILTER (WHERE metadata @> '{"genre": "poetry", "rating": 5}') AS poetry_5
FROM books;
```

## GIN: for values that contain many items

A **Generalized Inverted Index** (GIN) is built for columns where each row holds *multiple* searchable items: the elements of an array, the keys and values of a `jsonb` document, or the words ("lexemes") of a full-text document. GIN maps each item to the rows that contain it, so "find every row containing X" is a lookup rather than a scan. Without an index, a containment query reads every row:

```sql
-- sql/gin-baseline.sql
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF)
SELECT count(*) FROM books
WHERE metadata @> '{"genre": "poetry", "rating": 5, "tags": ["t3"]}';
```

## GiST: for geometric, range, and nearest-neighbour data

A **Generalized Search Tree** (GiST) indexes values that overlap or have a "distance": geometric shapes, ranges, and nearest-neighbour searches. For a table of room bookings (200 000 rows, each a `tstzrange`), "which bookings overlap this day?" is a `&&` (overlaps) query. A B-tree cannot answer it; without an index it is a scan:

```sql
-- sql/gist-setup.sql
CREATE TABLE rooms (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room_id       int NOT NULL,
  booked_during tstzrange NOT NULL
);
INSERT INTO rooms (room_id, booked_during)
SELECT g % 1000,
       tstzrange(timestamptz '2024-01-01 00:00+00' + (g / 1000) * interval '1 day',
                 timestamptz '2024-01-01 00:00+00' + (g / 1000) * interval '1 day' + interval '20 hours')
FROM generate_series(0, 199999) AS g;
ANALYZE rooms;
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF)
SELECT count(*) FROM rooms WHERE booked_during && tstzrange('2024-03-01 00:00+00', '2024-03-02 00:00+00');
```

GiST also powers **exclusion constraints**, which generalize `UNIQUE` from "no equal" to "no overlapping". With `btree_gist` you can combine equality on the room with overlap on the time range, and the database itself refuses a double booking:

```sql
-- sql/exclusion-constraint.sql
CREATE TABLE room_bookings (
  room_id       int NOT NULL,
  booked_during tstzrange NOT NULL,
  EXCLUDE USING gist (room_id WITH =, booked_during WITH &&)
);
INSERT INTO room_bookings VALUES (5, tstzrange('2024-03-01 09:00+00', '2024-03-01 11:00+00'));
INSERT INTO room_bookings VALUES (6, tstzrange('2024-03-01 10:00+00', '2024-03-01 12:00+00'));
```

## BRIN: for huge, naturally ordered tables

A **Block Range Index** (BRIN) stores just the minimum and maximum of a column for each block range of the table (128 pages by default). It works only when the column's values correlate with the physical order of the rows, which is the case for an append-only table with a timestamp. Here `created_at` grows with the row id:

```sql
-- sql/brin-baseline.sql
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF)
SELECT count(*) FROM books WHERE created_at >= '2021-06-01 00:00+00' AND created_at < '2021-06-08 00:00+00';
```

               ->  Parallel Seq Scan on books (actual time=4.016..9.782 rows=672.00 loops=3)

It answered a week of data in 0.9 ms against 13.9 ms for the sequential scan.

## Hash: for equality only

A **Hash index** stores a hash of the key. It supports only `=`; it cannot serve ranges or `ORDER BY`. Its selling point is size for long keys. For the 32-character ISBNs:

```sql
-- sql/hash-index.sql
CREATE INDEX books_isbn_hash  ON books USING hash (isbn);
CREATE INDEX books_isbn_btree ON books (isbn);
SELECT relname, pg_size_pretty(pg_relation_size(oid)) AS size
FROM pg_class WHERE relname IN ('books_isbn_hash', 'books_isbn_btree') ORDER BY 2 DESC;
DROP INDEX books_isbn_btree;
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE isbn = md5('777');
-- a range / ORDER BY cannot use a hash index
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE isbn > md5('777') ORDER BY isbn LIMIT 5;
```

The hash index is 8.2 MB against 17 MB for the B-tree, and the equality lookup takes 0.025 ms. ## Partial indexes: index only the rows you query

A **partial index** has a `WHERE` clause and contains only the rows that satisfy it. If you only ever look up out-of-print books (5 % of the table), a partial index is a fraction of the size of a full one, and cheaper to maintain:

```sql
-- sql/partial-index.sql
CREATE INDEX books_author_full ON books (author_id);
CREATE INDEX books_out_of_print_idx ON books (author_id) WHERE NOT in_print;
SELECT relname, pg_size_pretty(pg_relation_size(oid)) AS size
FROM pg_class WHERE relname IN ('books_author_full', 'books_out_of_print_idx') ORDER BY pg_relation_size(oid) DESC;
DROP INDEX books_author_full;  -- now only the partial index exists
-- the WHERE of the query implies the index predicate: usable
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE NOT in_print AND author_id = 21;
-- it does not: not usable
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE in_print AND author_id = 21;
```

## Expression indexes: index a computed value

An **expression index** stores the result of a function or expression. It fixes the case where the query wraps the column in a function and a plain index is useless:

```sql
-- sql/expression-index.sql
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE lower(title) = 'harbor notes 1234';
CREATE INDEX books_lower_title_idx ON books (lower(title));
ANALYZE books;
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE lower(title) = 'harbor notes 1234';
-- a different expression is a different question
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE title ILIKE 'harbor notes 1234';
```

## Covering indexes: answer the query from the index alone

An **Index Only Scan** answers a query from the index without touching the table, if every needed column is in the index. `INCLUDE` adds non-key columns to the index leaves for exactly this purpose: they are stored but not used for ordering.

There is a catch shown by `Heap Fetches`. An index entry does not say whether the row is visible to your transaction; the visibility map does, and only `VACUUM` builds it. Before `VACUUM` the planner does not even try an index-only scan (a bitmap heap scan, 1.35 ms); forced, it has to visit the heap for all 600 rows (`Heap Fetches: 600`); after `VACUUM` the visits disappear:

```sql
-- sql/covering-index.sql
CREATE INDEX books_author_incl ON books (author_id) INCLUDE (title);
-- before VACUUM the visibility map is empty: the planner avoids index-only scans
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT author_id, title FROM books WHERE author_id = 7;
-- force one to count the heap visits it would need (teaching switch)
BEGIN;
SET LOCAL enable_bitmapscan = off;
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT author_id, title FROM books WHERE author_id = 7;
ROLLBACK;
VACUUM books;
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT author_id, title FROM books WHERE author_id = 7;
```

## Mental Model

Every index type is a data structure that answers one family of questions cheaply. B-tree: "what comes before, after or equal to this?". GIN: "which rows contain this item?". GiST: "which values overlap or are near this?". BRIN: "which chunks of the table could hold this value?", tiny because it stores only min and max per chunk, and useful only when the table is physically ordered by the column. Hash: "is this exact key present?". The variants (partial, expression, covering) change *which rows* or *what value* is indexed, not the question the structure can answer. An index is used only when the query asks a question the index is built to answer.

## Tips / gotchas

- Match the access method to the query shape: GIN for "contains an item", GiST for "overlaps or is near", BRIN for "huge and physically ordered", Hash for "equality only", and B-tree for everything else.
- BRIN is safe to try on append-only time columns; check `pg_stats.correlation` first (near 1.0 or -1.0). After heavy updates or deletes reuse the free space, the correlation can degrade.
- For `jsonb`, prefer `jsonb_path_ops` when you only use `@>` (smaller, faster); keep the default class if you need `?`.
- A partial index is used only when the query's `WHERE` implies the predicate; an expression index only when the query repeats the expression.
- Index-only scans need `VACUUM` to build the visibility map; check `Heap Fetches`.
- Every extra index slows writes and costs disk space; measure before adding.

<Callout title="Pick the structure for the question">
Ask what the query does, not what the column is. A `jsonb` column queried by `->>` equality wants a B-tree expression index; the same column queried by `@>` wants GIN. A timestamp on an append-only table wants BRIN if size matters most, B-tree if you also need exact lookups.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| GIN (`jsonb_ops`) | `@>`, `?` on jsonb, arrays, full text; 25.8 ms to 5.2 ms here | 5 MB index, slower writes; useless for `->>` expressions |
| GIN (`jsonb_path_ops`) | Smaller (3.7 MB) and faster `@>` | No key-existence (`?`) queries |
| GiST | Overlap, nearest-neighbour, exclusion constraints; 13.1 ms to 0.53 ms here | 9.8 MB index; needs matching range types |
| BRIN | 24 kB instead of 6.6 MB | Only on physically ordered columns; lossy, rechecks rows |
| Hash | Half the size of a B-tree on long keys | Equality only, no ordering |
| Partial | 120 kB instead of 2 MB | Only serves queries that imply the predicate |
| Expression | Makes `lower(title) = ...` 600 times faster | Query must repeat the exact expression |
| Covering (`INCLUDE`) | Index Only Scan, 0.085 ms | Larger index; needs `VACUUM` to work |

## Common Misconceptions

- **"A GIN index on a jsonb column speeds up any filter on it."** Only operators on the column itself; `metadata->>'genre' = ...` ignored it (15.6 ms).
- **"BRIN is just a smaller B-tree."** It is a different question: with random order it prunes nothing (23.5 ms, slower than the scan).
- **"Hash indexes are unsafe."** Not since PostgreSQL 10; they are just equality-only.
- **"An index-only scan never touches the table."** It does until `VACUUM` marks pages all-visible (`Heap Fetches: 600` then 0).
- **"One index on `lower(title)` also serves `ILIKE`."** It serves only the same expression.
