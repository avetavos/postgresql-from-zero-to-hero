Now that PostgreSQL is running, you need a way to talk to it. There are three common doors in: the `psql` command-line shell, a graphical tool like pgAdmin, and your own application code through a driver. This lesson covers all three so you can pick whichever fits the moment.

> Everything below was run against **PostgreSQL 18.6** (`postgres:18.6`, psql 18.6 inside the container, aarch64, Docker Desktop on a Mac, September 2026). The GUI section (pgAdmin, DBeaver) is described from the tools' documentation and was **not** run here.

## psql basics

`psql` is the official terminal client. Once connected, you can type SQL directly, but its real superpower is **meta-commands** — short instructions that start with a backslash and inspect the database for you. Here are the ones you will use constantly.

| Command | What it does |
|---------|--------------|
| `\l` | List all databases in the server |
| `\c dbname` | Connect to a different database |
| `\dt` | List tables in the current database |
| `\d tablename` | Describe a table's columns, types, and constraints (`\d+` adds storage, stats target, and more) |
| `\x` | Toggle expanded (one column per line) output |
| `\timing` | Print how long each statement took |
| `\watch` | Re-run the last query every few seconds |
| `\copy` | Load or export a file from the client machine |
| `\conninfo` | Show what you are connected to |
| `\q` | Quit psql |

First look around a fresh server. This is the real `\l` from PostgreSQL 18.6 in the Docker image: since a new cluster has `postgres`, `template0` and `template1`, plus the `appdb` database created by `POSTGRES_DB` in the previous lesson. Running SQL is just typing the statement and ending it with a semicolon. The meta-commands save you from memorizing the system queries behind `\l`, `\dt`, and friends — they run those queries for you and format the result. (`\dt` on an empty database says `Did not find any tables.`; `\d name` on a missing object says `Did not find any relations.`)

`\copy` runs `COPY` through the client, so the file lives on the machine where psql runs, not on the server. That is why it works on a managed database where you have no server filesystem. Here it exports `books` to CSV and loads it into a copy of the table:

```sql
-- sql/psql-copy.sql
\copy books TO '/tmp/books.csv' WITH (FORMAT csv, HEADER)
CREATE TABLE books_copy (LIKE books INCLUDING ALL);
\copy books_copy (id, title, author_id, published, copies_sold) FROM '/tmp/books.csv' WITH (FORMAT csv, HEADER)
SELECT count(*) FROM books_copy;
```

```text
COPY 4
CREATE TABLE
COPY 4
 count 
-------
     4
(1 row)
```

```sql
\set min_year 2010
SELECT title FROM books WHERE published >= :min_year ORDER BY published;
```

```text
(3 rows)
```

## Scripts: `-c`, `-f`, `-1`, and `ON_ERROR_STOP`

Interactive use is half of psql. `-c` runs one command, `-f` runs a file, and the flags that decide what happens when something fails are the ones that matter in scripts. Given this small migration where the third line fails on purpose:

```sql
CREATE TABLE notes (id int PRIMARY KEY, body text);
INSERT INTO notes VALUES (1, 'first');
INSERT INTO notes VALUES (1, 'duplicate id');
INSERT INTO notes VALUES (2, 'second');
```

the three modes behave differently, real transcript:

```text
$ psql -U postgres -d appdb -f migrate.sql        # default: keeps going after an error
CREATE TABLE
INSERT 0 1
psql:migrate.sql:3: ERROR:  duplicate key value violates unique constraint "notes_pkey"
DETAIL:  Key (id)=(1) already exists.
INSERT 0 1
2 rows in notes

$ psql -U postgres -d appdb -v ON_ERROR_STOP=1 -f migrate.sql        # stop at the first error
CREATE TABLE
INSERT 0 1
psql:migrate.sql:3: ERROR:  duplicate key value violates unique constraint "notes_pkey"
DETAIL:  Key (id)=(1) already exists.
exit status 3
1 rows in notes

$ psql -U postgres -d appdb -1 -v ON_ERROR_STOP=1 -f migrate.sql        # -1: one transaction, all or nothing
CREATE TABLE
INSERT 0 1
psql:migrate.sql:3: ERROR:  duplicate key value violates unique constraint "notes_pkey"
DETAIL:  Key (id)=(1) already exists.
exit status 3
t
```

The rule to remember: by default psql keeps going and its exit status is `0` even after errors; `-v ON_ERROR_STOP=1` stops at the first error with exit status `3`; adding `-1` (`--single-transaction`) wraps the file in `BEGIN`/`COMMIT`, so a failure leaves nothing behind ([psql reference](https://www.postgresql.org/docs/18/app-psql.html)).

## A tour of pgAdmin

If you prefer clicking to typing, **pgAdmin** is the official graphical tool, and the Docker setup from the previous lesson can run it at `http://localhost:8080`. (Not run here; this section follows the [pgAdmin documentation](https://www.pgadmin.org/docs/).) Here is how to find your way around.

When you first open pgAdmin, log in with the email and password you set in the compose file. The left side shows a **browser tree** with a Servers group at the top. To connect to your database, right-click Servers and choose to register a new server. In the dialog, give the connection a name on the General tab, then switch to the Connection tab and fill in the host, port, username, and password. Because pgAdmin runs in its own container, the host is the service name `postgres` rather than `localhost`; the port stays `5432` and the user is `postgres`.

Once connected, the tree expands. Open your server, then **Databases**, then a database, then **Schemas**, then the `public` schema, and finally **Tables**. This nesting mirrors how PostgreSQL actually organizes data, which the next lesson explains in detail. Clicking any object shows its details in the main panel.

The workhorse is the **Query Tool**, opened from the toolbar or by right-clicking a database. It gives you a SQL editor where you type a statement and press the run button; results appear in a grid below, and messages such as row counts show on a separate tab. To browse a table's contents without writing SQL, right-click the table and choose to view its rows, which opens the same grid pre-filled with a `SELECT`.

If pgAdmin feels heavy, **DBeaver** is a popular free alternative — a desktop application that connects to PostgreSQL and many other databases with a similar tree-and-editor layout. The concepts carry over directly; only the menus differ.

## Connecting from each driver

In application code you connect through a **driver** — a library that speaks PostgreSQL's protocol. The connection details are the same ones you used above; only the syntax changes. Each program below reads the URL from the `DATABASE_URL` environment variable (never commit it) and was run once against a throw-away PostgreSQL 18.6 container.

<Tabs syncKey="lang">
  <TabItem label="psql">
    ```sql
    -- sql/connect.sql
    -- psql takes the connection string on the command line:
    --   psql "postgresql://postgres:<password>@localhost:5432/appdb"
    SELECT current_database();
    ```
  </TabItem>
  <TabItem label="Node.js">
    ```js
    import { Pool } from 'pg';

    const pool = new Pool({ connectionString: process.env.DATABASE_URL });

    const res = await pool.query('SELECT current_database(), current_user');
    console.log(res.rows[0]);
    await pool.end();
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    import os
    import psycopg

    with psycopg.connect(os.environ["DATABASE_URL"]) as conn:
        cur = conn.cursor()
        cur.execute("SELECT current_database(), current_user")
        print(cur.fetchone())
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    package main

    import (
    	"context"
    	"fmt"
    	"os"

    	"github.com/jackc/pgx/v5"
    )

    func main() {
    	ctx := context.Background()
    	conn, err := pgx.Connect(ctx, os.Getenv("DATABASE_URL"))
    	if err != nil {
    		fmt.Println(err)
    		os.Exit(1)
    	}
    	defer conn.Close(ctx)

    	var db, user string
    	if err := conn.QueryRow(ctx, "SELECT current_database(), current_user").Scan(&db, &user); err != nil {
    		fmt.Println(err)
    		os.Exit(1)
    	}
    	fmt.Println(db, user)
    }
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    use sqlx::postgres::PgPoolOptions;

    #[tokio::main]
    async fn main() -> Result<(), sqlx::Error> {
        let pool = PgPoolOptions::new()
            .max_connections(5)
            .connect(&std::env::var("DATABASE_URL").unwrap())
            .await?;

        let row: (String, String) = sqlx::query_as("SELECT current_database()::text, current_user::text")
            .fetch_one(&pool)
            .await?;
        println!("{:?}", row);
        Ok(())
    }
    ```
  </TabItem>
</Tabs>

Real output of each (versions stamped on each line):

```text
$ DATABASE_URL=postgresql://postgres:<password>@localhost:5432/appdb node app.mjs        # pg 8.23.0, Node 24.13.0
{ current_database: 'appdb', current_user: 'postgres' }
```

Notice that every driver accepts the same `postgresql://user:password@host:port/database` connection string. Learn that one format and you can connect from anywhere.

**In pgAdmin:** the same connection details live in the register-server dialog instead of a string — host, port, user, password, and database each have their own field.

## Reading AI-generated code

An assistant asked for a deploy script that applies a migration and reports success writes this. It reads correctly and it is dangerous:

<SpotTheBug lang="bash" code={`#!/usr/bin/env bash
# AI comment: "apply the migration, then report success"
psql -U postgres -d appdb -f migrate.sql
echo "migrations applied"`}>

With `migrate.sql` from above (the third statement fails), running the script prints the error, then `migrations applied`, and exits with status **0**:

```text
CREATE TABLE
INSERT 0 1
psql:migrate.sql:3: ERROR:  duplicate key value violates unique constraint "notes_pkey"
DETAIL:  Key (id)=(1) already exists.
INSERT 0 1
migrations applied
deploy.sh exit status 0
```

By default psql does not stop on an error and does not fail the script: the duplicate row was skipped but everything after it still ran, a CI job sees a green build, and the database is half-migrated. The fix is `-v ON_ERROR_STOP=1` so the first error stops the run, `-1` so nothing is left behind, `set -e` so the shell script stops, and `-X` so a stray `~/.psqlrc` cannot change behaviour. The same run now fails with status 3 and the transaction is rolled back (the `notes` table does not exist afterwards):

```bash
# scripts/deploy.sh
set -euo pipefail
psql -X -U postgres -d appdb -v ON_ERROR_STOP=1 -1 -f migrate.sql
echo "migrations applied"
```

```text
CREATE TABLE
INSERT 0 1
psql:migrate.sql:3: ERROR:  duplicate key value violates unique constraint "notes_pkey"
DETAIL:  Key (id)=(1) already exists.
deploy2.sh exit status 3
```

</SpotTheBug>

## Mental Model

psql is a thin client that sends text to the server and prints what comes back; meta-commands (backslash) are client-side and never reach the server, while everything else (SQL) is. That explains why `\copy` reads your local file, why `\watch` is psql's loop and not a database feature, and why scripts need `ON_ERROR_STOP`: the client, not the server, decides whether to continue.

## Tips / gotchas

- A connection string follows the shape `postgresql://user:password@host:port/database`. Each part is optional once a default applies.
- From inside another container (like pgAdmin), the host is the service name, not `localhost`; from your own machine it is `localhost`.
- Use `psql` for quick checks and scripting, a GUI like pgAdmin or DBeaver for browsing and exploration, and a driver for anything your application does repeatedly.
- Never hard-code passwords in committed code. Read connection strings from environment variables (as the driver programs above do) or a `~/.pgpass` file; the placeholder `<password>` above is not a real value.
- The `\d` family of meta-commands is the fastest way to remember a table's exact shape without leaving the shell.
- In scripts, always `-X -v ON_ERROR_STOP=1`; add `-1` for migrations.

<Callout title="Three doors, one database">
psql, pgAdmin, and your application driver all connect to the very same PostgreSQL server with the very same credentials. Choose the door that suits the task — the shell for speed, the GUI for exploring, the driver for your app — and know that the database underneath does not care which one you walked through.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| `psql` CLI | Fast, scriptable, low overhead | Must remember meta-commands and syntax |
| pgAdmin GUI | Clear view of data structure, friendly for beginners | Heavier, and needs a desktop machine with a browser open |
| A driver in application code | The real thing production runs every day | Writing extra code just to run one query is not worth it |

## Common Misconceptions

- **"A GUI is enough."** The moment you SSH into a production box with no GUI available, you are stuck without `\dt`, `\d`, and friends.
- **"If the script printed `migrations applied`, it worked."** Not without `ON_ERROR_STOP`: psql exits `0` after errors by default (proved above).
- **"pgAdmin and DBeaver connect through `localhost`."** From the host machine yes, but from another container you need the service name, such as `postgres`, as set in compose.
- **"`\copy` and `COPY` are the same."** `COPY` reads and writes files on the *server*; `\copy` uses files on the *client*.
- **"Copying SQL between tools is harmless."** psql and some GUIs handle autocommit differently; a copied `BEGIN` without `COMMIT` can leave a transaction hanging.
