`LIKE '%word%'` compares characters. It cannot rank results, it finds letters hiding inside other words, it does not know that `runs` and `running` are forms of the same word, and without a special index it reads every row. PostgreSQL has a built-in answer: **full-text search**. A document is reduced to a set of normalized words (a `tsvector`), a search is a set of words joined by logic (a `tsquery`), and the `@@` operator asks whether the query matches the document.

Everything below was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). The `sql` fences run top to bottom in one empty database, the outputs are pasted from `psql`, and the timings are single runs from this Mac.

## The dataset

```sql
INSERT INTO articles (title, body) VALUES
```

## Two new types

A `tsvector` is a sorted list of **lexemes** (normalized words) with their positions. Producing one drops stop words such as "the" and "were", lowercases, and **stems**: it reduces each word to a root using the rules of a text search configuration. `SHOW default_text_search_config` tells you which one is the default here:

```sql
-- sql/tsvector.sql
SHOW default_text_search_config;
SELECT to_tsvector('english', 'The quick brown foxes were running quickly');
SELECT to_tsvector('english', title) FROM articles WHERE id IN (1, 5) ORDER BY id;
```

```text
 default_text_search_config 
----------------------------
 pg_catalog.english
(1 row)

              to_tsvector              
---------------------------------------
 'brown':3 'fox':4 'quick':2,7 'run':6
(1 row)

        to_tsvector         
----------------------------
 'run':2 'shoe':3 'trail':1
 'run':4 'stretch':1
(2 rows)
```

Note the default is `pg_catalog.english` on this server. `initdb` derives it from the locale of the cluster (under the `C` locale it would be `simple`, which does no stemming and drops no stop words), so always pass the configuration explicitly, as every query in this lesson does ([docs](https://www.postgresql.org/docs/18/textsearch-configuration.html)). In the first line, "quick" and "quickly" both became `quick` (positions 2 and 7), "foxes" became `fox`, "running" became `run`.

Stemming joins forms that follow rules, and only those. `running` matches `run`, but the irregular past tense `ran` is a different lexeme, and `mice` does not become `mouse`. The dictionaries are rule-based; they are not a thesaurus:

```sql
-- sql/stemming.sql
-- stemming maps different forms to one lexeme; irregular forms are NOT joined
SELECT to_tsvector('english', 'I ran home')                               AS ran_home,
       to_tsvector('english', 'I ran home') @@ plainto_tsquery('english', 'running') AS running_matches_ran,
       to_tsvector('english', 'I run home') @@ plainto_tsquery('english', 'running') AS running_matches_run,
       to_tsvector('english', 'mice geese')                               AS irregular;
```

```text
     ran_home     | running_matches_ran | running_matches_run |     irregular     
------------------+---------------------+---------------------+-------------------
 'home':3 'ran':2 | f                   | t                   | 'gees':2 'mice':1
(1 row)
```

## Building a query

A `tsquery` is a set of lexemes with `&` (and), `|` (or), `!` (not) and `<->` (followed by). PostgreSQL has four constructors, from strictest to friendliest:

```sql
-- sql/tsquery-forms.sql
SELECT plainto_tsquery('english', 'trail running shoes')            AS plain,
       to_tsquery('english', 'trail & (shoes | boots) & !leather')  AS operators,
       phraseto_tsquery('english', 'trail running shoes')           AS phrase,
       websearch_to_tsquery('english', '"trail shoes" -leather')    AS websearch;
```

```text
          plain           |                 operators                  |            phrase            |            websearch            
--------------------------+--------------------------------------------+------------------------------+---------------------------------
 'trail' & 'run' & 'shoe' | 'trail' & ( 'shoe' | 'boot' ) & !'leather' | 'trail' <-> 'run' <-> 'shoe' | 'trail' <-> 'shoe' & !'leather'
(1 row)
```

`plainto_tsquery` ANDs every word. `to_tsquery` takes operator syntax and is strict about it (a bare space is a syntax error, below). `phraseto_tsquery` requires the words in order. `websearch_to_tsquery` reads what users actually type: quotes make a phrase, `or` is OR, `-` is NOT, and it never raises a syntax error on user input, which is why it is the one to put behind a search box.

```sql
-- @expect-error 42601
SELECT to_tsquery('english', 'trail shoes');
```

```text
ERROR:  syntax error in tsquery: "trail shoes"
```

## Matching with the @@ operator

`tsvector @@ tsquery` is true when the document matches. Because `runs` and `run` and `running` share the stem `run`, a search for "runs" finds all five articles that use any of those forms:

```sql
-- sql/match.sql
SELECT id, title
FROM articles
WHERE to_tsvector('english', title || ' ' || body) @@ plainto_tsquery('english', 'runs')
ORDER BY id;
```

```text
 id |         title          
----+------------------------
  1 | Trail running shoes
  2 | Marathon training plan
  5 | Stretching after a run
  6 | Choosing trail food
  8 | Shoe care
(5 rows)
```

Compare with `LIKE`, which matches characters, not words. It finds the literal `runs` (one article) and, worse, finds letters inside unrelated words:

```sql
-- sql/like-contrast.sql
-- LIKE compares characters: it finds the literal "runs" but not run / running
SELECT id, title FROM articles WHERE title || ' ' || body ILIKE '%runs%' ORDER BY id;
-- and it finds letters inside other words
SELECT 'a lovely brunch' ILIKE '%run%' AS like_says,
       to_tsvector('english', 'a lovely brunch') @@ plainto_tsquery('english', 'run') AS fts_says;
```

```text
 id |         title          
----+------------------------
  2 | Marathon training plan
(1 row)

 like_says | fts_says 
-----------+----------
 t         | f
(1 row)
```

## Ranking results

A match is not a good match. `ts_rank` scores by term frequency; `ts_rank_cd` also rewards words that appear close together (cover density). To make a title hit count more than a body hit, weight the parts with `setweight` (`A` is heaviest; the defaults are 1.0 for A, 0.4 for B, 0.2 for C and 0.1 for D). Search "trail or shoes":

```sql
-- sql/ranking.sql
SELECT id, title,
       round(ts_rank(setweight(to_tsvector('english', title), 'A') || setweight(to_tsvector('english', body), 'B'),
                     websearch_to_tsquery('english', 'trail or shoes'))::numeric, 4) AS rank,
       round(ts_rank_cd(setweight(to_tsvector('english', title), 'A') || setweight(to_tsvector('english', body), 'B'),
                        websearch_to_tsquery('english', 'trail or shoes'))::numeric, 4) AS rank_cd
FROM articles
WHERE (setweight(to_tsvector('english', title), 'A') || setweight(to_tsvector('english', body), 'B'))
      @@ websearch_to_tsquery('english', 'trail or shoes')
ORDER BY rank DESC, id;
```

```text
 id |         title          |  rank  | rank_cd 
----+------------------------+--------+---------
  1 | Trail running shoes    | 0.6822 |  3.2000
  8 | Shoe care              | 0.3479 |  1.8000
  6 | Choosing trail food    | 0.3040 |  1.0000
  7 | Rain gear for cyclists | 0.1216 |  0.4000
(4 rows)
```

"Trail running shoes" wins because both words are in its title (weight A). "Shoe care" beats "Choosing trail food" (0.3479 against 0.3040): *shoe* occurs three times in it (once in the title, twice in the body) while *trail* occurs once in the other. `ts_headline` builds a snippet with the matched words marked, for the results page:

```sql
-- sql/headline.sql
SELECT id, ts_headline('english', body, websearch_to_tsquery('english', 'trail or shoes'),
                       'StartSel=<b>, StopSel=</b>, MaxWords=12, MinWords=5') AS snippet
FROM articles
WHERE to_tsvector('english', body) @@ websearch_to_tsquery('english', 'trail or shoes')
ORDER BY id;
```

```text
 id |                 snippet                 
----+-----------------------------------------
  1 | <b>trail</b> <b>shoes</b> grip wet rock
  7 | <b>shoe</b> covers and a rain
  8 | <b>shoes</b> with a soft brush
(3 rows)
```

## Indexing the search

Recomputing `to_tsvector` for every row on every search is slow. Two designs avoid that. The clean one is a **generated column** holding the `tsvector`, plus a GIN index on it. The column is kept in sync by PostgreSQL itself, and the query is short:

```sql
-- sql/generated-column.sql
ALTER TABLE articles ADD COLUMN search tsvector
  GENERATED ALWAYS AS (setweight(to_tsvector('english', title), 'A') || setweight(to_tsvector('english', body), 'B')) STORED;
CREATE INDEX articles_search_idx ON articles USING gin (search);
SELECT id, title FROM articles WHERE search @@ websearch_to_tsquery('english', 'trail shoes -leather') ORDER BY id;
```

```text
ALTER TABLE
CREATE INDEX
 id |        title        
----+---------------------
  1 | Trail running shoes
(1 row)
```

The same query with parameters, from each driver (the same `websearch_to_tsquery` text goes in as a bind value, so it is safe to expose to user input):

```sql
-- sql/param-search.sql
SELECT title
FROM articles
WHERE search @@ websearch_to_tsquery('english', $1)
ORDER BY ts_rank(search, websearch_to_tsquery('english', $1)) DESC, id
\bind 'trail or shoes -leather' \g
```

### What the index buys

On 100 000 articles of 30 words each (drawn from a 3 000-word vocabulary) the same search, before and after the GIN index:

```sql

  id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title  text NOT NULL,
  body   text NOT NULL
);
-- 100 000 articles of 30 words each, drawn from a vocabulary of 3 000 words (w0 ... w2999)
INSERT INTO big_articles (title, body)
SELECT 'Article ' || g,
       (SELECT string_agg('w' || (('x' || substr(md5(g::text || ':' || i::text), 1, 6))::bit(24)::int % 3000), ' ')
        FROM generate_series(1, 30) AS i)

SELECT count(*) AS rows, pg_size_pretty(pg_relation_size('big_articles')) AS heap FROM big_articles;
```

## A contrast: trigrams and accents

Full-text search matches whole, correctly spelled words. A typo (`runing`) stems to a different lexeme and finds nothing. For fuzzy matching, the `pg_trgm` extension compares three-letter fragments; and `unaccent` strips accents so `café` matches `cafe` ([pg_trgm](https://www.postgresql.org/docs/18/pgtrgm.html), [unaccent](https://www.postgresql.org/docs/18/unaccent.html)):

```sql
-- sql/trigram.sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS unaccent;
SELECT similarity('runing', 'running') AS typo_score,
       'runing' % 'running'            AS typo_matches,
       to_tsvector('english', 'runing') @@ plainto_tsquery('english', 'running') AS fts_matches_typo,
       unaccent('caf' || chr(233) || ' cr' || chr(232) || 'me') AS unaccented;
```

```text
CREATE EXTENSION
CREATE EXTENSION
 typo_score | typo_matches | fts_matches_typo | unaccented 
------------+--------------+------------------+------------
  0.6666667 | t            | f                | cafe creme
(1 row)
```

The typo scores 0.67 similarity and matches with the `%` operator, while full-text search finds nothing. Use `pg_trgm` for "did you mean" and autocomplete, full-text search for relevance-ranked prose.

## Reading AI-generated code

An assistant is asked to make article search fast. It writes an expression index on `to_tsvector('english', body)` and a search query, with a comment saying the index handles it:

<SpotTheBug lang="sql" code={`-- AI comment: "GIN index on the article text - search is now fast"
CREATE INDEX big_articles_body_gin ON big_articles USING gin (to_tsvector('english', body));

SELECT id, title FROM big_articles
WHERE to_tsvector(body) @@ to_tsquery('w17 & w42');`}>

The index and the query use *different* expressions: the index is on `to_tsvector('english', body)`, the query calls the one-argument `to_tsvector(body)`, which uses `default_text_search_config`. To the planner these are different functions, so the index cannot be used, and the query computes a tsvector for every row: 573 ms for 100 000 short rows.

## Mental Model

Full-text search is a pipeline: parse the text into tokens, throw away stop words, stem the rest with a dictionary, and store lexemes with positions (`tsvector`); do the same to the user's query, joined by operators (`tsquery`). `@@` is set logic over lexemes, not string matching, so it is fast to index (GIN maps each lexeme to its documents) and blind to anything the dictionaries do not connect, such as irregular forms and typos. Ranking is a separate step over the matches.

## Tips / gotchas

- Always pass the configuration (`to_tsvector('english', ...)`); never depend on `default_text_search_config`.
- For search boxes use `websearch_to_tsquery`: it never raises syntax errors on user input.
- Index a stored generated `tsvector` column with GIN. A virtual generated column cannot be indexed.
- An expression index is used only when the query repeats the same expression, configuration included.
- Weight title over body with `setweight`; rank with `ts_rank` or `ts_rank_cd` and order by it.
- Stemming is rule-based: `ran` is not `run`; typos need `pg_trgm`.

<Callout title="Search is a feature, not just a query">
`@@` answers "does this match?". A real search box also needs ranking, snippets, typo tolerance, filters and pagination. PostgreSQL gives you the building blocks in one database with transactional consistency; a dedicated search engine is worth its operational cost only when you need much more than that.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| `LIKE '%x%'` / `ILIKE` | No setup, exact characters | Seq Scan unless trigram-indexed; no stemming, ranking or word boundaries |
| Full-text search + GIN | Word-aware, ranked, 16.8 ms to 0.28 ms on 100 000 rows | 15 MB index; stemming rules, no typo tolerance |
| `pg_trgm` | Typo tolerance, arbitrary substrings | Larger index; similarity, not language |
| Stored generated `tsvector` | One expression, always in sync, indexable | Extra disk for the column; writes recompute it |
| Expression index | No extra column | Queries must repeat the exact expression (573 ms when they did not) |

## Common Misconceptions

- **"Full-text search understands language."** It applies dictionaries: `running` matches `run`, `ran` does not.
- **"FTS is just a faster LIKE."** It matches lexemes, ranks, and cannot find substrings like `%un%`.
- **"The default config is `simple`."** It is `english` here (derived from the locale); `simple` under `C`.
- **"The index handles the query if the column matches."** The whole expression must match, configuration included.
- **"I can index a virtual generated column."** PostgreSQL 18 refuses: `indexes on virtual generated columns are not supported`.
