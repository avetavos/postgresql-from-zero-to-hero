Some queries are long, or used in many places, or joined and aggregated in the same way every time. Instead of copying the SQL around, PostgreSQL lets you give the query a name and treat it as a table: a **view**. A **materialized view** goes one step further and stores the query's result rows, trading freshness for speed.

Everything below was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). The `sql` fences run top to bottom in one empty database; outputs are pasted from `psql`; the two-session runs are real (two `psql` processes started together). Timings are from this Mac.

## A view is a stored query

`CREATE VIEW` saves a `SELECT` under a name. It stores no rows. Every time you query the view, PostgreSQL runs the saved query against the current data. This one summarizes each author, keeping authors without books:

```sql
-- sql/create-view.sql
CREATE VIEW author_sales AS
SELECT a.id AS author_id,
       a.name,
       count(b.id)                        AS books,
       coalesce(sum(b.copies_sold), 0)    AS copies_sold
FROM authors AS a
LEFT JOIN books AS b ON b.author_id = a.id
GROUP BY a.id, a.name;
```

Because the view stores nothing, its results are always current. It also costs nothing extra to plan: the view is expanded into your query before optimization, so it is not a black box the planner has to run first. Ask for one author and the filter reaches the base table:

```sql
-- sql/view-plan.sql
-- the view is not a black box: its query is merged into yours, and the filter reaches the base table
EXPLAIN (COSTS OFF) SELECT * FROM author_sales WHERE name = 'Owen Pryce';
```

```text
                          QUERY PLAN                           
---------------------------------------------------------------
 GroupAggregate
   Group Key: a.id
   ->  Sort
         Sort Key: a.id
         ->  Hash Right Join
               Hash Cond: (b.author_id = a.id)
               ->  Seq Scan on books b
               ->  Hash
                     ->  Seq Scan on authors a
                           Filter: (name = 'Owen Pryce'::text)
(10 rows)
```

The `Filter: (name = 'Owen Pryce')` sits on the scan of `authors`, under the join: the view's `GROUP BY` did not stop it from being pushed down. A view is a naming and reuse tool; it is not a performance feature ([docs](https://www.postgresql.org/docs/18/sql-createview.html)).

### A view remembers its columns, not your intentions

`SELECT *` in a view definition is expanded once, when the view is created. Add a column to the table later and the view does not show it:

```sql
-- sql/select-star-frozen.sql
CREATE VIEW book_titles AS SELECT * FROM books;
ALTER TABLE books ADD COLUMN isbn text;
SELECT * FROM book_titles LIMIT 1;
SELECT * FROM books LIMIT 1;
```

```text
CREATE VIEW
ALTER TABLE
 id |     title     | author_id | published | copies_sold 
----+---------------+-----------+-----------+-------------
  1 | Quiet Harbors |         1 |      2003 |         450
(1 row)

 id |     title     | author_id | published | copies_sold | isbn 
----+---------------+-----------+-----------+-------------+------
  1 | Quiet Harbors |         1 |      2003 |         450 | 
(1 row)
```

`book_titles` still has five columns; `books` now has six. Write the columns you want.

### Updatable views and WITH CHECK OPTION

A view over one table, without aggregates, `DISTINCT` or set operations, is **automatically updatable**: `INSERT`, `UPDATE` and `DELETE` on the view change the base table. `WITH CHECK OPTION` keeps rows you write through the view inside the view's own `WHERE`:

```sql
-- sql/updatable-view.sql
CREATE VIEW recent_books AS
SELECT id, title, author_id, published, copies_sold
FROM books
WHERE published >= 2010
WITH CHECK OPTION;
SELECT id, title, published FROM recent_books ORDER BY id;
BEGIN;
-- a simple view is updatable: this changes the base table
UPDATE recent_books SET copies_sold = copies_sold + 10 WHERE title = 'Tidal Notes' RETURNING id, title, copies_sold;
ROLLBACK;
```

```text
CREATE VIEW
 id |       title       | published 
----+-------------------+-----------
  2 | The Glass Orchard |      2018
  3 | Tidal Notes       |      2011
  4 | Unlinked Draft    |      2020
(3 rows)

BEGIN
 id |    title    | copies_sold 
----+-------------+-------------
  3 | Tidal Notes |         610
(1 row)

UPDATE 1
ROLLBACK
```

```sql
-- @expect-error 44000
INSERT INTO recent_books (title, author_id, published) VALUES ('Old Book', 1, 1999);
```

```text
ERROR:  new row violates check option for view "recent_books"
DETAIL:  Failing row contains (5, Old Book, 1, 1999, 0, null).
```

Without `WITH CHECK OPTION` that insert would succeed and the new row would simply be invisible through the view.

### Dependencies

A view depends on its base tables, and PostgreSQL knows it. Dropping a table that views use is refused, and the message lists every dependent:

```sql
-- @expect-error 2BP01
DROP TABLE books;
```

```text
ERROR:  cannot drop table books because other objects depend on it
DETAIL:  constraint sales_book_id_fkey on table sales depends on table books
view author_sales depends on table books
view book_titles depends on table books
view recent_books depends on table books
HINT:  Use DROP ... CASCADE to drop the dependent objects too.
```

### security_invoker

By default a view runs with the privileges of the view's **owner**, not the caller. That is a feature (it can hide columns and rows), and a trap (a role that cannot read the tables can read the view). PostgreSQL 15 added `security_invoker`: the view then runs with the caller's privileges. A role with `SELECT` on the view only:

```sql
-- sql/security-invoker.sql
CREATE ROLE report_reader NOLOGIN;
GRANT USAGE ON SCHEMA public TO report_reader;
GRANT SELECT ON author_sales TO report_reader;    -- the view only, no table privileges

-- default: the view runs with its OWNER's privileges, so the reader gets data
SET ROLE report_reader;
SELECT name, books FROM author_sales ORDER BY name;
RESET ROLE;

-- security_invoker (PostgreSQL 15+): the view runs with the CALLER's privileges
ALTER VIEW author_sales SET (security_invoker = true);
```

```text
CREATE ROLE
GRANT
GRANT
SET
    name    | books 
------------+-------
 Mara Linde |     2
 Owen Pryce |     1
 Sela Vance |     0
(3 rows)

RESET
ALTER VIEW
```

Now the same role, after `security_invoker = true`:

```sql
-- @expect-error 42501
SET ROLE report_reader;
SELECT name, books FROM author_sales ORDER BY name;
```

```text
SET
ERROR:  permission denied for table authors
```

With `security_invoker` the caller needs privileges on the base tables too, and row-level security policies apply to the caller rather than the owner ([docs](https://www.postgresql.org/docs/18/sql-createview.html)). Clean up the demo role:

```sql
-- sql/security-cleanup.sql
RESET ROLE;
DROP OWNED BY report_reader;
DROP ROLE report_reader;
ALTER VIEW author_sales RESET (security_invoker);
```

## A materialized view caches the result

`CREATE MATERIALIZED VIEW` runs the query now and stores the rows. Reading it is as cheap as reading a table, and just as stale as the last refresh. We insert a new sale, and the materialized view does not notice until we `REFRESH` it:

```sql
-- sql/materialized-view.sql
CREATE MATERIALIZED VIEW sales_by_region AS
SELECT region, count(*) AS sales, sum(copies) AS copies
FROM sales
GROUP BY region;
SELECT * FROM sales_by_region ORDER BY region;
-- the source changes, the materialized view does not
INSERT INTO sales (book_id, region, copies) VALUES (3, 'East', 1000);
SELECT 'view says' AS source, region, copies FROM sales_by_region WHERE region = 'East'
UNION ALL
SELECT 'live table', region, sum(copies) FROM sales WHERE region = 'East' GROUP BY region;
REFRESH MATERIALIZED VIEW sales_by_region;
SELECT 'after refresh' AS source, region, copies FROM sales_by_region WHERE region = 'East';
```

```text
SELECT 2
 region | sales | copies 
--------+-------+--------
 East   |     3 |   1150
 West   |     3 |    950
(2 rows)

INSERT 0 1
   source   | region | copies 
------------+--------+--------
 view says  | East   |   1150
 live table | East   |   2150
(2 rows)

REFRESH MATERIALIZED VIEW
    source     | region | copies 
---------------+--------+--------
 after refresh | East   |   2150
(1 row)
```

`view says 1150`, `live table 2150`: the materialized view is a snapshot. It is the right tool for expensive aggregates that many readers need and that can be a little stale (a dashboard, a nightly report).

`WITH NO DATA` creates the definition without running the query; reading it before the first refresh is an error:

```sql
-- sql/with-no-data.sql
CREATE MATERIALIZED VIEW empty_mv AS SELECT region, sum(copies) AS copies FROM sales GROUP BY region WITH NO DATA;
```

```sql
-- @expect-error 55000
SELECT * FROM empty_mv;
```

```text
ERROR:  materialized view "empty_mv" has not been populated
HINT:  Use the REFRESH MATERIALIZED VIEW command.
```

### REFRESH blocks readers, CONCURRENTLY does not

A plain `REFRESH MATERIALIZED VIEW` takes an `ACCESS EXCLUSIVE` lock while it rewrites the stored rows, so readers wait. `REFRESH MATERIALIZED VIEW CONCURRENTLY` builds the new contents on the side and swaps in only the differences, so readers keep reading the old rows. It needs a unique index on the materialized view, otherwise it refuses:

```sql
-- @expect-error 55000
REFRESH MATERIALIZED VIEW CONCURRENTLY sales_by_region;
```

```text
ERROR:  cannot refresh materialized view "public.sales_by_region" concurrently
HINT:  Create a unique index with no WHERE clause on one or more columns of the materialized view.
```

```sql
-- sql/concurrently.sql
CREATE UNIQUE INDEX sales_by_region_region_idx ON sales_by_region (region);
```

To see the difference we need a refresh slow enough to observe, so this materialized view is *artificially* slow: `pg_sleep(1)` runs once per group, making every refresh take about 2 seconds.

```sql
-- sql/slow-mv.sql
-- an artificially slow materialized view: pg_sleep makes the refresh take about 2 seconds
CREATE MATERIALIZED VIEW slow_mv AS
SELECT region, sum(copies) AS copies, pg_sleep(1) IS NOT NULL AS slept
FROM sales GROUP BY region;
CREATE UNIQUE INDEX slow_mv_region_idx ON slow_mv (region);
```

Session A refreshes it while session B tries to read 0.3 s later:

```text
-- session A: script
\timing on
REFRESH MATERIALIZED VIEW slow_mv;
-- session A: psql output
Timing is on.
REFRESH MATERIALIZED VIEW
Time: 2011.220 ms (00:02.011)

-- session B (starts 0.3 s later): script
\o /dev/null
SELECT pg_sleep(0.3);
\o
\timing on
SELECT region, copies FROM slow_mv ORDER BY region;
-- session B: psql output
Timing is on.
 region | copies 
--------+--------
 East   |   2150
 West   |    955
(2 rows)

Time: 1710.883 ms (00:01.711)
```

B waited **1.7 seconds**, the remaining time of A's refresh. Now the same with `CONCURRENTLY`:

```text
-- session A: script
\timing on
REFRESH MATERIALIZED VIEW CONCURRENTLY slow_mv;
-- session A: psql output
Timing is on.
REFRESH MATERIALIZED VIEW
Time: 2016.039 ms (00:02.016)

-- session B (same script as above): psql output
Timing is on.
 region | copies 
--------+--------
 East   |   2150
 West   |    955
(2 rows)

Time: 1.892 ms
```

A took just as long (2.0 s), but B read the old rows in **1.9 ms**. The price of `CONCURRENTLY` is the unique index and more work per refresh (it computes a diff) ([docs](https://www.postgresql.org/docs/18/sql-refreshmaterializedview.html)).

## Choosing between them

| Question | View | Materialized view |
|---|---|---|
| Are results always current? | Yes | No, only as of the last `REFRESH` |
| Is it faster than the raw query? | No (merged into the query) | Yes: rows are precomputed |
| Does it use storage? | No | Yes, plus indexes you add on it |
| Who refreshes it? | Nobody, no need | You: a schedule, a trigger or `pg_cron` |

## Reading AI-generated code

An assistant sets up a nightly job to refresh a summary "without blocking readers", using `CONCURRENTLY`:

<SpotTheBug lang="sql" code={`-- AI comment: "nightly cron: refresh without blocking readers"
CREATE MATERIALIZED VIEW daily_totals AS
SELECT region, sum(copies) AS copies FROM sales GROUP BY region;

REFRESH MATERIALIZED VIEW CONCURRENTLY daily_totals;`}>

It runs, and fails every night: `CONCURRENTLY` requires a unique index on the materialized view, and the assistant never created one. The materialized view is created (that part works), then the refresh is refused, the job logs an error nobody reads, and the data goes stale:

```sql
-- sql/stb-setup.sql
CREATE MATERIALIZED VIEW daily_totals AS
SELECT region, sum(copies) AS copies FROM sales GROUP BY region;
```

```sql
-- @expect-error 55000
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_totals;
```

```text
ERROR:  cannot refresh materialized view "public.daily_totals" concurrently
HINT:  Create a unique index with no WHERE clause on one or more columns of the materialized view.
```

The fix is the unique index (here `region` is unique per row), and then the refresh works while readers keep reading:

```sql
-- sql/stb-fixed.sql
CREATE UNIQUE INDEX daily_totals_region_idx ON daily_totals (region);
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_totals;
SELECT * FROM daily_totals ORDER BY region;
```

## Mental Model

A view is a *definition*: a name for a query, expanded into whatever query uses it. A materialized view is a *table that remembers how it was made*: rows are stored, and `REFRESH` re-runs the definition. Every question about them follows: a view is always fresh and no faster than its query; a materialized view is fast to read and as stale as its last refresh, occupies space, can be indexed, and needs someone to refresh it.

## Tips / gotchas

- Use a view to name and reuse a query, to expose a stable interface over changing tables, or to narrow what a role can see.
- List the columns; `SELECT *` in a view is frozen at creation.
- Set `security_invoker = true` on views that should respect the caller's privileges and row-level security.
- Add indexes to materialized views like any table; `REFRESH ... CONCURRENTLY` needs a unique one.
- Schedule refreshes and monitor them: a refresh that fails silently leaves stale data forever.
- Views can nest views; each layer is expanded, so deep stacks can produce large plans.

<Callout title="Fresh or fast: pick one on purpose">
A view is always fresh and as slow as its query. A materialized view is as fast as a table and only as fresh as its last refresh. If staleness is unacceptable but the query is slow, look at indexes first, then at incremental summary tables kept up to date by triggers or application code.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| View | Always current, no storage, reusable and permission-friendly | No speedup; changing base tables can break it |
| Materialized view | Fast reads of an expensive query | Stale between refreshes; storage; a plain refresh blocked a reader for 1.7 s |
| `REFRESH ... CONCURRENTLY` | Readers not blocked (1.9 ms) | Needs a unique index; slower, more work per refresh |
| `security_invoker` view | Caller's privileges and RLS apply | Callers need base-table privileges |
| `WITH CHECK OPTION` | Writes can't leave the view | Only for updatable views |

## Common Misconceptions

- **"A view caches its result."** It stores no rows; it is re-run every time (and merged into your query).
- **"A view makes a slow query fast."** The filter reached the base table, but the work is the same as the raw query.
- **"`SELECT *` in a view tracks new columns."** It is expanded at creation: `book_titles` did not get `isbn`.
- **"A materialized view refreshes itself."** Only when you `REFRESH` it: 1150 stayed 1150 while the table said 2150.
- **"`REFRESH ... CONCURRENTLY` just works."** It needs a unique index, or fails with `55000`.
- **"A role needs table access to read through a view."** Not by default: the view runs as its owner, unless `security_invoker` is set.
