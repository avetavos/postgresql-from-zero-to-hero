Sometimes a row needs to hold data whose shape is not fixed in advance: a product whose attributes differ by category, an event payload from a third party, or user preferences that grow over time. PostgreSQL lets a single column store a whole JSON document with the `jsonb` type, and then query inside it as if its keys were columns.

Everything below was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). The `sql` fences run top to bottom in one empty database, outputs are pasted from `psql`, and timings are single runs from this Mac.

## Creating a JSONB column

The `jsonb` type stores JSON in a decomposed binary form. Compared with the plain `json` type, it strips insignificant whitespace, keeps only the last of duplicate keys, does not preserve key order, and, crucially, can be indexed. This lesson uses a table of products where each row carries a flexible `attributes` document.

```sql
-- sql/setup.sql
CREATE TABLE products (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       text  NOT NULL,
  attributes jsonb NOT NULL DEFAULT '{}'
);
```

## Storing a document

Insert JSON as a string literal; PostgreSQL parses and validates it. Note how `jsonb` prints each document: its keys come out in its own order (shorter keys first, then alphabetical), not in the order you wrote them:

```sql
-- sql/insert-documents.sql
INSERT INTO products (name, attributes) VALUES
  ('Trail Jacket',  '{"color": "teal",   "price": 129.5, "tags": ["outdoor", "rain"],    "specs": {"weight_g": 480, "waterproof": true}}'),
  ('City Backpack', '{"color": "black",  "price": 89,    "tags": ["urban"],              "specs": {"weight_g": 900, "waterproof": false}}'),
  ('Camp Stove',    '{"color": "silver", "price": 45,    "tags": ["outdoor", "cooking"], "specs": {"weight_g": 350}}'),
  ('Wool Socks',    '{"color": "teal",   "price": 12.5,  "tags": ["outdoor"]}'),
  ('Rain Poncho',   '{"color": "yellow", "price": 9,     "tags": ["rain", "outdoor"],    "specs": {"waterproof": true}}');
SELECT id, name, attributes FROM products ORDER BY id;
```

`json` and `jsonb` differ on exactly the points above. The same literal, with extra whitespace and a duplicate key:

```sql
-- sql/json-vs-jsonb.sql
SELECT '{"b": 1,   "a": 2, "a": 3}'::json  AS as_json,
       '{"b": 1,   "a": 2, "a": 3}'::jsonb AS as_jsonb;
```

```text
          as_json           |     as_jsonb     
----------------------------+------------------
 {"b": 1,   "a": 2, "a": 3} | {"a": 3, "b": 1}
(1 row)
```

`json` keeps the text as written (whitespace, both `"a"` keys, order). `jsonb` normalizes it: `{"a": 3, "b": 1}`, the last duplicate wins ([docs](https://www.postgresql.org/docs/18/datatype-json.html)). Invalid JSON is rejected at insert time, with the exact spot:

```sql
-- @expect-error 22P02
INSERT INTO products (name, attributes) VALUES ('Broken', '{"color": }');
```

```text
ERROR:  invalid input syntax for type json
LINE 1: ...NTO products (name, attributes) VALUES ('Broken', '{"color":...
                                                             ^
DETAIL:  Expected JSON value, but found "}".
CONTEXT:  JSON data, line 1: {"color": }
```

## Reaching inside a document

`->` returns a `jsonb` value, `->>` returns `text`, and `#>` / `#>>` follow a path. A missing key returns `NULL`, not an error:

```sql
-- sql/operators.sql
SELECT name,
       attributes -> 'color'                     AS color_jsonb,
       attributes ->> 'color'                    AS color_text,
       attributes #>> '{specs,weight_g}'         AS weight,
       attributes -> 'tags' -> 0                 AS first_tag,
       attributes ->> 'missing'                  AS missing_key
FROM products
ORDER BY id;
```

```text
     name      | color_jsonb | color_text | weight | first_tag | missing_key 
---------------+-------------+------------+--------+-----------+-------------
 Trail Jacket  | "teal"      | teal       | 480    | "outdoor" | 
 City Backpack | "black"     | black      | 900    | "urban"   | 
 Camp Stove    | "silver"    | silver     | 350    | "outdoor" | 
 Wool Socks    | "teal"      | teal       |        | "outdoor" | 
 Rain Poncho   | "yellow"    | yellow     |        | "rain"    | 
(5 rows)
```

Because `->>` gives text, arithmetic and numeric comparison need a cast:

```sql
-- sql/numeric-cast.sql
SELECT name, (attributes ->> 'price')::numeric AS price
FROM products
WHERE (attributes ->> 'price')::numeric > 40
ORDER BY price DESC;
```

```text
     name      | price 
---------------+-------
 Trail Jacket  | 129.5
 City Backpack |    89
 Camp Stove    |    45
(3 rows)
```

## Filtering with containment and key tests

`@>` asks "does the left document contain the right one?". It matches nested objects and array elements, which is exactly what makes it indexable. `?`, `?|` and `?&` test for keys:

```sql
-- sql/containment.sql
SELECT name FROM products WHERE attributes @> '{"color": "teal"}' ORDER BY id;
-- nested keys and array elements work in containment too
SELECT name FROM products WHERE attributes @> '{"specs": {"waterproof": true}, "tags": ["rain"]}' ORDER BY id;
-- key existence, any key, all keys
SELECT name FROM products WHERE attributes ? 'specs' ORDER BY id;
SELECT name FROM products WHERE attributes ?| array['specs', 'discount'] ORDER BY id;
SELECT name FROM products WHERE attributes ?& array['specs', 'tags'] ORDER BY id;
```

**jsonpath** ([docs](https://www.postgresql.org/docs/18/functions-json.html#FUNCTIONS-SQLJSON-PATH)) is a small query language over the document. `jsonb_path_query` extracts, `@?` tests existence with a filter, `jsonb_path_exists` is the function form:

```sql
-- sql/jsonpath.sql
SELECT name, jsonb_path_query(attributes, '$.specs.weight_g') AS weight_g
FROM products ORDER BY id;
SELECT name FROM products WHERE attributes @? '$.specs ? (@.weight_g < 500)' ORDER BY id;
SELECT name FROM products WHERE jsonb_path_exists(attributes, '$.tags[*] ? (@ == "cooking")') ORDER BY id;
```

```sql
-- sql/json-table.sql

       color    text    PATH '$.color',
       price    numeric PATH '$.price',
```

### The two traps

The first: comparing `->` output with a bare string. `->` returns `jsonb`, so the right-hand side is parsed as JSON, and `teal` is not valid JSON. The error is a JSON parse error, not a type error:

```sql
-- @expect-error 22P02
SELECT name FROM products WHERE attributes -> 'color' = 'teal';
```

```text
ERROR:  invalid input syntax for type json
LINE 1: ...ECT name FROM products WHERE attributes -> 'color' = 'teal';
                                                                ^
DETAIL:  Token "teal" is invalid.
CONTEXT:  JSON data, line 1: teal
```

Both of these work: compare against a JSON string (`'"teal"'`), or extract text with `->>` and compare with an ordinary string:

```sql
-- sql/equality-forms.sql
SELECT name FROM products WHERE attributes -> 'color' = '"teal"' ORDER BY id;
SELECT name FROM products WHERE attributes ->> 'color' = 'teal' ORDER BY id;
```

```text
     name     
--------------
 Trail Jacket
 Wool Socks
(2 rows)

     name     
--------------
 Trail Jacket
 Wool Socks
(2 rows)
```

The second trap: `->>` returns **text**, and text compares character by character. `'9' > '50'` is true, `'129.5' > '50'` is false. This is a silent wrong answer, and the *Reading AI-generated code* section below is built on it:

```sql
-- sql/text-comparison-trap.sql
-- ->> returns text, and text compares character by character: '9' sorts after '89'
SELECT name, attributes ->> 'price' AS price_text
FROM products
WHERE attributes ->> 'price' > '50'
ORDER BY name;
```

```text
     name      | price_text 
---------------+------------
 City Backpack | 89
 Rain Poncho   | 9
(2 rows)
```

## Updating part of a document

`||` merges two documents, but only at the top level. Setting `specs` this way **replaces the whole `specs` object** (the `waterproof` key is gone). `jsonb_set(doc, path, value)` changes one nested path and keeps its siblings. The optional fourth argument `create_missing` (default `true`) decides whether a missing last key is created; `-` and `#-` remove a key or a nested key. Everything below is in transactions that roll back:

```sql
-- sql/update-documents.sql
BEGIN;
-- || merges TOP-LEVEL keys only: the whole "specs" object is replaced
UPDATE products SET attributes = attributes || '{"specs": {"weight_g": 470}}' WHERE name = 'Trail Jacket'
RETURNING name, attributes -> 'specs' AS specs_after_concat;
ROLLBACK;
BEGIN;
-- jsonb_set changes one nested path and keeps its siblings
UPDATE products SET attributes = jsonb_set(attributes, '{specs,weight_g}', '470') WHERE name = 'Trail Jacket'
RETURNING name, attributes -> 'specs' AS specs_after_set;
-- missing path: create_missing (default true) creates the last key, false leaves the row alone
UPDATE products SET attributes = jsonb_set(attributes, '{specs,fabric}', '"nylon"', false) WHERE name = 'Trail Jacket'
RETURNING attributes -> 'specs' AS specs_create_missing_false;
-- remove a key, and a nested key
UPDATE products SET attributes = attributes - 'tags' #- '{specs,waterproof}' WHERE name = 'Trail Jacket'
RETURNING attributes;
ROLLBACK;
```

```text
BEGIN
     name     | specs_after_concat 
--------------+--------------------
 Trail Jacket | {"weight_g": 470}
(1 row)

UPDATE 1
ROLLBACK
BEGIN
     name     |            specs_after_set            
--------------+---------------------------------------
 Trail Jacket | {"weight_g": 470, "waterproof": true}
(1 row)

UPDATE 1
      specs_create_missing_false       
---------------------------------------
 {"weight_g": 470, "waterproof": true}
(1 row)

UPDATE 1
                          attributes                           
---------------------------------------------------------------
 {"color": "teal", "price": 129.5, "specs": {"weight_g": 470}}
(1 row)

UPDATE 1
ROLLBACK
```

## Indexing for containment queries

Without an index, a containment query reads every row. Here is a 100 000-row `catalog` with the same kind of document; the query asks for teal items tagged `t7`:

```sql
-- sql/catalog-setup.sql
CREATE TABLE catalog (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  attributes jsonb NOT NULL
);
INSERT INTO catalog (attributes)
SELECT jsonb_build_object(
         'color',  (ARRAY['teal', 'black', 'silver', 'yellow', 'red', 'green', 'blue', 'white'])[1 + h % 8],
         'price',  5 + (h / 8) % 200,
         'tags',   jsonb_build_array('t' || (h / 1600) % 60, 't' || (h / 96000) % 97),
         'specs',  jsonb_build_object('weight_g', 100 + (h / 7) % 900))
FROM (SELECT ('x' || substr(md5(g::text), 1, 7))::bit(28)::int AS h FROM generate_series(1, 100000) g) s;
ANALYZE catalog;
SELECT count(*) AS rows, pg_size_pretty(pg_relation_size('catalog')) AS heap FROM catalog;
```

```text
CREATE TABLE
INSERT 0 100000
ANALYZE
  rows  | heap  
--------+-------

(1 row)
```

```sql
-- sql/catalog-no-index.sql
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF)
SELECT count(*) FROM catalog WHERE attributes @> '{"color": "teal", "tags": ["t7"]}';
```

```text
   ->  Seq Scan on catalog (actual time=0.133..15.531 rows=330.00 loops=1)
```

A GIN index with `jsonb_path_ops` (smaller and faster for `@>`; the default `jsonb_ops` class also supports `?`) turns it into an index lookup:

```sql
-- sql/catalog-gin.sql
CREATE INDEX catalog_attr_gin ON catalog USING gin (attributes jsonb_path_ops);
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF)
SELECT count(*) FROM catalog WHERE attributes @> '{"color": "teal", "tags": ["t7"]}';
SELECT pg_size_pretty(pg_relation_size('catalog_attr_gin')) AS gin_size;
```

```text

         Heap Blocks: exact=305
         ->  Bitmap Index Scan on catalog_attr_gin (actual time=0.234..0.234 rows=330.00 loops=1)
               Index Cond: (attributes @> '{"tags": ["t7"], "color": "teal"}'::jsonb)
```

16 ms became 0.8 ms for 330 matching rows, at a cost of a 1.7 MB index on a 15 MB table. The index serves only operators on the column itself (`@>`, `?`, `@?`): an extracted expression like `attributes->>'color'` needs its own B-tree expression index. The specialized indexes lesson compares the GIN operator classes in detail.

### Big documents and TOAST

A row larger than about 2 kB has its big values moved out of line into a **TOAST** table (and compressed if that helps). `jsonb` documents are stored as one value, so changing one small key rewrites the whole document. 2 000 documents of about 9.6 kB each (random text, which does not compress):

```sql
-- sql/toast.sql
CREATE TABLE docs (id int PRIMARY KEY, body jsonb NOT NULL);
INSERT INTO docs
SELECT g, jsonb_build_object('id', g, 'note', 'first', 'blob', (SELECT string_agg(md5(random()::text), '') FROM generate_series(1, 300)))
FROM generate_series(1, 2000) g;
ANALYZE docs;
SELECT pg_column_size(body) AS stored_bytes, octet_length(body::text) AS as_text_bytes FROM docs WHERE id = 1;
SELECT pg_size_pretty(pg_relation_size('docs')) AS heap,
       pg_size_pretty(pg_relation_size((SELECT reltoastrelid FROM pg_class WHERE relname = 'docs'))) AS toast;
-- change ONE small key in every document
UPDATE docs SET body = jsonb_set(body, '{note}', '"second"');
SELECT pg_size_pretty(pg_relation_size((SELECT reltoastrelid FROM pg_class WHERE relname = 'docs'))) AS toast_after_small_update;
```

```text
CREATE TABLE
INSERT 0 2000
ANALYZE
 stored_bytes | as_text_bytes 
--------------+---------------
         9653 |          9638
(1 row)

  heap  | toast 
--------+-------
 104 kB | 20 MB
(1 row)

UPDATE 2000
 toast_after_small_update 
--------------------------
 39 MB
(1 row)
```

The heap is 104 kB and the documents live in TOAST (20 MB). Changing the small `note` key in every document made the TOAST table grow to 39 MB: each update wrote a full new copy of the document, and the old copies wait for `VACUUM`. If you update one field of a large document often, that field belongs in its own column.

## Reading AI-generated code

An assistant is asked for "products over 100" from a `jsonb` price and writes the obvious query:

<SpotTheBug lang="sql" code={`-- AI comment: "products over 100"
SELECT name, attributes ->> 'price' AS price
FROM products
WHERE attributes ->> 'price' > '100'
ORDER BY name;`}>

The result looks plausible and is wrong. `->>` yields text, and text sorts character by character, so `'9'`, `'12.5'`, `'45'` and `'89'` are all "greater than" `'100'`. On this data the query returns **every** product, including the ones priced 9 and 12.5, and would drop or include the wrong ones as prices change:

```sql
-- sql/stb-wrong.sql
SELECT name, attributes ->> 'price' AS price
FROM products
WHERE attributes ->> 'price' > '100'
ORDER BY name;
```

```text
     name      | price 
---------------+-------
 Camp Stove    | 45
 City Backpack | 89
 Rain Poncho   | 9
 Trail Jacket  | 129.5
 Wool Socks    | 12.5
(5 rows)
```

Cast to `numeric` before comparing (and, if this filter matters, index the expression `((attributes->>'price')::numeric)`):

```sql
-- sql/stb-fixed.sql
SELECT name, attributes ->> 'price' AS price
FROM products
WHERE (attributes ->> 'price')::numeric > 100
ORDER BY name;
```

```text
     name     | price 
--------------+-------
 Trail Jacket | 129.5
(1 row)
```

</SpotTheBug>

## Mental Model

`jsonb` is a value type that happens to have keys. You can extract from it (`->`, `->>`, jsonpath), test it (`@>`, `?`), rebuild it (`||`, `jsonb_set`, `-`), and unnest it into rows (`jsonb_each`, `jsonb_array_elements`, `JSON_TABLE`). Extraction gives you either `jsonb` or `text`: pick deliberately, and cast before you compare numbers or dates. Storage is one opaque value per row: a GIN index makes containment fast, and every write to any key rewrites the whole value.

## Tips / gotchas

- Use `jsonb`, not `json`, unless you must preserve the exact original text.
- `->` returns `jsonb`, `->>` returns `text`; cast (`::numeric`, `::date`) before comparing numbers or dates.
- Prefer `@>` for filters you want indexed; `attributes->>'k' = 'v'` needs an expression index instead.
- `||` is a shallow merge; use `jsonb_set` for nested changes.
- Give columns you filter, join or update often a real column of their own; keep `jsonb` for the truly flexible remainder.
- Drivers differ: `pg` parses to objects, `psycopg` gives `dict`, `pgx` gives `map[string]any`, `sqlx` needs a feature flag.

<Callout title="A column of documents is not a schema">
`jsonb` lets you defer decisions, but it does not remove them. Constraints, types and foreign keys live on real columns. A good pattern is real columns for what you query, join and constrain, and one `jsonb` column for the long tail.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| `jsonb` column | Flexible shape, no migration per attribute, GIN-indexable | No type checking of keys; a small change rewrites the whole document (TOAST 20 MB to 39 MB above) |
| Real columns | Types, constraints, foreign keys, cheap updates | Schema change (migration) for each new attribute |
| `json` (text) | Exact original text preserved | Reparsed on every access, cannot be indexed |
| GIN `jsonb_path_ops` | 16 ms to 0.8 ms for `@>` | 1.7 MB here; no `?` key-existence support |

## Common Misconceptions

- **"`->` returns text."** It returns `jsonb`; comparing it with `'teal'` is a JSON parse error. `->>` returns text.
- **"`jsonb` keeps my key order and duplicates."** It keeps neither: `{"a": 3, "b": 1}`.
- **"`||` merges nested objects."** It replaces the whole nested object: `specs` lost `waterproof`.
- **"Comparing `->>` values numerically works."** It compares text: `'9' > '50'`.
- **"A GIN index speeds up any filter on the column."** Only containment/existence operators on the column, not `->>` expressions.
