A single server is a single point of failure. If its disk dies or the machine reboots, your database is gone until someone fixes it. **Replication** removes that risk by keeping one or more copies of the data on other machines, continuously updated as the original changes. Those copies also let you spread read traffic across several servers.

PostgreSQL offers two flavours: **streaming replication**, which copies the entire cluster byte-for-byte, and **logical replication**, which copies selected tables row-by-row. They solve different problems, so this lesson covers both ([docs](https://www.postgresql.org/docs/18/warm-standby.html)).

Everything below was run for real on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). The lab is two containers on a Docker network created with `--internal`, so they can talk to each other and to nobody else; the containers, volumes and network are all named `postgresql-b3-*` and were removed when the lesson was finished. The password `<your-password>` stands for any value you choose, and the addresses and process ids in the output are from that run. The commands and their output are pasted as they came back; nothing on this page is a sketch.

<Callout title="Lab safety">
Docker Desktop allocates memory to all of its containers together. Run this lab with nothing else heavy running, and remove it (last block of the lesson) when you are done. Nothing here publishes a port to your host.
</Callout>

## The write-ahead log is the source of truth

Before a change touches a table file, PostgreSQL records it in the **write-ahead log** (WAL): an append-only stream of every modification. This log exists for crash recovery, but it is also exactly what a replica needs. If a second server replays the same WAL records in the same order, it ends up with an identical copy of the data.

Streaming replication does precisely that. The primary ships its WAL to each replica over a network connection, and each replica continuously applies those records to stay in step.

export const streamDiagram = `flowchart LR
  C[Client write] --> P[(Primary)]
  P -->|append| W[Write-ahead log]
  W -->|stream WAL| R1[(Replica 1 - read only)]
  W -->|stream WAL| R2[(Replica 2 - read only)]
  RC1[Read query] --> R1
  RC2[Read query] --> R2`;

<Mermaid code={streamDiagram} title="Primary ships its WAL to read replicas" />

A replica is read-only: it applies the primary's changes and answers `SELECT` queries, but it rejects writes. This makes it perfect for offloading reporting, analytics, or any read-heavy workload from the primary.

## Setting up streaming replication

On PostgreSQL 18 the settings streaming replication needs are already the defaults. The primary comes up with `wal_level = replica`, room for 10 WAL senders and 10 replication slots, and `hot_standby = on`; `wal_keep_size` is 0, which means old WAL is not kept for replicas unless you use a slot. What is not open by default is the door: you need a role with the `REPLICATION` attribute and a `pg_hba.conf` line for the special `replication` database name. `host all all all` does not cover it, because `all` does not include `replication`.

```text
# 1. one internal network (no route out), one named volume, one primary

$ docker network create --internal postgresql-b3-net

$ docker run -d --name postgresql-b3-primary --network postgresql-b3-net -e POSTGRES_PASSWORD=<your-password> -v postgresql-b3-primary-data:/var/lib/postgresql postgres:18.6

-- primary: script
SELECT name, setting FROM pg_settings
WHERE name IN ('wal_level', 'max_wal_senders', 'max_replication_slots', 'wal_keep_size', 'hot_standby')
```

A replica is created by taking a base backup of the primary and then pointing it at the primary to stream ongoing WAL. ## Replication lag

Asynchronous replication is not instantaneous. To make the gap visible, pause WAL replay on the replica (`pg_wal_replay_pause()`), write on the primary, and read from both. The replica has received the new WAL but has not applied it:

```text
-- replica: script
SELECT pg_wal_replay_pause();
-- replica: psql output
 pg_wal_replay_pause 
---------------------
 
(1 row)

-- primary: script
INSERT INTO accounts (owner, balance) VALUES ('Grace', 300);
-- primary: psql output
INSERT 0 1

-- replica: script
SELECT count(*) AS rows_on_replica FROM accounts;
SELECT pg_last_wal_receive_lsn() AS received, pg_last_wal_replay_lsn() AS replayed;
-- replica: psql output
 rows_on_replica 
-----------------
               2
(1 row)

 received  | replayed  
-----------+-----------
 0/3000248 | 0/3000000
(1 row)

-- primary: script
SELECT application_name, state, pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_lag_bytes
FROM pg_stat_replication;
-- primary: psql output
 application_name |   state   | replay_lag_bytes 
------------------+-----------+------------------
 replica1         | streaming |              584
(1 row)

-- replica: script
SELECT pg_wal_replay_resume();
-- replica: psql output
 pg_wal_replay_resume 
----------------------
 
(1 row)

-- replica: script
SELECT count(*) AS rows_on_replica FROM accounts;
-- replica: psql output
 rows_on_replica 
-----------------
               3
(1 row)
```

The replica still returned two rows while the primary had three, and the receive and replay positions differ by 584 bytes. After `pg_wal_replay_resume()` it catches up. In real life the gap is not a pause button but a slow disk, a long-running query on the replica, or a network hiccup; the columns `write_lag`, `flush_lag` and `replay_lag` of `pg_stat_replication` measure it in time.

## Synchronous versus asynchronous

The big choice in streaming replication is *when* the primary considers a write done.

| Mode         | Primary confirms a commit when...                 | Trade-off                                  |
|--------------|---------------------------------------------------|--------------------------------------------|
| Asynchronous | The WAL is written locally                        | Fast, but a replica may lag behind         |
| Synchronous  | At least one named standby has also stored the WAL | No data loss on failover, but slower writes |

Asynchronous is the default and the common choice. Writes never wait for the network, so the primary stays fast — but a replica can fall a little behind, called **replication lag**. A query sent to a lagging replica may not yet see the most recent commit.

Synchronous replication makes the primary wait for a standby to acknowledge each commit. You enable it by naming the standbys that must confirm, and the name must match the standby's `application_name` (we set it to `replica1` in the clone):

```conf
# postgresql.conf (or ALTER SYSTEM) on the primary
synchronous_standby_names = 'replica1'   # must equal the standby's application_name
```

If the name matches no connected standby, every commit waits forever, so this setting deserves a test. Below, the standby is stopped, and a client inserts a row. Its statement completes, the commit does not: the operator's `pg_stat_activity` shows the client in wait event `SyncRep`. The only ways out are to bring the standby back, remove the setting, or cancel the wait:

```text
-- primary: script
ALTER SYSTEM SET synchronous_standby_names = 'replica1';
SELECT pg_reload_conf();
-- primary: psql output
ALTER SYSTEM
```

How much the primary waits for is controlled by `synchronous_commit`, per session or per transaction ([docs](https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT)). Pick the weakest level that gives the guarantee you need.

## Replication holds back vacuum

A standby that runs long queries can conflict with the primary's cleanup. With `hot_standby_feedback = on` (and `wal_receiver_status_interval` lowered to 1 s so the demo is quick) the standby reports its oldest snapshot to the primary, which then refuses to remove rows that snapshot might still need. A report runs on the replica for ten seconds while the primary updates one row 1 000 times and vacuums:

```text
-- replica: script
ALTER SYSTEM SET hot_standby_feedback = on;
ALTER SYSTEM SET wal_receiver_status_interval = '1s';
SELECT pg_reload_conf();
-- replica: psql output
ALTER SYSTEM
ALTER SYSTEM

----------------

(1 row)

-- primary: script

SELECT pg_reload_conf();
```

## Failover

If the primary dies, one replica must be **promoted** to become the new primary so writes can resume. Promotion tells a replica to stop following and start accepting writes: `pg_promote()` in SQL, or `pg_ctl promote` from the shell. Here it is on the lab replica:

```text
-- primary: script
SELECT pg_walfile_name(pg_current_wal_lsn()) AS primary_wal_file;
-- primary: psql output
     primary_wal_file     
--------------------------
 000000010000000000000003
(1 row)

-- replica: script
SELECT pg_promote();
-- replica: psql output
 pg_promote 
------------
 t
(1 row)

-- replica: script
SELECT pg_is_in_recovery() AS still_a_standby;
INSERT INTO accounts (owner, balance) VALUES ('after-promote', 1) RETURNING id, owner;
SELECT pg_walfile_name(pg_current_wal_lsn()) AS promoted_wal_file;
-- replica: psql output
 still_a_standby 
-----------------
 f
(1 row)

 id |     owner     
----+---------------
 36 | after-promote
(1 row)

INSERT 0 1
    promoted_wal_file     
--------------------------
 000000020000000000000003
(1 row)

-- primary: script
SELECT count(*) AS after_promote_rows_on_old_primary FROM accounts WHERE owner = 'after-promote';
-- primary: psql output
 after_promote_rows_on_old_primary 
-----------------------------------
                                 0
(1 row)
```

After the promotion the replica accepts writes, and its WAL file name changed from `000000010...` to `000000020...`: the first eight digits are the **timeline**, which PostgreSQL increments at every promotion so histories cannot be mixed up. The old primary, still running, has no idea: the row written after the promotion (`after-promote`) exists only on the new one. If clients kept writing to both, you would have two diverging primaries (**split brain**), which is why real deployments need something to fence the old primary. Failover tools such as [Patroni](https://github.com/patroni/patroni), which describes itself as a Python template for building PostgreSQL high availability clusters and coordinates leader election through ZooKeeper, etcd, Consul or Kubernetes, exist to make that decision safely. The promote itself is the same single step.

## Logical replication: copy selected tables

Streaming replication copies the *whole cluster* and only flows one way to read-only standbys. Sometimes you want less than that — just a few tables — or you want to copy between different PostgreSQL major versions, for example during an upgrade. That is **logical replication**, built on a publish-and-subscribe model ([docs](https://www.postgresql.org/docs/18/logical-replication.html)).

On the source you create a **publication** naming the tables to share. On the destination you create a **subscription** that connects and copies them.

export const logicalDiagram = `flowchart LR
  S[(Source database)] -->|CREATE PUBLICATION| Pub[Publication: orders]
  Pub -->|row changes| Sub[Subscription]
  Sub --> D[(Destination database - writable)]`;

<Mermaid code={logicalDiagram} title="Logical replication publishes selected tables to a subscriber" />

Logical replication needs `wal_level = logical` on the source, which changes what goes into the WAL and needs a restart. On a default server the publication is created anyway, but with a warning, and writes to a table without a **replica identity** fail:

```text
$ docker rm -f postgresql-b3-replica && docker volume rm postgresql-b3-replica-data
postgresql-b3-replica
postgresql-b3-replica-data

-- publisher: script
CREATE TABLE orders (id int, item text NOT NULL, qty int NOT NULL);
CREATE PUBLICATION shop_pub FOR TABLE orders;
INSERT INTO orders VALUES (1, 'lamp', 2);
UPDATE orders SET qty = 3 WHERE id = 1;
-- publisher: psql output
CREATE TABLE
WARNING:  "wal_level" is insufficient to publish logical changes
HINT:  Set "wal_level" to "logical" before creating subscriptions.
CREATE PUBLICATION
INSERT 0 1
ERROR:  cannot update table "orders" because it does not have a replica identity and publishes updates
HINT:  To enable updating the table, set REPLICA IDENTITY using ALTER TABLE.

-- publisher: script

-- publisher: psql output
ALTER SYSTEM

$ docker restart postgresql-b3-primary
postgresql-b3-primary

-- publisher: script
SHOW wal_level;
ALTER TABLE orders ADD PRIMARY KEY (id);

-- publisher: psql output

-----------

(1 row)

```

The `UPDATE` failed because the table has no primary key: a logical subscriber needs some way to find the row to update. Adding a primary key (or `REPLICA IDENTITY FULL`) fixes it. The subscriber is a separate server; the table must already exist there, because schema is not replicated. `CREATE SUBSCRIPTION` copies the existing rows first and then keeps applying new changes:

```text
$ docker run -d --name postgresql-b3-subscriber --network postgresql-b3-net -e POSTGRES_PASSWORD=<your-password> -v postgresql-b3-sub-data:/var/lib/postgresql postgres:18.6

-- subscriber: script
CREATE TABLE orders (id int PRIMARY KEY, item text NOT NULL, qty int NOT NULL);
CREATE SUBSCRIPTION shop_sub
  CONNECTION 'host=postgresql-b3-primary dbname=postgres user=replicator password=<your-password>'
  PUBLICATION shop_pub;
\! sleep 2
SELECT * FROM orders ORDER BY id;
-- subscriber: psql output
CREATE TABLE
NOTICE:  created replication slot "shop_sub" on publisher
CREATE SUBSCRIPTION
 id | item | qty 
----+------+-----
  1 | lamp |   3
  2 | desk |   1
(2 rows)

-- publisher: script
INSERT INTO orders VALUES (3, 'chair', 4);
UPDATE orders SET qty = 9 WHERE id = 2;
-- publisher: psql output
INSERT 0 1
UPDATE 1

-- subscriber: script
SELECT * FROM orders ORDER BY id;
INSERT INTO orders VALUES (100, 'subscriber-only', 1);
-- subscriber: psql output
 id | item  | qty 
----+-------+-----
  1 | lamp  |   3
  2 | desk  |   9
  3 | chair |   4
(3 rows)

INSERT 0 1
```

The subscriber is a fully writable database: the `subscriber-only` row could be inserted there. It is not a read-only copy. Now the limitation that surprises people. DDL is not replicated ([docs](https://www.postgresql.org/docs/18/logical-replication-restrictions.html)); sequences and large objects are not either. Add a column on the publisher and insert a row that uses it:

```text
INSERT INTO orders VALUES (4, 'lamp', 1, 'gift');
-- publisher: psql output

INSERT 0 1
```

There is a second cost, and it is the one that fills disks. The publisher must keep every WAL segment the subscriber has not yet consumed, held by a **replication slot**. With the subscriber stopped, WAL piles up:

```text

FROM pg_replication_slots;
-- publisher: psql output

-----------+-----------+--------+------------+----------
 shop_sub  | logical   | t      | reserved   | 56 bytes
(1 row)

postgresql-b3-subscriber

-----------+--------+------------+----------

(1 row)

-- publisher: script

INSERT INTO orders SELECT g + 2000000, 'bulk2', 1, NULL FROM generate_series(1, 600000) g;
CHECKPOINT;

-- publisher: psql output

----------------
 t
(1 row)

-----------+--------+------------+---------------------
 shop_sub  | f      | lost       | wal_removed
(1 row)

$ docker start postgresql-b3-subscriber

	DETAIL:  This replication slot has been invalidated due to "wal_removed".
```

26 MB retained after 200 000 rows. A stopped subscriber that never comes back would eventually fill the primary's disk. `max_slot_wal_keep_size` puts a ceiling on it: after it was set to 32 MB and 600 000 more rows were written, the slot was invalidated (`wal_status = lost`, `invalidation_reason = wal_removed`) and the subscriber could not resume, so it would need a fresh initial copy. Monitor `pg_replication_slots`, and drop slots you no longer use ([docs](https://www.postgresql.org/docs/18/view-pg-replication-slots.html)).

## Reading AI-generated code

An assistant is asked to set up logical replication of the `orders` table and writes two statements with a confident comment:

<SpotTheBug lang="sql" code={`-- AI comment: "publish orders; a subscriber will pick up every change"
CREATE TABLE orders (id int, item text NOT NULL, qty int NOT NULL);
CREATE PUBLICATION shop_pub FOR TABLE orders;`}>

Both statements run without error on a default server, and the comment is wrong twice. `wal_level` is `replica` by default, so nothing can be decoded for subscribers: PostgreSQL prints a `WARNING: "wal_level" is insufficient to publish logical changes` at `CREATE PUBLICATION`, easy to miss in a migration log. Worse, the table has no primary key, so the first `UPDATE` fails with `cannot update table "orders" because it does not have a replica identity and publishes updates`. Both appear in the first block of the logical-replication transcript above: the publication is created with the warning, `INSERT` works, and `UPDATE` fails. The fix is `wal_level = logical` (a restart), a primary key (or `REPLICA IDENTITY FULL` when there is no key), and the same table definition on the subscriber before `CREATE SUBSCRIPTION`. After the primary key was added, the same `UPDATE` succeeded in the lab.

</SpotTheBug>

## Mental Model

A standby is a second server reading the same diary the primary is writing. Physical replication copies every line exactly and the standby can never write in it; logical replication reads the diary for a chosen chapter and re-enacts it in a different, independent book. Synchronous replication means "do not tell the client it worked until the second reader has the line". Every design question is: how long may the second reader be behind, and what happens when it disappears.

## Tips / gotchas

- Replicas are for reads and availability. Send every write to the primary; a replica will reject it (`read-only transaction`).
- With asynchronous replication, expect some lag. If a read must reflect a write that just happened, send it to the primary, wait for the replica to catch up, or use `remote_apply` for that transaction.
- Synchronous replication trades latency and availability for safety. Name the standby correctly, test what happens when it is down, and use it when losing even one acknowledged transaction is unacceptable, not as a blanket default.
- Streaming replication copies the entire cluster and matches versions; logical replication copies chosen tables and can cross major versions, which is why it shines for upgrades.
- Logical replication needs a replica identity — usually a primary key — on every published table, and the schema must be kept in sync by hand.
- Watch `pg_replication_slots`; a slot that nobody consumes eventually fills the disk unless `max_slot_wal_keep_size` is set.

<Callout title="One log, two uses">
The write-ahead log was invented so PostgreSQL could recover after a crash by replaying recent changes. Replication reuses that same log: a replica is simply another server replaying the primary's WAL, forever and over the network. Understanding the WAL is understanding replication.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| Synchronous replication | No data loss on failover, since the standby has the WAL before commit acknowledges | Every write waits on a network round trip; if the standby is unreachable, writes hang (3 s wait above until cancelled) |
| Asynchronous replication | Fast writes, since the primary never waits on the replica | The replica can lag behind (2 rows vs 3 above), with a small chance of data loss on failover |
| Logical replication | Selected tables, writable subscriber, works across major versions | DDL not replicated, needs replica identity, unconsumed slots retain WAL (26 MB above) |
| `hot_standby_feedback` | Fewer cancelled queries on the replica | The primary cannot vacuum what the standby still needs (1 000 dead tuples above) |

## Common Misconceptions

- **"A replica is a backup."** It copies mistakes too: a `DROP TABLE` on the primary arrives on the replica within milliseconds. A replica is availability, not recovery.
- **"Synchronous replication means the replica always shows my write."** Only `remote_apply` does; `on` means the WAL is flushed there, not replayed.
- **"Promoting a replica is safe to do while the old primary is up."** Both accept writes and the timelines diverge.
- **"Logical replication replicates the schema."** It does not; the row for the new column stalled the apply worker.
- **"Streaming replication needs a lot of configuration."** On PostgreSQL 18 the defaults suffice; the missing pieces are a role and a `pg_hba.conf` line.
