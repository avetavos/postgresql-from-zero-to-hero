A surprising amount of production trouble traces back to one fact: in PostgreSQL, every client connection is backed by its own operating-system process on the server. A few connections cost almost nothing. A few thousand cost a great deal of memory and scheduling overhead, and the server slows to a crawl long before it runs out of useful work to do.

**Connection pooling** fixes this by putting a small middleman between your applications and the database. The pooler keeps a modest number of real server connections open and hands them out to clients as needed, so the database only ever deals with a handful of connections no matter how many clients exist.

Everything below was run for real on **PostgreSQL 18.6** and **PgBouncer 1.26.0** (aarch64, Docker Desktop on a Mac, September 2026). The lab is three containers on an `--internal` Docker network — a database limited to 768 MB and 4 CPUs, a client container for `psql` and `pgbench`, and PgBouncer — all named `postgresql-b3-*` and removed at the end. The PgBouncer project publishes no official image, so the lab builds one from the PostgreSQL apt repository. `<your-password>` stands for any value you choose. Throughput numbers are from this Mac and only their proportions carry over; the sizing experiment repeats each measurement three times to show the noise.

## Why connections are heavy

When a client connects, the PostgreSQL postmaster forks a dedicated backend process to serve it. That process holds memory for caches, sort buffers, and bookkeeping, and the operating system must schedule it alongside every other backend. Idle connections still occupy a process. ## A pooler in the middle

A pooler such as **PgBouncer** sits between the clients and the server. Clients connect to the pooler, which is cheap to talk to, and the pooler maintains a small set of real connections to PostgreSQL. When a client needs the database, the pooler lends it a server connection, then takes it back so another client can reuse it.

export const poolDiagram = `flowchart LR
  Cli[Thousands of clients] -->|cheap client connections| Pool[PgBouncer pooler]
  Pool -->|few reused server connections| PG[(PostgreSQL)]`;

<Mermaid code={poolDiagram} title="Many clients share a few server connections through a pooler" />

The last block above is the same 200 clients, now through PgBouncer with a pool of 10. While the run was going, `SHOW POOLS` in the admin console showed 16 clients actively in a transaction, 184 waiting their turn, 10 server connections busy, and `pg_stat_activity` on the database confirmed exactly 10 server connections. All 200 clients were served, at about 56 000 transactions per second and 3.5 ms average latency. No client held a server connection while it was idle.

## Pooling modes

PgBouncer offers three modes that differ in *how long* a client keeps a borrowed server connection ([docs](https://www.pgbouncer.org/config.html)).

| Mode        | Server connection is returned after... | Notes                                              |
|-------------|-----------------------------------------|----------------------------------------------------|
| Session     | The client disconnects                  | Safest, but a connection is held for the whole session |
| Transaction | Each transaction commits or rolls back  | The common choice; great reuse with caveats         |
| Statement   | Each individual statement               | Most aggressive; forbids multi-statement transactions |

**Transaction mode** is the popular choice. A server connection is borrowed only for the duration of one transaction, so between transactions it is free for others. This gives excellent reuse for typical web traffic, where each request is a short transaction. The catch is that anything tied to a *session* rather than a transaction can break, because the next transaction may land on a different server connection. The PgBouncer feature map lists what does not work in transaction mode "by design": `SET`/`RESET`, `LISTEN`, `WITH HOLD` cursors, `PREPARE`/`DEALLOCATE`, `LOAD`, and session-level advisory locks ([docs](https://www.pgbouncer.org/features.html)).

## A minimal pgbouncer.ini

PgBouncer is configured with a small INI file. The essentials are which databases it fronts, where it listens, and the pooling mode. This is the file the lab uses; the `shopN` entries are the same database with different pool sizes, for the experiments below. `userlist.txt` holds the SCRAM verifier of the `app` role, and `admin_users` lets `app` open the admin console (the pseudo-database `pgbouncer`).

```ini
[databases]
shop   = host=postgresql-b3-db port=5432 dbname=shop
shop1  = host=postgresql-b3-db port=5432 dbname=shop pool_size=1
shop1b = host=postgresql-b3-db port=5432 dbname=shop pool_size=1
shop2  = host=postgresql-b3-db port=5432 dbname=shop pool_size=2
shop4  = host=postgresql-b3-db port=5432 dbname=shop pool_size=4
shop30 = host=postgresql-b3-db port=5432 dbname=shop pool_size=30
shop60 = host=postgresql-b3-db port=5432 dbname=shop pool_size=60

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt
admin_users = app
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 10
max_prepared_statements = 0
ignore_startup_parameters = extra_float_digits
```

Here `max_client_conn` is how many clients may connect to PgBouncer, while `default_pool_size` is how many real PostgreSQL connections it keeps per database and user (per-database `pool_size=` overrides it). The lab builds and starts everything like this:

## What breaks in transaction mode

Because a client keeps no server connection between transactions, session state can leak between clients or disappear. Three cases, all run on the alias `shop1`, whose pool has exactly one server connection, so every client is guaranteed to share it. (With a bigger pool the same bugs are intermittent, which is worse.)

```text
# each command is a separate client connection; the database alias shop1 has pool_size=1, so every client shares ONE server connection

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client psql -h postgresql-b3-pgbouncer -p 6432 -U app -d shop1 -c "SET app.tenant = 'alice'"
SET

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client psql -h postgresql-b3-pgbouncer -p 6432 -U app -d shop1 -c "SHOW app.tenant"    # a different client

-----------------------

-- database: script
SELECT locktype, objid, mode, granted FROM pg_locks WHERE locktype = 'advisory';
-- database: psql output
 locktype | objid |     mode      | granted

 advisory |    42 | ExclusiveLock | t
```

**`SET` leaks.** One client runs `SET app.tenant = 'alice'` and disconnects; a different client that just connected reads `alice`. A direct connection knows nothing about it. The safe forms are `SET LOCAL` or `set_config(name, value, true)` inside a transaction: the value lives until the transaction ends and the next client sees an empty setting.

**Advisory locks belong to the server connection.** Client one takes `pg_advisory_lock(42)` and leaves. A second client asks for the same lock and gets it (`t`), because it is the same backend, while a direct connection is refused (`f`) and `pg_locks` shows one lock held by nobody in particular. Use `pg_advisory_xact_lock` in transaction mode.

**Prepared statements.** Protocol-level prepared statements are what most drivers use by default, and a prepared statement lives on one server connection. Until PgBouncer 1.21 that made them unusable in transaction mode; since then PgBouncer tracks them and re-prepares on whichever server connection a client lands on, if you give it room with `max_prepared_statements` ([docs](https://www.pgbouncer.org/features.html)). The setting is 200 by default in 1.26; the lab file set it to 0 to show the failure. `pgbench -M prepared` uses the protocol-level extended query flow:

```text

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client sh -c 'psql -h postgresql-b3-pgbouncer -p 6432 -U app -d pgbouncer -Atc "SHOW CONFIG" | grep ^max_prepared_statements | cut -d"|" -f1,2'
max_prepared_statements|0

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client pgbench -h postgresql-b3-pgbouncer -p 6432 -U app -M prepared -c 20 -j 4 -T 4 -S shop    # distinct error messages, with counts

ERROR:  prepared statement "P_0" does not exist  (x17)
pgbench: error: Run was aborted; the above results are incomplete.

# max_prepared_statements = 100 in pgbouncer.ini, then RELOAD from the admin console

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client sh -c 'psql -h postgresql-b3-pgbouncer -p 6432 -U app -d pgbouncer -Atc "SHOW CONFIG" | grep ^max_prepared_statements | cut -d"|" -f1,2'
max_prepared_statements|100

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client pgbench -h postgresql-b3-pgbouncer -p 6432 -U app -M prepared -c 20 -j 4 -T 4 -S shop
```

With `max_prepared_statements = 0` the run aborts with `prepared statement "P_0" already exists` and `does not exist` — two clients on one server connection collide, or a client lands on a connection that never saw its statement. With `100` and a `RELOAD` of the config from the admin console, the same run completes with 0 failed transactions.

## Sizing the pool

`default_pool_size` should follow the database's capacity, not the client count. The same write-heavy `pgbench` run (60 clients, TPC-B-like, 8 s per run) against the database limited to 4 CPUs, direct and then through pools of increasing size:

```text
# the same TPC-B-like pgbench run (60 clients, 8 s each, three runs per line, database limited to 4 CPUs), direct first, then through pools of different sizes

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client pgbench -h postgresql-b3-db -U app -c 60 -j 4 -T 8 shop      (direct)    # three runs, tps: 7078, 6697, 6379

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client pgbench -h postgresql-b3-pgbouncer -p 6432 -U app -c 60 -j 4 -T 8 shop1      (pool_size=1)    # three runs, tps: 1350, 1250, 1429

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client pgbench -h postgresql-b3-pgbouncer -p 6432 -U app -c 60 -j 4 -T 8 shop2      (pool_size=2)    # three runs, tps: 2601, 2547, 2591

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client pgbench -h postgresql-b3-pgbouncer -p 6432 -U app -c 60 -j 4 -T 8 shop4      (pool_size=4)    # three runs, tps: 4231, 3409, 4055

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client pgbench -h postgresql-b3-pgbouncer -p 6432 -U app -c 60 -j 4 -T 8 shop      (pool_size=10)    # three runs, tps: 5708, 4300, 5439

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client pgbench -h postgresql-b3-pgbouncer -p 6432 -U app -c 60 -j 4 -T 8 shop30      (pool_size=30)    # three runs, tps: 6022, 5738, 6469

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client pgbench -h postgresql-b3-pgbouncer -p 6432 -U app -c 60 -j 4 -T 8 shop60      (pool_size=60)    # three runs, tps: 6492, 5709, 5738
```

Each line is three runs, so you can see the noise (about 10 percent). Throughput climbs almost linearly from 1 connection (about 1 300 transactions per second) to 2 (2 600) and 4 (about 3 900), a pool of 10 already reaches about 5 200, and 30 (about 6 100) and 60 (about 6 000) are no better than each other; the direct run with 60 connections was about 6 700. Once the CPUs are saturated, more server connections only add contention. What the pool buys you is not speed at the top, it is that the number stays bounded: 200 clients still ran on 10 connections. Where the knee is depends on your hardware and query mix; measure.

## Connecting through the pooler

From your application's point of view, the pooler looks just like PostgreSQL. You point your driver at the pooler's host and port — `6432` above instead of `5432` — and nothing else changes, except for the transaction-mode rules above. Each program below opens 10 client connections, runs 20 workers that execute the same parameterized query three times, and was run twice against a pool of just 2 server connections so that clients are forced to share: first with `max_prepared_statements = 0`, then with `100`.

    ```rust
    #[tokio::main]
    async fn main() -> Result<(), sqlx::Error> {
        let password = std::env::var("PGPASSWORD").unwrap();
        let pool = PgPoolOptions::new()
            .max_connections(10)
            .connect(&format!("postgres://app:{password}@127.0.0.1:6432/shop"))

        let mut tasks = Vec::new();

            if t.await.unwrap().is_ok() {

            }
    ```

## Reading AI-generated code

An assistant writes multi-tenant data access and, told the deployment uses PgBouncer in transaction mode, decides it is fine:

<SpotTheBug lang="python" code={`# AI comment: "transaction-mode PgBouncer is fine: set the tenant once when we get the connection"
def get_conn(tenant):
    conn = pool.getconn()
    conn.execute("SET app.tenant = %s", (tenant,))  # session-level setting
    return conn

def orders_for(conn):
    return conn.execute("SELECT * FROM orders WHERE tenant = current_setting('app.tenant')").fetchall()`}>

`SET` is a session-level command, and in transaction mode a session does not belong to the client. The setting sticks to the server connection and the next client that borrows it inherits the previous tenant — exactly the `alice` in the transcript above. With row-level security or a `WHERE tenant = current_setting(...)` filter that is a data leak between customers, and it does not fail loudly. The fix is to scope the setting to the transaction, as the `shop1b` run did: `set_config('app.tenant', value, true)` (or `SET LOCAL`) inside `BEGIN ... COMMIT`, and read the data in the same transaction. The next client sees an empty setting.

```python
def orders_for(conn, tenant):
    with conn.transaction():  # the setting lives exactly as long as this transaction
        conn.execute("SELECT set_config('app.tenant', %s, true)", (tenant,))
        return conn.execute("SELECT * FROM orders WHERE tenant = current_setting('app.tenant')").fetchall()
```

</SpotTheBug>

## Mental Model

A pooler is a taxi rank. Clients are passengers, server connections are the cabs, and a transaction is one ride. In transaction mode a passenger only holds a cab for the ride, so twenty cabs can serve thousands of passengers — but nothing you left inside the cab (a `SET`, a session lock, a prepared statement without support) is yours anymore when the ride ends.

## Tips / gotchas

- Transaction mode is the usual recommendation because it gives the best connection reuse for short web requests. Reach for session mode only when you genuinely need session continuity.
- In transaction mode, avoid features that span transactions on one connection — session `SET`, session advisory locks and `LISTEN`/`NOTIFY`. Prepared statements work in PgBouncer 1.21 and later with a non-zero `max_prepared_statements`.
- A pooler does not replace the driver's own connection pool; you can run both, but size them so the driver never asks for more than the pooler can supply.
- Set `default_pool_size` based on your server's capacity (cores, not clients), and remember the pooler's own server connections count against `max_connections` too.
- Use `SHOW POOLS` and `SHOW STATS` on the admin console to see waiting clients (`cl_waiting`) before users tell you.
- Keep database credentials out of the images; the lab used a throw-away password on an internal network.

<Callout title="Idle is the enemy">
The core insight of pooling is that most application connections sit idle most of the time, yet each idle PostgreSQL connection still costs a process. A pooler lets those idle moments be shared. You are not adding capacity to the database — you are stopping clients from hoarding it while they have nothing to do.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| Transaction-mode pooling (PgBouncer) | Far more clients per real PostgreSQL connection (200 clients on 10) | Session-level features (`SET`, session advisory locks, `LISTEN`) break; prepared statements need `max_prepared_statements` and a recent PgBouncer |
| Session-mode pooling / no pooler at all | Full support for session-level features, a straightforward connection | PostgreSQL connections are expensive and limited (about 3 MB each, hard cap at `max_connections`) |
| A bigger pool | Fewer clients waiting | Past the CPU count more server connections stop adding throughput (30 vs 60 above) |

## Common Misconceptions

- **"A pooler makes the database faster."** It bounds the connection count; throughput at the top was about the same with or without it.
- **"Raising max_connections solves 'too many clients'."** It creates more processes at about 3 MB each and more contention; a pooler solves it.
- **"Prepared statements do not work with PgBouncer."** That was true before 1.21; with `max_prepared_statements` above zero they do.
- **"Transaction mode is safe if my code opens transactions."** Only if nothing depends on session state; a plain `SET` outside `BEGIN` leaked to another client.
- **"Pool size should equal client count."** It should follow the server's capacity; 60 server connections were no better than 30.
