The last two operational duties are the ones you hope never to need and cannot afford to skip. **Backups** let you rebuild after a disk failure, a bad deploy, or a mistaken `DELETE`. **Security** controls who may connect, who may see what, and how the data travels over the network. A database that is fast and highly available is still a liability if it cannot be restored or if anyone on the internet can read it.

This lesson covers both families of backup PostgreSQL offers, then walks down the layers of access control from the network edge to individual rows. Everything was run for real on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). The backup and network-security parts use one container started with `--network none` (it has no network at all; connections go over its own loopback) and named volumes `postgresql-b3-*`, all removed at the end. The role and row-level-security parts are `sql` fences run in one empty database. `<your-password>` stands for any value you choose.

## Two kinds of backup

PostgreSQL backups come in two styles that suit different needs.

| Type     | Tool                          | What it captures                        | Best for                          |
|----------|-------------------------------|-----------------------------------------|-----------------------------------|
| Logical  | `pg_dump` / `pg_restore`      | SQL or an archive of one database       | Single databases, version moves   |
| Physical | base backup + WAL archiving   | The whole cluster's files, byte-for-byte| Large clusters, point-in-time recovery |

The lab: one database with archiving switched on. `archive_command` copies each finished WAL segment to a volume that outlives the server; `summarize_wal` (needed for incremental backups) is on too.

```bash
# scripts/backup-lab.sh
docker volume create postgresql-b3-pgdata
docker volume create postgresql-b3-archive
docker volume create postgresql-b3-backup
# the archive and backup volumes must be writable by the postgres user
docker run --rm --user root -v postgresql-b3-archive:/archive -v postgresql-b3-backup:/backup \
  postgres:18.6 chown postgres:postgres /archive /backup

docker run -d --name postgresql-b3-pg --network none --memory 768m --cpus 4 \
  -e POSTGRES_PASSWORD=<your-password> \
  -v postgresql-b3-pgdata:/var/lib/postgresql -v postgresql-b3-archive:/archive -v postgresql-b3-backup:/backup \
  postgres:18.6 \
  -c archive_mode=on -c 'archive_command=test ! -f /archive/%f && cp %p /archive/%f' -c summarize_wal=on
```

### Logical backups

A logical backup runs `pg_dump`, which reads a database and writes out the statements needed to recreate it. It is portable across machines and even across major versions, which makes it ideal for moving or cloning a single database ([docs](https://www.postgresql.org/docs/18/app-pgdump.html)). It captures one database only; roles and other cluster-wide objects come from `pg_dumpall --globals-only`. The custom format is compressed and lets `pg_restore` select parts and run in parallel; the same database as plain SQL is four and a half times larger here.

```text
$ docker exec --user postgres postgresql-b3-pg pg_dump --format=custom --file=/backup/shop.dump shop

$ docker exec --user postgres postgresql-b3-pg sh -c "pg_dump shop | wc -c; ls -l /backup/shop.dump | awk '{print $5, $9}'"    # plain SQL bytes, then the custom-format file
4559583
1006636 /backup/shop.dump

$ docker exec --user postgres postgresql-b3-pg pg_restore --list /backup/shop.dump | head -12
;
; Archive created at 2026-09-30 08:42:43 UTC
;     dbname: shop
;     TOC Entries: 9
;     Compression: gzip
;     Dump Version: 1.16-0
;     Format: CUSTOM
;     Integer: 4 bytes
;     Offset: 8 bytes
;     Dumped from database version: 18.6 (Debian 18.6-1.pgdg13+2)
;     Dumped by pg_dump version: 18.6 (Debian 18.6-1.pgdg13+2)
;

# --create names the database to CONNECT to first; the database restored is the one in the dump

$ docker exec --user postgres postgresql-b3-pg pg_restore --dbname=shop_restored --create /backup/shop.dump    # shop_restored does not exist yet
pg_restore: error: connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed: FATAL:  database "shop_restored" does not exist

$ docker exec --user postgres postgresql-b3-pg createdb shop_restored

$ docker exec --user postgres postgresql-b3-pg pg_restore --dbname=shop_restored --jobs=2 /backup/shop.dump

$ docker exec --user postgres postgresql-b3-pg psql -d shop -Atc "SELECT count(*), sum(amount) FROM orders"
200000|9900000

$ docker exec --user postgres postgresql-b3-pg psql -d shop_restored -Atc "SELECT count(*), sum(amount) FROM orders"
200000|9900000

# restoring INTO the cluster under the dump's own name: drop the original, then --create with a maintenance database

$ docker exec --user postgres postgresql-b3-pg dropdb shop

$ docker exec --user postgres postgresql-b3-pg pg_restore --dbname=postgres --create /backup/shop.dump

$ docker exec --user postgres postgresql-b3-pg psql -d shop -Atc "SELECT count(*), sum(amount) FROM orders"
200000|9900000
```

Two lessons in the transcript. The dump and the restored copy agree on count and sum, which is the kind of check a restore drill should run. And `--create` does not mean "restore into a new database of the name I give": `--dbname` names the database to *connect to first* (it must exist), and the database that gets created is the one named in the dump. The first attempt failed because `shop_restored` did not exist; the working forms are either `createdb` + restore without `--create`, or `--dbname=postgres --create` after dropping the original.

### Physical backups and point-in-time recovery

For a large or busy cluster, dumping logically is too slow. Instead you take a **base backup** — a byte-level copy of the data files — and continuously archive the write-ahead log. Replaying the WAL on top of the base backup lets you restore to any moment in time, known as **point-in-time recovery** (PITR, [docs](https://www.postgresql.org/docs/18/continuous-archiving.html)).

export const backupDiagram = `flowchart LR
  PG[(Primary cluster)] -->|pg_basebackup| Base[Base backup]
  PG -->|archive_command| WAL[Archived WAL segments]
  Base --> Restore[Restore]
  WAL -->|replay to a chosen time| Restore
  Restore --> Recovered[(Recovered cluster)]`;

<Mermaid code={backupDiagram} title="Base backup plus archived WAL enables point-in-time recovery" />

`pg_basebackup` takes the base backup, and `pg_verifybackup` checks it against the manifest it wrote. PostgreSQL 17 added **incremental** backups: after a full backup, a second one copies only the blocks that changed (this is what `summarize_wal` records), and `pg_combinebackup` merges the chain back into a full backup ([release notes](https://www.postgresql.org/docs/17/release-17.html), [docs](https://www.postgresql.org/docs/18/app-pgcombinebackup.html)).

```text
$ docker exec --user postgres postgresql-b3-pg pg_basebackup --pgdata=/backup/full --checkpoint=fast --verbose

pg_basebackup: write-ahead log end point: 0/7000120
pg_basebackup: waiting for background process to finish streaming ...
pg_basebackup: syncing data to disk ...
pg_basebackup: renaming backup_manifest.tmp to backup_manifest
pg_basebackup: base backup completed

$ docker exec --user postgres postgresql-b3-pg pg_verifybackup /backup/full

SELECT count(*) AS orders FROM orders;
-- database: psql output

# an incremental backup: only the blocks changed since the full one (needs summarize_wal = on)

$ docker exec --user postgres postgresql-b3-pg pg_basebackup --pgdata=/backup/incr1 --incremental=/backup/full/backup_manifest --checkpoint=fast

$ docker exec --user postgres postgresql-b3-pg du -sh /backup/full /backup/incr1
```

The incremental backup is 30 MB against 88 MB for the full one, after adding 50 003 rows to a 200 000-row table; the combined result verifies like any base backup.

It fetched segments 7 through B from the archive, replayed them, and stopped *before the commit of transaction 773*, the `DELETE`, whose commit time was after our target. The restored server is no longer in recovery, and `orders` holds 250 003 rows: the 200 000 from the backup plus the 3 and the 50 000 written afterwards. Only the mistake is missing. That is the point of PITR: a backup alone would have given 200 000 rows and lost the later work.

Three cautions. `archive_command` must report failure honestly (`test ! -f ... && cp ...` refuses to overwrite an existing file); if it keeps failing, WAL piles up on the primary until its disk fills. A backup and its WAL must be stored somewhere the primary's failure cannot take with it. And none of this is a backup until a restore has been done from it, which is what this transcript is.

**In pgAdmin:** the Tools menu has Backup and Restore dialogs that run `pg_dump` and `pg_restore` for you; the physical backup and PITR flow above is done from the command line.

## Security in layers

Access control in PostgreSQL is best pictured as a series of gates a request passes through: first the network, then authentication, then role privileges, and finally row-level rules. Each layer can stop a request the previous one let through.

export const securityDiagram = `flowchart LR
  Client[Client] -->|encrypted with TLS| HBA["pg_hba.conf - who may connect"]
  HBA --> Auth[Authenticate the role]
  Auth --> Priv["Role privileges - GRANT and REVOKE"]
  Priv --> RLS[Row-level security policy]
  RLS --> Data[(Table rows)]`;

<Mermaid code={securityDiagram} title="A connection passes through network, auth, privilege, and row gates" />

### The network gate: pg_hba.conf and TLS

The first gate is `pg_hba.conf` (host-based authentication). Each line says which roles may connect to which databases from which addresses, and how they must authenticate. Rules are read top to bottom, and **the first match wins** ([docs](https://www.postgresql.org/docs/18/auth-pg-hba-conf.html)). Passwords are stored as SCRAM verifiers by default (`password_encryption = scram-sha-256`); the stored value starts with `SCRAM-SHA-256$`:

```text
-- database: script
SHOW password_encryption;
CREATE ROLE app LOGIN PASSWORD '<your-password>';
SELECT rolname, left(rolpassword, 14) AS stored_as FROM pg_authid WHERE rolname = 'app';
-- database: psql output
 password_encryption 
---------------------
 scram-sha-256
(1 row)

CREATE ROLE
 rolname |   stored_as    
---------+----------------
 app     | SCRAM-SHA-256$
(1 row)

# 1. first match wins: the reject line for app comes before the general rule

# pg_hba.conf (reject before allow):
local   all   all                    trust
host    all   app   127.0.0.1/32      reject
host    all   all   127.0.0.1/32      scram-sha-256

$ docker exec --user postgres postgresql-b3-pg psql "host=127.0.0.1 user=app dbname=shop" -Atc "SELECT current_user AS connected_as"
psql: error: connection to server at "127.0.0.1", port 5432 failed: FATAL:  pg_hba.conf rejects connection for host "127.0.0.1", user "app", database "shop", no encryption

# pg_hba.conf (allow app first):
local   all   all                    trust
host    all   app   127.0.0.1/32      scram-sha-256
host    all   all   127.0.0.1/32      reject

$ docker exec --user postgres postgresql-b3-pg psql "host=127.0.0.1 user=app dbname=shop" -Atc "SELECT current_user AS connected_as"
app

$ docker exec --user postgres postgresql-b3-pg psql "host=127.0.0.1 user=postgres dbname=shop" -Atc "SELECT 1"
psql: error: connection to server at "127.0.0.1", port 5432 failed: FATAL:  pg_hba.conf rejects connection for host "127.0.0.1", user "postgres", database "shop", no encryption
```

With the reject line first, `app` is refused even though the rule below would have allowed it; with the allow line first, `app` gets in, and now *everyone else*, `postgres` included, hits the reject line, since it also matches. The error text names the rule that fired: `pg_hba.conf rejects connection`. An order mistake in this file is a common way to lock yourself out, so keep a local socket line for the administrator.

The `hostssl` keyword requires the connection to be encrypted with **TLS**, which you enable by pointing PostgreSQL at a certificate and key. The lab makes a self-signed certificate that lives for a day; a real server uses one from your certificate authority. With only a `hostssl` line for `app`, an unencrypted attempt falls through to the reject line, and an encrypted one is accepted:

```text

$ docker exec --user postgres postgresql-b3-pg sh -c "cd /var/lib/postgresql/18/docker && openssl req -new -x509 -nodes -days 1 -subj '/CN=localhost' -keyout server.key -out server.crt && chmod 600 server.key"

-- database: script
ALTER SYSTEM SET ssl = on;
SELECT pg_reload_conf();
-- database: psql output
ALTER SYSTEM
 pg_reload_conf 
----------------
 t
(1 row)

# pg_hba.conf (hostssl only for app):
local   all   all                    trust
hostssl all   app   127.0.0.1/32      scram-sha-256
host    all   all   127.0.0.1/32      reject

$ docker exec --user postgres postgresql-b3-pg psql "host=127.0.0.1 user=app dbname=shop sslmode=disable" -Atc "SELECT current_user AS connected_as"
psql: error: connection to server at "127.0.0.1", port 5432 failed: FATAL:  pg_hba.conf rejects connection for host "127.0.0.1", user "app", database "shop", no encryption

$ docker exec --user postgres postgresql-b3-pg psql "host=127.0.0.1 user=app dbname=shop sslmode=require" -Atc "SELECT ssl, version AS tls_version FROM pg_stat_ssl WHERE pid = pg_backend_pid()"
```

### Roles and privileges: GRANT and REVOKE

Once connected, what a role may do is governed by privileges. You create roles, then `GRANT` specific rights and `REVOKE` them. The guiding principle is **least privilege**: give each role only what it needs. The fences below use three roles without login (so they can be switched into with `SET ROLE`): an owner of the tables, a reporting role and the application.

```sql
-- sql/setup.sql
CREATE ROLE shop_owner NOLOGIN;      -- owns the tables
CREATE ROLE shop_reporting NOLOGIN;  -- read-only reports
CREATE ROLE shop_app NOLOGIN;        -- the application
GRANT CREATE ON SCHEMA public TO shop_owner;

SET ROLE shop_owner;
CREATE TABLE orders (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id bigint NOT NULL,
  item      text NOT NULL,
  amount    numeric NOT NULL
);
INSERT INTO orders (tenant_id, item, amount) VALUES (1, 'lamp', 30), (1, 'desk', 200), (2, 'chair', 80);
RESET ROLE;
```

Since PostgreSQL 15, ordinary roles can no longer create objects in the `public` schema by default; the application role cannot even create a table until someone grants it the right:

```sql
-- @expect-error 42501
SET ROLE shop_app;
CREATE TABLE sneaky (x int);
RESET ROLE;
```

```text
SET
ERROR:  permission denied for schema public
LINE 1: CREATE TABLE sneaky (x int);
                     ^
RESET
```

Now the read-only reporting role and the application role get exactly what they need, and the reporting role cannot change anything:

```sql
-- sql/grants.sql
GRANT USAGE ON SCHEMA public TO shop_reporting, shop_app;
GRANT SELECT ON orders TO shop_reporting;
GRANT SELECT, INSERT, UPDATE ON orders TO shop_app;

SET ROLE shop_reporting;
SELECT count(*) AS reporting_sees FROM orders;
RESET ROLE;
```

```text
GRANT
GRANT
GRANT
SET
 reporting_sees 
----------------
              3
(1 row)

RESET
```

```sql
-- @expect-error 42501
SET ROLE shop_reporting;
DELETE FROM orders WHERE id = 1;
RESET ROLE;
```

```text
SET
ERROR:  permission denied for table orders
RESET
```

One trap: `GRANT SELECT ON ALL TABLES` covers the tables that exist now, not the ones created later. A new table is unreadable until it is granted; `ALTER DEFAULT PRIVILEGES` fixes the future:

```sql
-- sql/refunds.sql
SET ROLE shop_owner;
CREATE TABLE refunds (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, order_id bigint NOT NULL);
RESET ROLE;
```

```sql
-- @expect-error 42501
SET ROLE shop_reporting;
SELECT count(*) FROM refunds;
RESET ROLE;
```


```sql
-- sql/default-privileges.sql

SET ROLE shop_owner;
CREATE TABLE payouts (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, amount numeric NOT NULL);
RESET ROLE;

SET ROLE shop_reporting;
SELECT count(*) AS payouts_readable FROM payouts;
RESET ROLE;
```

### Row-level security

Privileges control whole tables. **Row-level security** (RLS) goes finer, letting a policy decide which *rows* a role may see or change — the foundation of multi-tenant systems where each tenant must see only its own data ([docs](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)). The policy below compares each row's `tenant_id` with a setting the application chooses for its session.

```sql
-- sql/rls.sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;   -- run as the owner in real life; the superuser session here is equivalent
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id')::bigint);
```

With the setting missing, the first query does not silently return nothing, it fails:

```sql
-- @expect-error 42704
SET ROLE shop_app;
SELECT count(*) FROM orders;
RESET ROLE;
```

```text
SET
ERROR:  unrecognized configuration parameter "app.tenant_id"
RESET
```

With `app.tenant_id = 1` the application role sees only tenant 1's rows, and it cannot insert a row for another tenant (the policy's condition also applies to new rows):

```sql
-- sql/rls-tenant.sql
SET app.tenant_id = 1;
SET ROLE shop_app;
SELECT id, item FROM orders ORDER BY id;
RESET ROLE;
```

```text
SET
```

Two more details of a policy that fails safely. After a custom setting has been used in a session, `RESET` leaves it as an empty string, and `''::bigint` is an error rather than "no tenant":

```sql
-- @expect-error 22P02

RESET app.tenant_id;   -- the setting now exists, with an empty string as its value
SET ROLE shop_app;
SELECT count(*) FROM orders;
RESET ROLE;
```

```text
ERROR:  invalid input syntax for type bigint: ""
RESET
```

So write the policy to fail closed: `current_setting(name, true)` returns NULL when the setting does not exist, `nullif(..., '')` turns the empty string into NULL, and a comparison with NULL matches no row. ## Mental Model

A backup is a time machine, and the WAL archive is the film that runs between snapshots. A dump is a photograph of one room; a base backup plus WAL is a recording of the whole building that you can rewind to any second. Security is a series of doors, each one narrower than the last: the network line decides who may knock, the role decides which rooms they may enter, and row-level security decides which shelves they may look at. Doors are checked in order, and the first rule that fits decides.

## Tips / gotchas

- A backup is only real once you have restored it successfully. Schedule regular test restores into a throwaway database and compare counts, as the lab did.
- Logical dumps are portable and great for single databases; physical base backups plus WAL archiving are what you need for large clusters and point-in-time recovery. `pg_dump` does not include roles; `pg_dumpall --globals-only` does.
- Note the exact restore target time before any risky operation, or create a named restore point with `pg_create_restore_point()`.
- Apply least privilege everywhere. The application role should not own the schema or be able to drop tables, and reporting should be read-only.
- Never use `trust` authentication on any address reachable from outside the host — it lets anyone connect as any role with no password.
- Require TLS for connections that cross a network with `hostssl`, and remember that `pg_hba.conf` rules are matched top to bottom, first match wins.
- Connect the application as a role that does not own the tables and does not have `BYPASSRLS`, or RLS will not apply to it.

<Callout title="Defence in depth">
No single control is enough. The network gate keeps strangers out, authentication proves identity, role privileges limit actions, and row-level security limits visibility. Backups sit beneath all of it as the final safety net. Operate as though each layer will occasionally fail, and make sure the next one still protects you.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| Logical backup (`pg_dump`) | Portable, selective, a 1 MB archive for a 200 000-row table | One database at a time, restores by replaying SQL, no point-in-time |
| Physical backup + WAL archive | Any point in time (the restore stopped before the `DELETE`), whole cluster | Same major version, more moving parts, the archive must never fail |
| Incremental backups | 30 MB instead of 88 MB | Needs `summarize_wal` and a chain to combine before restore |
| RLS with a strict policy | Isolation enforced by the database | Owners and `BYPASSRLS` roles skip it; missing settings error out unless the policy is written to fail closed |
| Relying on replication alone for durability | Fast failover, high availability | A replica is not a backup — it copies mistakes and deletions too |

## Common Misconceptions

- **"A backup exists, so I am safe."** Only a restore proves it; the lab ran one and compared the counts.
- **"pg_restore --create restores into the database I name with --dbname."** It connects there and creates the database named in the dump.
- **"Replication is a backup."** The `DELETE` would have reached every replica within milliseconds.
- **"RLS protects every connection."** Not the owner, not superusers, not `BYPASSRLS` roles; the owner saw 3 rows against the policy's 2.
- **"GRANT SELECT ON ALL TABLES covers future tables."** The new `refunds` table was unreadable until `ALTER DEFAULT PRIVILEGES`.
