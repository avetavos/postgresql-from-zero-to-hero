A `GROUP BY` collapses many rows into one summary row, and that is sometimes exactly wrong: you want the summary *and* the original detail side by side. Window functions do that. A window function looks at a set of rows related to the current row, its *window*, and computes a value, but it leaves every row in the output. That is how you add a rank, a running total, or a per-group average as an extra column without losing any detail.

Everything below was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026), copied from `psql`. The `sql` fences run top to bottom in one empty database; timings are from this Mac.

## The OVER clause

You turn an ordinary function into a window function by adding an `OVER` clause. Inside it, `PARTITION BY` divides the rows into groups (like `GROUP BY`, but without collapsing them), and `ORDER BY` sets the order within each partition. First, a plain aggregate over a window: each sale next to the total of its region.

Look at the West tie (400 and 400):

- `row_number()` never repeats: 1 and 2. **Which** of the two tied rows gets 1 is not defined by the query. Here Tidal Notes got 1 and Quiet Harbors 2; a different plan could swap them. Add a tiebreaker to the window `ORDER BY` whenever the number must be reproducible.

- `dense_rank()` gives both 1 and does not skip: the next is 2.

## Running totals and the default frame

A window with an `ORDER BY` has a **frame**: the subset of the partition the function sees. If you do not write one, the default frame is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, which includes every *peer* of the current row, meaning all rows that sort equal to it. With unique sort values that behaves like "everything up to this row". With a tie it does not:

```sql
-- sql/running-total-default.sql
-- default frame: RANGE ... CURRENT ROW, which includes all peers (rows with an equal ORDER BY value)
SELECT s.region, b.title, s.copies,
       sum(s.copies) OVER (PARTITION BY s.region ORDER BY s.copies DESC) AS running_default
FROM sales AS s
JOIN books AS b ON b.id = s.book_id
ORDER BY s.region, s.copies DESC, b.title;
```

```text
 region |       title       | copies | running_default 
--------+-------------------+--------+-----------------
 East   | The Glass Orchard |    900 |             900
 East   | Tidal Notes       |    200 |            1100
 East   | Quiet Harbors     |     50 |            1150
 West   | Quiet Harbors     |    400 |             800
 West   | Tidal Notes       |    400 |             800
 West   | The Glass Orchard |    150 |             950
(6 rows)
```

West shows **800, 800, 950**, not 400, 800, 950: both 400 rows are peers, so each already "sees" the other. That is a wrong running total, silently. Spell the frame out with `ROWS`, and add a tiebreaker so the order is defined:

`ROWS`, `RANGE` and `GROUPS` measure the frame differently. On the six sales sorted by `copies`, a one-step-back frame gives three different sums for the same rows: `ROWS` counts physical rows, `RANGE` counts by value distance (here: rows whose `copies` is within 100 below the current one), `GROUPS` counts groups of peers ([docs](https://www.postgresql.org/docs/18/sql-expressions.html#SYNTAX-WINDOW-FUNCTIONS)):

```sql
-- sql/frames.sql
-- the same 6 rows, ordered by copies, under the three frame modes
SELECT copies,
       sum(copies) OVER (ORDER BY copies ROWS   BETWEEN 1 PRECEDING AND CURRENT ROW) AS rows_frame,
       sum(copies) OVER (ORDER BY copies RANGE  BETWEEN 100 PRECEDING AND CURRENT ROW) AS range_frame,
       sum(copies) OVER (ORDER BY copies GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW) AS groups_frame
FROM sales
ORDER BY copies, id;
```

```text
 copies | rows_frame | range_frame | groups_frame 
--------+------------+-------------+--------------
     50 |         50 |          50 |           50
    150 |        200 |         200 |          200
    200 |        350 |         350 |          350
    400 |        600 |         800 |         1000
    400 |        800 |         800 |         1000
    900 |       1300 |         900 |         1700
(6 rows)
```

### first_value and last_value

The same default frame catches `last_value`. With `ORDER BY` and no frame, the frame stops at the current row (and its peers), so "the last value" is just the current one:

```sql
-- sql/last-value-trap.sql
SELECT region, copies,
       last_value(copies) OVER (PARTITION BY region ORDER BY copies DESC) AS last_default,
       last_value(copies) OVER (
         PARTITION BY region ORDER BY copies DESC
         ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS last_real,
       first_value(copies) OVER (PARTITION BY region ORDER BY copies DESC) AS first_val
FROM sales
ORDER BY region, copies DESC, id;
```

```text
 region | copies | last_default | last_real | first_val 
--------+--------+--------------+-----------+-----------
 East   |    900 |          900 |        50 |       900
 East   |    200 |          200 |        50 |       900
 East   |     50 |           50 |        50 |       900
 West   |    400 |          400 |       150 |       400
 West   |    400 |          400 |       150 |       400
 West   |    150 |          150 |       150 |       400
(6 rows)
```

`last_default` equals `copies` on every row. `last_real`, with `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`, is really the smallest sale of the region (50 and 150).

## LAG, LEAD, NTILE and friends

`lag` and `lead` read a column from the previous and next row of the window: no self-join needed. The first and last rows have nothing to read, so they get `NULL`:

```sql
-- sql/lag-lead.sql
SELECT title, published,
       lag(title)  OVER (ORDER BY published) AS previous_title,
       lead(title) OVER (ORDER BY published) AS next_title,
       published - lag(published) OVER (ORDER BY published) AS years_since_previous
FROM books
ORDER BY published;
```

```text
       title       | published |  previous_title   |    next_title     | years_since_previous 
-------------------+-----------+-------------------+-------------------+----------------------
 Quiet Harbors     |      2003 |                   | Tidal Notes       |                     
 Tidal Notes       |      2011 | Quiet Harbors     | The Glass Orchard |                    8
 The Glass Orchard |      2018 | Tidal Notes       | Unlinked Draft    |                    7
 Unlinked Draft    |      2020 | The Glass Orchard |                   |                    2
(4 rows)
```

`ntile(n)` cuts the ordered rows into `n` buckets, and `percent_rank()` gives a row's relative position (0 for the first, 1 for the last):

```sql
-- sql/ntile-percent.sql
SELECT title, copies_sold,
       ntile(2)       OVER (ORDER BY copies_sold DESC) AS half,
       percent_rank() OVER (ORDER BY copies_sold)      AS pct_rank
FROM books
ORDER BY copies_sold DESC;
```

```text

-------------------+-------------+------+--------------------

(4 rows)
```

## Windows keep rows; GROUP BY collapses them

A window function is evaluated after `WHERE`, `GROUP BY` and `HAVING`, just before `ORDER BY` and `LIMIT`. That has a consequence: you cannot filter on a window function in `WHERE`, because at that point it does not exist yet:

```sql
-- @expect-error 42P20
SELECT region, copies FROM sales
WHERE rank() OVER (PARTITION BY region ORDER BY copies DESC) = 1;
```

```text
ERROR:  window functions are not allowed in WHERE
LINE 2: WHERE rank() OVER (PARTITION BY region ORDER BY copies DESC)...
              ^
```

To filter on a rank (the classic "top one per group"), compute it in a subquery or CTE, then filter outside:

```sql
-- sql/top-n-per-group.sql
SELECT region, title, copies
FROM (
  SELECT s.region, b.title, s.copies,
         row_number() OVER (PARTITION BY s.region ORDER BY s.copies DESC, b.title) AS rn
  FROM sales s JOIN books b ON b.id = s.book_id
) AS ranked
WHERE rn = 1
ORDER BY region;
```

```text
 region |       title       | copies 
--------+-------------------+--------
 East   | The Glass Orchard |    900
 West   | Quiet Harbors     |    400
(2 rows)
```

A window function is a `WindowAgg` node fed by a `Sort` on `(region, copies DESC)`: the sort is the price of `PARTITION BY ... ORDER BY`, and here it dominates (the `Sort` node accounts for about 460 ms of the 560 ms; `Sort Method: external merge  Disk: 12728kB` because the 12 MB sort does not fit in the default `work_mem` of 4 MB, and the `temp read/written` buffers confirm it). Raising `work_mem` for one transaction removes the spill:

```sql
-- sql/window-plan-work-mem.sql
BEGIN;
SET LOCAL work_mem = '64MB';
EXPLAIN (ANALYZE, COSTS OFF)
SELECT id, region, copies,
       row_number() OVER (PARTITION BY region ORDER BY copies DESC) AS rn
FROM big_sales;
ROLLBACK;
```

When you only want the top rows of each partition, PostgreSQL 15+ can stop early. The `WHERE rn <= 3` on the outside appears as a `Run Condition` on the `WindowAgg`, and the node emits 15 rows (3 per region) instead of 500 000:

```sql
-- sql/window-plan-top3.sql
EXPLAIN (ANALYZE, COSTS OFF)
SELECT * FROM (
  SELECT id, region, copies,
         row_number() OVER (PARTITION BY region ORDER BY copies DESC) AS rn
  FROM big_sales
) AS ranked
WHERE rn <= 3;
```

## Reading AI-generated code

An assistant is asked for a running total of copies per region, biggest sale first, and writes the version every tutorial writes:

<SpotTheBug lang="sql" code={`-- AI comment: "running total of copies per region, biggest sale first"
SELECT region, copies,
       SUM(copies) OVER (PARTITION BY region ORDER BY copies DESC) AS running_total
FROM sales
ORDER BY region, copies DESC;`}>

It looks right, and East is right. West is wrong: with the default `RANGE` frame the two 400 rows are peers, so both show **800** and the running total never passes through 400. Nothing errors:

```sql
-- sql/stb-wrong.sql
SELECT region, copies,
       SUM(copies) OVER (PARTITION BY region ORDER BY copies DESC) AS running_total
FROM sales
ORDER BY region, copies DESC;
```

```text

 East   |    900 |           900

 East   |     50 |          1150
 West   |    400 |           800
 West   |    400 |           800
 West   |    150 |           950
```

Two changes fix it: a tiebreaker in `ORDER BY` so the order is total, and an explicit `ROWS` frame so each row sees only itself and the rows before it.

```sql
-- sql/stb-fixed.sql
SELECT region, copies,
       SUM(copies) OVER (
         PARTITION BY region
         ORDER BY copies DESC, id
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM sales
ORDER BY region, copies DESC, id;
```

```text
 region | copies | running_total 
--------+--------+---------------
 East   |    900 |           900
 East   |    200 |          1100
 East   |     50 |          1150
 West   |    400 |           400
 West   |    400 |           800
 West   |    150 |           950
(6 rows)
```

## Mental Model

A window function computes a value for each row by looking at a *frame* of rows around it, then puts the value back next to that row. Three settings define what it sees: `PARTITION BY` (which rows are even related), `ORDER BY` (in what order), and the frame (how far to look inside that order). The frame has an implicit default, and that default is `RANGE ... CURRENT ROW`, which includes peers. Whenever a wrong number comes out of a window function, the first suspect is the frame.

## Tips / gotchas

- The window function's `OVER` is what makes it a window function: `sum(x)` alone is an aggregate, `sum(x) OVER (...)` is a window.
- You cannot use a window function in `WHERE` (`42P20`), `GROUP BY` or `HAVING`. Wrap the query in a subquery or CTE and filter outside.
- With `ORDER BY` and no explicit frame, the frame is `RANGE ... CURRENT ROW` (peers included). Write `ROWS BETWEEN ...` for running totals and `last_value`.
- `row_number()` on ties is arbitrary; add a tiebreaker to the window `ORDER BY` if you need stable numbering.
- `PARTITION BY ... ORDER BY` costs a sort. Check `EXPLAIN` on big tables, watch for `external merge` spills, and see whether an index can provide the order.

<Callout title="Window or GROUP BY?">
Need one row per group? `GROUP BY`. Need every row plus something computed across a group (rank, running total, share of the group, previous row)? A window function. Need both? Aggregate first in a subquery and window over the result.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| Window function | Keeps every row; no self-join for rank, running total, lag | Needs a sort per distinct `PARTITION BY`/`ORDER BY` (the sort is about 460 ms of 560 ms above); default frame surprises |
| `GROUP BY` + join back | Works everywhere, explicit | Two passes and a join to reattach the totals |
| Correlated subquery per row | Simple to read for one number | Re-runs per row (see the subqueries lesson) |
| Application-side ranking | Flexible | Pulls all rows over the network |

## Common Misconceptions

- **"SUM() OVER (ORDER BY x) is a row-by-row running total."** With duplicates in `x` it is a running total over peers: 800, 800, 950 above.
- **"last_value gives the last row of the partition."** Only with a frame that reaches the end. By default it returns the current row.
- **"row_number() breaks ties in a stable way."** The tie order is undefined unless you add a tiebreaker.
- **"Window functions are free."** Each distinct window needs a sort; the 500 000-row example spilled to disk at the default `work_mem`.
- **"I can filter on a rank in WHERE."** It is evaluated after `WHERE`; use a subquery or CTE.
