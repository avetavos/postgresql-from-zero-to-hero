## NULL and empty groups

Aggregates skip `NULL` inputs (except `count(*)`, which counts rows). So `avg(author_id)` is the average of the three non-`NULL` values, not of four. And an aggregate over **zero rows** is `NULL` for `sum`, `avg`, `min`, `max`, while `count` is `0`:

```sql
-- sql/aggregate-nulls.sql
-- books.author_id is NULL for one of the four books
SELECT count(*) AS books, count(author_id) AS with_author, avg(author_id) AS avg_author_id
FROM books;

-- an aggregate over ZERO rows: count is 0, everything else is NULL
SELECT count(*) AS n, sum(copies) AS total, coalesce(sum(copies), 0) AS total_or_zero
FROM sales
WHERE region = 'North';
```

```text
 books | with_author |   avg_author_id    
-------+-------------+--------------------
     4 |           3 | 1.3333333333333333
(1 row)

 n | total | total_or_zero 
---+-------+---------------
 0 |       |             0
(1 row)
```

If a report must show `0` for "no sales", wrap it: `coalesce(sum(copies), 0)`.

## GROUP BY: one summary per group

`GROUP BY` splits the rows into buckets that share the same value in the listed column, then runs the aggregate once per bucket. Here we total the copies sold per region.

    GROUP BY region
    ORDER BY copies_in_region DESC;

Each region becomes one output row. The `region` column is allowed in the `SELECT` because it is the thing we grouped by; everything else must be inside an aggregate, unless it is functionally dependent on the grouped columns (see below).

## Filtering groups with HAVING

`WHERE` filters individual rows *before* they are grouped. To filter on the result of an aggregate you need `HAVING`, which runs *after* grouping. Here we keep only regions that sold more than a thousand copies.

    SELECT region, sum(copies) AS copies_in_region
    FROM sales
    GROUP BY region
    HAVING sum(copies) > 1000
    ORDER BY copies_in_region DESC;

Use `WHERE` to discard rows you never want counted, and `HAVING` to discard whole groups based on their totals. They often appear in the same query. An aggregate in `WHERE` is refused outright:

`count(*)` counts rows. `count(column)` counts rows where that column is not `NULL`. The difference matters whenever a column can be missing. Joining `authors` to `books` with a `LEFT JOIN` shows it clearly.

## The GROUP BY rule, and its one exception

Every column in the `SELECT` list must be grouped, aggregated, or functionally dependent on the grouped columns. Ask for a column that is none of these and PostgreSQL refuses instead of guessing:

```sql
-- @expect-error 42803
SELECT a.name, b.title, count(*)
FROM authors a JOIN books b ON b.author_id = a.id
GROUP BY a.name;
```

```text
ERROR:  column "b.title" must appear in the GROUP BY clause or be used in an aggregate function
LINE 1: SELECT a.name, b.title, count(*)
                       ^
```

The exception: if you group by a table's **primary key**, every other column of that table is determined by it, so PostgreSQL accepts it without listing it. `GROUP BY a.id` lets us select `a.name` ([docs](https://www.postgresql.org/docs/18/sql-select.html#SQL-GROUPBY)):

```sql
-- sql/group-by-primary-key.sql
-- authors.id is the primary key, so a.name is functionally dependent on it: allowed
SELECT a.name, count(b.id) AS books
FROM authors a LEFT JOIN books b ON b.author_id = a.id
GROUP BY a.id
ORDER BY a.name;
```

```text
    name    | books 
------------+-------
 Mara Linde |     2
 Owen Pryce |     1
 Sela Vance |     0
(3 rows)
```

## FILTER, DISTINCT, and subtotals

`FILTER (WHERE ...)` restricts one aggregate to some of the rows, so several conditional totals fit in one pass over the table, and `count(DISTINCT col)` counts distinct non-`NULL` values:

```sql
-- sql/filter-clause.sql
SELECT
  sum(copies)                                 AS total,
  sum(copies) FILTER (WHERE region = 'East')  AS east,
  sum(copies) FILTER (WHERE region = 'West')  AS west,
  count(DISTINCT book_id)                     AS books_sold
FROM sales;
```

```text
 total | east | west | books_sold 
-------+------+------+------------
  2100 | 1150 |  950 |          3
(1 row)
```

`ROLLUP` adds subtotal and grand-total rows: after each region's per-book lines comes a row with `NULL` in `book_id` (the region subtotal), and the last row, with both `NULL`, is the grand total 2100:

```sql
-- sql/rollup.sql
SELECT region, book_id, sum(copies) AS copies
FROM sales
GROUP BY ROLLUP (region, book_id)
ORDER BY region NULLS LAST, book_id NULLS LAST;
```

```text
 region | book_id | copies 
--------+---------+--------
 East   |       1 |     50
 East   |       2 |    900
 East   |       3 |    200
 East   |         |   1150
 West   |       1 |    400
 West   |       2 |    150
 West   |       3 |    400
 West   |         |    950
        |         |   2100
(9 rows)
```

`GROUPING SETS` names exactly the groupings you want (here per region, per book and overall). The `grouping()` function tells a subtotal `NULL` from a real `NULL` in the data:

```sql
-- sql/grouping-sets.sql
SELECT region, book_id, sum(copies) AS copies, grouping(region, book_id) AS g
FROM sales
GROUP BY GROUPING SETS ((region), (book_id), ())
ORDER BY g, region, book_id;
```

```text
 region | book_id | copies | g 
--------+---------+--------+---
 East   |         |   1150 | 1
 West   |         |    950 | 1
        |       1 |    450 | 2
        |       2 |   1050 | 2
        |       3 |    600 | 2
        |         |   2100 | 3
(6 rows)
```

## How PostgreSQL aggregates, in a real plan

Six rows do not tell you much about the plan. This section builds `big_sales` with 500 000 rows over 5 regions:

```sql
-- sql/aggregate-plans-setup.sql
CREATE TABLE big_sales (
  id     int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  region text NOT NULL,
  copies int NOT NULL
);
INSERT INTO big_sales (region, copies)
SELECT (ARRAY['East', 'West', 'North', 'South', 'Central'])[1 + g % 5], g % 1000
FROM generate_series(1, 500000) AS g;
ANALYZE big_sales;
```

```text
CREATE TABLE
INSERT 0 500000
ANALYZE
```

```sql
-- sql/plan-group-by.sql
EXPLAIN (ANALYZE, COSTS OFF)
SELECT region, sum(copies) FROM big_sales GROUP BY region;
```

```text

-----------------------------------------------------------------------------------------------------------
 Finalize GroupAggregate (actual time=62.620..64.583 rows=5.00 loops=1)
   Group Key: region
   Buffers: shared hit=2711
   ->  Gather Merge (actual time=62.594..64.556 rows=10.00 loops=1)
         Workers Planned: 1
         Workers Launched: 1
         Buffers: shared hit=2711
         ->  Sort (actual time=61.122..61.123 rows=5.00 loops=2)
               Sort Key: region
               Sort Method: quicksort  Memory: 25kB
               Buffers: shared hit=2711
               Worker 0:  Sort Method: quicksort  Memory: 25kB
               ->  Partial HashAggregate (actual time=61.097..61.099 rows=5.00 loops=2)
                     Group Key: region
                     Batches: 1  Memory Usage: 32kB
                     Buffers: shared hit=2703
                     Worker 0:  Batches: 1  Memory Usage: 32kB
                     ->  Parallel Seq Scan on big_sales (actual time=0.006..17.918 rows=250000.00 loops=2)
                           Buffers: shared hit=2703

   Buffers: shared hit=90
 Planning Time: 0.240 ms
 Execution Time: 64.664 ms
(23 rows)
```

Read it from the inside out: a `Parallel Seq Scan` reads half of the table in each of two processes (`loops=2`, `rows=250000.00` each), each computes a `Partial HashAggregate` of 5 groups (32 kB of hash table), the five-row partial results are sorted and merged by `Gather Merge`, and a `Finalize GroupAggregate` combines them. The whole query took 65 ms on this Mac (500 000 rows, 1 worker). Only 5 rows leave the aggregation, out of 500 000 scanned: that is the "sends little data over the network" argument for aggregating in the database.

And where does `HAVING` run? A condition that does not mention an aggregate is pushed below the aggregation into the scan (`Filter: (region = 'East')` under `Parallel Seq Scan`, so the other four regions are never aggregated); one that needs the aggregate stays above it as a `Filter` on the finalize node:

```sql
-- sql/plan-having.sql
-- a HAVING that does not use an aggregate is moved below the aggregation
EXPLAIN (COSTS OFF)
SELECT region, sum(copies) FROM big_sales GROUP BY region HAVING region = 'East';

-- one that needs the aggregate stays above it
EXPLAIN (COSTS OFF)
SELECT region, sum(copies) FROM big_sales GROUP BY region HAVING sum(copies) > 1000;
```

```text
                     QUERY PLAN                      
-----------------------------------------------------
 Finalize GroupAggregate
   ->  Gather
         Workers Planned: 1
         ->  Partial GroupAggregate
               ->  Parallel Seq Scan on big_sales
                     Filter: (region = 'East'::text)
(6 rows)

                       QUERY PLAN                       
--------------------------------------------------------
 Finalize GroupAggregate
   Group Key: region
   Filter: (sum(copies) > 1000)
   ->  Gather Merge
         Workers Planned: 1
         ->  Sort
               Sort Key: region
               ->  Partial HashAggregate
                     Group Key: region
                     ->  Parallel Seq Scan on big_sales
(10 rows)
```

So a `HAVING` without an aggregate ends up as a scan filter anyway, but write the row filter in `WHERE`: it says what you mean and does not rely on that optimisation.

## Mental Model

Think of `GROUP BY` as sorting rows into labelled boxes (one box per distinct combination of the grouped values), then running each aggregate function once per box. The `SELECT` list is evaluated per box, which is why it can only show the label, an aggregate of the contents, or something the label already determines (the primary-key exception). `WHERE` decides which rows go into boxes; `HAVING` decides which boxes are kept. Physically PostgreSQL fills the boxes with a hash table (`HashAggregate`) or by walking sorted input (`GroupAggregate`), and it can compute partial boxes in parallel workers and merge them.

## Tips / gotchas

- Every column in the `SELECT` list that is not wrapped in an aggregate must appear in the `GROUP BY`, or be functionally dependent on a grouped primary key. Otherwise PostgreSQL raises `42803`.
- Reach for `count(*)` to count rows and `count(col)` to count non-`NULL` values; use `count(DISTINCT col)` to count distinct non-`NULL` values.
- `WHERE` filters rows before grouping; `HAVING` filters groups after. You cannot put an aggregate in `WHERE` (`42803`).
- Aggregates ignore `NULL` for `sum`, `avg`, `min`, and `max` too, and return `NULL` over an empty input; `count` returns `0`. Use `coalesce` when you need a number.
- Node.js returns `bigint` aggregate results as strings; convert deliberately (`Number(...)`, `BigInt(...)`).

<Callout title="GROUP BY collapses, and that is the point">
After a `GROUP BY` you no longer have the original rows — you have one row per group. If you find yourself wanting both the group total and the individual rows in the same result, that is the signal to reach for a window function, covered in the last lesson of this module.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| Aggregate with `GROUP BY` in PostgreSQL | Runs close to the data, can use parallel workers, sends 5 rows instead of 500 000 (plan above) | You must write correct SQL, including the rules for `GROUP BY`/`HAVING` |
| Fetch every row and summarize in application code | Easy to write, free to change the logic | Wastes bandwidth transferring data and does not scale as the table grows |
| `FILTER` clauses in one query | One scan for many conditional totals | Wide, harder-to-read `SELECT` list |
| `ROLLUP` / `GROUPING SETS` | Subtotals and totals in one pass | `NULL` in the result now means two things; use `grouping()` to tell them apart |

## Common Misconceptions

- **"PostgreSQL forces you to list every selected column in GROUP BY."** Not when you group by a primary key: `GROUP BY a.id` with `SELECT a.name` is valid.
- **"count(*) and count(col) are the same after a LEFT JOIN."** `count(*)` counts the `NULL`-extended row (Sela Vance: 1), `count(b.id)` does not (0).
- **"An empty sum is 0."** It is `NULL`; only `count` gives 0.
- **"HAVING is only for aggregates."** It can hold any condition on the group; a non-aggregate condition is pushed down to the scan by the planner, but `WHERE` is the honest place for it.
- **"Aggregating is done by fetching rows first."** The aggregate runs in the database, in parallel where possible; only the group rows travel to the client.
