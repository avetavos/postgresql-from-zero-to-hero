A join takes two tables and pairs up their rows according to a rule you write in the `ON` clause. Because a book stores its author's `id`, you can ask PostgreSQL to walk that link and produce rows that contain columns from both tables at once. The only real choice you make is what to do with rows that have no match on the other side, and that is exactly what distinguishes the join types.

Everything below was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026). The `sql` fences run top to bottom in one empty database; the outputs are copied from `psql`, and the timings in the plans are from this Mac.

## INNER JOIN: only matching rows

An `INNER JOIN` returns one combined row for every pair where the `ON` condition is true. Rows on either side that find no partner are dropped. This is the join you reach for most often.

## LEFT JOIN: keep every row on the left

A `LEFT OUTER JOIN` (the `OUTER` keyword is optional) keeps every row from the left-hand table even when no match exists on the right. The right-hand columns are filled with `NULL` for those unmatched rows. This is how you list authors and see which ones have no books yet.

## RIGHT and FULL OUTER JOIN

A `RIGHT JOIN` is the mirror image: it keeps every row from the right-hand table and fills the left with `NULL` where there is no match. `A RIGHT JOIN B` produces the same rows as `B LEFT JOIN A`, so many people only ever write `LEFT JOIN`. A `FULL OUTER JOIN` keeps unmatched rows from both sides at once.

## Without ON: syntax error, or a cross join

`JOIN` with no `ON` or `USING` is not a silent cross join in PostgreSQL. It is a syntax error:

```sql
-- @expect-error 42601
SELECT * FROM authors JOIN books;
```

```text
ERROR:  syntax error at or near ";"
LINE 1: SELECT * FROM authors JOIN books;
                                        ^
```

The silent version is the comma join. `FROM a, b` with no `WHERE` pairs every left row with every right row (3 authors × 4 books = 12), exactly what an explicit `CROSS JOIN` returns, while the proper join returns 3:

```sql
-- sql/comma-cross.sql
SELECT count(*) AS comma_join FROM authors, books;
SELECT count(*) AS cross_join FROM authors CROSS JOIN books;
SELECT count(*) AS proper_join FROM authors a JOIN books b ON b.author_id = a.id;
```

```text
 comma_join 
------------
         12
(1 row)

 cross_join 
------------
         12
(1 row)

 proper_join 
-------------
           3
(1 row)
```

## ON versus WHERE in an outer join

For an inner join, a condition in `ON` and the same condition in `WHERE` give the same rows. For an outer join they do not. `ON` decides which rows *match*; `WHERE` runs afterwards and removes rows from the result, including the `NULL`-extended ones that a `LEFT JOIN` just went to the trouble of keeping.

```sql
-- sql/on-vs-where.sql
-- filter in ON: every author survives, the filter only limits which books match
SELECT a.name, b.title
FROM authors a
LEFT JOIN books b ON b.author_id = a.id AND b.published > 2010
ORDER BY a.name, b.title;

-- same filter in WHERE: the NULL-extended rows are thrown away, it is an INNER JOIN now
SELECT a.name, b.title
FROM authors a
LEFT JOIN books b ON b.author_id = a.id
WHERE b.published > 2010
ORDER BY a.name, b.title;
```

```text
    name    |       title       
------------+-------------------
 Mara Linde | The Glass Orchard
 Owen Pryce | Tidal Notes
 Sela Vance | 
(3 rows)

    name    |       title       
------------+-------------------
 Mara Linde | The Glass Orchard
 Owen Pryce | Tidal Notes
(2 rows)
```

Sela Vance is in the first result and gone from the second. The `WHERE` version quietly turned the `LEFT JOIN` into an `INNER JOIN`, because `NULL > 2010` is not true. This is the bug the *Reading AI-generated code* section below is about.

## USING, and why NATURAL JOIN is a trap

When the joined columns have the same name in both tables, `USING (col)` is shorthand for `ON a.col = b.col` and it emits the column once in `SELECT *`. `NATURAL JOIN` goes further and joins on **every** column that has the same name in both tables, with no way to say which. In our dataset `authors.id` and `books.id` are both called `id`, so a `NATURAL JOIN` compares an author's id with a *book's* id and pairs Owen Pryce with *The Glass Orchard*, an author with an unrelated book:

```sql
-- sql/using-natural.sql
-- USING: the joined column appears once in SELECT *
SELECT *
FROM books
JOIN (SELECT id AS author_id, name FROM authors) AS a USING (author_id)
ORDER BY books.id;

-- NATURAL JOIN: matches on EVERY same-named column. authors and books both have "id"
SELECT a.name, b.title
FROM authors a NATURAL JOIN books b
ORDER BY a.name;
```

```text
 author_id | id |       title       | published | copies_sold |    name    
-----------+----+-------------------+-----------+-------------+------------
         1 |  1 | Quiet Harbors     |      2003 |         450 | Mara Linde
         1 |  2 | The Glass Orchard |      2018 |        1250 | Mara Linde
         2 |  3 | Tidal Notes       |      2011 |         600 | Owen Pryce
(3 rows)

    name    |       title       
------------+-------------------
 Mara Linde | Quiet Harbors
 Owen Pryce | The Glass Orchard
 Sela Vance | Tidal Notes
(3 rows)
```

It gets worse over time, because the join condition depends on the column names in the tables today. Add an `author_id` column to `authors` (a perfectly ordinary migration) and the same `NATURAL JOIN` now needs `id` *and* `author_id` to match: the result shrinks from 3 rows to 1, with no error:

```sql
-- sql/natural-drift.sql
-- someone adds a column to both tables, and the NATURAL JOIN silently changes meaning
BEGIN;
ALTER TABLE authors ADD COLUMN author_id bigint;
UPDATE authors SET author_id = id;
SELECT * FROM books NATURAL JOIN authors ORDER BY books.id;
ROLLBACK;
```

```text
BEGIN
ALTER TABLE
UPDATE 3
 id | author_id |     title     | published | copies_sold |    name    | born 
----+-----------+---------------+-----------+-------------+------------+------
  1 |         1 | Quiet Harbors |      2003 |         450 | Mara Linde | 1968
(1 row)

ROLLBACK
```

Write `ON` explicitly. It costs a few characters and cannot change meaning behind your back ([PostgreSQL docs, joined tables](https://www.postgresql.org/docs/18/queries-table-expressions.html#QUERIES-JOIN)).

## NULL never equals NULL in ON

A join condition is an ordinary boolean expression. `NULL = NULL` is not true, so the two rows with a `NULL` `author_id` never match each other in a self-join; the null-safe comparison `IS NOT DISTINCT FROM` does match them:

```sql
-- sql/null-in-on.sql
SELECT count(*) AS with_equals
FROM books x JOIN books y ON x.author_id = y.author_id;

SELECT count(*) AS with_not_distinct
FROM books x JOIN books y ON x.author_id IS NOT DISTINCT FROM y.author_id;
```

```text
 with_equals 
-------------
           5
(1 row)

 with_not_distinct 
-------------------
                 6
(1 row)
```

The 5 are the four (1,1) pairs plus the one (2,2) pair; the extra row in the second query is *Unlinked Draft* matching itself.

## LATERAL: a subquery that sees the row to its left

Normally each `FROM` item is independent. A subquery marked `LATERAL` may refer to columns of the items before it, so it runs once per left row ([docs](https://www.postgresql.org/docs/18/queries-table-expressions.html#QUERIES-LATERAL)). That makes "top N per group" a short query. Here, the biggest sale of each book; `LEFT JOIN LATERAL ... ON true` keeps *Unlinked Draft*, which has no sales:

```sql
-- sql/lateral.sql
-- the biggest sale for each book; LEFT JOIN LATERAL ... ON true keeps books with no sales
SELECT b.title, s.region, s.copies
FROM books b
LEFT JOIN LATERAL (
  SELECT region, copies
  FROM sales
  WHERE sales.book_id = b.id
  ORDER BY copies DESC
  LIMIT 1
) AS s ON true
ORDER BY b.id;
```

```text
       title       | region | copies 
-------------------+--------+--------
 Quiet Harbors     | West   |    400
 The Glass Orchard | East   |    900
 Tidal Notes       | West   |    400
 Unlinked Draft    |        |       
(4 rows)
```

`LIMIT 1` inside the subquery is the point: a plain join cannot express "only the first row of the right side, per left row".

## Semi joins and anti joins

"Authors that have at least one book" and "authors with no book" are not really joins, since you do not want columns from the other table; they are filters. Write them with `EXISTS` and `NOT EXISTS` (or `IN` for the first). The planner turns them into *semi* and *anti* joins internally, and, unlike a plain join, a semi join never returns a left row twice (Mara Linde has two books and appears once):

```sql
-- sql/semi-anti.sql
SELECT name FROM authors a
WHERE EXISTS (SELECT 1 FROM books b WHERE b.author_id = a.id);

SELECT name FROM authors a
WHERE NOT EXISTS (SELECT 1 FROM books b WHERE b.author_id = a.id);
```

```text
    name    
------------
 Mara Linde
 Owen Pryce
(2 rows)

    name    
------------
 Sela Vance
(1 row)
```

## The three join algorithms, in a real plan

`EXPLAIN` shows how the join is executed. PostgreSQL has three algorithms and picks by cost. To see all three we need more than four rows, so this section builds 10 000 `customers` and 200 000 `orders` (20 orders per customer, an index on `orders.customer_id`):

```sql
-- sql/join-algorithms-setup.sql
CREATE TABLE customers (
  id   int PRIMARY KEY,
  name text NOT NULL
);
CREATE TABLE orders (
  id          int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id int NOT NULL REFERENCES customers (id),
  total       numeric(10, 2) NOT NULL
);
INSERT INTO customers SELECT g, 'customer ' || g FROM generate_series(1, 10000) AS g;
INSERT INTO orders (customer_id, total)
SELECT 1 + (g * 7919) % 10000, g % 500 FROM generate_series(1, 200000) AS g;
CREATE INDEX orders_customer_id_idx ON orders (customer_id);
ANALYZE customers;
ANALYZE orders;
```

```sql

SELECT c.name, o.total
FROM customers c JOIN orders o ON o.customer_id = c.id
WHERE c.id = 42;
```

Semi and anti joins show up in plans as join nodes too. `EXPLAIN` of an `EXISTS` and a `NOT EXISTS` filter on the same tables:

```sql
-- sql/plan-semi-anti.sql
EXPLAIN (COSTS OFF)
SELECT c.id FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.total > 498);

EXPLAIN (COSTS OFF)
SELECT c.id FROM customers c
```

## Reading AI-generated code

An assistant is asked for "every author, with their books published after 2010" and writes a query that looks right:

<SpotTheBug lang="sql" code={`-- AI comment: "list every author with their books published after 2010"
SELECT a.name, b.title
FROM authors a
LEFT JOIN books b ON b.author_id = a.id
WHERE b.published > 2010;`}>

The intent is a `LEFT JOIN` (every author), but the filter sits in `WHERE`. After the join, Sela Vance's row has `b.published = NULL`, `NULL > 2010` is not true, and the row is filtered out. The query returns two rows, not three, and nothing errors:

```sql
-- sql/stb-wrong.sql
SELECT a.name, b.title
FROM authors a
LEFT JOIN books b ON b.author_id = a.id
WHERE b.published > 2010;
```

```text
    name    |       title       
------------+-------------------
 Mara Linde | The Glass Orchard
 Owen Pryce | Tidal Notes
(2 rows)
```

The fix is to move the condition that describes *which books match* into `ON`, so authors without a matching book keep their `NULL`-extended row:

```sql
-- sql/stb-fixed.sql
SELECT a.name, b.title
FROM authors a
LEFT JOIN books b ON b.author_id = a.id AND b.published > 2010
ORDER BY a.name, b.title;
```

```text
    name    |       title       
------------+-------------------
 Mara Linde | The Glass Orchard
 Owen Pryce | Tidal Notes
 Sela Vance | 
(3 rows)
```

</SpotTheBug>

## Mental Model

A join is a filtered cross product: conceptually every left row is paired with every right row, and the `ON` condition keeps the pairs that pass. Outer joins add one step *after* that test: any left (or right, or both) row that ended up with no partner is re-added with `NULL`s. `WHERE` runs after all of that. Everything else in this lesson (`USING`, `LATERAL`, semi joins) is a variation on which pairs are kept, and the algorithms (nested loop, hash, merge) are three different ways to compute the same result without materializing the full product.

## Tips / gotchas

- `JOIN` without `ON` or `USING` is a syntax error (`42601`). An accidental cross join comes from listing tables with a comma (`FROM a, b`) and forgetting the `WHERE`: ten and ten rows give one hundred output rows.
- Give each table a short alias such as `a` and `b`, then prefix every column. It keeps queries readable and avoids ambiguity when both tables share a column name like `id`.
- A `NULL` in an outer-join result means "no matching row was found", not "the value is zero or empty". Test for it with `IS NULL`, never `= NULL`.
- Put filters that describe the *optional* side in `ON`, filters on the side you are keeping in `WHERE`.
- Prefer `EXISTS` / `NOT EXISTS` when you only need to test for presence: no duplicates, no columns you will throw away.

<Callout title="Pick the side you want to keep">
Decide which table must always appear in the output, put it first, and `LEFT JOIN` the other onto it. "Every author, with their books if any" is a `LEFT JOIN` from `authors`. "Only authors who have books" is an `INNER JOIN` (or `EXISTS`). The English phrasing usually tells you the join type.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| Join normalized tables at query time | Data is never duplicated and is always current | Queries are more complex, and the join is recomputed every time |
| Denormalize / copy data ahead of time | Reads are faster since there is no join at query time | Risk of stale or inconsistent data; you must keep the copies in sync yourself |
| `NATURAL JOIN` / `USING` | Short to write | `NATURAL` silently changes meaning when columns are added or renamed |
| `EXISTS` instead of a join for presence tests | Never duplicates left rows; planner uses a semi join | Cannot return columns from the other table |
| Forcing a join algorithm with `enable_*` | Useful to diagnose a plan | Never a fix: it overrides the planner for the whole session |

## Common Misconceptions

- **"A JOIN with no ON is a silent cross join."** It is a syntax error in PostgreSQL. The silent cross join is `FROM a, b` with no `WHERE`.
- **"ON and WHERE are interchangeable."** Only for inner joins. In a `LEFT JOIN`, a `WHERE` on the right table turns it into an inner join (2 rows instead of 3 above).
- **"NATURAL JOIN joins on the foreign key."** It joins on every same-named column, here `id` against `id`, pairing unrelated rows.
- **"NULL = NULL matches in a join."** It never does; use `IS NOT DISTINCT FROM` when you mean it.
- **"Hash join is always fastest."** The planner picks by cost: a nested loop took 0.17 ms for one customer, and forcing a merge join took 116 ms against the hash join's 98 ms for all of them.
