A subquery is a `SELECT` written inside another statement. The inner query runs first and hands its result to the outer one, which lets you answer questions in two steps: "find the average", then "show the rows above it". A common table expression, or CTE, takes the same idea and gives the intermediate result a name with `WITH`, so a long query reads like a short story instead of a tangle of nesting.

Everything below was run on **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop on a Mac, September 2026), copied from `psql`. The `sql` fences run top to bottom in one empty database; timings are from this Mac.

### NOT IN and the NULL trap

`NOT IN` is different, and this is the subquery mistake with real consequences. `x NOT IN (1, 2, NULL)` is never true: for a value not in the list it evaluates to `NULL` (unknown), not `true`. Our `books.author_id` contains one `NULL`, so "authors who have no book" returns **nothing**, when the answer is Sela Vance:

```sql
-- sql/not-in-vs-not-exists.sql
-- books.author_id contains a NULL (Unlinked Draft), so NOT IN can never be true
SELECT name FROM authors WHERE id NOT IN (SELECT author_id FROM books) ORDER BY name;

SELECT name FROM authors a
WHERE NOT EXISTS (SELECT 1 FROM books b WHERE b.author_id = a.id)
ORDER BY name;
```

```text
 name 
------
(0 rows)

    name    
------------
 Sela Vance
(1 row)
```

Filtering the `NULL` out of the subquery repairs it, but `NOT EXISTS` never had the problem:

```sql
-- sql/not-in-filtered.sql
-- NOT IN works again once the NULLs are removed from the subquery
SELECT name FROM authors
WHERE id NOT IN (SELECT author_id FROM books WHERE author_id IS NOT NULL)
ORDER BY name;
```

```text
    name    
------------
 Sela Vance
(1 row)
```

It is also a plan problem. `NOT EXISTS` becomes an anti join; `NOT IN` cannot (because of the `NULL` rule) and stays a filter over a hashed subplan:

```sql
-- sql/plan-not-in-vs-not-exists.sql
EXPLAIN (COSTS OFF) SELECT count(*) FROM parents WHERE id NOT IN (SELECT parent_id FROM children);
EXPLAIN (COSTS OFF) SELECT count(*) FROM parents p WHERE NOT EXISTS (SELECT 1 FROM children c WHERE c.parent_id = p.id);
```

### Correlated subqueries

A correlated subquery refers to the outer row, so it conceptually runs once per outer row. In a scalar position that is literally what the plan does (`SubPlan 1 ... loops=1000`), and here it is about three times slower than the equivalent join with `GROUP BY` (165 ms against 51 ms on this Mac, 1 000 parents and 200 000 children; the first run also paid for 165 cold buffer reads):

```sql
-- sql/correlated-subquery.sql
-- a correlated scalar subquery cannot be flattened: one probe per parent
EXPLAIN (ANALYZE, COSTS OFF)
SELECT p.id, (SELECT count(*) FROM children c WHERE c.parent_id = p.id) AS n
FROM parents p;

-- the same answer as a join + GROUP BY
EXPLAIN (ANALYZE, COSTS OFF)
SELECT p.id, count(c.id) AS n
FROM parents p LEFT JOIN children c ON c.parent_id = p.id
GROUP BY p.id;
```

## CTEs: naming a step with WITH

    SELECT b.title, t.copies

-- sql/cte-chain.sql
WITH per_book AS (
  SELECT book_id, sum(copies) AS copies FROM sales GROUP BY book_id

  GROUP BY b.author_id

### Is a CTE a fence? It depends, and you can choose

Since PostgreSQL 12 a CTE is **inlined** into the outer query when it is not recursive, has no side effects, and is referenced only once; otherwise it is computed once and its result is reused (materialized). `AS MATERIALIZED` and `AS NOT MATERIALIZED` override the default ([docs](https://www.postgresql.org/docs/18/queries-with.html#QUERIES-WITH-CTE-MATERIALIZATION)). The four plans below show all four shapes, on the 200 000-row `children`:

```sql
-- sql/cte-inline.sql
-- referenced once: inlined into the outer query
EXPLAIN (COSTS OFF)
WITH c AS (SELECT * FROM children WHERE k = 5)
SELECT * FROM c WHERE id < 100;

-- referenced twice: computed once and shared (materialized)
EXPLAIN (COSTS OFF)
WITH c AS (SELECT * FROM children WHERE k = 5)
SELECT (SELECT count(*) FROM c) AS n, (SELECT max(id) FROM c) AS newest;

-- forced with AS MATERIALIZED even though used once
EXPLAIN (COSTS OFF)
WITH c AS MATERIALIZED (SELECT * FROM children WHERE k = 5)
SELECT * FROM c WHERE id < 100;

-- forced inlining with NOT MATERIALIZED even though used twice
EXPLAIN (COSTS OFF)
WITH c AS NOT MATERIALIZED (SELECT * FROM children WHERE k = 5)
SELECT (SELECT count(*) FROM c) AS n, (SELECT max(id) FROM c) AS newest;
```

```text
                 QUERY PLAN                 
--------------------------------------------
 Index Scan using children_pkey on children
   Index Cond: (id < 100)
   Filter: (k = 5)
(3 rows)

           QUERY PLAN            
---------------------------------
 Result
   CTE c
     ->  Seq Scan on children
           Filter: (k = 5)
   InitPlan 2
     ->  Aggregate
           ->  CTE Scan on c
   InitPlan 3
     ->  Aggregate
           ->  CTE Scan on c c_1
(10 rows)

          QUERY PLAN          
------------------------------
 CTE Scan on c
   Filter: (id < 100)
   CTE c
     ->  Seq Scan on children
           Filter: (k = 5)
(5 rows)

                                      QUERY PLAN                                      
--------------------------------------------------------------------------------------
 Result
   InitPlan 1
     ->  Finalize Aggregate
           ->  Gather
                 Workers Planned: 1
                 ->  Partial Aggregate
                       ->  Parallel Seq Scan on children
                             Filter: (k = 5)
   InitPlan 3
     ->  Result
           InitPlan 2
             ->  Limit
                   ->  Index Scan Backward using children_pkey on children children_1
                         Filter: (k = 5)
(14 rows)
```

1. Referenced once: no `CTE` node at all. The outer `id < 100` was pushed into the CTE's own scan (`Index Cond: (id < 100)`, `Filter: (k = 5)`).
2. Referenced twice: `CTE c` is scanned once and read by two `CTE Scan` nodes.
3. `AS MATERIALIZED` on a single reference: the CTE is computed in full first, and `id < 100` is only a `Filter` on the `CTE Scan`, an optimisation fence.
4. `NOT MATERIALIZED` on two references: inlined twice; each reference gets its own plan (the `max(id)` even becomes a backward index scan).

Neither is better in general. Materialize when the CTE is expensive and read several times; inline when the outer query can filter it.

## WITH RECURSIVE

A recursive CTE has a starting query, `UNION ALL`, and a recursive part that refers to the CTE itself; it repeats until the recursive part returns no new rows. It is the standard way to walk a tree, such as an org chart:

```sql
-- sql/recursive-setup.sql
CREATE TABLE staff (
  id      int PRIMARY KEY,
  name    text NOT NULL,
  boss_id int REFERENCES staff (id)
);
INSERT INTO staff VALUES
  (1, 'Ada', NULL), (2, 'Ben', 1), (3, 'Cy', 1), (4, 'Di', 2), (5, 'Eli', 2), (6, 'Flo', 3), (7, 'Gus', 4);
```

```sql
-- sql/recursive.sql
WITH RECURSIVE tree AS (
  SELECT id, name, 0 AS depth, name AS path
  FROM staff
  WHERE boss_id IS NULL
  UNION ALL
  SELECT s.id, s.name, t.depth + 1, t.path || ' > ' || s.name
  FROM staff s
  JOIN tree t ON s.boss_id = t.id
)
SELECT repeat('  ', depth) || name AS org_chart, path
FROM tree
ORDER BY path;
```

```text
 org_chart |         path         
-----------+----------------------
 Ada       | Ada
   Ben     | Ada > Ben
     Di    | Ada > Ben > Di
       Gus | Ada > Ben > Di > Gus
     Eli   | Ada > Ben > Eli
   Cy      | Ada > Cy
     Flo   | Ada > Cy > Flo
(7 rows)
```

Bad data can make the recursion never stop: if the graph has a cycle, the recursive part keeps finding new rows forever. The `CYCLE` clause (PostgreSQL 14+) marks a row that revisits an `id` it has already seen and stops there. We corrupt the data inside a transaction so Ada reports to her own great-grandchild Gus, and roll back:

```sql
-- sql/recursive-cycle.sql
BEGIN;
-- corrupt the data on purpose: Ada now reports to Gus, who reports (via Di, Ben) to Ada
UPDATE staff SET boss_id = 7 WHERE id = 1;
WITH RECURSIVE tree AS (
  SELECT id, name, boss_id FROM staff WHERE id = 1
  UNION ALL
  SELECT s.id, s.name, s.boss_id FROM staff s JOIN tree t ON s.boss_id = t.id
) CYCLE id SET is_cycle USING seen
SELECT id, name, is_cycle FROM tree;
ROLLBACK;
```

```text
BEGIN
UPDATE 1
 id | name | is_cycle 
----+------+----------
  1 | Ada  | f
  2 | Ben  | f
  3 | Cy   | f
  4 | Di   | f
  5 | Eli  | f
  6 | Flo  | f
  7 | Gus  | f
  1 | Ada  | t
(8 rows)

ROLLBACK
```

The last row (`is_cycle = t`) is Ada seen a second time; the recursion stopped instead of running forever.

## Data-modifying CTEs

`DELETE`, `UPDATE` and `INSERT` can appear in a `WITH` if they have `RETURNING`, and their output can feed the main statement. This moves the West sales into an archive table in one statement (inside a transaction here, so we can look and then roll back):

```sql
-- sql/data-modifying-cte.sql
CREATE TABLE sales_archive (LIKE sales);
BEGIN;
WITH moved AS (
  DELETE FROM sales WHERE region = 'West' RETURNING *
)
INSERT INTO sales_archive SELECT * FROM moved;
SELECT (SELECT count(*) FROM sales) AS live, (SELECT count(*) FROM sales_archive) AS archived;
ROLLBACK;
SELECT (SELECT count(*) FROM sales) AS live, (SELECT count(*) FROM sales_archive) AS archived;
```

```text
CREATE TABLE
BEGIN
INSERT 0 3
 live | archived 
------+----------
    3 |        3
(1 row)

ROLLBACK
 live | archived 
------+----------
    6 |        0
(1 row)
```

Inside the transaction 3 rows were live and 3 archived; after the rollback the archive is empty again.

## Mental Model

A subquery is an expression whose value is a table, a row or a single value. Ask what it must be, and the syntax follows: a single value (scalar comparison), a list to test membership (`IN`), or just "is it empty?" (`EXISTS`). A CTE is a named subquery placed at the top. It is a naming device first; whether it is also a computation boundary is the planner's decision, which you can override. Recursion adds one idea: a CTE that feeds its own new rows back until none remain.

## Tips / gotchas

- A scalar subquery must return one row and one column, or PostgreSQL raises `21000`.
- `IN` and `EXISTS` (and `NOT EXISTS`) plan alike; prefer `NOT EXISTS` over `NOT IN` whenever the subquery column can be `NULL`.
- CTE = readability, not an automatic performance fence or a guaranteed materialization. Check `EXPLAIN` when it matters.
- Every `WITH RECURSIVE` walk over data you do not control should have a stop: `CYCLE`, a depth counter with a `WHERE depth < n`, or a `UNION` instead of `UNION ALL`.
- Data-modifying CTEs all see the same snapshot and run whether or not the main query reads them.

<Callout title="Subquery or CTE?">
Use a subquery when the step is small and used once. Use a CTE when you want to name the step, reuse it, or read the query top to bottom. If the query has three or four levels of nested parentheses, it is time for CTEs.
</Callout>

## Trade-offs

| Option | Benefit | Cost |
|---------|---------|------|
| Inline subquery | Compact, planner sees everything | Deep nesting is hard to read and debug |
| CTE (inlined by default) | Readable top-to-bottom, same plan as a subquery when used once | Referencing it twice materializes it and blocks pushdown of outer filters |
| `AS MATERIALIZED` | Computes an expensive step once, predictable | Optimisation fence: outer filters are applied after the fact |
| Correlated scalar subquery | Very direct to write | Per-outer-row probe (165 ms vs 51 ms for the join above) |
| `WITH RECURSIVE` | Walks trees and graphs in SQL | Needs a termination guard; can be slow on large graphs |

## Common Misconceptions

- **"EXISTS is faster than IN."** Both compile to the same semi join (identical plan and cost above).
- **"NOT IN and NOT EXISTS are the same."** They differ the moment the subquery returns a `NULL`: `NOT IN` returns no rows at all.
- **"A CTE is always materialized."** Not since PostgreSQL 12: a CTE referenced once is inlined.
- **"A CTE is always inlined."** Referenced twice it is materialized; `AS MATERIALIZED` forces it.
- **"Recursive CTEs loop forever on a cycle."** They do unless you guard them; `CYCLE` does it for you.
