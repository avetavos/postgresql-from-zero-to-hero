`LIKE '%word%'` เทียบตัวอักษร มันจัดอันดับผลไม่ได้ เจอตัวอักษรที่ซ่อนอยู่ในคำอื่น ไม่รู้ว่า `runs` กับ `running` เป็นรูปของคำเดียวกัน และถ้าไม่มี index พิเศษมันอ่านทุก row PostgreSQL มีคำตอบในตัว: **full-text search** เอกสารถูกลดรูปเป็นชุดคำที่ปรับมาตรฐานแล้ว (`tsvector`) การค้นหาคือชุดคำที่เชื่อมด้วยตรรกะ (`tsquery`) และ operator `@@` ถามว่า query ตรงกับเอกสารไหม

ทุกอย่างด้านล่างรันบน **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) fence `sql` รันจากบนลงล่างในฐานข้อมูลเปล่าหนึ่งตัว ผลลัพธ์คัดลอกจาก `psql` และเวลาเป็นการรันครั้งเดียวจาก Mac เครื่องนี้

## ชุดข้อมูล

บทความสั้นแปดชิ้น เล็กพอให้อ่านทุกผล แต่มีคำซ้อนกัน (running, runner, shoes, trail, waterproof) พอให้การจัดอันดับน่าสนใจ:

```sql
-- sql/setup.sql
CREATE TABLE articles (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text NOT NULL,
  body  text NOT NULL
);
INSERT INTO articles (title, body) VALUES
  ('Trail running shoes',          'Lightweight trail shoes grip wet rock and mud. A good runner rotates two pairs of shoes.'),
  ('Marathon training plan',       'Twelve weeks of running: long runs on Sunday, easy runs midweek. The runner who ran the most miles improved fastest.'),
  ('Caring for leather boots',     'Clean leather boots after each hike, then condition the leather. Waterproofing wax protects the stitching.'),
  ('Waterproof jackets compared',  'We tested five waterproof jackets in heavy rain. The best jacket kept us dry and never wetted out.'),
  ('Stretching after a run',       'A short stretching routine after a run reduces stiffness. Runners often skip stretching.'),
  ('Choosing trail food',          'Nuts, dried fruit and cheese travel well. Avoid heavy food before a long run.'),
  ('Rain gear for cyclists',       'Cyclists need waterproof shoe covers and a rain jacket that breathes.'),
  ('Shoe care',                    'Wash muddy shoes with a soft brush. Never machine-dry running shoes.');
```

## สองชนิดใหม่

`tsvector` คือรายการเรียงลำดับของ **lexeme** (คำที่ปรับมาตรฐานแล้ว) พร้อมตำแหน่ง การสร้างมันทิ้ง stop word เช่น "the" และ "were" แปลงเป็นตัวพิมพ์เล็ก และ **stem**: ลดแต่ละคำเป็นรากตามกฎของ text search configuration `SHOW default_text_search_config` บอกว่าค่าเริ่มต้นที่นี่คืออะไร:

```sql
-- sql/tsvector.sql
SHOW default_text_search_config;
SELECT to_tsvector('english', 'The quick brown foxes were running quickly');
SELECT to_tsvector('english', title) FROM articles WHERE id IN (1, 5) ORDER BY id;
```

```text
 default_text_search_config 
----------------------------
 pg_catalog.english
(1 row)

              to_tsvector              
---------------------------------------
 'brown':3 'fox':4 'quick':2,7 'run':6
(1 row)

        to_tsvector         
----------------------------
 'run':2 'shoe':3 'trail':1
 'run':4 'stretch':1
(2 rows)
```

สังเกตว่าค่าเริ่มต้นบน server นี้คือ `pg_catalog.english` `initdb` หามาจาก locale ของ cluster (ใต้ locale `C` มันจะเป็น `simple` ที่ไม่ stem และไม่ทิ้ง stop word) จึงระบุ configuration ให้ชัดเสมอ เหมือนทุก query ในบทนี้ ([docs](https://www.postgresql.org/docs/18/textsearch-configuration.html)) ในบรรทัดแรก "quick" และ "quickly" กลายเป็น `quick` ทั้งคู่ (ตำแหน่ง 2 และ 7), "foxes" กลายเป็น `fox`, "running" กลายเป็น `run`

stemming รวมรูปที่ตามกฎ และเฉพาะรูปเหล่านั้น `running` match `run` แต่อดีตกาลไม่ปกติ `ran` เป็นคนละ lexeme และ `mice` ไม่กลายเป็น `mouse` dictionary เป็นแบบอิงกฎ ไม่ใช่ thesaurus:

```sql
-- sql/stemming.sql
-- stemming maps different forms to one lexeme; irregular forms are NOT joined
SELECT to_tsvector('english', 'I ran home')                               AS ran_home,
       to_tsvector('english', 'I ran home') @@ plainto_tsquery('english', 'running') AS running_matches_ran,
       to_tsvector('english', 'I run home') @@ plainto_tsquery('english', 'running') AS running_matches_run,
       to_tsvector('english', 'mice geese')                               AS irregular;
```

```text
     ran_home     | running_matches_ran | running_matches_run |     irregular     
------------------+---------------------+---------------------+-------------------
 'home':3 'ran':2 | f                   | t                   | 'gees':2 'mice':1
(1 row)
```

## การสร้าง query

`tsquery` คือชุด lexeme พร้อม `&` (และ), `|` (หรือ), `!` (ไม่) และ `<->` (ตามด้วย) PostgreSQL มีตัวสร้างสี่แบบ จากเข้มงวดที่สุดไปเป็นมิตรที่สุด:

```sql
-- sql/tsquery-forms.sql
SELECT plainto_tsquery('english', 'trail running shoes')            AS plain,
       to_tsquery('english', 'trail & (shoes | boots) & !leather')  AS operators,
       phraseto_tsquery('english', 'trail running shoes')           AS phrase,
       websearch_to_tsquery('english', '"trail shoes" -leather')    AS websearch;
```

```text
          plain           |                 operators                  |            phrase            |            websearch            
--------------------------+--------------------------------------------+------------------------------+---------------------------------
 'trail' & 'run' & 'shoe' | 'trail' & ( 'shoe' | 'boot' ) & !'leather' | 'trail' <-> 'run' <-> 'shoe' | 'trail' <-> 'shoe' & !'leather'
(1 row)
```

`plainto_tsquery` AND ทุกคำ `to_tsquery` รับ syntax แบบ operator และเข้มงวด (ช่องว่างเปล่า ๆ เป็น syntax error ดังข้างล่าง) `phraseto_tsquery` ต้องการคำเรียงตามลำดับ `websearch_to_tsquery` อ่านสิ่งที่ผู้ใช้พิมพ์จริง: เครื่องหมายคำพูดทำเป็นวลี `or` คือ OR, `-` คือ NOT และมันไม่ส่ง syntax error กับ input ผู้ใช้ จึงเป็นตัวที่ควรวางหลังช่องค้นหา

```sql
-- @expect-error 42601
SELECT to_tsquery('english', 'trail shoes');
```

```text
ERROR:  syntax error in tsquery: "trail shoes"
```

## จับคู่ด้วย operator @@

`tsvector @@ tsquery` เป็นจริงเมื่อเอกสารตรง เพราะ `runs`, `run` และ `running` ใช้ stem `run` เดียวกัน การค้นหา "runs" จึงเจอบทความทั้งห้าชิ้นที่ใช้รูปใดรูปหนึ่ง:

```sql
-- sql/match.sql
SELECT id, title
FROM articles
WHERE to_tsvector('english', title || ' ' || body) @@ plainto_tsquery('english', 'runs')
ORDER BY id;
```

```text
 id |         title          
----+------------------------
  1 | Trail running shoes
  2 | Marathon training plan
  5 | Stretching after a run
  6 | Choosing trail food
  8 | Shoe care
(5 rows)
```

เทียบกับ `LIKE` ที่ match ตัวอักษร ไม่ใช่คำ มันเจอ `runs` ตามตัวอักษร (หนึ่งบทความ) และที่แย่กว่าคือเจอตัวอักษรข้างในคำอื่นที่ไม่เกี่ยว:

```sql
-- sql/like-contrast.sql
-- LIKE compares characters: it finds the literal "runs" but not run / running
SELECT id, title FROM articles WHERE title || ' ' || body ILIKE '%runs%' ORDER BY id;
-- and it finds letters inside other words
SELECT 'a lovely brunch' ILIKE '%run%' AS like_says,
       to_tsvector('english', 'a lovely brunch') @@ plainto_tsquery('english', 'run') AS fts_says;
```

```text
 id |         title          
----+------------------------
  2 | Marathon training plan
(1 row)

 like_says | fts_says 
-----------+----------
 t         | f
(1 row)
```

## จัดอันดับผลลัพธ์

การ match ไม่ใช่การ match ที่ดี `ts_rank` ให้คะแนนตามความถี่ของคำ; `ts_rank_cd` ให้รางวัลคำที่อยู่ใกล้กัน (cover density) เพิ่มด้วย เพื่อให้ผลตรงใน title มีน้ำหนักมากกว่าใน body ให้ถ่วงน้ำหนักแต่ละส่วนด้วย `setweight` (`A` หนักสุด; ค่าเริ่มต้นคือ 1.0 สำหรับ A, 0.4 สำหรับ B, 0.2 สำหรับ C และ 0.1 สำหรับ D) ค้นหา "trail or shoes":

```sql
-- sql/ranking.sql
SELECT id, title,
       round(ts_rank(setweight(to_tsvector('english', title), 'A') || setweight(to_tsvector('english', body), 'B'),
                     websearch_to_tsquery('english', 'trail or shoes'))::numeric, 4) AS rank,
       round(ts_rank_cd(setweight(to_tsvector('english', title), 'A') || setweight(to_tsvector('english', body), 'B'),
                        websearch_to_tsquery('english', 'trail or shoes'))::numeric, 4) AS rank_cd
FROM articles
WHERE (setweight(to_tsvector('english', title), 'A') || setweight(to_tsvector('english', body), 'B'))
      @@ websearch_to_tsquery('english', 'trail or shoes')
ORDER BY rank DESC, id;
```

```text
 id |         title          |  rank  | rank_cd 
----+------------------------+--------+---------
  1 | Trail running shoes    | 0.6822 |  3.2000
  8 | Shoe care              | 0.3479 |  1.8000
  6 | Choosing trail food    | 0.3040 |  1.0000
  7 | Rain gear for cyclists | 0.1216 |  0.4000
(4 rows)
```

"Trail running shoes" ชนะเพราะทั้งสองคำอยู่ใน title (น้ำหนัก A) "Shoe care" เหนือ "Choosing trail food" (0.3479 เทียบกับ 0.3040): *shoe* ปรากฏสามครั้งในนั้น (title หนึ่ง body สอง) ขณะที่ *trail* ปรากฏครั้งเดียวในอีกอัน `ts_headline` สร้าง snippet ที่ทำเครื่องหมายคำที่ตรง สำหรับหน้าผลลัพธ์:

```sql
-- sql/headline.sql
SELECT id, ts_headline('english', body, websearch_to_tsquery('english', 'trail or shoes'),
                       'StartSel=<b>, StopSel=</b>, MaxWords=12, MinWords=5') AS snippet
FROM articles
WHERE to_tsvector('english', body) @@ websearch_to_tsquery('english', 'trail or shoes')
ORDER BY id;
```

```text
 id |                 snippet                 
----+-----------------------------------------
  1 | <b>trail</b> <b>shoes</b> grip wet rock
  7 | <b>shoe</b> covers and a rain
  8 | <b>shoes</b> with a soft brush
(3 rows)
```

## Index การค้นหา

การคำนวณ `to_tsvector` ใหม่ทุก row ทุกครั้งที่ค้นหาช้า มีสองแบบที่หลีกเลี่ยงได้ แบบที่สะอาดคือ **generated column** ที่เก็บ `tsvector` บวก GIN index บนมัน PostgreSQL ดูแลให้ column ตรงกันเอง และ query สั้น:

```sql
-- sql/generated-column.sql
ALTER TABLE articles ADD COLUMN search tsvector
  GENERATED ALWAYS AS (setweight(to_tsvector('english', title), 'A') || setweight(to_tsvector('english', body), 'B')) STORED;
CREATE INDEX articles_search_idx ON articles USING gin (search);
SELECT id, title FROM articles WHERE search @@ websearch_to_tsquery('english', 'trail shoes -leather') ORDER BY id;
```

```text
ALTER TABLE
CREATE INDEX
 id |        title        
----+---------------------
  1 | Trail running shoes
(1 row)
```

query เดียวกันแบบมี parameter จากแต่ละ driver (ข้อความ `websearch_to_tsquery` เดียวกันส่งเป็นค่า bind จึงปลอดภัยที่จะเปิดให้ input ผู้ใช้):

```sql
-- sql/param-search.sql
SELECT title
FROM articles
WHERE search @@ websearch_to_tsquery('english', $1)
ORDER BY ts_rank(search, websearch_to_tsquery('english', $1)) DESC, id
\bind 'trail or shoes -leather' \g
```

### index ให้อะไร

บนบทความ 100 000 ชิ้นชิ้นละ 30 คำ (สุ่มจากคลังคำ 3 000 คำ) การค้นหาเดียวกัน ก่อนและหลัง GIN index:

```sql
-- sql/big-articles.sql
CREATE TABLE big_articles (
  id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title  text NOT NULL,
  body   text NOT NULL
);
-- 100 000 articles of 30 words each, drawn from a vocabulary of 3 000 words (w0 ... w2999)
INSERT INTO big_articles (title, body)
SELECT 'Article ' || g,
       (SELECT string_agg('w' || (('x' || substr(md5(g::text || ':' || i::text), 1, 6))::bit(24)::int % 3000), ' ')
        FROM generate_series(1, 30) AS i)
FROM generate_series(1, 100000) AS g;
ALTER TABLE big_articles ADD COLUMN search tsvector GENERATED ALWAYS AS (to_tsvector('english', title || ' ' || body)) STORED;
ANALYZE big_articles;
SELECT count(*) AS rows, pg_size_pretty(pg_relation_size('big_articles')) AS heap FROM big_articles;
```

## เทียบเคียง: trigram และเครื่องหมายกำกับ

full-text search match คำเต็มที่สะกดถูก คำสะกดผิด (`runing`) stem เป็น lexeme อื่นและไม่เจออะไร สำหรับการ match แบบ fuzzy extension `pg_trgm` เทียบชิ้นส่วนสามตัวอักษร และ `unaccent` ตัดเครื่องหมายกำกับให้ `café` match `cafe` ([pg_trgm](https://www.postgresql.org/docs/18/pgtrgm.html), [unaccent](https://www.postgresql.org/docs/18/unaccent.html)):

```sql
-- sql/trigram.sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS unaccent;
SELECT similarity('runing', 'running') AS typo_score,
       'runing' % 'running'            AS typo_matches,
       to_tsvector('english', 'runing') @@ plainto_tsquery('english', 'running') AS fts_matches_typo,
       unaccent('caf' || chr(233) || ' cr' || chr(232) || 'me') AS unaccented;
```

```text
CREATE EXTENSION
CREATE EXTENSION
 typo_score | typo_matches | fts_matches_typo | unaccented 
------------+--------------+------------------+------------
  0.6666667 | t            | f                | cafe creme
(1 row)
```

คำสะกดผิดได้คะแนนความคล้าย 0.67 และ match ด้วย operator `%` ขณะที่ full-text search ไม่เจออะไร ใช้ `pg_trgm` สำหรับ "หมายถึงคำนี้ไหม" และ autocomplete ใช้ full-text search สำหรับข้อความร้อยแก้วที่จัดอันดับตามความเกี่ยวข้อง

ผู้ช่วย AI ถูกขอให้ทำการค้นหาบทความเร็วขึ้น มันเขียน expression index บน `to_tsvector('english', body)` และ query ค้นหา พร้อมคอมเมนต์ว่า index รองรับ:

CREATE INDEX big_articles_body_gin ON big_articles USING gin (to_tsvector('english', body));

SELECT id, title FROM big_articles
WHERE to_tsvector(body) @@ to_tsquery('w17 & w42');`}>

index กับ query ใช้ expression *คนละตัว*: index อยู่บน `to_tsvector('english', body)` ส่วน query เรียก `to_tsvector(body)` แบบ argument เดียว ซึ่งใช้ `default_text_search_config` สำหรับ planner นี่คือคนละฟังก์ชัน จึงใช้ index ไม่ได้ และ query คำนวณ tsvector ทุก row: 573 ms สำหรับ 100 000 row สั้น ๆ

## Mental Model

full-text search คือ pipeline: parse ข้อความเป็น token, ทิ้ง stop word, stem ที่เหลือด้วย dictionary และเก็บ lexeme พร้อมตำแหน่ง (`tsvector`); ทำเหมือนกันกับ query ของผู้ใช้ เชื่อมด้วย operator (`tsquery`) `@@` เป็นตรรกะเซตบน lexeme ไม่ใช่การเทียบสตริง มันจึง index ได้เร็ว (GIN แมปแต่ละ lexeme ไปยังเอกสาร) และมองไม่เห็นสิ่งที่ dictionary ไม่ได้เชื่อม เช่นรูปไม่ปกติและคำสะกดผิด การจัดอันดับเป็นอีกขั้นบนผลที่ match

## เคล็ดลับและข้อควรระวัง

- ระบุ configuration เสมอ (`to_tsvector('english', ...)`) อย่าพึ่ง `default_text_search_config`
- สำหรับช่องค้นหาใช้ `websearch_to_tsquery`: มันไม่ส่ง syntax error กับ input ผู้ใช้
- index column `tsvector` แบบ generated ที่ `STORED` ด้วย GIN virtual generated column index ไม่ได้
- expression index ถูกใช้เฉพาะเมื่อ query เขียน expression เดิมซ้ำ รวม configuration
- ถ่วงน้ำหนัก title เหนือ body ด้วย `setweight`; จัดอันดับด้วย `ts_rank` หรือ `ts_rank_cd` แล้ว order ตามนั้น
- stemming อิงกฎ: `ran` ไม่ใช่ `run`; คำสะกดผิดต้องใช้ `pg_trgm`

<Callout title="การค้นหาเป็นฟีเจอร์ ไม่ใช่แค่ query">
`@@` ตอบ "ตรงไหม?" ช่องค้นหาจริงยังต้องมีการจัดอันดับ snippet การทนคำสะกดผิด ตัวกรอง และ pagination PostgreSQL ให้ส่วนประกอบเหล่านี้ในฐานข้อมูลเดียวที่สอดคล้องแบบ transaction; search engine เฉพาะทางคุ้มกับต้นทุนการดูแลเมื่อคุณต้องการมากกว่านั้นมากเท่านั้น
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| `LIKE '%x%'` / `ILIKE` | ไม่ต้องตั้งค่า ตัวอักษรตรงเป๊ะ | Seq Scan ถ้าไม่มี trigram index; ไม่มี stemming การจัดอันดับ หรือขอบเขตคำ |
| Full-text search + GIN | รู้จักคำ จัดอันดับได้ 16.8 ms เหลือ 0.28 ms บน 100 000 row | index 15 MB; กฎ stemming ไม่ทนคำสะกดผิด |
| `pg_trgm` | ทนคำสะกดผิด substring ใดก็ได้ | index ใหญ่กว่า; ความคล้าย ไม่ใช่ภาษา |
| `tsvector` แบบ generated ที่ stored | expression เดียว ตรงกันเสมอ index ได้ | ดิสก์เพิ่มสำหรับ column; การเขียนคำนวณใหม่ |
| Expression index | ไม่ต้องมี column เพิ่ม | query ต้องเขียน expression เดิมเป๊ะ (573 ms เมื่อไม่ตรง) |

## Common Misconceptions

- **"Full-text search เข้าใจภาษา"** มันใช้ dictionary: `running` match `run`, `ran` ไม่ match
- **"FTS คือ LIKE ที่เร็วกว่า"** มัน match lexeme จัดอันดับได้ และหา substring เช่น `%un%` ไม่ได้
- **"config เริ่มต้นคือ `simple`"** ที่นี่คือ `english` (หามาจาก locale); `simple` ใต้ `C`
- **"index รองรับ query ถ้า column ตรงกัน"** expression ทั้งหมดต้องตรงกัน รวม configuration
- **"ฉัน index virtual generated column ได้"** PostgreSQL 18 ปฏิเสธ: `indexes on virtual generated columns are not supported`
