บางครั้ง row ต้องเก็บข้อมูลที่รูปร่างไม่ได้ตายตัวล่วงหน้า: สินค้าที่ attribute ต่างกันตามหมวด, payload ของ event จากภายนอก หรือค่ากำหนดของผู้ใช้ที่เพิ่มขึ้นเรื่อย ๆ PostgreSQL ให้ column เดียวเก็บเอกสาร JSON ทั้งก้อนด้วยชนิด `jsonb` แล้ว query ข้างในราวกับ key เป็น column

ทุกอย่างด้านล่างรันบน **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) fence `sql` รันจากบนลงล่างในฐานข้อมูลเปล่าหนึ่งตัว ผลลัพธ์คัดลอกจาก `psql` และเวลาเป็นการรันครั้งเดียวจาก Mac เครื่องนี้

## การสร้าง column JSONB

ชนิด `jsonb` เก็บ JSON ในรูปไบนารีที่แยกส่วนแล้ว เมื่อเทียบกับชนิด `json` ธรรมดา มันตัดช่องว่างที่ไม่มีความหมาย เก็บเฉพาะ key ซ้ำตัวสุดท้าย ไม่รักษาลำดับ key และที่สำคัญคือ index ได้ บทนี้ใช้ table สินค้าที่แต่ละ row มีเอกสาร `attributes` ยืดหยุ่น

```sql
-- sql/setup.sql
CREATE TABLE products (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       text  NOT NULL,
  attributes jsonb NOT NULL DEFAULT '{}'
);
```

## การเก็บเอกสาร

insert JSON เป็น string literal PostgreSQL parse และตรวจสอบให้ สังเกตว่า `jsonb` พิมพ์แต่ละเอกสารอย่างไร: key ออกมาในลำดับของมันเอง (key สั้นก่อน แล้วเรียงตามตัวอักษร) ไม่ใช่ลำดับที่คุณเขียน:

```sql
-- sql/insert-documents.sql
INSERT INTO products (name, attributes) VALUES
  ('Trail Jacket',  '{"color": "teal",   "price": 129.5, "tags": ["outdoor", "rain"],    "specs": {"weight_g": 480, "waterproof": true}}'),
  ('City Backpack', '{"color": "black",  "price": 89,    "tags": ["urban"],              "specs": {"weight_g": 900, "waterproof": false}}'),
  ('Camp Stove',    '{"color": "silver", "price": 45,    "tags": ["outdoor", "cooking"], "specs": {"weight_g": 350}}'),
  ('Wool Socks',    '{"color": "teal",   "price": 12.5,  "tags": ["outdoor"]}'),
  ('Rain Poncho',   '{"color": "yellow", "price": 9,     "tags": ["rain", "outdoor"],    "specs": {"waterproof": true}}');
SELECT id, name, attributes FROM products ORDER BY id;
```

`json` กับ `jsonb` ต่างกันตรงประเด็นข้างบนพอดี literal เดียวกัน ที่มีช่องว่างเกินและ key ซ้ำ:

```sql
-- sql/json-vs-jsonb.sql
SELECT '{"b": 1,   "a": 2, "a": 3}'::json  AS as_json,
       '{"b": 1,   "a": 2, "a": 3}'::jsonb AS as_jsonb;
```

```text
          as_json           |     as_jsonb     
----------------------------+------------------
 {"b": 1,   "a": 2, "a": 3} | {"a": 3, "b": 1}
(1 row)
```

`json` เก็บข้อความตามที่เขียน (ช่องว่าง, key `"a"` ทั้งสอง, ลำดับ) `jsonb` ปรับให้เป็นมาตรฐาน: `{"a": 3, "b": 1}` ตัวซ้ำสุดท้ายชนะ ([docs](https://www.postgresql.org/docs/18/datatype-json.html)) JSON ที่ไม่ถูกต้องถูกปฏิเสธตอน insert พร้อมตำแหน่งที่แน่นอน:

```sql
-- @expect-error 22P02
INSERT INTO products (name, attributes) VALUES ('Broken', '{"color": }');
```

```text

LINE 1: ...NTO products (name, attributes) VALUES ('Broken', '{"color":...
                                                             ^
DETAIL:  Expected JSON value, but found "}".
CONTEXT:  JSON data, line 1: {"color": }
```

## เข้าไปข้างในเอกสาร

`->` คืนค่า `jsonb`, `->>` คืน `text` และ `#>` / `#>>` เดินตาม path key ที่ไม่มีคืน `NULL` ไม่ใช่ error:

```sql
-- sql/operators.sql
SELECT name,
       attributes -> 'color'                     AS color_jsonb,
       attributes ->> 'color'                    AS color_text,
       attributes #>> '{specs,weight_g}'         AS weight,
       attributes -> 'tags' -> 0                 AS first_tag,
       attributes ->> 'missing'                  AS missing_key
FROM products
ORDER BY id;
```

```text
     name      | color_jsonb | color_text | weight | first_tag | missing_key 
---------------+-------------+------------+--------+-----------+-------------
 Trail Jacket  | "teal"      | teal       | 480    | "outdoor" | 
 City Backpack | "black"     | black      | 900    | "urban"   | 
 Camp Stove    | "silver"    | silver     | 350    | "outdoor" | 
 Wool Socks    | "teal"      | teal       |        | "outdoor" | 
 Rain Poncho   | "yellow"    | yellow     |        | "rain"    | 
(5 rows)
```

เพราะ `->>` ให้ text การคำนวณและการเปรียบเทียบตัวเลขจึงต้อง cast:

```sql
-- sql/numeric-cast.sql
SELECT name, (attributes ->> 'price')::numeric AS price
FROM products
WHERE (attributes ->> 'price')::numeric > 40
ORDER BY price DESC;
```

## กรองด้วย containment และการทดสอบ key

`@>` ถามว่า "เอกสารซ้ายมีเอกสารขวาอยู่ข้างในไหม?" มัน match object ซ้อนและสมาชิกของ array ซึ่งเป็นเหตุที่ทำให้ index ได้ `?`, `?|` และ `?&` ทดสอบ key:

```sql
-- sql/containment.sql
SELECT name FROM products WHERE attributes @> '{"color": "teal"}' ORDER BY id;
-- nested keys and array elements work in containment too
SELECT name FROM products WHERE attributes @> '{"specs": {"waterproof": true}, "tags": ["rain"]}' ORDER BY id;
-- key existence, any key, all keys
SELECT name FROM products WHERE attributes ? 'specs' ORDER BY id;
SELECT name FROM products WHERE attributes ?| array['specs', 'discount'] ORDER BY id;
SELECT name FROM products WHERE attributes ?& array['specs', 'tags'] ORDER BY id;
```

**jsonpath** ([docs](https://www.postgresql.org/docs/18/functions-json.html#FUNCTIONS-SQLJSON-PATH)) เป็นภาษา query ขนาดเล็กบนเอกสาร `jsonb_path_query` ดึงค่า, `@?` ทดสอบการมีอยู่พร้อมตัวกรอง, `jsonb_path_exists` เป็นรูปแบบฟังก์ชัน:

```sql
-- sql/jsonpath.sql
SELECT name, jsonb_path_query(attributes, '$.specs.weight_g') AS weight_g
FROM products ORDER BY id;
SELECT name FROM products WHERE attributes @? '$.specs ? (@.weight_g < 500)' ORDER BY id;
SELECT name FROM products WHERE jsonb_path_exists(attributes, '$.tags[*] ? (@ == "cooking")') ORDER BY id;
```

PostgreSQL 17 เพิ่ม `JSON_TABLE` ซึ่งเปลี่ยนเอกสารเป็น column เชิงสัมพันธ์ใน clause เดียว (ค่าที่ไม่มีเป็น `NULL`):

```sql
-- sql/json-table.sql
SELECT p.name, jt.color, jt.price, jt.weight_g
FROM products AS p,
     JSON_TABLE(p.attributes, '$' COLUMNS (
       color    text    PATH '$.color',
       price    numeric PATH '$.price',
       weight_g int     PATH '$.specs.weight_g'
     )) AS jt
ORDER BY p.id;
```

```text

---------------+--------+-------+----------
 Trail Jacket  | teal   | 129.5 |      480
 City Backpack | black  |    89 |      900
 Camp Stove    | silver |    45 |      350
 Wool Socks    | teal   |  12.5 |         
 Rain Poncho   | yellow |     9 |         
(5 rows)
```

และเพื่อเปลี่ยนสมาชิก array เป็น row ใช้ `jsonb_array_elements_text`; ไปอีกทางใช้ `jsonb_build_object` และ `jsonb_agg`:

```sql
-- sql/expand-arrays.sql
SELECT tag, count(*) AS products

GROUP BY tag
```

```sql
-- sql/build-and-agg.sql
SELECT jsonb_build_object('total', count(*), 'names', jsonb_agg(name ORDER BY name)) AS summary
FROM products
WHERE attributes @> '{"tags": ["outdoor"]}';
```

### สองกับดัก

กับดักแรก: การเทียบผลของ `->` กับสตริงเปล่า ๆ `->` คืน `jsonb` ฝั่งขวาจึงถูก parse เป็น JSON และ `teal` ไม่ใช่ JSON ที่ถูกต้อง error เป็น error การ parse JSON ไม่ใช่ error เรื่องชนิด:

```sql
-- @expect-error 22P02
SELECT name FROM products WHERE attributes -> 'color' = 'teal';
```

```text
ERROR:  invalid input syntax for type json
LINE 1: ...ECT name FROM products WHERE attributes -> 'color' = 'teal';
                                                                ^
DETAIL:  Token "teal" is invalid.
CONTEXT:  JSON data, line 1: teal
```

ทั้งสองแบบนี้ใช้ได้: เทียบกับ JSON string (`'"teal"'`) หรือดึง text ด้วย `->>` แล้วเทียบกับสตริงธรรมดา:

```sql
-- sql/equality-forms.sql
SELECT name FROM products WHERE attributes -> 'color' = '"teal"' ORDER BY id;
SELECT name FROM products WHERE attributes ->> 'color' = 'teal' ORDER BY id;
```

```text
     name     
--------------
 Trail Jacket
 Wool Socks
(2 rows)

     name     
--------------
 Trail Jacket
 Wool Socks
(2 rows)
```

กับดักที่สอง: `->>` คืน **text** และ text เทียบทีละตัวอักษร `'9' > '50'` เป็นจริง `'129.5' > '50'` เป็นเท็จ นี่คือคำตอบผิดแบบเงียบ และหัวข้อ *Reading AI-generated code* ด้านล่างสร้างจากมัน:

```sql
-- sql/text-comparison-trap.sql
-- ->> returns text, and text compares character by character: '9' sorts after '89'
SELECT name, attributes ->> 'price' AS price_text
FROM products
WHERE attributes ->> 'price' > '50'
ORDER BY name;
```

```text
     name      | price_text 
---------------+------------
 City Backpack | 89
 Rain Poncho   | 9
(2 rows)
```

## Update บางส่วนของเอกสาร

`||` รวมสองเอกสารแต่เฉพาะระดับบนสุด การตั้ง `specs` ด้วยวิธีนี้ **แทนที่ทั้ง object `specs`** (key `waterproof` หายไป) `jsonb_set(doc, path, value)` เปลี่ยน path ซ้อนหนึ่งจุดและเก็บ key พี่น้อง argument ที่สี่ `create_missing` (ค่าเริ่มต้น `true`) ตัดสินว่าจะสร้าง key สุดท้ายที่ไม่มีหรือไม่; `-` และ `#-` ลบ key หรือ key ซ้อน ทั้งหมดด้านล่างอยู่ใน transaction ที่ rollback:

```sql
-- sql/update-documents.sql
BEGIN;
-- || merges TOP-LEVEL keys only: the whole "specs" object is replaced
UPDATE products SET attributes = attributes || '{"specs": {"weight_g": 470}}' WHERE name = 'Trail Jacket'
RETURNING name, attributes -> 'specs' AS specs_after_concat;
ROLLBACK;
BEGIN;
-- jsonb_set changes one nested path and keeps its siblings
UPDATE products SET attributes = jsonb_set(attributes, '{specs,weight_g}', '470') WHERE name = 'Trail Jacket'
RETURNING name, attributes -> 'specs' AS specs_after_set;
-- missing path: create_missing (default true) creates the last key, false leaves the row alone
UPDATE products SET attributes = jsonb_set(attributes, '{specs,fabric}', '"nylon"', false) WHERE name = 'Trail Jacket'
RETURNING attributes -> 'specs' AS specs_create_missing_false;
-- remove a key, and a nested key
UPDATE products SET attributes = attributes - 'tags' #- '{specs,waterproof}' WHERE name = 'Trail Jacket'
RETURNING attributes;
ROLLBACK;
```

```text
BEGIN
     name     | specs_after_concat 
--------------+--------------------
 Trail Jacket | {"weight_g": 470}
(1 row)

UPDATE 1
ROLLBACK
BEGIN
     name     |            specs_after_set            
--------------+---------------------------------------
 Trail Jacket | {"weight_g": 470, "waterproof": true}
(1 row)

UPDATE 1
      specs_create_missing_false       
---------------------------------------
 {"weight_g": 470, "waterproof": true}
(1 row)

UPDATE 1
                          attributes                           
---------------------------------------------------------------
 {"color": "teal", "price": 129.5, "specs": {"weight_g": 470}}
(1 row)

UPDATE 1
ROLLBACK
```

## Index สำหรับ query แบบ containment

เมื่อไม่มี index query แบบ containment อ่านทุก row นี่คือ `catalog` 100 000 row ที่มีเอกสารแบบเดียวกัน query ขอสินค้าสี teal ที่ติดแท็ก `t7`:

```sql
-- sql/catalog-setup.sql
CREATE TABLE catalog (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  attributes jsonb NOT NULL
);
INSERT INTO catalog (attributes)
SELECT jsonb_build_object(
         'color',  (ARRAY['teal', 'black', 'silver', 'yellow', 'red', 'green', 'blue', 'white'])[1 + h % 8],
         'price',  5 + (h / 8) % 200,
         'tags',   jsonb_build_array('t' || (h / 1600) % 60, 't' || (h / 96000) % 97),
         'specs',  jsonb_build_object('weight_g', 100 + (h / 7) % 900))
FROM (SELECT ('x' || substr(md5(g::text), 1, 7))::bit(28)::int AS h FROM generate_series(1, 100000) g) s;
ANALYZE catalog;
SELECT count(*) AS rows, pg_size_pretty(pg_relation_size('catalog')) AS heap FROM catalog;
```

```text
CREATE TABLE
INSERT 0 100000
ANALYZE
  rows  | heap  
--------+-------
 100000 | 15 MB
(1 row)
```

```sql
-- sql/catalog-no-index.sql
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF)
SELECT count(*) FROM catalog WHERE attributes @> '{"color": "teal", "tags": ["t7"]}';
```

```text

----------------------------------------------------------------------------
 Aggregate (actual time=15.556..15.561 rows=1.00 loops=1)
   ->  Seq Scan on catalog (actual time=0.133..15.531 rows=330.00 loops=1)
         Filter: (attributes @> '{"tags": ["t7"], "color": "teal"}'::jsonb)
         Rows Removed by Filter: 99670
 Planning Time: 0.215 ms
 Execution Time: 15.599 ms
(6 rows)
```

GIN index แบบ `jsonb_path_ops` (เล็กกว่าและเร็วกว่าสำหรับ `@>`; class `jsonb_ops` เริ่มต้นรองรับ `?` ด้วย) เปลี่ยนมันเป็นการค้นหาผ่าน index:

```sql
-- sql/catalog-gin.sql
CREATE INDEX catalog_attr_gin ON catalog USING gin (attributes jsonb_path_ops);
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF)
```

### เอกสารใหญ่และ TOAST

row ที่ใหญ่กว่าราว 2 kB จะถูกย้ายค่าใหญ่ออกไปไว้ใน **TOAST** table (และบีบอัดถ้าช่วยได้) เอกสาร `jsonb` ถูกเก็บเป็นค่าเดียว การเปลี่ยน key เล็ก ๆ หนึ่งตัวจึงเขียนเอกสารใหม่ทั้งฉบับ เอกสาร 2 000 ฉบับขนาดราว 9.6 kB (ข้อความสุ่มซึ่งบีบอัดไม่ได้):

```sql
-- sql/toast.sql
CREATE TABLE docs (id int PRIMARY KEY, body jsonb NOT NULL);
INSERT INTO docs
SELECT g, jsonb_build_object('id', g, 'note', 'first', 'blob', (SELECT string_agg(md5(random()::text), '') FROM generate_series(1, 300)))
FROM generate_series(1, 2000) g;
ANALYZE docs;
SELECT pg_column_size(body) AS stored_bytes, octet_length(body::text) AS as_text_bytes FROM docs WHERE id = 1;
SELECT pg_size_pretty(pg_relation_size('docs')) AS heap,
       pg_size_pretty(pg_relation_size((SELECT reltoastrelid FROM pg_class WHERE relname = 'docs'))) AS toast;
-- change ONE small key in every document
UPDATE docs SET body = jsonb_set(body, '{note}', '"second"');
SELECT pg_size_pretty(pg_relation_size((SELECT reltoastrelid FROM pg_class WHERE relname = 'docs'))) AS toast_after_small_update;
```

heap มี 104 kB และเอกสารอยู่ใน TOAST (20 MB) การเปลี่ยน key เล็ก `note` ในทุกเอกสารทำให้ TOAST table โตเป็น 39 MB: แต่ละ update เขียนสำเนาเต็มของเอกสารใหม่ และสำเนาเก่ารอ `VACUUM` ถ้าคุณ update field เดียวของเอกสารใหญ่บ่อย field นั้นควรเป็น column ของตัวเอง

## Reading AI-generated code

ผู้ช่วย AI ถูกขอ "สินค้าที่แพงกว่า 100" จากราคาใน `jsonb` และเขียน query ที่ตรงไปตรงมา:

<SpotTheBug lang="sql" code={`-- AI comment: "products over 100"
SELECT name, attributes ->> 'price' AS price
FROM products
WHERE attributes ->> 'price' > '100'
ORDER BY name;`}>

ผลดูสมเหตุสมผลและผิด `->>` ให้ text และ text เรียงทีละตัวอักษร `'9'`, `'12.5'`, `'45'` และ `'89'` จึง "มากกว่า" `'100'` ทั้งหมด บนข้อมูลนี้ query คืน **ทุก** สินค้า รวมถึงตัวที่ราคา 9 และ 12.5 และจะทิ้งหรือรวมตัวที่ผิดเมื่อราคาเปลี่ยน:

```sql
-- sql/stb-wrong.sql
SELECT name, attributes ->> 'price' AS price
FROM products
WHERE attributes ->> 'price' > '100'
ORDER BY name;
```

## Mental Model

`jsonb` เป็นชนิดค่าที่บังเอิญมี key คุณดึงจากมันได้ (`->`, `->>`, jsonpath) ทดสอบได้ (`@>`, `?`) สร้างใหม่ได้ (`||`, `jsonb_set`, `-`) และคลายเป็น row ได้ (`jsonb_each`, `jsonb_array_elements`, `JSON_TABLE`) การดึงให้ `jsonb` หรือ `text`: เลือกอย่างตั้งใจ และ cast ก่อนเทียบตัวเลขหรือวันที่ การเก็บคือหนึ่งค่าทึบต่อ row: GIN index ทำให้ containment เร็ว และทุกการเขียนไปยัง key ใดก็เขียนทั้งค่าใหม่

## เคล็ดลับและข้อควรระวัง

- ใช้ `jsonb` ไม่ใช่ `json` เว้นแต่ต้องรักษาข้อความเดิมเป๊ะ
- `->` คืน `jsonb`, `->>` คืน `text`; cast (`::numeric`, `::date`) ก่อนเทียบตัวเลขหรือวันที่
- ใช้ `@>` สำหรับตัวกรองที่ต้องการ index; `attributes->>'k' = 'v'` ต้องใช้ expression index แทน
- `||` เป็น shallow merge; ใช้ `jsonb_set` สำหรับการเปลี่ยนแบบซ้อน
- column ที่คุณ filter, join หรือ update บ่อย ควรมี column จริงของตัวเอง เก็บ `jsonb` ไว้สำหรับส่วนที่ยืดหยุ่นจริง ๆ
- driver ต่างกัน: `pg` parse เป็น object, `psycopg` ให้ `dict`, `pgx` ให้ `map[string]any`, `sqlx` ต้องมี feature flag

<Callout title="column ของเอกสารไม่ใช่ schema">
`jsonb` ให้คุณเลื่อนการตัดสินใจ แต่ไม่ได้ขจัดมัน constraint, ชนิด และ foreign key อยู่บน column จริง รูปแบบที่ดีคือ column จริงสำหรับสิ่งที่ query, join และ constrain และ column `jsonb` หนึ่งตัวสำหรับส่วนหางยาว
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| column `jsonb` | รูปร่างยืดหยุ่น ไม่ต้อง migration ต่อ attribute index ด้วย GIN ได้ | ไม่ตรวจชนิดของ key; การเปลี่ยนเล็ก ๆ เขียนเอกสารใหม่ทั้งฉบับ (TOAST 20 MB เป็น 39 MB ข้างบน) |
| column จริง | ชนิด, constraint, foreign key, update ถูก | ต้องเปลี่ยน schema (migration) ต่อ attribute ใหม่ |
| `json` (text) | รักษาข้อความเดิม | parse ใหม่ทุกครั้งที่เข้าถึง index ไม่ได้ |
| GIN `jsonb_path_ops` | 16 ms เหลือ 0.8 ms สำหรับ `@>` | 1.7 MB ที่นี่; ไม่รองรับ `?` |

## Common Misconceptions

- **"`->` คืน text"** มันคืน `jsonb`; การเทียบกับ `'teal'` เป็น error การ parse JSON `->>` ต่างหากที่คืน text
- **"`jsonb` เก็บลำดับ key และค่าซ้ำของฉัน"** มันไม่เก็บทั้งสอง: `{"a": 3, "b": 1}`
- **"`||` รวม object ซ้อนกัน"** มันแทนที่ทั้ง object ซ้อน: `specs` เสีย `waterproof`
- **"การเทียบค่า `->>` เป็นตัวเลขใช้ได้"** มันเทียบ text: `'9' > '50'`
- **"GIN index เร่งทุกตัวกรองบน column"** เฉพาะ operator containment/existence บน column ไม่ใช่ expression `->>`
