จนถึงตอนนี้ตรรกะทุกชิ้นอยู่ในแอปพลิเคชันของคุณ PostgreSQL รันตรรกะเองได้ด้วย: **function** คือบล็อกโค้ดที่มีชื่อและใช้ซ้ำได้ เก็บในฐานข้อมูล และ **trigger** คือกฎที่เรียก function โดยอัตโนมัติเมื่อ row เปลี่ยน ทั้งสองอย่างรวมกันให้คุณบังคับพฤติกรรมในที่เดียว ไม่ว่าแอปหรือคนไหนแตะ table

ทุกอย่างด้านล่างรันบน **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) fence `sql` รันจากบนลงล่างในฐานข้อมูลเปล่าหนึ่งตัว ผลลัพธ์ (รวมข้อความ `NOTICE`) คัดลอกจาก `psql` ตัวเลขเวลามาจาก Mac เครื่องนี้

## ชุดข้อมูล

table `products` ที่ติดตามว่าแต่ละ row เปลี่ยนล่าสุดเมื่อไร และ table `product_audit` สำหรับบันทึกการเปลี่ยนแปลง:

```sql
-- sql/setup.sql
CREATE TABLE products (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       text NOT NULL,
  price      numeric(10, 2) NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE product_audit (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  product_id bigint NOT NULL,
  action     text NOT NULL,
  old_price  numeric(10, 2),
  new_price  numeric(10, 2),
  changed_at timestamptz NOT NULL DEFAULT now()
);
INSERT INTO products (name, price) VALUES ('Trail Jacket', 129.50), ('City Backpack', 89.00), ('Camp Stove', 45.00);
```

## function PL/pgSQL ขนาดเล็ก

`CREATE FUNCTION` ด้วย `LANGUAGE plpgsql` นิยาม function ในภาษาโพรซีเดอรัลของ PostgreSQL PL/pgSQL เพิ่มตัวแปร เงื่อนไข และ loop บน SQL ตัวนี้ลดราคาตามเปอร์เซ็นต์ และปฏิเสธ input ที่ไร้สาระด้วย `RAISE EXCEPTION` มันถูกระบุเป็น `IMMUTABLE` (input เดียวกัน ผลเดียวกัน ไม่เข้าถึงฐานข้อมูล) ด้วยเหตุผลที่อธิบายสองหัวข้อถัดไป:

```sql
-- sql/function.sql
CREATE FUNCTION apply_discount(price numeric, pct numeric)
RETURNS numeric
LANGUAGE plpgsql
IMMUTABLE
AS $$
BEGIN
  IF pct < 0 OR pct > 100 THEN
    RAISE EXCEPTION 'discount must be between 0 and 100, got %', pct;
  END IF;
  RETURN round(price * (1 - pct / 100), 2);
END;
$$;

SELECT name, price, apply_discount(price, 15) AS after_15_percent FROM products ORDER BY id;
```

```text

---------------+--------+------------------

 City Backpack |  89.00 |            75.65
 Camp Stove    |  45.00 |            38.25
(3 rows)
```

input ที่ผิดล้มด้วยข้อความชัดเจน และ SQLSTATE `P0001` (ค่าเริ่มต้นของ `RAISE EXCEPTION`) บวกบรรทัด `CONTEXT` ที่บอกชื่อ function และบรรทัด:

```sql
-- @expect-error P0001

```


### IMMUTABLE, STABLE, VOLATILE

ทุก function มีป้าย **volatility** ที่บอก planner ว่าสมมติอะไรได้ `IMMUTABLE`: argument เดียวกัน ผลเดียวกัน ตลอดไป (`lower`, เลขคณิต) `STABLE`: ผลเดียวกันภายใน statement เดียว (`now()` หรือการอ่าน table) `VOLATILE` (ค่าเริ่มต้น): อะไรก็ได้ รวมถึง side effect (`random()`) มันสำคัญกับ index: expression index ต้องการ function ที่ planner เชื่อได้ว่าไม่เปลี่ยนคำตอบ function ใหม่เป็น `VOLATILE` โดยค่าเริ่มต้น:

```sql
-- sql/volatility.sql
CREATE TABLE items (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, price numeric(10, 2) NOT NULL);
INSERT INTO items (price) SELECT (g % 1000) + 0.5 FROM generate_series(1, 100000) g;
-- a function is VOLATILE unless you say otherwise
CREATE FUNCTION discounted(p numeric) RETURNS numeric LANGUAGE plpgsql
AS $$ BEGIN RETURN round(p * 0.9, 2); END; $$;
SELECT proname, provolatile FROM pg_proc WHERE proname = 'discounted';
```

```text
CREATE TABLE
INSERT 0 100000
CREATE FUNCTION
  proname   | provolatile 
------------+-------------
 discounted | v
(1 row)
```

```sql
-- @expect-error 42P17
CREATE INDEX items_discounted_idx ON items (discounted(price));
```

```text
ERROR:  functions in index expression must be marked IMMUTABLE
```

ประกาศเป็น `IMMUTABLE` (เฉพาะเมื่อเป็นจริง: index ที่สร้างบน function ที่โกหกจะคืนคำตอบผิดทีหลัง) แล้ว index ทำงานและถูกใช้โดย query ที่เขียน expression ซ้ำ:

```sql
-- sql/volatility-immutable.sql
ALTER FUNCTION discounted(numeric) IMMUTABLE;
CREATE INDEX items_discounted_idx ON items (discounted(price));
ANALYZE items;
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM items WHERE discounted(price) = 450.45;
```

## trigger function

trigger function ไม่รับ argument และคืน `trigger` ข้างใน `NEW` คือ row ที่กำลังเขียนและ `OLD` คือ row ที่มันแทนที่; `TG_OP` บอกการดำเนินการ `BEFORE` row trigger เปลี่ยน `NEW` ได้และ **ต้อง return มัน** เพื่อให้ row ถูกเขียน ตัวนี้ทำให้ `updated_at` ตรงเสมอไม่ว่า client ไหนจะ update row:

```sql
-- sql/before-trigger.sql
CREATE FUNCTION set_updated_at() RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  NEW.updated_at := now();
  RETURN NEW;
END;
$$;

CREATE TRIGGER products_set_updated_at
BEFORE UPDATE ON products
FOR EACH ROW EXECUTE FUNCTION set_updated_at();

-- the caller never mentions updated_at, yet it changes
UPDATE products SET price = 132.00 WHERE name = 'Trail Jacket'
RETURNING name, price, old.updated_at < new.updated_at AS timestamp_bumped;
```

```text
CREATE FUNCTION
CREATE TRIGGER
     name     | price  | timestamp_bumped 
--------------+--------+------------------
 Trail Jacket | 132.00 | t
(1 row)

UPDATE 1
```

`RETURNING old.updated_at < new.updated_at` (`old`/`new` ใน `RETURNING` ของ PostgreSQL 18) พิสูจน์ว่า timestamp ถูก trigger ยก statement ไม่เคยพูดถึง `updated_at`

## Audit ด้วย AFTER trigger และ WHEN

`AFTER` row trigger ทำงานเมื่อ row ถูกเขียนแล้ว ค่าที่คืนถูกละเลย `RETURN NULL` จึงใช้ได้ clause `WHEN` กรองที่ระดับ trigger: trigger สำหรับ update ด้านล่างทำงานเมื่อราคาเปลี่ยนจริงเท่านั้น และ update เหมือนเดิมครั้งที่สองไม่ทิ้ง audit row:

```sql
-- sql/after-trigger.sql
CREATE FUNCTION audit_product() RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    INSERT INTO product_audit (product_id, action, new_price) VALUES (NEW.id, 'insert', NEW.price);
  ELSE
    INSERT INTO product_audit (product_id, action, old_price, new_price) VALUES (NEW.id, 'update', OLD.price, NEW.price);
  END IF;
  RETURN NULL;   -- the return value of an AFTER row trigger is ignored
END;
$$;

CREATE TRIGGER products_audit_insert AFTER INSERT ON products
FOR EACH ROW EXECUTE FUNCTION audit_product();

-- WHEN: fire only if the price really changed
CREATE TRIGGER products_audit_update AFTER UPDATE ON products
FOR EACH ROW WHEN (OLD.price IS DISTINCT FROM NEW.price)
EXECUTE FUNCTION audit_product();

INSERT INTO products (name, price) VALUES ('Wool Socks', 12.50);
UPDATE products SET price = 14.00 WHERE name = 'Wool Socks';
UPDATE products SET price = 14.00 WHERE name = 'Wool Socks';   -- same price: the audit trigger does not fire
SELECT product_id, action, old_price, new_price FROM product_audit ORDER BY id;
```

```text

------------+--------+-----------+-----------
```

## พฤติกรรม trigger อื่น ๆ

**`BEFORE` trigger ที่คืน `NULL` ยกเลิกการดำเนินการสำหรับ row นั้น** อย่างเงียบ ๆ (statement รายงาน `DELETE 0` และไม่มี error) บางครั้งมีประโยชน์ มักทำให้แปลกใจ:

```sql
-- sql/cancel-row.sql
CREATE FUNCTION forbid_delete() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  RAISE NOTICE 'not deleting %', OLD.name;
  RETURN NULL;   -- NULL from a BEFORE row trigger silently skips this row
END;
$$;
CREATE TRIGGER products_no_delete BEFORE DELETE ON products FOR EACH ROW EXECUTE FUNCTION forbid_delete();
DELETE FROM products WHERE name = 'Camp Stove';
SELECT count(*) AS products_left FROM products;
DROP TRIGGER products_no_delete ON products;
```

```text
CREATE FUNCTION
CREATE TRIGGER
NOTICE:  not deleting Camp Stove
DELETE 0
 products_left 
---------------
             5
(1 row)

DROP TRIGGER
```

**trigger ระดับ statement** ทำงานครั้งเดียวต่อ statement ไม่ใช่ต่อ row และเห็น row ที่เปลี่ยนทั้งหมดผ่าน *transition table* (`REFERENCING NEW TABLE AS new_rows`) ตรงนี้ `UPDATE` หนึ่งครั้งของห้า row สร้าง notice หนึ่งข้อความ:

```sql
-- sql/statement-trigger.sql
CREATE FUNCTION log_bulk() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  RAISE NOTICE 'statement changed % rows, average new price %',
    (SELECT count(*) FROM new_rows), (SELECT round(avg(price), 2) FROM new_rows);
  RETURN NULL;
END;
$$;
CREATE TRIGGER products_bulk AFTER UPDATE ON products
REFERENCING NEW TABLE AS new_rows
FOR EACH STATEMENT EXECUTE FUNCTION log_bulk();
BEGIN;
UPDATE products SET price = price * 1.1;
ROLLBACK;
DROP TRIGGER products_bulk ON products;
```

```text
CREATE FUNCTION
CREATE TRIGGER
BEGIN
NOTICE:  statement changed 5 rows, average new price 65.78
UPDATE 5
ROLLBACK
DROP TRIGGER
```

**การตรวจสอบ** ควรอยู่ใน constraint `CHECK` เมื่อเขียนเป็นแบบนั้นได้ เมื่อทำไม่ได้ (ต้องดู table อื่น หรือต้องการข้อความเอง) `BEFORE` trigger ส่ง error class เดียวกันได้ด้วย `USING ERRCODE = 'check_violation'` (SQLSTATE `23514`):

```sql
-- sql/raise-in-trigger.sql
CREATE FUNCTION require_positive_price() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.price <= 0 THEN
    RAISE EXCEPTION 'price must be positive, got %', NEW.price USING ERRCODE = 'check_violation';
  END IF;
  RETURN NEW;
END;
$$;
CREATE TRIGGER products_positive_price BEFORE INSERT OR UPDATE ON products
FOR EACH ROW EXECUTE FUNCTION require_positive_price();
```

```sql
-- @expect-error 23514
INSERT INTO products (name, price) VALUES ('Free Thing', 0);
```

```text
ERROR:  price must be positive, got 0.00
CONTEXT:  PL/pgSQL function require_positive_price() line 4 at RAISE
```

## trigger วนซ้ำได้

trigger ที่เขียนลง table ของตัวเองจะทำให้ตัวเองทำงาน trigger `AFTER UPDATE` นี้ update row เดิมอีกครั้ง ซึ่งทำให้ trigger ทำงานอีก จนกระทั่ง PostgreSQL ยอมแพ้:

```sql
-- sql/recursion-setup.sql
CREATE FUNCTION touch_again() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  UPDATE products SET updated_at = now() WHERE id = NEW.id;   -- fires this trigger again
  RETURN NULL;
END;
$$;
CREATE TRIGGER products_touch AFTER UPDATE ON products FOR EACH ROW EXECUTE FUNCTION touch_again();
```

```sql
-- @expect-error stack depth limit exceeded
\set VERBOSITY terse
UPDATE products SET price = price WHERE id = 1;
\set VERBOSITY verbose
```

```text
ERROR:  stack depth limit exceeded
```

(`\set VERBOSITY terse` ซ่อน `CONTEXT` ราว 100 บรรทัดที่แต่ละระดับพิมพ์ซ้ำ ข้อความเต็มยังมี `HINT: Increase the configuration parameter "max_stack_depth" (currently 2048kB)` ซึ่งเป็นวิธีแก้ที่ผิด: recursion ไม่มีจุดจบ) ตัวป้องกันคือ `pg_trigger_depth()` ที่นับการเรียก trigger ซ้อน ด้วย `WHEN (pg_trigger_depth() = 0)` trigger ทำงานเฉพาะ statement ของผู้ใช้เอง:

```sql
-- sql/recursion-fix.sql
DROP TRIGGER products_touch ON products;
CREATE TRIGGER products_touch AFTER UPDATE ON products
FOR EACH ROW WHEN (pg_trigger_depth() = 0) EXECUTE FUNCTION touch_again();
UPDATE products SET price = price WHERE id = 1 RETURNING name, price;
DROP TRIGGER products_touch ON products;
```

```text
DROP TRIGGER
CREATE TRIGGER
     name     | price  
--------------+--------
 Trail Jacket | 132.00
(1 row)

UPDATE 1
DROP TRIGGER
```

## trigger ทำงานอย่างไร

การไหลเหมือนกันเสมอ: statement เขียนมาถึง PostgreSQL ตรวจพบว่าตรงกับ event ของ trigger, trigger function ทำงาน และการดำเนินการดำเนินต่อด้วยสิ่งที่ function คืน `pg_trigger` ลิสต์ trigger บน table:

export const triggerDiagram = `flowchart TD
  W["INSERT or UPDATE on products"] --> E{"Matches a trigger event?"}
  E -->|BEFORE| B["set_updated_at runs, returns NEW"]
  B --> S[("Row written with new timestamp")]
  E -->|AFTER| A["audit_product runs"]
  S --> A
  A --> L[("Row recorded in product_audit")]`;

## trigger มีต้นทุนเท่าไร

row trigger คือการเรียก function หนึ่งครั้งต่อ row สอง table เหมือนกัน 200 000 row อันหนึ่งมี `BEFORE UPDATE` trigger ที่แค่ประทับ column:

```sql
-- sql/trigger-cost.sql
CREATE TABLE t_plain (id int PRIMARY KEY, n int NOT NULL, touched timestamptz);
CREATE TABLE t_trig  (id int PRIMARY KEY, n int NOT NULL, touched timestamptz);
INSERT INTO t_plain SELECT g, 0, now() FROM generate_series(1, 200000) g;
INSERT INTO t_trig  SELECT g, 0, now() FROM generate_series(1, 200000) g;
CREATE FUNCTION stamp() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN NEW.touched := clock_timestamp(); RETURN NEW; END;
$$;
CREATE TRIGGER t_trig_stamp BEFORE UPDATE ON t_trig FOR EACH ROW EXECUTE FUNCTION stamp();
VACUUM ANALYZE t_plain;
VACUUM ANALYZE t_trig;
\timing on
UPDATE t_plain SET n = n + 1;
UPDATE t_trig  SET n = n + 1;
\timing off
```


437 ms เมื่อไม่มี trigger, 636 ms เมื่อมี: ใช้เวลามากขึ้นราว 45 % สำหรับ trigger ที่แทบไม่ทำอะไร ซึ่งไม่เป็นไรสำหรับ audit log บน table แบบ OLTP แต่มากสำหรับ bulk load trigger ระดับ statement ที่ใช้ transition table จ่ายครั้งเดียวต่อ statement แทนต่อ row

## SECURITY DEFINER

function ปกติรันด้วยสิทธิ์ของผู้เรียก `SECURITY DEFINER` ทำให้มันรันด้วยสิทธิ์ของ **เจ้าของ**: ประตูที่ควบคุมได้ไปสู่ข้อมูลที่ผู้เรียกแตะไม่ได้ ตรงนี้ `app_user` ไม่มีสิทธิ์บน `secrets` แต่เรียก function ที่นับ row ของมันได้:

```sql
-- sql/security-definer.sql
CREATE TABLE secrets (id int PRIMARY KEY, note text NOT NULL);
INSERT INTO secrets VALUES (1, 'a'), (2, 'b'), (3, 'c');
CREATE ROLE app_user NOLOGIN;
GRANT USAGE ON SCHEMA public TO app_user;

-- runs with the OWNER's rights, so app_user can count rows it cannot SELECT
CREATE FUNCTION secret_count() RETURNS bigint LANGUAGE sql SECURITY DEFINER
AS 'SELECT count(*) FROM secrets';
GRANT EXECUTE ON FUNCTION secret_count() TO app_user;
```

ประตูนั้นมีกับดักที่รู้จักกันดี ซึ่งหัวข้อถัดไปใช้

## Mental Model

function คือโค้ดที่เก็บไว้ข้างข้อมูล; trigger คือการสมัครรับ: "เมื่อ event นี้เกิดกับ table นี้ ให้เรียก function นั้น" trigger `BEFORE` อยู่บนเส้นทางการเขียนและแก้หรือ veto row ได้; trigger `AFTER` เห็น row ที่เสร็จแล้วและใช้สำหรับผลที่ตามมา ทุกอย่างที่ trigger ทำรันใน transaction เดียวกับ statement จึง commit หรือ rollback ไปพร้อมกัน และรันไม่ว่าผู้เรียกจะรู้ว่ามันมีอยู่หรือไม่ นั่นคือทั้งคุณค่าและอันตราย

## เคล็ดลับและข้อควรระวัง

- trigger ซ่อนตรรกะจากคนที่อ่านโค้ดแอป บันทึกทุก trigger (ทำอะไรและอยู่บน table ไหน) เพื่อไม่ให้ timestamp ที่อัปเดต "ด้วยเวทมนตร์" เป็นปริศนา
- เก็บ function ให้เล็กและมีจุดประสงค์เดียว function ที่ตรวจสอบ input ทดสอบและใช้ซ้ำได้ง่าย
- เลือก `BEFORE` เพื่อแก้หรือตรวจสอบ row ที่เข้ามา (เปลี่ยน `NEW` ได้) และ `AFTER` สำหรับ side effect เช่น logging ที่ควรเกิดเมื่อการเขียนสำเร็จแล้ว
- function ของ `BEFORE` row-level trigger ต้อง `RETURN NEW` เพื่อให้ row ผ่าน; การคืน `NULL` ยกเลิก row อย่างเงียบ ๆ
- ใช้ `WHEN (OLD.* IS DISTINCT FROM NEW.*)` หรือการทดสอบ column เพื่อไม่ให้ทำงานกับ update ที่ไม่เปลี่ยนอะไร และ `pg_trigger_depth()` เพื่อหยุด recursion
- ติดป้าย function อย่างซื่อสัตย์: `IMMUTABLE` เฉพาะเมื่อเป็น; expression ของ index ต้องการมัน
- ทุก function แบบ `SECURITY DEFINER` ต้องมี `SET search_path = ..., pg_temp` และ `GRANT EXECUTE` น้อยที่สุด
- เลือก constraint `CHECK` แทน trigger ตรวจสอบเมื่อมันแสดงกฎได้

<Callout title="ตรรกะที่ทำงานเสมอ">
จุดแข็งของ trigger คือข้ามไม่ได้: ทุก insert หรือ update ผ่านมัน ไม่ว่า client ไหนเป็นผู้เปลี่ยน จุดแข็งเดียวกันคืออันตรายของมัน: พฤติกรรมอยู่ในที่ที่โค้ดแอปไม่เคยพูดถึง ใช้ trigger สำหรับ invariant ที่คุณต้องการบังคับทุกที่จริง ๆ และเก็บทุกอย่างอื่นไว้ในแอป
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| trigger ในฐานข้อมูล | ทำงานกับทุก client ข้ามไม่ได้ | ตรรกะซ่อน; row trigger เพิ่ม 45 % บน update 200 000 ครั้ง (437 ms เป็น 636 ms) |
| ตรรกะเดียวกันในโค้ดแอป | เห็นได้ ทดสอบได้ มีเวอร์ชันไปกับแอป | ทุก client ต้องจำ; ถูกข้ามโดย SQL แบบ ad-hoc |
| trigger ระดับ statement + transition table | เรียกครั้งเดียวต่อ statement เห็นทุก row | ซับซ้อนกว่า; ไม่เหมาะกับการแก้ต่อ row |
| constraint `CHECK` | declarative ถูก เห็นใน `\d` | ดู table อื่นหรือปรับข้อความไม่ได้ |
| `SECURITY DEFINER` | เข้าถึงข้อมูลที่ผู้เรียกอ่านไม่ได้แบบควบคุมได้ | ถูกแย่งผ่าน search path ได้ถ้าไม่ตรึง |

## Common Misconceptions

- **"ค่าที่ trigger คืนสำคัญเสมอ"** สำคัญเฉพาะ `BEFORE` row trigger: `NULL` ยกเลิก row ใน `AFTER` trigger มันถูกละเลย
- **"function ใดก็ index ได้"** เฉพาะตัวที่ `IMMUTABLE` (หรือ SQL function ง่าย ๆ ที่ inline เป็น expression แบบ immutable)
- **"trigger ที่ update table ตัวเองไม่เป็นไร"** มันวนจน `stack depth limit exceeded`; ป้องกันด้วย `pg_trigger_depth()`
- **"`SECURITY DEFINER` ปลอดภัยเพราะผู้เรียกไม่มีสิทธิ์"** ผู้เรียกควบคุม `search_path` และ `pg_temp` (42 row จาก table ที่ผู้เรียกสร้างเอง)
- **"trigger ฟรี"** ช้าลง 45 % สำหรับ trigger ที่แค่ประทับ column
