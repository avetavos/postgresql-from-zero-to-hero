ทุก table เริ่มต้นชีวิตด้วยคำสั่ง `CREATE TABLE` คุณตั้งชื่อ table จากนั้นจึงไล่รายชื่อ column ของมันภายในวงเล็บ โดยให้แต่ละตัวมีชื่อและ data type เซิร์ฟเวอร์จะเก็บคำนิยามนั้นไว้ และนับจากนั้นก็จะบังคับใช้กับทุก row ที่คุณ insert การสร้าง table คือ **DDL** — data definition language — และมักจะเขียนและรันเป็น SQL ธรรมดา ไม่ว่าคุณจะพิมพ์ลงใน `psql` หรือป้อนให้กับเครื่องมือ migration

เราจะสร้าง table `products` สำหรับร้านค้าเล็ก ๆ และทำให้มันเติบโตขึ้นไปเรื่อย ๆ ตามที่บทเรียนดำเนินไป

## รูปทรงพื้นฐาน

อย่างน้อยที่สุดคือชื่อ table และ column หนึ่งตัวขึ้นไป แต่ละ column คือชื่อตามด้วยชนิด โดย column ต่าง ๆ คั่นด้วยจุลภาค

```sql
CREATE TABLE products (
  id     integer,
  name   text,
  price  numeric(10, 2)
);
```

นั่นสร้าง table ที่มีสาม column: `id` ที่เป็นจำนวนเต็ม, `name` ที่เป็น text และ `price` ที่เก็บเป็นทศนิยมแบบแม่นยำได้ถึงสิบหลักและสองหลักหลังจุด มันใช้ได้ แต่หลวมเกินไป — ไม่มีอะไรห้ามสินค้าสองชิ้นใช้ `id` ร่วมกัน และทุก column อาจถูกปล่อยว่างไว้ได้ เราจะแก้ปัญหานั้นด้วย primary key และ constraints ในลำดับถัดไป

**ใน pgAdmin:** หลังจากรันคำสั่งใน Query Tool ให้ refresh โหนด Tables ในแผนผัง browser แล้ว table `products` ใหม่จะปรากฏขึ้น เมื่อขยายมันออกจะเผยให้เห็นโหนด Columns ที่ไล่รายชื่อแต่ละ column และชนิดของมัน

## ตรวจสอบ table ด้วย backslash-d

ใน `psql` คำสั่ง `\d` จะอธิบาย table: column ของมัน, ชนิดของมัน, ความสามารถในการเป็น null และ default ใด ๆ มันเป็นวิธีที่เร็วที่สุดในการยืนยันว่า table มีหน้าตาอย่างที่คุณตั้งใจไว้

```sql
\d products
```

```text
                        Table "public.products"
 Column |     Type      | Collation | Nullable | Default
--------+---------------+-----------+----------+---------
 id     | integer       |           |          |
 name   | text          |           |          |
 price  | numeric(10,2) |           |          |
```

ตอนนี้ทุก column สามารถเป็น null ได้และยังไม่มี default เมื่อเราเพิ่ม primary key และ constraints เซลล์เหล่านั้นจะถูกเติมเต็มขึ้นมากขึ้น

## สร้าง primary key โดยอัตโนมัติ

คุณแทบไม่อยากกำหนดเลข id ด้วยมือเลย PostgreSQL ทำให้คุณได้ วิธีสมัยใหม่คือ `GENERATED ALWAYS AS IDENTITY` ซึ่งทำให้เซิร์ฟเวอร์จัดหาค่าถัดไปให้โดยอัตโนมัติ ทางลัดแบบเก่าคือ `SERIAL` ซึ่งคุณยังคงพบเห็นได้ในโค้ดที่มีอยู่จำนวนมาก

```sql
CREATE TABLE products (
  id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name   text NOT NULL,
  price  numeric(10, 2) NOT NULL
);
```

ตอนนี้ `id` ถูกเติมโดยเซิร์ฟเวอร์ ถูกประกาศให้เป็น primary key และ `name` กับ `price` ก็ไม่สามารถถูกปล่อยว่างได้อีกต่อไป table เดียวกันนี้ถ้าเขียนด้วยสไตล์เก่าจะใช้ `id bigserial PRIMARY KEY` ทั้งสองแบบให้คีย์ที่เพิ่มค่าอัตโนมัติ แบบ `IDENTITY` เป็นแบบที่เป็นมาตรฐาน SQL และเป็นที่นิยมกว่าใน PostgreSQL สมัยใหม่

## สร้าง table จาก driver

แอปพลิเคชันส่วนใหญ่รันคำสั่ง `CREATE TABLE` เพียงครั้งเดียว ตอน setup หรือผ่านขั้นตอน migration แทนที่จะรันในทุก request นี่คือ migration เดียวกันที่ส่งจากแต่ละ driver — มีประโยชน์เมื่อแอปพลิเคชันของคุณเป็นเจ้าของ schema เอง

## IF NOT EXISTS และ DROP TABLE

การรัน `CREATE TABLE products` เป็นครั้งที่สองจะเป็น error เพราะ table มีอยู่แล้ว การเพิ่ม `IF NOT EXISTS` ทำให้คำสั่งกลายเป็น no-op เมื่อ table มีอยู่แล้ว ซึ่งสะดวกในสคริปต์ setup ที่อาจถูกรันมากกว่าหนึ่งครั้ง

```sql
CREATE TABLE IF NOT EXISTS products (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL,
  price numeric(10, 2) NOT NULL
);
```

หากต้องการลบ table และ row ทั้งหมดของมัน ให้ใช้ `DROP TABLE` มันถาวรและเกิดขึ้นทันที จึงควรปฏิบัติกับมันด้วยความระมัดระวังเช่นเดียวกับ `DELETE` แบบ `IF EXISTS` ช่วยเลี่ยง error เมื่อ table หายไปแล้ว

```sql
DROP TABLE IF EXISTS products;
```

**ใน pgAdmin:** คุณยัง drop table ได้โดยคลิกขวาที่มันในแผนผัง browser แล้วเลือก Delete/Drop แต่การรัน `DROP TABLE` ใน Query Tool จะเก็บการกระทำนั้นไว้ในประวัติสคริปต์ของคุณ

## Tips / gotchas

- เลือก `GENERATED ALWAYS AS IDENTITY` มากกว่า `SERIAL` สำหรับ table ใหม่ มันเป็นไวยากรณ์มาตรฐาน SQL หลีกเลี่ยงความแปลกประหลาดเรื่องความเป็นเจ้าของของ sequence ที่ `SERIAL` สร้างขึ้นเบื้องหลัง และอ่านได้ชัดเจนกว่า
- ใช้ `bigint` แทนที่จะเป็น `integer` สำหรับ identity key บน table ที่คุณคาดว่าจะเติบโต `integer` ขนาดสี่ไบต์จะหมดที่ราว ๆ สองพันล้าน row และการสลับชนิดในภายหลังนั้นสร้างความปั่นป่วน
- เพิ่ม `IF NOT EXISTS` ลงในสคริปต์สร้างที่อาจถูกรันซ้ำ ๆ แต่อย่าใส่ในการ migration แบบครั้งเดียวที่ table ซ้ำควรเป็น error ที่คุณสังเกตเห็น
- `DROP TABLE` ลบทั้งโครงสร้างและทุก row โดยไม่มีการยืนยัน ตรวจสอบชื่อ table ให้ดี และควร drop ภายใน transaction ที่คุณ roll back ได้หากไม่แน่ใจ
- ชื่อ column และ table จะถูกแปลงเป็นตัวพิมพ์เล็กเว้นแต่จะใส่ double-quote ดังนั้นจงเลือกชื่อตัวพิมพ์เล็กแบบ snake_case เพื่อหลีกเลี่ยงความประหลาดใจ

เมื่อคุณมองหาคีย์ที่เพิ่มค่าอัตโนมัติ ให้เขียน `bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY` มันแสดงเจตนาได้ชัดเจน เป็นไปตามมาตรฐาน SQL และเลี่ยงพฤติกรรมแบบเก่าของ `SERIAL` ได้ เก็บ `SERIAL` ไว้สำหรับอ่านโค้ดเก่า ไม่ใช่สำหรับเขียน table ใหม่
</Callout>

## Trade-offs

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| ออกแบบ schema ให้ครบตั้งแต่ต้น | โครงสร้างชัดเจน มี migration discipline ตั้งแต่วันแรก | ใช้เวลาเก็บ requirement นานขึ้นก่อนเริ่มเขียนโค้ด |
| เพิ่ม column ทีหลังตามที่เจอ requirement จริง | ยืดหยุ่น ปรับตามธุรกิจได้เร็ว | schema drift ต้องตามแก้ constraint และ migration ย้อนหลัง |
| `bigint GENERATED ALWAYS AS IDENTITY` เป็น primary key | เรียงลำดับได้ตามเวลา insert ขนาดเล็ก index เร็ว | เดา id ถัดไปได้ เปิดเผยจำนวน row |
| `uuid` เป็น primary key | ไม่ซ้ำกันได้ในระดับ global สร้างจาก client ได้โดยไม่ต้อง round-trip ไปเซิร์ฟเวอร์ | ขนาดใหญ่กว่า เรียงลำดับตามเวลาไม่ได้ตามธรรมชาติ ทำให้ index กระจายตัว |

## Common Mistakes

- **สร้าง table โดยไม่มี primary key** — ทุก table ควรมี primary key เสมอ ไม่งั้นจะ update/delete row เจาะจงได้ยากและ replication บางแบบก็ต้องการมัน
- **ใช้ `varchar(255)` กับทุก column แบบไม่คิด** — เลือกความยาวที่มีความหมายจริงตามกฎธุรกิจ หรือใช้ `text` ไปเลยถ้าไม่มีขีดจำกัดที่แท้จริง เพราะ `varchar(255)` ที่ copy กันมาไม่ได้ป้องกันอะไรและไม่ได้เร็วกว่า `text`
- **ลืมใส่ `NOT NULL` ให้ column ที่ต้องมีค่าเสมอ** — ถ้า column อย่าง `name` หรือ `price` ไม่ควรว่างเปล่าได้ ต้องประกาศ `NOT NULL` ตั้งแต่ตอนสร้าง table ไม่ใช่ปล่อยให้แอปพลิเคชันเป็นคนคอยเช็คเอง

> 💡 Real World Example
>
> **Stripe** — ใช้ id แบบ string ที่มี prefix บอกประเภท object เช่น `cus_...` สำหรับ customer หรือ `ch_...` สำหรับ charge แทนที่จะใช้ UUID ดิบ ๆ ทำให้ id ทั้ง unique และอ่านแล้วรู้ทันทีว่าเป็น object ประเภทไหน ช่วยเวลา debug log
>
> **Notion** — เก็บเนื้อหา block ที่มีโครงสร้างยืดหยุ่นสูงไว้ใน column แบบ JSONB ควบคู่กับ metadata อย่าง ownership และ permission ที่ยังคงเก็บแบบ relational ปกติเพื่อให้ query และบังคับ constraint ได้ตรงไปตรงมา
