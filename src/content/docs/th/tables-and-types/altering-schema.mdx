schema ไม่เคยเสร็จสมบูรณ์ ฟีเจอร์ใหม่ต้องการ column ใหม่ ตัวเก่ากลายเป็นของล้าสมัย และกฎเข้มขึ้นเมื่อคุณรู้ว่าข้อมูลจริงหน้าตาเป็นอย่างไร statement `ALTER TABLE` เปลี่ยนรูปร่างของ table ที่มีอยู่ในที่เดิมโดยเก็บ row ที่คุณมีไว้ เช่นเดียวกับ `CREATE TABLE` มันคือ DDL และมักถูกใช้ผ่านขั้นตอน migration เพื่อให้การเปลี่ยนแปลงมี version และทำซ้ำได้

เราทำต่อกับ table `products` คราวนี้มี 1,000 row เพื่อให้ migration มีอะไรให้เคี้ยว ทุกอย่างด้านล่างคือ output จริงจาก **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) จากบนลงล่างในฐานข้อมูลเปล่าหนึ่งตัว ตัวเลขเวลามาจาก Mac เครื่องนี้ คำถามสำคัญสำหรับทุก statement ไม่ใช่แค่ "ใช้ได้ไหม" แต่คือ "มัน rewrite table ไหม และถือ lock อะไร?"

```sql
-- sql/products.sql
CREATE TABLE products (
  id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name   text NOT NULL,
  price  numeric(10, 2) NOT NULL
);
INSERT INTO products (name, price)
SELECT 'product-' || g, (g % 50) + 0.99 FROM generate_series(1, 1000) g;
SELECT count(*) AS rows, min(price), max(price) FROM products;
```

```text
CREATE TABLE
INSERT 0 1000
 rows | min  |  max  
------+------+-------
 1000 | 0.99 | 49.99
(1 row)
```

## การเพิ่มและลบ column

`ADD COLUMN` ต่อ column ใหม่เข้าไปในทุก row ที่มีอยู่ ถ้าไม่ให้ default row ที่มีอยู่จะได้ null ใน column ใหม่ `DROP COLUMN` ลบ column และข้อมูลของมันถาวร คุณรวมหลายการเปลี่ยนแปลงใน statement เดียวโดยคั่นด้วยจุลภาคได้ ซึ่งเก็บการแก้ไขที่เกี่ยวข้องไว้ในขั้นเดียวแบบ atomic

```sql
-- sql/add-drop-column.sql
ALTER TABLE products ADD COLUMN description text;
SELECT count(description) AS non_null_descriptions, count(*) AS rows FROM products;
ALTER TABLE products DROP COLUMN description;
ALTER TABLE products
  ADD COLUMN sku text,
  ADD COLUMN in_stock boolean NOT NULL DEFAULT true;
SELECT count(*) FILTER (WHERE in_stock) AS in_stock_true, count(sku) AS sku_filled FROM products;
```

```text
ALTER TABLE
 non_null_descriptions | rows 
-----------------------+------
                     0 | 1000
(1 row)

ALTER TABLE
ALTER TABLE
 in_stock_true | sku_filled 
---------------+------------
          1000 |          0
(1 row)
```

**ใน pgAdmin:** หลังแก้ไข table ให้ refresh โหนด Columns ใน browser tree เพื่อดูการเปลี่ยนแปลง หรือใช้กล่อง Properties ของ table เพื่อเพิ่มและลบ column ผ่านฟอร์ม

## การเปลี่ยน type ของ column

`ALTER COLUMN ... TYPE` แปลง column เป็น type ใหม่ PostgreSQL แปลงหลายกรณีได้อัตโนมัติ แต่เมื่อการเปลี่ยนไม่ชัดเจน คุณต้องใส่นิพจน์ `USING` ที่บอกว่าจะแปลงแต่ละค่าที่มีอยู่อย่างไร

```sql
-- sql/change-type.sql
UPDATE products SET sku = 'SKU-' || lpad(id::text, 4, '0');
ALTER TABLE products
  ALTER COLUMN sku TYPE varchar(32);
ALTER TABLE products
  ALTER COLUMN price TYPE numeric(12, 2) USING price::numeric(12, 2);
\d products
```

```text
UPDATE 1000
ALTER TABLE
ALTER TABLE
                                Table "public.products"
  Column  |         Type          | Collation | Nullable |           Default            
----------+-----------------------+-----------+----------+------------------------------
 id       | bigint                |           | not null | generated always as identity
 name     | text                  |           | not null | 
 price    | numeric(12,2)         |           | not null | 
 sku      | character varying(32) |           |          | 
 in_stock | boolean               |           | not null | true
Indexes:
    "products_pkey" PRIMARY KEY, btree (id)
```

ถ้าค่าใดแปลงไม่ได้ ทั้ง statement ล้มเหลวและไม่มีอะไรเปลี่ยน:

```sql
-- @expect-error 22P02
ALTER TABLE products ALTER COLUMN sku TYPE integer USING sku::integer;
```

```text
ERROR:  invalid input syntax for type integer: "SKU-0001"
```

`USING` คือวิธีบอกว่าจะทำอย่างไรกับค่าเหล่านั้น:

```sql
-- sql/using-ok.sql
ALTER TABLE products ADD COLUMN sku_num text;
UPDATE products SET sku_num = sku;
ALTER TABLE products ALTER COLUMN sku_num TYPE integer USING substr(sku_num, 5)::integer;
SELECT sku, sku_num FROM products WHERE id IN (1, 1000) ORDER BY id;
ALTER TABLE products DROP COLUMN sku_num;
```

```text
ALTER TABLE
UPDATE 1000
ALTER TABLE
   sku    | sku_num 
----------+---------
 SKU-0001 |       1
 SKU-1000 |    1000
(2 rows)

ALTER TABLE
```

### มัน rewrite table ไหม?

การแปลงอาจรันทุก row ดังนั้นบน table ใหญ่อาจใช้เวลาและถือ lock แต่ไม่ใช่ทุก `ALTER` ที่ rewrite table และการรู้ว่าตัวไหนทำคือหัวใจทั้งหมด การ rewrite สร้างสำเนาใหม่ของไฟล์ table ซึ่งเห็นได้จาก `pg_relation_filenode` ที่เปลี่ยน นี่คือ matrix รันทีละ statement กับ table เดียวกัน (แต่ละแถวใช้หลังแถวก่อนหน้า):

```sql
-- sql/rewrite-matrix.sql
CREATE TABLE rw (id int, t text, v varchar(32), n numeric(10, 2), i int);
INSERT INTO rw SELECT g, 'row-' || g, 'v' || g, g, g FROM generate_series(1, 1000) g;

CREATE FUNCTION rewrites(ddl text) RETURNS text LANGUAGE plpgsql AS $$
DECLARE before_node oid := pg_relation_filenode('rw');
BEGIN
  EXECUTE ddl;
  RETURN CASE WHEN pg_relation_filenode('rw') = before_node THEN 'no rewrite' ELSE 'REWRITE' END;
END $$;

SELECT ddl, rewrites(ddl) AS result
FROM (VALUES
  (1,  'ALTER TABLE rw ALTER COLUMN n TYPE numeric(12,2)'),
  (2,  'ALTER TABLE rw ALTER COLUMN v TYPE varchar(64)'),
  (3,  'ALTER TABLE rw ALTER COLUMN v TYPE text'),
  (4,  'ALTER TABLE rw ALTER COLUMN t TYPE varchar(32)'),
  (5,  'ALTER TABLE rw ALTER COLUMN t TYPE varchar(8)'),
  (6,  'ALTER TABLE rw ALTER COLUMN n TYPE numeric(12,3)'),
  (7,  'ALTER TABLE rw ALTER COLUMN i TYPE bigint'),
  (8,  'ALTER TABLE rw ADD COLUMN c1 int DEFAULT 0'),
  (9,  'ALTER TABLE rw ADD COLUMN c2 timestamptz DEFAULT now()'),
  (10, 'ALTER TABLE rw ADD COLUMN c3 uuid DEFAULT gen_random_uuid()'),
  (11, 'ALTER TABLE rw ADD COLUMN c4 bigint GENERATED ALWAYS AS (i * 2) STORED'),
  (12, 'ALTER TABLE rw ADD COLUMN c5 bigint GENERATED ALWAYS AS (i * 2)'),
  (13, 'ALTER TABLE rw DROP COLUMN c1'),
  (14, 'ALTER TABLE rw ALTER COLUMN id SET NOT NULL')
) AS t(step, ddl)
ORDER BY step;
```

```text
CREATE TABLE
INSERT 0 1000
CREATE FUNCTION
                                  ddl                                   |   result   
------------------------------------------------------------------------+------------
 ALTER TABLE rw ALTER COLUMN n TYPE numeric(12,2)                       | no rewrite
 ALTER TABLE rw ALTER COLUMN v TYPE varchar(64)                         | no rewrite
 ALTER TABLE rw ALTER COLUMN v TYPE text                                | no rewrite
 ALTER TABLE rw ALTER COLUMN t TYPE varchar(32)                         | REWRITE
 ALTER TABLE rw ALTER COLUMN t TYPE varchar(8)                          | REWRITE
 ALTER TABLE rw ALTER COLUMN n TYPE numeric(12,3)                       | REWRITE
 ALTER TABLE rw ALTER COLUMN i TYPE bigint                              | REWRITE
 ALTER TABLE rw ADD COLUMN c1 int DEFAULT 0                             | no rewrite
 ALTER TABLE rw ADD COLUMN c2 timestamptz DEFAULT now()                 | no rewrite
 ALTER TABLE rw ADD COLUMN c3 uuid DEFAULT gen_random_uuid()            | REWRITE
 ALTER TABLE rw ADD COLUMN c4 bigint GENERATED ALWAYS AS (i * 2) STORED | REWRITE
 ALTER TABLE rw ADD COLUMN c5 bigint GENERATED ALWAYS AS (i * 2)        | no rewrite
 ALTER TABLE rw DROP COLUMN c1                                          | no rewrite
 ALTER TABLE rw ALTER COLUMN id SET NOT NULL                            | no rewrite
(14 rows)
```

อ่านให้ละเอียด เพราะคำแนะนำที่คุ้นเคยบางข้อผิด:

- การเพิ่ม precision ของ `numeric` ที่ scale เท่าเดิม การขยาย `varchar(n)` และการเปลี่ยน `varchar` เป็น `text` เป็นแค่ metadata
- การเปลี่ยน *ไปเป็น* ขีดจำกัดความยาว (`text` เป็น `varchar(32)`) การลด `varchar(n)` การเปลี่ยน scale ของ `numeric` และ `integer` เป็น `bigint` rewrite table
- การเพิ่ม column ที่มี default เป็นค่าคงที่หรือ `now()` เป็นแค่ metadata (fast default, PostgreSQL 11+) ส่วน default แบบ volatile เช่น `gen_random_uuid()` rewrite generated column แบบ `STORED` rewrite ส่วนแบบ virtual (ค่าเริ่มต้นของ PostgreSQL 18) ไม่ rewrite
- `DROP COLUMN` แค่ทำเครื่องหมายว่า column ถูก drop `SET NOT NULL` สแกน table เพื่อตรวจแต่ไม่ rewrite

กฎอยู่ใน [หมายเหตุของ ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html#SQL-ALTERTABLE-NOTES) matrix ข้างบนคือสิ่งที่เซิร์ฟเวอร์นี้ทำจริง

### Lock: "บล็อกชั่วครู่" จริง ๆ แล้วหมายถึงอะไร

ทุกรูปแบบข้างบนถือ lock `ACCESS EXCLUSIVE` บน table ซึ่งเป็น lock ที่แรงที่สุด ขัดแย้งกับทุกอย่างรวมถึง `SELECT` ธรรมดา ถือจนจบ transaction และเวลา rewrite ถูกใช้ไปภายในนั้น:

```sql
-- sql/lock-modes.sql
BEGIN;
ALTER TABLE products ALTER COLUMN name TYPE varchar(100);
SELECT mode FROM pg_locks WHERE relation = 'products'::regclass AND pid = pg_backend_pid() AND mode LIKE '%Exclusive%' ORDER BY mode;
ROLLBACK;
```

```text
BEGIN
ALTER TABLE
        mode         
---------------------
 AccessExclusiveLock
(1 row)

ROLLBACK
```

ปัญหาที่ซ่อนอยู่คือ **lock queue** `ALTER TABLE` ต้องรอทุก transaction ที่แตะ table อยู่แล้ว และระหว่างที่มันรอ ทุกอย่างที่มาถึงทีหลังจะต่อคิวอยู่ข้างหลัง *มัน* แม้แต่ `ADD COLUMN` ที่เสร็จทันทีก็หยุดทราฟฟิกทั้งหมดได้ถ้ามี transaction ยาวเปิดอยู่ รันจริงด้วยสาม session (แต่ละตัวเป็น `psql` แยก): session A ถือการอ่านใน transaction 5 วินาที session B ลอง `ALTER TABLE` session C รัน `SELECT` ธรรมดาสองวินาทีหลัง A เริ่ม session D ดู `pg_stat_activity`:

```text
-- session A: holds an ordinary read lock inside a transaction for 5 seconds
BEGIN
 a_rows 
--------
   1000
(1 row)

COMMIT

-- session B (starts 1 s later): the migration
Timing is on.
ALTER TABLE
Time: 3995.829 ms (00:03.996)

-- session C (starts 2 s later): a plain SELECT, nothing to do with the migration
Timing is on.
 c_rows 
--------
   1000
(1 row)

Time: 2993.559 ms (00:02.994)

-- session D (looks at 3.5 s): who is waiting?
               query                | state  | wait_event_type | wait_event 
------------------------------------+--------+-----------------+------------
 ALTER TABLE rw ADD COLUMN x int;   | active | Lock            | relation
 SELECT count(*) AS c_rows FROM rw; | active | Lock            | relation
(2 rows)
```

C แค่อ่านอย่างเดียวและถูกบล็อก 3 วินาทีเพราะต่อคิวหลัง B ซึ่งต่อคิวหลัง A ตัวป้องกันคือ `lock_timeout`: ยอมแพ้เร็วแล้วลองใหม่ แทนที่จะบล็อก table ของทุกคน:

```text
-- session B, same as before but with lock_timeout = 500ms
SET
Timing is on.
ERROR:  canceling statement due to lock timeout
Time: 502.981 ms

-- session C
Timing is on.
 c_rows 
--------
   1000
(1 row)

Time: 1.527 ms
```

migration ล้มเหลวด้วย `canceling statement due to lock timeout` (SQLSTATE `55P03`) หลัง 0.5 วินาที และ C รันใน 1.5 ms ใส่ `SET lock_timeout` ที่หัวของทุก migration บนระบบที่ใช้งานอยู่ แล้วลองใหม่

## การเพิ่มและลบ constraint

คุณผูก constraint กับ table หลังจากมันมีอยู่แล้วได้ หรือลบตามชื่อ การตั้งชื่อ constraint ตอนสร้าง ตามที่บทก่อนแนะนำ คือสิ่งที่ทำให้การลบสะอาด

```sql
-- sql/add-constraint.sql
ALTER TABLE products
  ADD CONSTRAINT products_price_positive CHECK (price > 0);
ALTER TABLE products
  DROP CONSTRAINT products_price_positive;
```

การเพิ่ม constraint สแกน row ที่มีอยู่เพื่อยืนยันว่าทุกตัวผ่าน ถ้า row ใดไม่ผ่าน ทั้ง statement ถูกปฏิเสธและไม่มีอะไรเปลี่ยน (บทก่อนแสดง error นั้น) การสแกนเกิดภายใต้ lock ที่แรง `NOT VALID` แยกเป็นสองขั้น: เพิ่ม constraint เพื่อให้การเขียน *ใหม่* ถูกตรวจทันที แล้วตรวจ row เก่าแยกภายใต้ lock ที่อ่อนกว่ามาก ก่อนอื่น เมื่อมี row เสียอยู่ (`qty = -3`):

```sql
-- sql/not-valid.sql
CREATE TABLE stock (id int PRIMARY KEY, qty int);
INSERT INTO stock VALUES (1, 5), (2, -3);
ALTER TABLE stock ADD CONSTRAINT stock_qty_nonneg CHECK (qty >= 0) NOT VALID;
SELECT conname, convalidated FROM pg_constraint WHERE conname = 'stock_qty_nonneg';
```

```text
CREATE TABLE
INSERT 0 2
ALTER TABLE
     conname      | convalidated 
------------------+--------------
 stock_qty_nonneg | f
(1 row)
```

`convalidated = f` หมายความว่า row เก่ายังไม่ถูกตรวจ แต่ row ใหม่ถูกตรวจ:

```sql
-- @expect-error 23514
INSERT INTO stock VALUES (3, -1);
```

```text
ERROR:  new row for relation "stock" violates check constraint "stock_qty_nonneg"
DETAIL:  Failing row contains (3, -1).
```

`VALIDATE CONSTRAINT` ปฏิเสธขณะมี row เสียอยู่:

```sql
-- @expect-error 23514
ALTER TABLE stock VALIDATE CONSTRAINT stock_qty_nonneg;
```

```text
ERROR:  check constraint "stock_qty_nonneg" of relation "stock" is violated by some row
```

แก้ข้อมูลแล้วค่อย validate ดู lock: `ShareUpdateExclusiveLock` ไม่บล็อกการอ่านหรือเขียน ต่างจาก `AccessExclusiveLock` ของ `ADD CONSTRAINT` ธรรมดา:

```sql
-- sql/validate.sql
UPDATE stock SET qty = 0 WHERE qty < 0;
BEGIN;
ALTER TABLE stock VALIDATE CONSTRAINT stock_qty_nonneg;
SELECT mode FROM pg_locks WHERE relation = 'stock'::regclass AND pid = pg_backend_pid() AND mode LIKE '%Exclusive%' ORDER BY mode;
COMMIT;
SELECT conname, convalidated FROM pg_constraint WHERE conname = 'stock_qty_nonneg';
```

```text
UPDATE 1
BEGIN
ALTER TABLE
           mode           
--------------------------
 ShareUpdateExclusiveLock
(1 row)

COMMIT
     conname      | convalidated 
------------------+--------------
 stock_qty_nonneg | t
(1 row)
```

## การเปลี่ยนชื่อ

`RENAME` เปลี่ยนชื่อ table หรือ column เดียวโดยไม่แตะข้อมูล มันทันที แต่ไม่ใช่ทุกอย่างที่ตามการเปลี่ยนชื่อ view ถูกเก็บตามตัวตนของ object จึงตามไป (ด้านล่าง view ตอนนี้อ่านว่า `product_code AS sku FROM catalog_items`) ส่วน body ของฟังก์ชันเป็นแค่ข้อความและไม่ตาม:

```sql
-- sql/rename.sql
CREATE VIEW product_skus AS SELECT id, sku FROM products;
CREATE FUNCTION sku_of(pid bigint) RETURNS text LANGUAGE sql AS $$ SELECT sku FROM products WHERE id = pid $$;
ALTER TABLE products RENAME COLUMN sku TO product_code;
ALTER TABLE products RENAME TO catalog_items;
SELECT pg_get_viewdef('product_skus'::regclass) AS view_follows_the_rename;
```

```text
CREATE VIEW
CREATE FUNCTION
ALTER TABLE
ALTER TABLE
 view_follows_the_rename 
-------------------------
  SELECT id,            +
     product_code AS sku+
    FROM catalog_items;
(1 row)
```

```sql
-- @expect-error 42P01
SELECT sku_of(1);
```

```text
ERROR:  relation "products" does not exist
LINE 1:  SELECT sku FROM products WHERE id = pid 
                         ^
QUERY:   SELECT sku FROM products WHERE id = pid 
CONTEXT:  SQL function "sku_of" during inlining
```

query ของแอปพลิเคชัน รายงานที่บันทึกไว้ และ body ของฟังก์ชันต้องอัปเดตด้วยมือ คืนชื่อกลับสำหรับส่วนที่เหลือของบทเรียน:

```sql
-- sql/rename-back.sql
ALTER TABLE catalog_items RENAME TO products;
ALTER TABLE products RENAME COLUMN product_code TO sku;
DROP VIEW product_skus;
DROP FUNCTION sku_of(bigint);
```

## Migration ที่ปลอดภัย: กับดัก NOT NULL

อุบัติเหตุ migration ที่พบบ่อยที่สุดคือการเพิ่ม column `NOT NULL` ให้ table ที่มี row อยู่แล้ว row เหล่านั้นไม่มีค่าให้ column ใหม่ constraint จึงถูกฝ่าฝืนทันทีและ statement ล้มเหลว

```sql
-- @expect-error 23502
ALTER TABLE products ADD COLUMN currency text NOT NULL;
```

```text
ERROR:  column "currency" of relation "products" contains null values
```

มีสองทางที่ปลอดภัย: ให้ column มี `DEFAULT` เพื่อเติมทุก row ที่มีอยู่ในคราวเดียว (แค่ metadata ถ้าเป็นค่าคงที่) หรือเพิ่ม column แบบ nullable, backfill ค่า แล้วเข้มงวดเป็น `NOT NULL` ทางที่สองเป็นตัวเลือกมาตรฐานเมื่อไม่มี default ที่สมเหตุสมผลเพียงค่าเดียว เพราะให้คุณคำนวณค่าของแต่ละ row ก่อนล็อก column (เมื่อมี `CHECK (region IS NOT NULL)` ที่ validate แล้ว `SET NOT NULL` ข้ามการสแกน table ได้ ดู [docs](https://www.postgresql.org/docs/18/sql-altertable.html))

```sql
-- sql/not-null-paths.sql
-- Path 1: a default fills every existing row in one step
ALTER TABLE products
  ADD COLUMN currency text NOT NULL DEFAULT 'USD';

-- Path 2: add nullable, backfill, then enforce
ALTER TABLE products ADD COLUMN region text;
UPDATE products SET region = 'global' WHERE region IS NULL;
ALTER TABLE products ALTER COLUMN region SET NOT NULL;
SELECT currency, region, count(*) FROM products GROUP BY 1, 2;
```

```text
ALTER TABLE
ALTER TABLE
UPDATE 1000
ALTER TABLE
 currency | region | count 
----------+--------+-------
 USD      | global |  1000
(1 row)
```

## การรัน migration ใน transaction

statement `ALTER TABLE` ส่วนใหญ่ใน PostgreSQL เป็น transactional (DDL เป็น transactional ที่นี่ ต่างจากฐานข้อมูลอื่นบางตัว) คุณจึงครอบ migration หลายขั้นด้วย transaction ให้ apply แบบทั้งหมดหรือไม่เลยได้ ถ้าขั้นใดล้มเหลว `ROLLBACK` ทำให้ table กลับเหมือนเดิม:

```sql
-- sql/transactional-ddl.sql
BEGIN;
ALTER TABLE products ADD COLUMN tmp_flag boolean;
ALTER TABLE products DROP COLUMN region, DROP COLUMN currency;
SELECT count(*) AS columns_inside_tx FROM information_schema.columns WHERE table_name = 'products';
ROLLBACK;
SELECT count(*) AS columns_after_rollback FROM information_schema.columns WHERE table_name = 'products';
```

```text
BEGIN
ALTER TABLE
ALTER TABLE
 columns_inside_tx 
-------------------
                 6
(1 row)

ROLLBACK
 columns_after_rollback 
------------------------
                      7
(1 row)
```

ภายใน transaction table มีรูปร่างต่างออกไป (เพิ่มหนึ่ง column ลบสอง column) หลัง `ROLLBACK` ก็เหมือนไม่มีอะไรเกิดขึ้น ตัว migration เอง:

```sql
-- sql/migration-in-tx.sql
BEGIN;
ALTER TABLE products ADD COLUMN region2 text;
UPDATE products SET region2 = 'global' WHERE region2 IS NULL;
ALTER TABLE products ALTER COLUMN region2 SET NOT NULL;
COMMIT;
SELECT count(*) AS migrated FROM products WHERE region2 = 'global';
```

```text
BEGIN
ALTER TABLE
UPDATE 1000
ALTER TABLE
COMMIT
 migrated 
----------
     1000
(1 row)
```

## Mental Model

ทุก `ALTER TABLE` มีสองต้นทุน: **งานมากแค่ไหน** (metadata อย่างเดียว สแกน table หรือ rewrite ทั้งหมด) และ **lock แรงแค่ไหน นานเท่าไร** (รวมเวลาที่ต่อคิว) การเปลี่ยน type หรือ default ที่ต้องการรูปร่าง row กายภาพใหม่จะ rewrite ส่วนการเปลี่ยนที่แค่เปลี่ยน catalog หรือแค่ต้องอ่าน row ไม่ rewrite migration ที่ปลอดภัยคืออันที่ทำให้ทั้งสองต้นทุนเล็ก: ใช้รูปแบบถูก รอ lock ด้วย timeout และแยกทุกอย่างที่แพงเป็นขั้นที่ lock อ่อน

## เคล็ดลับและข้อควรระวัง

- `ALTER TABLE` ถือ lock บน table และ lock queue เปลี่ยนการเปลี่ยนแปลงระดับมิลลิวินาทีให้เป็นเหตุขัดข้องได้ เริ่มทุก migration บน production ด้วย `SET lock_timeout` และพร้อมลองใหม่
- การเพิ่ม column ที่มี `DEFAULT` เป็นค่าคงที่ (หรือ `now()`) เร็วใน PostgreSQL สมัยใหม่เพราะไม่ rewrite ทุก row ส่วน default แบบ volatile และการเปลี่ยน type ส่วนใหญ่ rewrite
- ครอบ migration หลายขั้นด้วย transaction เพื่อให้ความล้มเหลวกลางทาง rollback อย่างสะอาดและไม่ทิ้ง schema ที่เปลี่ยนไปครึ่งเดียว
- เพิ่ม constraint เป็น `NOT VALID` และ `VALIDATE CONSTRAINT` แยกบน table ใหญ่ การ validate ใช้ lock ที่ไม่บล็อกทราฟฟิกปกติ
- `DROP COLUMN` และ `DROP CONSTRAINT` ย้อนกลับไม่ได้เมื่อ commit แล้ว ยืนยันว่าไม่มีอะไรพึ่งพาสิ่งที่คุณกำลังลบ และพึ่ง transaction ที่ rollback ได้ระหว่างตรวจ
- การเปลี่ยนชื่อไม่อัปเดต body ของฟังก์ชัน โค้ดแอปพลิเคชัน หรือรายงานที่บันทึกไว้

<Callout title="Migrate ไปข้างหน้า อย่าทำแบบมั่ว">
ปฏิบัติต่อทุกการเปลี่ยน schema เป็น migration: ขั้นตอนเล็ก มีชื่อ ย้อนกลับได้ ที่คุณทดสอบได้ก่อนแตะ production เพิ่ม column พร้อม default หรือ backfill เข้มงวด constraint หลังข้อมูลสะอาดเท่านั้น และรันการเปลี่ยนหลายขั้นใน transaction migration ที่รอบคอบผู้ใช้มองไม่เห็น migration ที่ประมาทคือเหตุขัดข้อง
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| migration แบบออนไลน์/ไม่บล็อก (แยกขั้น, `NOT VALID`, เป็นชุด) | ปลอดภัยแม้ในเวลาทำการปกติ ไม่กระทบทราฟฟิก | ต้องมีหลายขั้นและวางแผนมากขึ้นเพื่อเขียน |
| `ALTER TABLE` ตรง ๆ | เขียนและรันเร็ว โค้ดสั้น | อาจถือ lock เข้มที่บล็อกทราฟฟิก production บน table ใหญ่ |
| เพิ่ม column ที่มี `DEFAULT` เป็นค่าคงที่ | แค่ metadata — ไม่ rewrite ทุก row จึงเร็วมาก | ต้องเป็นค่าคงที่หรือ stable เท่านั้น `gen_random_uuid()` rewrite (วัดข้างบน) |
| เปลี่ยน type ของ column ด้วย `ALTER COLUMN ... TYPE` | ตรงไปตรงมา statement เดียว | บางการเปลี่ยน rewrite table (ดู matrix) บางอันไม่ |
| `lock_timeout` บน migration | migration ไม่ทำให้ทราฟฟิกกองอยู่ข้างหลัง | อาจล้มเหลวและต้องลองใหม่ |

## Common Misconceptions

- **"`ALTER COLUMN TYPE` ทุกอันต้อง rewrite table"** หลายอันไม่ (matrix ข้างบน) เช่นการขยาย `numeric(10,2)` เป็น `numeric(12,2)` ไม่ rewrite
- **"`ALTER` ที่เสร็จทันทีทำร้าย production ไม่ได้"** มันยังต้องได้ lock ก่อน เมื่อต่อคิวหลัง transaction ยาวตัวเดียว มันบล็อก `SELECT` ธรรมดาไป 3 วินาที (ข้างบน)
- **"PostgreSQL 11+ ทำให้ `ADD COLUMN ... DEFAULT` ทุกแบบทันที"** เฉพาะ default ที่ไม่ volatile
- **"การเปลี่ยนชื่อปลอดภัยเพราะ view อัปเดตเอง"** view ตามไป แต่ body ของฟังก์ชันและ query ของแอปไม่ตาม
- **"`NOT NULL` ต้อง rewrite"** ต้องสแกน ไม่ใช่ rewrite ถ้ามี CHECK ที่ validate แล้วก็ข้ามแม้แต่การสแกนได้
