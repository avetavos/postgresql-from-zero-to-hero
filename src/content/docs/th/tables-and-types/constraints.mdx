ชนิดข้อมูลตัดสินว่า column สามารถเก็บค่าแบบใดได้ ส่วน **constraints** ตัดสินว่าค่าและชุดค่าผสมใดที่ได้รับอนุญาตจริง ๆ constraint คือกฎที่เซิร์ฟเวอร์ตรวจสอบในทุกการ insert และ update โดยปฏิเสธสิ่งใดก็ตามที่ละเมิดมัน เนื่องจากฐานข้อมูลบังคับใช้มัน constraints จึงยังคงอยู่ไม่ว่าแอปพลิเคชันหรือบุคคลใดจะเป็นผู้เขียนข้อมูล — มันเป็นกระดูกสันหลังของความสมบูรณ์ของข้อมูล

เราจะจำลองร้านค้าจิ๋ว ๆ ที่มี `customers` และ `orders` เพื่อดู constraint แต่ละชนิดทำงาน

## NOT NULL และ DEFAULT

constraint แบบ `NOT NULL` ห้ามการไม่มีค่า ดังนั้น column นั้นต้องถูกเติมเสมอ ส่วน `DEFAULT` จัดหาค่าให้เมื่อการ insert ละเว้น column นั้นไป ทั้งคู่จับคู่กันได้อย่างเป็นธรรมชาติ: default ที่สมเหตุสมผลบวกกับ `NOT NULL` หมายความว่า column นั้นมีค่าอยู่เสมอโดยไม่บังคับให้ทุกการ insert ต้องระบุมันให้ชัดเจน

```sql
CREATE TABLE customers (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

ที่นี่ `name` ต้องถูกระบุเสมอ ขณะที่ `created_at` จะเติมตัวเองด้วยช่วงเวลาปัจจุบันเว้นแต่คุณจะจัดหาให้

## PRIMARY KEY

`PRIMARY KEY` ทำเครื่องหมาย column (หรือหลาย column) ที่ระบุ row ได้อย่างไม่ซ้ำกัน มันเป็นรูปแบบย่อของ `NOT NULL` บวก `UNIQUE` และ table หนึ่งมีได้เพียงตัวเดียว column `id` ข้างบนคือ primary key ของ `customers`

## UNIQUE

constraint แบบ `UNIQUE` ห้ามค่าที่ซ้ำกันใน column ขณะที่ยังคงอนุญาต null ได้ มันเป็นวิธีแสดงกฎอย่าง "ลูกค้าสองคนใช้ email ร่วมกันไม่ได้" โดยไม่ทำให้ column นั้นเป็น primary key

```sql
ALTER TABLE customers
  ADD COLUMN email text,
  ADD CONSTRAINT customers_email_unique UNIQUE (email);
```

การตั้งชื่อ constraint ว่า `customers_email_unique` นั้นจะทำหรือไม่ก็ได้ แต่มันคุ้มค่า: ข้อความ error และคำสั่ง `ALTER TABLE` ในภายหลังสามารถอ้างถึงมันด้วยชื่อแทนที่จะเป็นป้ายที่สร้างขึ้นอัตโนมัติ

## CHECK

constraint แบบ `CHECK` ทดสอบนิพจน์กับแต่ละ row และปฏิเสธการเขียนหากมันประเมินค่าได้เป็น false ใช้มันเพื่อเข้ารหัสกฎทางธุรกิจที่ชนิดเพียงอย่างเดียวแสดงไม่ได้ เช่น ราคาที่ต้องเป็นบวก

```sql
CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL,
  total       numeric(10, 2) NOT NULL,
  CONSTRAINT orders_total_positive CHECK (total > 0)
);
```

ความพยายามใด ๆ ที่จะ insert order ที่มี `total` เป็นศูนย์หรือค่าลบ จะล้มเหลวก่อนที่ row นั้นจะถูกเก็บ

## FOREIGN KEY

`FOREIGN KEY` ผูก column เข้ากับคีย์ในอีก table หนึ่ง รับประกันว่าทุก `customer_id` ใน `orders` ชี้ไปยัง row จริงใน `customers` นี่คือ **referential integrity**: ฐานข้อมูลจะไม่ยอมให้คุณสร้าง order สำหรับลูกค้าที่ไม่มีอยู่จริง และจะไม่ปล่อยให้ order ชี้ไปยังลูกค้าที่คุณลบไปแล้ว

```sql
ALTER TABLE orders
  ADD CONSTRAINT orders_customer_fk
  FOREIGN KEY (customer_id) REFERENCES customers (id)
  ON DELETE CASCADE;
```

clause `ON DELETE` ตัดสินว่าจะเกิดอะไรขึ้นกับ row ที่ขึ้นต่อกันเมื่อ row ที่ถูกอ้างถึงถูกลบ `CASCADE` จะลบ order ที่ตรงกันไปพร้อมกับลูกค้า ขณะที่ `RESTRICT` จะปิดกั้นการลบตราบเท่าที่ยังมี order ใดอ้างถึงลูกค้ารายนั้นอยู่ เลือก `CASCADE` เมื่อ row ลูกไม่มีความหมายหากไม่มี row แม่ และเลือก `RESTRICT` เมื่อคุณต้องการการ์ดที่ตั้งใจไว้เพื่อกันการสูญหายโดยอุบัติเหตุ

ตอนนี้ทั้งสอง table สัมพันธ์กันแบบนี้ โดยแต่ละ order ชี้กลับไปยังลูกค้าหนึ่งรายพอดี

## Tips / gotchas

- foreign key บังคับใช้ referential integrity ให้คุณ ดังนั้นฐานข้อมูลจะไม่มีวันถือ order สำหรับลูกค้าที่ไม่มีอยู่จริง การพึ่งพาโค้ดของแอปพลิเคชันเพียงอย่างเดียวเพื่อรักษาความถูกต้องของการอ้างอิงจะล้มเหลวในที่สุด
- ตั้งชื่อ constraints ของคุณให้ชัดเจน อย่าง `orders_total_positive` แทนที่จะยอมรับชื่อที่สร้างขึ้นอัตโนมัติ ชื่อที่ชัดเจนทำให้ข้อความ error อ่านได้และทำให้การเปลี่ยนแปลง `ALTER TABLE` ในภายหลังเป็นเรื่องตรงไปตรงมา
- เลือกพฤติกรรม `ON DELETE` อย่างตั้งใจ `CASCADE` ทำความสะอาด row ที่ขึ้นต่อกันโดยอัตโนมัติแต่อาจลบมากกว่าที่คุณคาด ส่วน `RESTRICT` คือค่าเริ่มต้นที่ปลอดภัยกว่าเมื่อคุณไม่แน่ใจ
- constraint แบบ `CHECK` สามารถอ้างถึงหลาย column ของ row เดียวกันได้ ดังนั้นคุณสามารถเข้ารหัสกฎอย่างส่วนลดที่ต้องไม่เกิน total แต่มันมอง row หรือ table อื่นไม่ได้
- การเพิ่ม constraint ลงใน table ที่มีข้อมูลอยู่แล้วจะล้มเหลวหาก row ที่มีอยู่ละเมิดมัน ทำความสะอาดข้อมูลก่อน แล้วจึงเพิ่ม constraint

<Callout title="ปล่อยให้ฐานข้อมูลเป็นคนปฏิเสธ">
ทุก constraint ที่คุณเพิ่มคือกฎที่ฐานข้อมูลบังคับใช้แทนคุณ ทุกครั้ง สำหรับผู้เขียนทุกคน ผลักดันกฎความสมบูรณ์ลงไปใน schema แทนที่จะกระจายมันไปทั่วโค้ดของแอปพลิเคชัน แล้วข้อมูลเสีย ๆ ทั้งจำพวกก็จะกลายเป็นสิ่งที่เก็บไม่ได้เลย
</Callout>

## Trade-offs

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| บังคับ invariant ด้วย constraint ในฐานข้อมูล (`CHECK`, `UNIQUE`, `FOREIGN KEY`) | ถูกต้องเสมอไม่ว่า client หรือ service ไหนเขียนข้อมูล | เปลี่ยนกฎทีหลังต้องรัน migration และอาจกระทบ row เดิม |
| validate เฉพาะใน application code | เปลี่ยนกฎได้เร็ว ไม่ต้องแตะ schema | ข้อมูลเสียหลุดเข้ามาได้ง่ายผ่านสคริปต์ตรง ๆ, service อื่น หรือ migration ที่ลืมเช็ค |

## Common Mistakes

- **พึ่งพา validation ระดับแอปพลิเคชันอย่างเดียว** — สคริปต์ ad-hoc, batch job หรือ service อื่นที่เขียนตรงเข้า database สามารถข้าม validation ของแอปได้เสมอ ต้องมี constraint ระดับฐานข้อมูลเป็นด่านสุดท้าย
- **ลืมกำหนดพฤติกรรม `ON DELETE` ของ foreign key** — ถ้าไม่ตั้งใจเลือก `CASCADE` หรือ `RESTRICT` อาจได้ orphaned row ที่ชี้ไปยังของที่ไม่มีอยู่แล้ว หรือถูก cascade delete ลบข้อมูลเกินคาด
- **เพิ่ม `UNIQUE` constraint บน table ที่เขียนหนักโดยไม่คิดเรื่อง index** — `UNIQUE` สร้าง index ให้อัตโนมัติ ซึ่งเพิ่มต้นทุนทุกครั้งที่ insert/update บน table ที่มี write volume สูง ต้องวางแผนล่วงหน้า
