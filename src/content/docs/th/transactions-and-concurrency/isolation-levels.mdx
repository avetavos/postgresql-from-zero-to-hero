เมื่อหลาย transaction รันพร้อมกัน พวกมันรบกวนกันได้ในทางที่ให้ผลลัพธ์น่าประหลาดใจ **isolation level** คือปุ่มหมุนที่ควบคุมว่า transaction หนึ่งได้รับการปกป้องจากงานที่กำลังทำของคนอื่นมากแค่ไหน หมุนขึ้นป้องกัน anomaly ได้มากขึ้น แต่ความขัดแย้งมีโอกาสล้มและต้อง retry มากขึ้นด้วย

ทุกอย่างด้านล่างรันบน **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) ตัวอย่าง concurrency แต่ละอันคือการรันจริงของสองโปรเซส `psql` ที่เริ่มพร้อมกัน พิมพ์ตามที่ตอบกลับมา บรรทัด `\o /dev/null` รอบ `pg_sleep(n)` แค่ซ่อนผลลัพธ์ว่างของการหลับ เพื่อให้ session หนึ่งรอได้ในขณะที่อีกอันทำงาน

ใช้สอง table: `accounts` สำหรับอ่านและ update และ `doctors` สำหรับเรื่อง write skew คลาสสิก (กฎของโรงพยาบาลว่าต้องมีหมออยู่เวรอย่างน้อยหนึ่งคน)

```sql
-- sql/setup.sql
CREATE TABLE accounts (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner   text NOT NULL,
  balance numeric NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts (owner, balance) VALUES ('Ada', 500), ('Linus', 100);

CREATE TABLE doctors (name text PRIMARY KEY, on_call boolean NOT NULL);
INSERT INTO doctors VALUES ('alice', true), ('bob', true);
```

## Anomaly

มาตรฐาน SQL ตั้งชื่อปรากฏการณ์ชุดหนึ่งที่ isolation ที่อ่อนกว่ายอมให้เกิด level ของ PostgreSQL นิยามด้วยว่ามันห้ามอะไรบ้าง ([docs, table 13.1](https://www.postgresql.org/docs/18/transaction-iso.html))

- **Dirty read** — อ่าน row ที่ transaction อื่นเปลี่ยนแต่ยังไม่ commit PostgreSQL ไม่เคยอนุญาตไม่ว่า level ใด
- **Non-repeatable read** — อ่าน row เดิมสองครั้งใน transaction เดียวแล้วได้ค่าที่ commit แล้วต่างกัน เพราะ transaction อื่นเปลี่ยนมันระหว่างนั้น
- **Phantom read** — รันการค้นหาเดิมสองครั้งแล้วเจอ row ที่ครั้งแรกไม่มี เพราะ transaction อื่น insert
- **Serialization anomaly (write skew คือตัวคลาสสิก)** — สอง transaction แต่ละอันอ่านชุด row ที่ซ้อนกัน แล้วแต่ละอันเขียนตามที่อ่าน ได้ผลลัพธ์ที่ไม่มีลำดับแบบ serial ใดสร้างได้

นี่คือสิ่งที่ PostgreSQL อนุญาตในแต่ละ level ตรงจากเอกสาร คอลัมน์สุดท้ายบอกว่าบทเรียนนี้ทำซ้ำช่องนั้นอย่างไร:

| Level | Dirty read | Non-repeatable read | Phantom read | Serialization anomaly | พิสูจน์ที่นี่ |
|---|---|---|---|---|---|
| Read Uncommitted | ไม่เกิด (ทำงานเหมือน Read Committed) | เกิดได้ | เกิดได้ | เกิดได้ | การรัน dirty read |
| Read Committed (default) | ไม่เกิด | เกิดได้ | เกิดได้ | เกิดได้ | Ada 500 แล้ว 600 จำนวน 2 แล้ว 3 |
| Repeatable Read | ไม่เกิด | ไม่เกิด | ไม่เกิดใน PostgreSQL | เกิดได้ | 500 และ 500 write skew commit ทั้งคู่ |
| Serializable | ไม่เกิด | ไม่เกิด | ไม่เกิด | ไม่เกิด | write skew ยก `40001` |

Read Uncommitted ยอมรับเป็นชื่อ แต่ภายในคือ Read Committed เพราะ PostgreSQL ไม่เคยแสดงข้อมูลที่ยังไม่ commit Repeatable Read แข็งแรงกว่าที่มาตรฐาน SQL ต้องการ: phantom ก็เกิดไม่ได้

## Read Committed: snapshot ใหม่ต่อ statement

Read Committed คือค่า default แต่ละ statement เห็น snapshot ของทุกอย่างที่ commit ก่อน statement นั้นเริ่ม นั่นคือเหตุผลที่สองการอ่านใน transaction เดียวกันขัดแย้งกันได้ session A อ่านยอดของ Ada และนับบัญชีที่มีอย่างน้อย 100 รอสองวินาทีแล้วอ่านอีกครั้ง เมื่อผ่านไปหนึ่งวินาที session B เพิ่ม 100 ให้ Ada และ insert บัญชีใหม่ ทั้งคู่ commit ทันที:

```text
-- session A: script
BEGIN;
SELECT balance AS ada_first FROM accounts WHERE owner = 'Ada';
SELECT count(*) AS rich_first FROM accounts WHERE balance >= 100;
\o /dev/null
SELECT pg_sleep(2);
\o
SELECT balance AS ada_second FROM accounts WHERE owner = 'Ada';
SELECT count(*) AS rich_second FROM accounts WHERE balance >= 100;
COMMIT;
-- session A: psql output
BEGIN
 ada_first 
-----------
       500
(1 row)

 rich_first 
------------
          2
(1 row)

 ada_second 
------------
        600
(1 row)

 rich_second 
-------------
           3
(1 row)

COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance + 100 WHERE owner = 'Ada';
INSERT INTO accounts (owner, balance) VALUES ('Grace', 300);
-- session B: psql output
UPDATE 1
INSERT 0 1
```

การอ่านครั้งที่สองเห็นยอดใหม่ของ Ada (**non-repeatable read**: 500 กลายเป็น 600) และ row ใหม่ (**phantom**: จำนวนจาก 2 เป็น 3) ทั้งสองการเปลี่ยนแปลง B commit ระหว่างสอง statement ของ A

## Repeatable Read: หนึ่ง snapshot ต่อ transaction

ที่ Repeatable Read query แรกถ่าย snapshot และทุก statement ถัดไปใน transaction ใช้อันนั้น script เดิมเป๊ะ เปลี่ยนแค่บรรทัดแรก:

```text
-- session A: script
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance AS ada_first FROM accounts WHERE owner = 'Ada';
SELECT count(*) AS rich_first FROM accounts WHERE balance >= 100;
\o /dev/null
SELECT pg_sleep(2);
\o
SELECT balance AS ada_second FROM accounts WHERE owner = 'Ada';
SELECT count(*) AS rich_second FROM accounts WHERE balance >= 100;
COMMIT;
-- session A: psql output
BEGIN
 ada_first 
-----------
       500
(1 row)

 rich_first 
------------
          2
(1 row)

 ada_second 
------------
        500
(1 row)

 rich_second 
-------------
           2
(1 row)

COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance + 100 WHERE owner = 'Ada';
INSERT INTO accounts (owner, balance) VALUES ('Grace', 300);
-- session B: psql output
UPDATE 1
INSERT 0 1
```

Ada ยังเป็น 500 และจำนวนยังเป็น 2 ทั้งที่ B commit ทั้งสองการเปลี่ยนแปลงไปนานก่อนการอ่านครั้งที่สองของ A snapshot คือเหตุผลที่การอ่านคงที่ ราคาคือ A ทำงานกับข้อมูลที่รู้ว่าอาจเก่า ซึ่งสำคัญทันทีที่ A อยากเขียน

## Dirty read ไม่เกิดเลย

ขอ `READ UNCOMMITTED` ได้ และ `SHOW` ยืนยันว่ารับ level แล้ว session B update Ada แต่ไม่ commit A หนึ่งวินาทีต่อมายังเห็นค่าที่ commit แล้ว:

```text
-- session A: script
BEGIN ISOLATION LEVEL READ UNCOMMITTED;
SHOW transaction_isolation;
\o /dev/null
SELECT pg_sleep(1);
\o
SELECT balance AS ada_sees FROM accounts WHERE owner = 'Ada';
COMMIT;
-- session A: psql output
BEGIN
 transaction_isolation 
-----------------------
 read uncommitted
(1 row)

 ada_sees 
----------
      500
(1 row)

COMMIT

-- session B: script
BEGIN;
UPDATE accounts SET balance = balance + 100 WHERE owner = 'Ada';
\o /dev/null
SELECT pg_sleep(2);
\o
ROLLBACK;
-- session B: psql output
BEGIN
UPDATE 1
ROLLBACK
```

## ตั้ง level

คุณเลือก level ให้ transaction หนึ่งด้วย `BEGIN ISOLATION LEVEL ...` หรือ `SET TRANSACTION ISOLATION LEVEL ...` เป็น statement แรกหลัง `BEGIN` ค่า default ของ transaction ใหม่คือ `default_transaction_isolation`

```sql
-- sql/set-level.sql
SHOW default_transaction_isolation;

BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SHOW transaction_isolation;
COMMIT;

-- the same thing in one line
BEGIN ISOLATION LEVEL SERIALIZABLE;
SHOW transaction_isolation;
ROLLBACK;
```

```text
 default_transaction_isolation 
-------------------------------
 read committed
(1 row)

BEGIN
SET
 transaction_isolation 
-----------------------
 repeatable read
(1 row)

COMMIT
BEGIN
 transaction_isolation 
-----------------------
 serializable
(1 row)

ROLLBACK
```

เมื่อ query ใดรันแล้ว เปลี่ยน level ไม่ได้อีก ([docs](https://www.postgresql.org/docs/18/sql-set-transaction.html)):

```sql
-- @expect-error 25001
BEGIN;
SELECT 1;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

```text
BEGIN
 ?column? 
----------
        1
(1 row)

ERROR:  SET TRANSACTION ISOLATION LEVEL must be called before any query
```

driver เปิดเผยแนวคิดเดียวกันผ่านตัวเลือก transaction snippet นี้อ่านยอดของ Ada สองครั้งที่ Repeatable Read ระหว่างที่มันหลับระหว่างการอ่าน session ที่สอง (เริ่มจาก script) commit update ทุก driver เห็นยอดเดิมสองครั้ง:

## level ตัดสินว่าจะอนุญาตอะไรอย่างไร

การตัดสินมีรูปร่างเดียวกันทุกครั้ง: เมื่อ statement อ่านข้อมูล level กำหนดว่ามันเห็น snapshot ไหน และ commit ที่ขัดแย้งของคนอื่นกระทบผลลัพธ์ได้หรือไม่

export const isoFlow = `flowchart TD
  A[Statement reads data] --> B{Isolation level}
  B -->|Read Committed| C[Fresh snapshot per statement]
  B -->|Repeatable Read| D[One snapshot for the whole transaction]
  B -->|Serializable| E[Snapshot plus conflict tracking]
  C --> F[Same row may differ on a second read]
  D --> G[Repeated reads are stable]
  E --> H[Abort if the result could not occur serially]`;

## เขียนภายใต้ Repeatable Read

snapshot ที่ทำให้การอ่านคงที่ยังหมายความว่า A อาจพยายามเปลี่ยน row ที่เปลี่ยนไปแล้วตั้งแต่ snapshot ของมัน สอง level ทำตัวต่างกัน ที่ Read Committed `UPDATE` รอผู้เขียนอีกคน อ่าน version ล่าสุดของ row ใหม่ และใช้การเปลี่ยนแปลงกับอันนั้น (update แบบสัมพัทธ์เช่น `balance - 50` จึงไม่ทำ +100 ของ B หาย):

```text
-- session A: script
BEGIN;
SELECT balance AS a_snapshot_sees FROM accounts WHERE owner = 'Ada';
\o /dev/null
SELECT pg_sleep(2);
\o
UPDATE accounts SET balance = balance - 50 WHERE owner = 'Ada';
COMMIT;
-- session A: psql output
BEGIN
 a_snapshot_sees 
-----------------
             500
(1 row)

UPDATE 1
COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance + 100 WHERE owner = 'Ada';
-- session B: psql output
UPDATE 1

-- afterwards:
SELECT owner, balance FROM accounts WHERE owner = 'Ada';
 owner | balance 
-------+---------
 Ada   |     550
(1 row)
```

ที่ Repeatable Read snapshot ของ A ยังบอก 500 ขณะที่ row ตอนนี้บอก 600 การใช้ update ของ A จะเขียนทับสิ่งที่ A ไม่เคยเห็นแบบเงียบ ๆ PostgreSQL ปฏิเสธแทน:

```text
-- session A: script
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance AS a_snapshot_sees FROM accounts WHERE owner = 'Ada';
\o /dev/null
SELECT pg_sleep(2);
\o
UPDATE accounts SET balance = balance - 50 WHERE owner = 'Ada';
COMMIT;
-- session A: psql output
BEGIN
 a_snapshot_sees 
-----------------
             500
(1 row)

ERROR:  could not serialize access due to concurrent update
ROLLBACK

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance + 100 WHERE owner = 'Ada';
-- session B: psql output
UPDATE 1

-- afterwards:
SELECT owner, balance FROM accounts WHERE owner = 'Ada';
 owner | balance 
-------+---------
 Ada   |     600
(1 row)
```

A ต้อง rollback และเริ่มใหม่บน snapshot สด เมื่อใดที่คุณใช้ Repeatable Read หรือ Serializable กับ transaction ที่เขียน error นี้เป็นผลลัพธ์ที่คาดไว้ ไม่ใช่ bug

## Write skew: สิ่งที่ Repeatable Read มองไม่เห็น

หมอสองคน alice และ bob อยู่เวรทั้งคู่ กฎ: ต้องอยู่อย่างน้อยหนึ่งคน แต่ละคนตรวจว่ามีสองคนอยู่เวร คิดสักพัก แล้วถอนตัวเองออก พวกเขาเขียนคนละ row จึงไม่มี write conflict และ snapshot ของแต่ละคนบอก 2 ที่ Repeatable Read ทั้งคู่ commit:

```text
-- session A: script
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) AS on_call_now FROM doctors WHERE on_call;
\o /dev/null
SELECT pg_sleep(2);
\o
UPDATE doctors SET on_call = false WHERE name = 'alice';
COMMIT;
-- session A: psql output
BEGIN
 on_call_now 
-------------
           2
(1 row)

UPDATE 1
COMMIT

-- session B: script
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) AS on_call_now FROM doctors WHERE on_call;
\o /dev/null
SELECT pg_sleep(2);
\o
UPDATE doctors SET on_call = false WHERE name = 'bob';
COMMIT;
-- session B: psql output
BEGIN
 on_call_now 
-------------
           2
(1 row)

UPDATE 1
COMMIT

-- afterwards:
SELECT name, on_call FROM doctors ORDER BY name;
 name  | on_call 
-------+---------
 alice | f
 bob   | f
(2 rows)
```

ไม่มีใครอยู่เวร นี่คือ **write skew** และมันอนุญาตที่ Read Committed และ Repeatable Read

## Serializable และการ retry

Serializable เข้มที่สุด: PostgreSQL รับประกันผลลัพธ์เหมือนว่า transaction ที่รันพร้อมกันรันทีละอันตามลำดับใดลำดับหนึ่ง มันติดตามว่า transaction ไหนอ่านสิ่งที่อีกอันเขียน และเมื่อเจอรูปแบบอันตราย มันยกเลิกหนึ่งอันด้วย **serialization failure** (SQLSTATE `40001`) script สองหมอเดิมที่ Serializable:

```text
-- session A: script
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) AS on_call_now FROM doctors WHERE on_call;
\o /dev/null
SELECT pg_sleep(2);
\o
UPDATE doctors SET on_call = false WHERE name = 'alice';
COMMIT;
-- session A: psql output
BEGIN
 on_call_now 
-------------
           2
(1 row)

UPDATE 1
COMMIT

-- session B: script
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) AS on_call_now FROM doctors WHERE on_call;
\o /dev/null
SELECT pg_sleep(2);
\o
UPDATE doctors SET on_call = false WHERE name = 'bob';
COMMIT;
-- session B: psql output
BEGIN
 on_call_now 
-------------
           2
(1 row)

UPDATE 1
ERROR:  could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during commit attempt.
HINT:  The transaction might succeed if retried.

-- afterwards:
SELECT name, on_call FROM doctors ORDER BY name;
 name  | on_call 
-------+---------
 alice | f
 bob   | t
(2 rows)
```

หมอหนึ่งคนยังอยู่เวร ผู้แพ้ได้ `40001` ตอน `COMMIT` พร้อม `HINT` ที่บอกสิ่งที่ต้องทำเป๊ะ: retry นั่นไม่ใช่ bug มันคือ level ทำหน้าที่ของมัน อันไหนแพ้ทำนายไม่ได้ แอปจึงต้องจับ error และรัน transaction ทั้งก้อนใหม่ ([docs](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE)) การ retry ต้องรันการอ่านซ้ำด้วย เพราะความพยายามครั้งที่สองควรเห็นว่าหมอคนแรกออกไปแล้ว

    fn is_serialization_failure(e: &sqlx::Error) -> bool {
        e.as_database_error().and_then(|d| d.code()).as_deref() == Some("40001")
    }

    async fn go_off_call_once(pool: &sqlx::PgPool, name: &str) -> Result<i64, sqlx::Error> {
        let mut tx = pool.begin().await?;
        sqlx::query("SET TRANSACTION ISOLATION LEVEL SERIALIZABLE").execute(&mut *tx).await?;
        let n: i64 = sqlx::query_scalar("SELECT count(*) FROM doctors WHERE on_call")
            .fetch_one(&mut *tx).await?;
        sqlx::query("SELECT pg_sleep(2)").execute(&mut *tx).await?; // stands in for slow application logic
        if n >= 2 {
            sqlx::query("UPDATE doctors SET on_call = false WHERE name = $1")
                .bind(name).execute(&mut *tx).await?;
        }
        tx.commit().await?;
        Ok(n)
    }

    async fn go_off_call(pool: &sqlx::PgPool, name: &str) -> Result<(), sqlx::Error> {
        for attempt in 1..=5 {
            match go_off_call_once(pool, name).await {
                Ok(n) => {
                    println!("{name}: attempt {attempt} committed (saw {n} on call)");
                    return Ok(());

                Err(e) if is_serialization_failure(&e) && attempt < 5 => {
                    println!("{name}: attempt {attempt} failed with 40001, retrying"); // run it all again
                }
                Err(e) => return Err(e),
            }
        }
        Ok(())
    }

## Mental Model

คิดว่าแต่ละ level คือคำสัญญาที่ต่างกันว่าคุณเห็นอะไรได้ Read Committed บอกว่า "แต่ละ statement เห็นโลกตอนที่มันเริ่ม" Repeatable Read บอกว่า "ทั้ง transaction ของคุณเห็นโลกตอน query แรก" Serializable บอกว่า "และฉันจะทำให้ผลลัพธ์ของคุณตรงกับลำดับที่คุณรันทีละอัน ไม่อย่างนั้นฉันจะยกเลิกคุณ" level ที่สูงขึ้นไม่ทำให้ฐานข้อมูลรอมากขึ้น มันทำให้ transaction มีโอกาสถูกบอกให้ลองใหม่มากขึ้น

## เคล็ดลับและข้อควรระวัง

- Read Committed คือ default ที่ถูกสำหรับ workload ส่วนใหญ่ ยกระดับก็ต่อเมื่อคุณมี anomaly จริงที่ต้องป้องกัน
- ที่ Serializable (และ Repeatable Read สำหรับ write conflict) ห่อ transaction ด้วย retry loop ที่รันใหม่เมื่อ SQLSTATE `40001` เสมอ hint ใน error ก็บอกคุณเช่นนั้น
- ตั้ง isolation level ตั้งแต่ต้น transaction เมื่อเข้าถึงข้อมูลแล้วเปลี่ยนไม่ได้ (`25001`)
- level ที่สูงกว่าไม่ "ถูกต้องกว่า" ฟรี มันแลกโอกาส abort ที่สูงขึ้นกับการรับประกันที่แข็งขึ้น จึงควรวัดก่อนใช้ Serializable ทุกที่
- transaction ยาวที่ Repeatable Read หรือ Serializable ถือ snapshot ที่ทำให้ dead row version ยังอยู่ (ดูบทเรียน MVCC)

<Callout title="เลือก level ที่อ่อนที่สุดที่ยังถูกต้อง">
isolation คือการกำจัด anomaly เฉพาะอย่าง ไม่ใช่การเข้มงวดสูงสุด ระบุว่า anomaly ไหนจะทำให้ตรรกะของคุณพัง เลือก level ต่ำสุดที่ห้ามมัน และเพิ่ม retry loop ถ้า level นั้น abort ได้ ถูกต้องและถูกดีกว่าเข้มและช้า
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| Serializable (เข้มที่สุด) | ป้องกันทุก anomaly รวมถึง write skew (หมอหนึ่งคนยังอยู่เวร) | บาง transaction abort ด้วย `40001` และต้อง retry การ retry มีต้นทุน |
| Repeatable Read | snapshot คงที่สำหรับรายงานและการอ่านหลาย statement (500 และ 500) | write skew ยัง commit (ไม่มีใครอยู่เวร) update พร้อมกันล้มด้วย `could not serialize access due to concurrent update` |
| Read Committed (default) | throughput สูง แทบไม่มี abort จาก isolation conflict | non-repeatable read และ phantom เกิดขึ้น (500 แล้ว 600, 2 แล้ว 3) |

## Common Misconceptions

- **"Serializable แปลว่า transaction รันทีละอัน"** มันยังรันพร้อมกัน PostgreSQL แค่ยกเลิกอันที่ไม่สามารถรันแบบ serial ได้
- **"Repeatable Read ป้องกันทุก anomaly"** มันป้องกัน non-repeatable read และ phantom แต่ไม่ใช่ write skew: หมอทั้งสองออกจากเวร
- **"40001 คือ bug ของแอป"** มันคือคำตอบที่มีเอกสารและคาดไว้ วิธีแก้คือ retry loop ไม่ใช่ลด isolation level
- **"READ UNCOMMITTED ให้เห็นข้อมูล dirty"** ใน PostgreSQL มันทำงานเหมือน Read Committed ตามที่การรัน dirty read แสดง
- **"เลือก Serializable โดยไม่มี retry loop ปลอดภัย"** ข้อมูลยังถูกต้อง แต่ request ล้ม
