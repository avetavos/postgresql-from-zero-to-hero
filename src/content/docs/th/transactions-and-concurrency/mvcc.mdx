isolation level ในบทเรียนก่อนหน้าทั้งหมดตั้งอยู่บนกลไกเดียว: **Multi-Version Concurrency Control** หรือ MVCC คำสัญญาของมันบอกง่ายและทรงพลังในทางปฏิบัติ — ผู้เขียนไม่บล็อกผู้อ่าน และผู้อ่านไม่บล็อกผู้เขียน รายงานยาว ๆ อ่านต่อไปได้ในขณะที่ update หลั่งเข้ามา และไม่มีฝั่งไหนรอฝั่งไหน ([docs](https://www.postgresql.org/docs/18/mvcc-intro.html))

ทุกอย่างด้านล่างรันบน **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) transaction id และหมายเลข page ต่างกันในทุก cluster ดังนั้นให้อ่านตัวเลขเพื่อความสัมพันธ์ของมัน (อันนี้มากกว่าอันนั้นหนึ่ง) ไม่ใช่ค่า extension `pageinspect` ใช้ดู heap page ดิบ เป็นโมดูล contrib ที่มีแต่ superuser ติดตั้งได้ จึงเหมาะกับแล็บ ไม่ใช่ production

```sql
-- sql/setup.sql
CREATE EXTENSION pageinspect;  -- a contrib extension for looking inside pages; needs a superuser

CREATE TABLE accounts (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner   text NOT NULL,
  balance numeric NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts (owner, balance) VALUES ('Ada', 500), ('Linus', 100);
```

## แนวคิดหลัก: ไม่เขียนทับที่เดิมเลย

เมื่อคุณ `UPDATE` row PostgreSQL ไม่เปลี่ยน byte ที่มีอยู่ มันเขียน **version ใหม่** ของ row และทำเครื่องหมาย version เก่าว่าถูกแทนที่ ชั่วขณะหนึ่งทั้งสอง version อยู่บนดิสก์ version ไหนที่ transaction หนึ่งเห็นขึ้นกับว่า transaction นั้นเริ่มเมื่อไร

แต่ละ row version มี system column ซ่อนที่บันทึกช่วงชีวิตของมัน:

- `xmin` — id ของ transaction ที่สร้าง version นี้
- `xmax` — id ของ transaction ที่ลบหรือแทนที่มัน (ศูนย์ตราบใดที่ version ยัง live)
- `ctid` — ตำแหน่งทางกายภาพของ version นี้: (หมายเลข page, line pointer)

transaction เห็น version ก็ต่อเมื่อมันถูกสร้างโดย transaction ที่ commit แล้วก่อน snapshot ของ transaction ที่อ่าน และยังไม่ถูกแทนที่ตามมุมมองของ snapshot นั้น

## แต่ละ transaction อ่าน snapshot

**snapshot** คือชุดข้อมูลที่ commit แล้วที่ transaction มีสิทธิ์เห็น ภายใต้ Read Committed แต่ละ statement ถ่าย snapshot ใหม่ ภายใต้ Repeatable Read และ Serializable ทั้ง transaction ใช้ร่วมกันหนึ่งอัน เพราะการอ่านตอบจาก snapshot `SELECT` ธรรมดาจึงไม่ต้อง lock อะไรและไม่รอ writer เลย

ในแผนภาพ transaction T2 เปลี่ยนยอดจาก 500 เป็น 400 ผู้อ่านที่ snapshot มาก่อน commit ของ T2 ยังเห็น 500 จาก version 1 ผู้อ่านที่เริ่มหลังจากนั้นเห็น 400 จาก version 2 ทั้งคู่อ่านโดยไม่ lock พร้อมกัน และถูกต้องทั้งคู่ตามจุดเวลาของตน นี่คือเหตุการณ์นั้นกับสอง session จริง: A เปิด Repeatable Read snapshot และอ่าน row ของ Ada หนึ่งวินาทีต่อมา B update และ commit แล้ว A อ่านอีกครั้ง:

```text

SELECT ctid, xmin, xmax, balance FROM accounts WHERE owner = 'Ada';
\o /dev/null
SELECT pg_sleep(2);
\o

COMMIT;
SELECT ctid, xmin, xmax, balance FROM accounts WHERE owner = 'Ada';
-- session A: psql output
BEGIN

-------+--------+------+---------
 (0,1) | 427048 |    0 |     500
(1 row)

 ctid  |  xmin  |  xmax  | balance 
-------+--------+--------+---------
 (0,1) | 427048 | 427049 |     500
(1 row)

COMMIT
 ctid  |  xmin  | xmax | balance 
-------+--------+------+---------
 (0,3) | 427049 |    0 |     400
(1 row)

-- session B: script
\o /dev/null

\o

SELECT ctid, xmin, xmax, balance FROM accounts WHERE owner = 'Ada';
```

การอ่านครั้งที่สองของ A แสดง version เก่าที่ `xmax` ถูกเติมแล้ว (id ของ transaction ของ B) แต่ A ยังเห็นมัน เพราะ commit ของ B ไม่ได้อยู่ใน snapshot ของ A หลัง `COMMIT` ของ A snapshot ใหม่เห็นเฉพาะ version ใหม่ที่ (0,3) ไม่มีใครรอใคร

## Dead tuple และ VACUUM

version เก่าที่ update และ delete ทิ้งไว้เรียกว่า **dead tuple** เมื่อไม่มี snapshot ของ transaction ที่รันอยู่จะต้องใช้ version นั้นอีก มันก็เป็นแค่พื้นที่เสียเปล่า PostgreSQL เรียกคืนพื้นที่ด้วย **VACUUM** ซึ่งรันอัตโนมัติเบื้องหลัง (autovacuum) และรันด้วยมือได้ view สถิตินับมัน `pg_stat_force_next_flush()` เผยแพร่ตัวนับที่ค้างของ session นี้เพื่อให้ view เป็นปัจจุบัน:

```sql
-- sql/dead-tuples.sql
SELECT pg_stat_force_next_flush();  -- publish this session's pending counters now
SELECT n_tup_upd, n_tup_hot_upd, n_live_tup, n_dead_tup
FROM pg_stat_user_tables WHERE relname = 'accounts';
```

```text
 pg_stat_force_next_flush 
--------------------------
 
(1 row)

 n_tup_upd | n_tup_hot_upd | n_live_tup | n_dead_tup 
-----------+---------------+------------+------------
         1 |             1 |          2 |          1
(1 row)
```

หนึ่ง update หนึ่ง dead tuple และ `n_tup_hot_upd` บอกว่ามันเป็น **HOT** (heap-only tuple) update: version ใหม่พอดีใน page เดิมและไม่มี column ที่ทำ index เปลี่ยน PostgreSQL จึงไม่ต้องแตะ index ใดเลย ทีนี้ vacuum:

non-HOT update ทิ้งร่องรอยต่างออกไป เมื่อ update เปลี่ยน column ที่มี index version ใหม่ต้องมี index entry ใหม่ version เก่าจึงเป็น redirect ธรรมดาไม่ได้ หลัง `VACUUM` line pointer ของมันถูกปล่อย (`lp_flags = 0`, unused) และ insert ครั้งต่อไปใช้ซ้ำได้:

```sql
-- sql/non-hot.sql
CREATE TABLE tagged (id int PRIMARY KEY, label text);
CREATE INDEX tagged_label_idx ON tagged (label);
INSERT INTO tagged VALUES (1, 'a');

SELECT pg_stat_force_next_flush();
SELECT relname, n_tup_upd, n_tup_hot_upd, n_dead_tup
FROM pg_stat_user_tables WHERE relname IN ('accounts', 'tagged') ORDER BY 1;

SELECT lp, lp_flags, lp_off, t_xmin, t_xmax, t_ctid
FROM heap_page_items(get_raw_page('tagged', 0));
```

## Visibility map: ทำไมการนับไม่ฟรี

ทุก row version ต้องถูกตรวจกับ snapshot ของผู้อ่าน นั่นคือเหตุผลที่ `count(*)` ใน PostgreSQL อ่าน table index-only scan ข้าม table ได้เฉพาะ page ที่ **visibility map** ทำเครื่องหมาย all-visible และ `VACUUM` คือสิ่งที่ตั้ง bit เหล่านั้น plan ข้างล่างนับ 100 000 row ผ่าน primary key index (planner จะเลือก sequential scan ที่นี่ จึงใช้ `enable_seqscan = off` บังคับ plan index-only เพื่อการสอนเท่านั้น):

```sql
-- sql/visibility-map.sql
CREATE TABLE big AS SELECT g AS id, md5(g::text) AS payload FROM generate_series(1, 100000) g;
ALTER TABLE big ADD PRIMARY KEY (id);
ANALYZE big;
SET enable_seqscan = off;  -- teaching switch only: force the index-only plan
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF, BUFFERS OFF) SELECT count(*) FROM big;
VACUUM big;
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF, BUFFERS OFF) SELECT count(*) FROM big;
UPDATE big SET payload = payload WHERE id <= 1000;
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF, BUFFERS OFF) SELECT count(*) FROM big;
```

## transaction ยาวยับยั้งการเก็บกวาด

version เก่าลบได้เมื่อ **ไม่มี** snapshot ใดในฐานข้อมูลที่ยังต้องใช้มัน snapshot ที่รันอยู่เก่าที่สุดจึงกำหนดขอบเขตการเก็บกวาด สองการรันของงานเดียวกัน: worker update หนึ่ง row 1 000 ครั้งและรัน `VACUUM (VERBOSE)` ขณะที่อีก session ถือ Repeatable Read transaction เปิดอยู่ ในการรันที่ 1 session นั้นเชื่อมต่อฐานข้อมูลอื่น ในการรันที่ 2 เชื่อมต่อฐานข้อมูลเดียวกัน:

```text
-- run 1: the open transaction is in ANOTHER database
-- session holder (b3_h2): script
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM t;
\! sleep 5
COMMIT;
-- session worker (b3_h1): script
\! sleep 1
SELECT 'UPDATE t SET n = n + 1 WHERE id = 1;' FROM generate_series(1, 1000) \gexec
VACUUM (VERBOSE, INDEX_CLEANUP OFF) t;
-- session worker: VACUUM output (three summary lines of the VERBOSE report)
pages: 0 removed, 1 remain, 1 scanned (100.00% of total), 0 eagerly scanned
tuples: 187 removed, 1 remain, 0 are dead but not yet removable
removable cutoff: 428058, which was 0 XIDs old when operation ended

-- run 2: the open transaction is in the SAME database
-- session holder (b3_h1): script
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM t;
\! sleep 5
COMMIT;
-- session worker (b3_h1): script
\! sleep 1
SELECT 'UPDATE t SET n = n + 1 WHERE id = 1;' FROM generate_series(1, 1000) \gexec
VACUUM (VERBOSE, INDEX_CLEANUP OFF) t;
-- session worker: VACUUM output (three summary lines of the VERBOSE report)
pages: 0 removed, 5 remain, 5 scanned (100.00% of total), 0 eagerly scanned
tuples: 0 removed, 1001 remain, 1000 are dead but not yet removable
removable cutoff: 428065, which was 1000 XIDs old when operation ended
```

ในการรันที่ 1 vacuum ของ worker ลบเท่าที่ลบได้และไม่พบอะไรที่ต้องเก็บ ในการรันที่ 2 ทั้ง 1 000 dead version เป็น "dead but not yet removable" และใช้ห้า page แทนหนึ่ง ขอบเขตเป็นต่อฐานข้อมูล (บวก shared catalog) ดังนั้น transaction ที่ลืมไว้ในฐานข้อมูลอื่นไม่เป็นอันตรายกับอันนี้ — แต่ transaction ที่ลืมไว้ที่นี่ถือทุกอย่างไว้ replication slot ก็ยับยั้งได้ด้วย: เอกสารอธิบาย `xmin` ของ slot ว่า "the oldest transaction that this slot needs the database to retain. `VACUUM` cannot remove tuples deleted by any later transaction" ([docs](https://www.postgresql.org/docs/18/view-pg-replication-slots.html)) และบทเรียน replication แสดงตัวอย่างในแล็บจริง

## Bloat: snapshot ที่เปิดค้างมีต้นทุนเท่าไร

table bloat คือพื้นที่ตายที่ค้างอยู่ในไฟล์ สร้างง่าย: ถือ snapshot หนึ่งอันเปิดไว้ขณะ update row ที่ร้อนซ้ำแล้วซ้ำอีก นี่คือ table counter หนึ่ง row ที่ update 50 000 ครั้งด้วย `pgbench` (script `UPDATE` คือ `UPDATE page_views SET views = views + 1 WHERE page = '/home';`) วัดบน Mac เครื่องนี้:

```text
-- run 1: nothing else is running
$ pgbench -n -f pv.sql -t 50000 shop
number of transactions actually processed: 50000/50000
tps = 5220.507993 (without initial connection time)
-- psql, right after pgbench
SELECT pg_relation_size('page_views') / 8192 AS heap_pages, pg_size_pretty(pg_relation_size('page_views')) AS heap_size, views FROM page_views;
 heap_pages | heap_size  | views 
------------+------------+-------
          1 | 8192 bytes | 50000
(1 row)

tuples: 150 removed, 1 remain, 0 are dead but not yet removable

-- run 2: session H holds a REPEATABLE READ snapshot open the whole time
-- session H: script
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM page_views;
\! sleep 45
COMMIT;
$ pgbench -n -f pv.sql -t 50000 shop
```

การรันที่ 1 และ 3 จบด้วย page ขนาด 8 kB **หนึ่ง** page: HOT pruning ทำความสะอาด page ไปเรื่อย ๆ การรันที่ 2 มี snapshot เก่าเปิดอยู่ตลอด จึงไม่มีอะไร prune ได้: table โตเป็นหลายร้อย page ที่มี row live หนึ่งและ row ตายราว 50 000 `VACUUM` รายงาน `50000 are dead but not yet removable` และแม้แต่ throughput ก็เหลือราวหนึ่งในสาม เมื่อ snapshot จบ `VACUUM` เรียก version ที่ตายคืนให้ใช้ซ้ำ แต่ไฟล์ไม่ค่อยหดกลับ: มีแต่ page ที่ว่างสนิทตอนท้ายเท่านั้นที่ถูกตัด

## Freezing และ transaction id wraparound

`xmin` และ `xmax` เป็นตัวนับ 32 บิต id จึงวนกลับในที่สุด PostgreSQL เปรียบเทียบมันแบบ modulo 2^31 ซึ่งหมายความว่า row ที่สร้าง "นานเกินไป" จะดูเหมือนอยู่ในอนาคตทันที เพื่อป้องกัน `VACUUM` **freeze** row version เก่า ทำเครื่องหมายว่ามองเห็นได้สำหรับทุกคนตลอดไป ([docs](https://www.postgresql.org/docs/18/routine-vacuuming.html#VACUUM-FOR-WRAPAROUND)) เอกสารระบุว่าทุก table ต้อง vacuum อย่างน้อยหนึ่งครั้งทุกสองพันล้าน transaction, autovacuum บังคับรอบ freeze ที่ `autovacuum_freeze_max_age` (ค่า default 200 ล้าน) และเซิร์ฟเวอร์เริ่มเตือน 40 ล้าน transaction ก่อน wraparound และปฏิเสธการกำหนด id ใหม่เมื่อเหลือ 3 ล้าน อายุของ id ที่ยังไม่ freeze เก่าที่สุดดูได้:

```sql
-- sql/freeze.sql
SELECT age(datfrozenxid) AS database_age FROM pg_database WHERE datname = current_database();
SHOW autovacuum_freeze_max_age;
SELECT relname, age(relfrozenxid) FROM pg_class WHERE relname = 'accounts';
VACUUM (FREEZE) accounts;
SELECT relname, age(relfrozenxid) FROM pg_class WHERE relname = 'accounts';
SELECT lp, t_xmin, combined_flags
FROM heap_page_items(get_raw_page('accounts', 0)),
     LATERAL heap_tuple_infomask_flags(t_infomask, t_infomask2)
WHERE lp = 2;
```

อายุของฐานข้อมูลมากบน cluster ทดลองนี้เพราะการรันก่อนหน้าทั้งหมด และต่ำกว่าขีดจำกัด 200 ล้านมาก `VACUUM (FREEZE)` ทำให้อายุของ table เป็น 0 และ flag ของ row เป็น `HEAP_XMIN_FROZEN`: `t_xmin` ของมันยังถูกเก็บแต่ตอนนี้ถูกละเลย `pg_current_xact_id()` คืน `xid8` 64 บิตที่ไม่ wrap ขณะที่ `xmin` คือ `xid` 32 บิต

## Mental Model

คิดว่า table คือสมุดบัญชีที่ไม่มีอะไรถูกลบเลย update ขีดฆ่ารายการเก่า (ตั้ง `xmax`) และเขียนรายการใหม่ข้างล่าง ผู้อ่านดูสมุดตามจังหวะเวลาเดียวและเพิกเฉยรายการที่เขียนทีหลังหรือถูกขีดฆ่าก่อนหน้านั้นได้ ต้องมีใครกลับมาลบบรรทัดที่ขีดฆ่าที่ไม่มีใครดูอยู่แล้ว: นั่นคือ VACUUM และผู้อ่านที่เก่าที่สุดทั่วฐานข้อมูลกำหนดว่ามันไปได้ไกลแค่ไหน

## เคล็ดลับและข้อควรระวัง

- การอ่านธรรมดาไม่ถือ row lock ภายใต้ MVCC ถ้าต้องการให้การอ่านจอง row สำหรับการเขียนที่จะมา นั่นคือหน้าที่ของ `SELECT ... FOR UPDATE` ในบทเรียน locking
- transaction ที่รันนานคือศัตรูของ vacuum ขณะที่ transaction เปิดอยู่ snapshot ของมันอาจยังต้องใช้ version เก่า dead tuple จึงลบไม่ได้และ table บวม (271 page แทนหนึ่งข้างบน)
- `VACUUM` เรียกพื้นที่คืนให้ใช้ซ้ำภายใน table ปกติไม่ทำให้ไฟล์บนดิสก์หด (ตัดเฉพาะ page ว่างตอนท้าย) `VACUUM FULL` เขียน table ใหม่ แต่ lock มันตลอดที่รัน
- update ถี่ที่ row เดิมสร้าง version มาก ดู `n_dead_tup` ใน `pg_stat_user_tables` และให้ autovacuum ตามทัน หรือปรับจูนสำหรับ table ที่ร้อน
- update column ที่มี index ทำให้ HOT ใช้ไม่ได้และเสียต้นทุนดูแล index หลีกเลี่ยงการทำ index column ที่เปลี่ยนตลอดเวลา

<Callout title="ทำไม SELECT ของคุณไม่เคยรอ">
เหตุผลที่ query วิเคราะห์ช้า ๆ กับ update ที่ไหลเข้ามารันด้วยกันได้อย่างมีความสุขคือ MVCC ผู้อ่านเห็น snapshot ที่หยุดนิ่ง ผู้เขียนต่อ version ใหม่ข้าง version เก่า ไม่มีใครบล็อกใคร ราคาคือ dead tuple ที่ทิ้งไว้ ซึ่งเป็นเหตุผลว่าทำไมมี VACUUM
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| MVCC (ผู้อ่านไม่บล็อกผู้เขียน ผู้เขียนไม่บล็อกผู้อ่าน) | concurrency สูงมาก query ยาวรันคู่กับโหลดเขียนโดยไม่มีใครรอ (A อ่าน version เก่าขณะ B update) | ต้องเก็บ row version เก่าเป็น dead tuple ต้องมี `VACUUM` และการเฝ้าดู snapshot เก่าอันเดียวทำให้ table บวมราว 270 เท่า (271 page แทนหนึ่ง) |
| HOT update | ไม่ต้องดูแล index และ prune page ได้ในที่ (8 kB หลัง 50 000 update) | เฉพาะเมื่อไม่มี column ที่ทำ index เปลี่ยน และ version ใหม่พอดีใน page เดิม |
| Lock-based concurrency control (ที่ฐานข้อมูลอื่นบางตัวใช้) | ไม่มี dead tuple สะสม ไม่ต้อง vacuum | ผู้อ่านและผู้เขียนบล็อกกัน ทำให้ throughput ต่ำลงเมื่อ workload ผสม |

## Common Misconceptions

- **"UPDATE เขียนทับ row ที่เดิม"** มันเขียน version ใหม่ที่ `ctid` ใหม่ (0,1 กลายเป็น 0,3) และทิ้งของเก่าไว้
- **"transaction ที่รันนานหยุด vacuum ทั้งระบบ"** ขอบเขตการเก็บกวาดเป็นต่อฐานข้อมูล: การรันที่ 1 ข้างบนไม่ได้รับผลจาก transaction ในฐานข้อมูลอื่น แต่มันหยุดทั้งฐานข้อมูลที่มันอยู่
- **"VACUUM ทำให้ไฟล์หด"** มันคืนพื้นที่ให้ใช้ซ้ำ ไฟล์ 271 page ยังเป็น 271 page
- **"count(*) ควรเป็นทันที"** ทุก version ต้องถูกตรวจกับ snapshot ของคุณ ข้ามได้เฉพาะ page ที่ visibility map ทำเครื่องหมาย all-visible
- **"SELECT เห็นข้อมูลล่าสุด"** มันเห็น snapshot ของมัน ซึ่งเก่ากว่า commit ล่าสุดได้ (Repeatable Read แสดง 500 ขณะที่ row บอก 400 แล้ว)
