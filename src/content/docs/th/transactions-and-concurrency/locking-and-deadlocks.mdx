MVCC ขจัดความจำเป็นของ read lock แต่การเขียนยังต้องประสานกัน เมื่อสอง transaction ต้องการเปลี่ยน row เดียวกัน หนึ่งต้องรออีกอันจบ ส่วนใหญ่ PostgreSQL ถือ **row lock** ที่จำเป็นให้คุณระหว่าง `UPDATE` หรือ `DELETE` แต่บางครั้งคุณอยาก lock row ในขณะที่อ่านมัน เพื่อไม่ให้ใครเปลี่ยนก่อนคุณ ([docs](https://www.postgresql.org/docs/18/explicit-locking.html))

ทุกอย่างด้านล่างรันบน **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) fence `sql` แบบ session เดียวรันในฐานข้อมูลเปล่าหนึ่งตัว ตัวอย่างการรอ lock, deadlock และคิวทุกอันคือการรันจริงของสองหรือสามโปรเซส `psql` ที่เริ่มพร้อมกัน พิมพ์ตามที่ตอบกลับมา `\o /dev/null` รอบ `pg_sleep(n)` ซ่อนผลลัพธ์ว่างของการหลับ และ `\! sleep n` (คำสั่ง shell) หยุด session โดยไม่มี query รันอยู่ จึงปรากฏเป็น `idle in transaction` process id และเวลามาจาก Mac เครื่องนี้และต่างกันทุกครั้ง

สาม table: `accounts` และ `ledger_entries` (มี foreign key ไปหามัน) สำหรับ row lock และ table `jobs` สำหรับคิวงาน

```sql
-- sql/setup.sql
CREATE TABLE accounts (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner   text NOT NULL,
  balance numeric NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts (owner, balance) VALUES ('Ada', 500), ('Linus', 100);

CREATE TABLE ledger_entries (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  account_id bigint NOT NULL REFERENCES accounts (id),
  amount     numeric NOT NULL
);

CREATE TABLE jobs (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  status  text NOT NULL DEFAULT 'pending',
  payload text NOT NULL
);
INSERT INTO jobs (payload) SELECT 'job-' || g FROM generate_series(1, 6) g;
```

## การรอ lock และวิธีดูมัน

`SELECT ... FOR UPDATE` อ่าน row และ lock มันเหมือนคุณกำลังจะ update transaction อื่นที่พยายาม update, delete หรือ lock row นั้นด้วยต้องรอจนกว่าคุณจะ commit หรือ rollback session A lock row ของ Ada และถือไว้สามวินาที B ขอ lock เดียวกันที่วินาทีแรก C ดู `pg_stat_activity` และ `pg_locks` ที่วินาทีที่สอง:

```text
-- session A (holder): script
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
\! sleep 3
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
-- session A (holder): psql output
BEGIN
 balance 
---------
     500
(1 row)

UPDATE 1
COMMIT

-- session B (waiter): script
\o /dev/null
SELECT pg_sleep(1);
\o
\timing on
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- session B (waiter): psql output
Timing is on.
 balance 
---------
     400
(1 row)

Time: 2008.066 ms (00:02.008)

-- session C (observer): script
\o /dev/null
SELECT pg_sleep(2);
\o
SELECT pid, state, wait_event_type, wait_event, pg_blocking_pids(pid) AS blocked_by, left(query, 44) AS query
FROM pg_stat_activity
WHERE datname = current_database() AND backend_type = 'client backend' AND pid <> pg_backend_pid()
ORDER BY pid;
SELECT locktype, mode, granted, pid FROM pg_locks WHERE NOT granted;
-- session C (observer): psql output
  pid  |        state        | wait_event_type |  wait_event   | blocked_by |                    query                     
-------+---------------------+-----------------+---------------+------------+----------------------------------------------
 21999 | idle in transaction | Client          | ClientRead    | {}         | SELECT balance FROM accounts WHERE id = 1 FO
 22000 | active              | Lock            | transactionid | {21999}    | SELECT balance FROM accounts WHERE id = 1 FO
(2 rows)

   locktype    |   mode    | granted |  pid  
---------------+-----------+---------+-------
 transactionid | ShareLock | f       | 22000
(1 row)
```

B ไม่พิมพ์อะไรประมาณสองวินาที จน A commit แล้วจึงได้ยอดใหม่ (400 ไม่ใช่ 500) C แสดงเหตุผล: A เป็น `idle in transaction` ที่ไม่ทำอะไร ขณะที่ B เป็น `active` ด้วย `wait_event_type = Lock` และ `wait_event = transactionid` และ `pg_blocking_pids(pid)` ระบุโปรเซสของ A ใน `pg_locks` B ถือ `ShareLock` ที่ยังไม่ได้รับบน transaction id ของ A: การรอระดับ row ถูกทำเป็นการรอให้ transaction อื่นจบ เมื่อไรที่แอป "ค้าง" สอง view นี้บอกว่าใครรอใคร

## Lost update และ FOR UPDATE

นี่คือ bug อ่าน-แก้-เขียนที่เป็นเหตุผลของ row lock ทั้งสอง session อ่านยอดของ Ada (500) คำนวณค่าใหม่ในแอป และเขียนกลับ แต่ละอันถูกต้องตามที่มันอ่าน รวมกันแล้วเสียการถอนหนึ่งครั้ง:

```text
-- session A: script
BEGIN;
SELECT balance AS a_read FROM accounts WHERE id = 1;
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = 500 - 100 WHERE id = 1;  -- computed in the application
COMMIT;
-- session A: psql output
BEGIN
 a_read 
--------
    500
(1 row)

UPDATE 1
COMMIT

-- session B: script
BEGIN;
SELECT balance AS b_read FROM accounts WHERE id = 1;
\o /dev/null
SELECT pg_sleep(1.5);
\o
UPDATE accounts SET balance = 500 - 50 WHERE id = 1;   -- computed from the same stale read
COMMIT;
-- session B: psql output
BEGIN
 b_read 
--------
    500
(1 row)

UPDATE 1
COMMIT

-- afterwards:
SELECT balance FROM accounts WHERE id = 1;
 balance 
---------
     450
(1 row)
```

Ada ควรเหลือ 350 หลังถอน 100 และ 50 แต่ table บอก 450: การถอนของ A หายไป ถูกเขียนทับโดย B ซึ่งคำนวณจากการอ่านที่เก่า ถ้าใส่ `FOR UPDATE` ที่การอ่าน B ต้องรอ A และการอ่านของมันคืนค่าที่ A เขียน:

```text
-- session A: script
BEGIN;
SELECT balance AS a_read FROM accounts WHERE id = 1 FOR UPDATE;
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
-- session A: psql output
BEGIN
 a_read 
--------
    500
(1 row)

UPDATE 1
COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(0.3);
\o
BEGIN;
SELECT balance AS b_read FROM accounts WHERE id = 1 FOR UPDATE;
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
COMMIT;
-- session B: psql output
BEGIN
 b_read 
--------
    400
(1 row)

UPDATE 1
COMMIT

-- afterwards:
SELECT balance FROM accounts WHERE id = 1;
 balance 
---------
     350
(1 row)
```

เมื่อการเปลี่ยนแปลงเขียนเป็น statement เดียวได้ คุณไม่ต้องใช้ `FOR UPDATE` เลย: `UPDATE accounts SET balance = balance - 50` อ่านและเขียน row ภายใต้ lock เดียว ภายใต้ Read Committed `UPDATE` ที่รออยู่ยัง **ตรวจ WHERE ใหม่** กับ version ใหม่ของ row เมื่อ transaction อื่น commit (PostgreSQL เรียกว่า EvalPlanQual, [docs](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED)) A ถอน 100 จาก Ada และเปิด transaction ค้างไว้ B พยายามถอน 50 เฉพาะ `WHERE balance >= 450`:

```text
-- session A: script
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
\o /dev/null
SELECT pg_sleep(2);
\o
COMMIT;
-- session A: psql output
BEGIN
UPDATE 1
COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
UPDATE accounts SET balance = balance - 50 WHERE id = 1 AND balance >= 450;
-- session B: psql output
UPDATE 0

-- afterwards:
SELECT balance FROM accounts WHERE id = 1;
 balance 
---------
     400
(1 row)
```

B รอ ดู row ที่ A ทิ้งไว้ (400) พบว่าเงื่อนไขไม่เป็นจริงแล้ว และไม่ update อะไร: `UPDATE 0` ไม่ใช่ error

## row-lock สี่โหมด

`FOR UPDATE` เป็นโหมดที่แรงที่สุดในสี่โหมด session ขอโหมดที่อ่อนกว่าได้เมื่อแค่ต้องการกัน row จากการถูกลบหรือถูกเปลี่ยน key:

- `FOR UPDATE` — ฉันอาจลบ row นี้หรือเปลี่ยน column ใดก็ได้
- `FOR NO KEY UPDATE` — ฉันจะเปลี่ยน row แต่ไม่เปลี่ยน key column นี่คือสิ่งที่ `UPDATE` ธรรมดาถือ
- `FOR SHARE` — ไม่มีใครเปลี่ยนหรือลบ row นี้ได้ขณะฉันดู แต่คนอื่นแชร์ lock ได้
- `FOR KEY SHARE` — ไม่มีใครลบหรือเปลี่ยน key ของมันได้ นี่คือสิ่งที่การตรวจ foreign key ถือบน row ฝั่ง parent

คู่ไหนขัดแย้งกัน? ทุกช่องด้านล่างคือการรันจริง: session A ถือ row lock ในโหมดของแถว, session B ลองโหมดของคอลัมน์ด้วย `NOWAIT` ครึ่งวินาทีต่อมา:

| A ถือ \ B ขอ | FOR KEY SHARE | FOR SHARE | FOR NO KEY UPDATE | FOR UPDATE |
|---|---|---|---|---|
| FOR KEY SHARE | ok | ok | ok | conflict |
| FOR SHARE | ok | ok | conflict | conflict |
| FOR NO KEY UPDATE | ok | conflict | conflict | conflict |
| FOR UPDATE | conflict | conflict | conflict | conflict |

ผลในทางปฏิบัติอยู่ที่ foreign key การ insert row ลูกถือ `FOR KEY SHARE` บน row parent ถ้า transaction อื่นถือ `FOR UPDATE` บน parent นั้น insert ต้องรอ:

```text
-- session A: script
BEGIN;
SELECT id FROM accounts WHERE id = 1 FOR UPDATE;
\o /dev/null
SELECT pg_sleep(2);
\o
COMMIT;
-- session A: psql output
BEGIN
 id 
----
  1
(1 row)

COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(0.5);
\o
\timing on
INSERT INTO ledger_entries (account_id, amount) VALUES (1, 10);
-- session B: psql output
Timing is on.
INSERT 0 1
Time: 1513.899 ms (00:01.514)
```

แต่ถ้า transaction อื่นถือ `FOR NO KEY UPDATE` ซึ่งเป็นสิ่งที่ `UPDATE` ธรรมดาของ column ที่ไม่ใช่ key ถือ insert ผ่านไปเลย:

```text
-- session A: script
BEGIN;
SELECT id FROM accounts WHERE id = 1 FOR NO KEY UPDATE;
\o /dev/null
SELECT pg_sleep(2);
\o
COMMIT;
-- session A: psql output
BEGIN
 id 
----
  1
(1 row)

COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(0.5);
\o
\timing on
INSERT INTO ledger_entries (account_id, amount) VALUES (1, 10);
-- session B: psql output
Timing is on.
INSERT 0 1
Time: 8.963 ms
```

1.5 วินาทีเทียบกับ 9 มิลลิวินาที เลือก `FOR NO KEY UPDATE` แทน `FOR UPDATE` เมื่อคุณจะไม่ลบ row หรือเปลี่ยน key ของมัน

## เมื่อการรอกลายเป็น deadlock

**deadlock** เกิดเมื่อสอง transaction แต่ละอันถือ lock ที่อีกอันต้องการ transaction A lock row 1 แล้วต้องการ row 2 transaction B lock row 2 ไว้และตอนนี้ต้องการ row 1 ไม่มีใครไปต่อได้ และไม่มีใครปล่อยก่อน

export const deadlockCycle = `flowchart LR
  A["Txn A holds lock on row 1"] -->|waits for row 2| B["Txn B holds lock on row 2"]
  B -->|waits for row 1| A`;

<Mermaid code={deadlockCycle} title="วงจร deadlock: แต่ละ transaction รอ lock ที่อีกอันถือ" />

PostgreSQL มีตัวตรวจ deadlock ผู้รอตรวจหาวงจรก็ต่อเมื่อรอเกิน `deadlock_timeout` แล้ว ค่า default คือหนึ่งวินาที เมื่อเจอ มันยกเลิกหนึ่ง transaction เพื่อให้ที่เหลือไปต่อ (อันไหนทำนายยาก, [docs](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-DEADLOCKS)) สอง session ด้านล่าง update สอง row เดียวกันในลำดับตรงข้าม:

```sql
-- sql/timeouts.sql
SHOW deadlock_timeout;
SHOW lock_timeout;
```

```text

------------------

(1 row)

--------------

(1 row)
```

-- session B: script

\o

session A ถูกเลือกเป็นเหยื่อ: ได้ SQLSTATE `40P01` และต้อง retry ทั้ง transaction ขณะที่ update ที่สองของ B ซึ่งถูกปล่อยโดย rollback ของ A ผ่านไปได้ ข้อความฝั่ง client บอก process id แต่ไม่บอก statement ส่วนนั้นไปที่ server log ซึ่งคือที่ที่คุณวินิจฉัย deadlock ทีหลัง:

## เลือกไม่รอ: NOWAIT, lock_timeout และ SKIP LOCKED

บางครั้งการรอคือพฤติกรรมที่ผิด `NOWAIT` ทำให้ `SELECT ... FOR UPDATE` ล้มทันทีถ้า row ถูก lock `lock_timeout` จำกัดการรอของ statement ใดก็ได้ ทั้งคู่ยก SQLSTATE `55P03` (ข้อความต่างกัน) `SKIP LOCKED` ไม่ล้มเลย: มันก้าวข้าม row ที่ถูก lock เงียบ ๆ A ถือ row ของ Ada B ลองสามอย่าง:

```text
-- session A: script
BEGIN;
SELECT 1 FROM accounts WHERE id = 1 FOR UPDATE;
\o /dev/null
SELECT pg_sleep(3);
\o
COMMIT;
-- session A: psql output
BEGIN
 ?column? 
----------
        1
(1 row)

COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
SET lock_timeout = '500ms';
UPDATE accounts SET balance = balance WHERE id = 1;
SELECT * FROM accounts WHERE id = 2 FOR UPDATE NOWAIT;
-- session B: psql output
ERROR:  could not obtain lock on row in relation "accounts"
SET
ERROR:  canceling statement due to lock timeout
CONTEXT:  while updating tuple (0,1) in relation "accounts"
 id | owner | balance 
----+-------+---------
  2 | Linus |     100
(1 row)
```

`NOWAIT` บน row ที่ถูก lock ล้มทันทีด้วย `could not obtain lock on row in relation "accounts"` ด้วย `lock_timeout = '500ms'` `UPDATE` รอครึ่งวินาทีและถูกยกเลิกด้วย `canceling statement due to lock timeout` และ `NOWAIT` เดียวกันบน row อื่นที่ไม่ถูก lock (Linus) สำเร็จตามปกติ

`SKIP LOCKED` คือกระดูกสันหลังของคิวงานที่ worker หลายตัวแต่ละตัวหยิบงานว่างถัดไป เอกสาร PostgreSQL อธิบายว่าเป็นวิธีหลีกเลี่ยง lock contention กับ consumer หลายตัวของ table แบบคิว ([docs](https://www.postgresql.org/docs/18/sql-select.html#SQL-FOR-UPDATE-SHARE)) มันให้มุมมอง table ที่ไม่สอดคล้องโดยตั้งใจ จึงผิดสำหรับสิ่งที่ต้องเห็นทุก row สอง worker แต่ละตัวหยิบสองงาน pending จาก table หกงาน worker 2 เริ่มครึ่งวินาทีหลัง worker 1 ขณะที่ worker 1 ยังถือ row:

\o

COMMIT;

## Table lock และ advisory lock

ทุก statement ยังถือ lock ระดับ table ส่วนใหญ่ไม่เป็นอันตราย แต่ `ACCESS EXCLUSIVE` (ที่ `LOCK TABLE`, `DROP TABLE`, `VACUUM FULL` และ `ALTER TABLE` หลายแบบถือ) ขัดแย้งกับทุกอย่าง รวมถึง `SELECT` ธรรมดา A ถือมันสองวินาที `count(*)` ของ B เริ่มที่ครึ่งวินาที:

```text
-- session A: script
BEGIN;
LOCK TABLE accounts IN ACCESS EXCLUSIVE MODE;
\o /dev/null
SELECT pg_sleep(2);
\o
COMMIT;
-- session A: psql output
BEGIN
LOCK TABLE
COMMIT

-- session B: script
\o /dev/null
SELECT pg_sleep(0.5);
\o
\timing on
SELECT count(*) FROM accounts;
-- session B: psql output
Timing is on.
 count 
-------
     2
(1 row)

Time: 1504.090 ms (00:01.504)
```

B รอ 1.5 วินาทีสำหรับ query ที่อ่านหนึ่ง table นี่คือเหตุผลที่การเปลี่ยน schema บน table ที่ร้อนอันตราย

**advisory lock** คือ lock ที่ไม่มี table อยู่เบื้องหลัง: คุณเลือกตัวเลข ฐานข้อมูลติดตามว่าใครถือมัน มีไว้สำหรับการประสานที่แอปเป็นเจ้าของ เช่น "worker เดียวเท่านั้นที่รัน job กลางคืนนี้" advisory lock ระดับ session อยู่จนกว่าจะ unlock หรือ connection จบ ส่วนแบบ `xact` จบพร้อม transaction:

```text
-- session A: script
SELECT pg_try_advisory_lock(42) AS a_got_it;
\o /dev/null
SELECT pg_sleep(2);
\o
SELECT pg_advisory_unlock(42) AS a_released;
-- session A: psql output
 a_got_it 
----------
 t
(1 row)

 a_released 
------------

(1 row)

-- session B: script
\o /dev/null
SELECT pg_sleep(1);
\o
SELECT pg_try_advisory_lock(42) AS b_got_it;
\o /dev/null
SELECT pg_sleep(2);
\o

----------

(1 row)

----------------

(1 row)

------------

(1 row)
```

  UPDATE accounts SET balance = balance - amount WHERE id = from_id;

  UPDATE accounts SET balance = balance + amount WHERE id = to_id;

$$;

## Mental Model

lock คือบัตรคิวสำหรับสิ่งหนึ่ง MVCC หมายความว่าผู้อ่านไม่ต้องมีบัตร ผู้เขียนต้องมี หนึ่งใบต่อ row ที่เปลี่ยน และบัตรถือจนกว่าจะ commit หรือ rollback ไม่ใช่จนสิ้นสุด statement การรอจึงคือการรอ transaction เสมอ นั่นคือเหตุผลที่ transaction ที่ลืมไว้ทำให้ทุกคนข้างหลังติด deadlock คือสองคนแต่ละคนถือบัตรที่อีกคนต้องการ ฐานข้อมูลตัดสินโดยยกเลิกหนึ่ง

## เคล็ดลับและข้อควรระวัง

- lock row ในลำดับที่สม่ำเสมอทุกที่ในโค้ด ถ้าทุก transaction แตะ row 1 ก่อน row 2 วงจรที่ทำให้เกิด deadlock ก็ไม่มีวันเกิด
- ปฏิบัติต่อ deadlock error (`40P01`) และ serialization failure (`40001`) แบบเดียวกัน: rollback แล้ว retry ทั้ง transaction ทั้งคู่เป็นสิ่งที่คาดไว้ภายใต้ concurrency
- ทำงานระหว่างการถือ lock กับ commit ให้สั้นที่สุด ยิ่งถือ lock นาน คนอื่นยิ่งต่อคิวนาน
- เลือก `UPDATE` แบบสัมพัทธ์ statement เดียวแทนอ่านแล้วเขียน ใช้ `FOR UPDATE` เมื่อต้องอ่าน ตัดสินใจ แล้วเขียน
- `SKIP LOCKED` เหมาะกับคิวแต่ผิดสำหรับงานบัญชี มันข้าม row โดยตั้งใจ อย่าใช้ในที่ที่ต้องเห็นทุก row ที่ตรง
- ตั้ง `lock_timeout` (และ `idle_in_transaction_session_timeout`) เพื่อให้ session ที่ติดไม่บล็อก table ร้อนไม่มีกำหนด

<Callout title="ลำดับ lock ที่สม่ำเสมอป้องกัน deadlock ส่วนใหญ่">
deadlock ไม่ได้เกิดจาก lock มากเกินไป แต่เกิดจาก lock ในลำดับที่ขัดแย้งกัน ตัดสินใจลำดับสากลหนึ่งอันสำหรับการขอ lock เช่นเรียงตาม primary key จากน้อยไปมากเสมอ และใช้ในทุก transaction PostgreSQL ยังตรวจจับ deadlock ที่หลุดมาได้ แต่คุณแทบไม่ต้องส่งให้มันหา
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| Row-level lock | concurrency สูง เพราะ transaction อื่นยังแก้ row อื่นใน table เดียวกันได้ | ต้องออกแบบลำดับ lock ที่สม่ำเสมอเอง ไม่งั้นเสี่ยง deadlock |
| Table-level lock | เขียนง่าย รับประกันว่าไม่มีใครแตะทั้ง table ขณะคุณทำงาน | บล็อกแม้ `SELECT` ธรรมดา (รอ 1.5 วินาทีข้างบน) |
| `SELECT ... FOR UPDATE` แบบชัดเจน | ควบคุมเวลาการถือ lock ได้แม่นยำ ป้องกัน lost update (350 ไม่ใช่ 450) | เขียนโค้ดมากขึ้น และต้องคิดลำดับ lock เอง |
| พึ่ง lock โดยนัยของ `UPDATE` แบบสัมพัทธ์ statement เดียว | โค้ดสั้น ไม่ต้องคิดเรื่อง lock ล่วงหน้า | ใช้ได้เมื่อการเปลี่ยนพอดีใน statement เดียว |
| `NOWAIT` / `lock_timeout` | ล้มเร็วแทนการต่อคิว | ผู้เรียกต้องจัดการ `55P03` |
| `SKIP LOCKED` | worker หลายตัวแชร์คิวโดยไม่บล็อกกัน | มุมมอง table ที่ไม่สอดคล้องโดยตั้งใจ |

## Common Misconceptions

- **"deadlock แปลว่าฉัน lock มากเกินไป"** มันแปลว่าสอง transaction lock ในลำดับต่างกัน lock ชุดเดียวกันในลำดับเดียวไม่มีวัน deadlock
- **"ฐานข้อมูลเลือกเหยื่อ deadlock อย่างยุติธรรม"** ทำนายไม่ได้: ในการรันข้างบน transaction ที่บังเอิญรันการตรวจถูกยกเลิก
- **"SELECT FOR UPDATE กับ UPDATE เป็น lock คนละชนิด"** `UPDATE` ธรรมดาถือ `FOR NO KEY UPDATE` ซึ่งขัดแย้งกับ `FOR UPDATE` และกับตัวมันเอง
- **"lock ถูกปล่อยเมื่อจบ statement"** row lock อยู่จนกว่า transaction จบ
- **"Read Committed ทำให้อ่านแล้วเขียนปลอดภัย"** ทั้งสอง session อ่าน 500 และการถอนหนึ่งครั้งหาย
