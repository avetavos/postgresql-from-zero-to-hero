การอ่านคือสิ่งที่พบบ่อยที่สุดที่คุณทำกับฐานข้อมูล และ `SELECT` คือวิธีที่ทำ `SELECT` อธิบายว่าคุณต้องการ column ไหน row ไหนผ่านเกณฑ์ เรียงอย่างไร และกี่แถว เซิร์ฟเวอร์ส่งชุดผลลัพธ์ — ศูนย์ row หรือมากกว่า — โดยไม่เปลี่ยนอะไรบนดิสก์

ทุก output ด้านล่างเป็นของจริงจาก **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) รันในฐานข้อมูลเปล่าหนึ่งตัว จากบนลงล่าง เริ่มด้วยชุดข้อมูลมาตรฐานของคอร์ส row ที่คุณเห็นที่นี่จึงเป็น row เดียวกับที่ได้จากบท insert ตัวเลขเวลามาจาก Mac เครื่องนี้

```sql
-- sql/setup.sql
CREATE TABLE authors (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  born int
);
CREATE TABLE books (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title       text NOT NULL,
  author_id   bigint REFERENCES authors (id),
  published   int,
  copies_sold int NOT NULL DEFAULT 0
);
CREATE TABLE sales (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  book_id bigint REFERENCES books (id),
  region  text NOT NULL,
  copies  int NOT NULL
);
INSERT INTO authors (name, born) VALUES ('Mara Linde', 1968), ('Owen Pryce', 1975), ('Sela Vance', 1990);
INSERT INTO books (title, author_id, published, copies_sold) VALUES
  ('Quiet Harbors', 1, 2003, 450), ('The Glass Orchard', 1, 2018, 1250), ('Tidal Notes', 2, 2011, 600), ('Unlinked Draft', NULL, 2020, 0);
INSERT INTO sales (book_id, region, copies) VALUES
  (2, 'East', 900), (3, 'West', 400), (1, 'West', 400), (3, 'East', 200), (2, 'West', 150), (1, 'East', 50);
```

## IN, BETWEEN และการจับคู่รูปแบบ

`IN` ตรวจการเป็นสมาชิกในลิสต์ `BETWEEN` คือช่วงแบบรวมปลายทั้งสอง (รวม 1968 และ 1975 ด้านล่าง) และ `LIKE` จับคู่รูปแบบข้อความ

```sql
-- sql/select-between-in.sql
SELECT name, born
FROM authors
WHERE born BETWEEN 1968 AND 1975;

SELECT title FROM books WHERE published IN (2003, 2011);
```

```text
    name    | born 
------------+------
 Mara Linde | 1968
 Owen Pryce | 1975
(2 rows)

     title     
---------------
 Quiet Harbors
 Tidal Notes
(2 rows)
```

`LIKE` แยกตัวพิมพ์เล็กใหญ่ PostgreSQL มี `ILIKE` สำหรับการจับคู่แบบไม่สนตัวพิมพ์ ในรูปแบบ `%` ตรงกับตัวอักษรกี่ตัวก็ได้ และ `_` ตรงกับหนึ่งตัวพอดี

กฎเรื่องตัวพิมพ์เทียบข้างกัน (`'m%'` เป็นตัวพิมพ์เล็ก ชื่อขึ้นต้นด้วย `M`):

```sql
-- sql/select-like-case.sql
SELECT name,
       name LIKE 'm%'  AS like_lower_m,
       name ILIKE 'm%' AS ilike_lower_m,
       name LIKE '_ara%' AS underscore_matches_one_char
FROM authors WHERE id = 1;
```

```text

------------+--------------+---------------+-----------------------------

(1 row)
```

## การจัดการ NULL

`NULL` หมายถึง "ไม่ทราบ" จึงไม่ทำตัวเหมือนค่าปกติ คุณทดสอบด้วย `=` ไม่ได้ ใช้ `IS NULL` และ `IS NOT NULL` แทน `Unlinked Draft` ในชุดข้อมูลไม่มี author

<Tabs syncKey="lang">

  </TabItem>

  </TabItem>
  <TabItem label="Rust">
    ```rust

        .fetch_all(&pool)
        .await?;
    ```

```text
----------------

```

ส่วนที่เหลือของตรรกะสามค่า รันบน table เดียวกัน `= NULL` ไม่คืนอะไร `<> 1` **ทิ้ง** row ที่ author เป็น NULL ด้วย เพราะ `unknown <> 1` คือ unknown ไม่ใช่ true ส่วน `IS DISTINCT FROM` ปฏิบัติต่อ NULL เหมือนค่าปกติ และ `count(column)` ข้าม NULL ขณะที่ `count(*)` ไม่ข้าม:

```sql
-- sql/select-null.sql
SELECT title FROM books WHERE author_id = NULL;
SELECT title FROM books WHERE author_id <> 1 ORDER BY id;
SELECT title FROM books WHERE author_id IS DISTINCT FROM 1 ORDER BY id;
SELECT count(*) AS all_rows, count(author_id) AS non_null_author_id FROM books;
```

```text

-------
(0 rows)

    title    
-------------
 Tidal Notes
(1 row)

     title      
----------------

 Unlinked Draft
(2 rows)

 all_rows | non_null_author_id 
----------+--------------------
        4 |                  3
(1 row)
```

NULL ยังมีตำแหน่งการเรียง: ท้ายสุดในการเรียงจากน้อยไปมากโดยค่าเริ่มต้น และหน้าสุดเมื่อใช้ `NULLS FIRST`:

```sql
-- sql/select-null-order.sql
SELECT title, author_id FROM books ORDER BY author_id;
SELECT title, author_id FROM books ORDER BY author_id NULLS FIRST, id;
```

```text
(4 rows)

-------------------+-----------

 Quiet Harbors     |         1
 The Glass Orchard |         1
 Tidal Notes       |         2
(4 rows)
```

ลำดับการเรียงแน่นอนได้ก็ต่อเมื่อ key ที่ใช้เรียงไม่ซ้ำ `sales` มี tie (สอง row ที่ 400 copies) เพิ่ม tiebreaker เช่น primary key เพื่อให้ลำดับทำซ้ำได้:

```sql
-- sql/select-order-tiebreaker.sql
SELECT id, region, copies FROM sales ORDER BY copies DESC, id LIMIT 3;
```

```text

----+--------+--------
  1 | East   |    900
  2 | West   |    400
  3 | West   |    400
(3 rows)
```

ข้อความเรียงตาม collation ของฐานข้อมูล ไม่ใช่ตามค่าไบต์ ใน `en_US.utf8` `apple` กับ `Apple` อยู่ติดกัน ใน `"C"` ตัวพิมพ์ใหญ่ทุกตัวมาก่อนตัวพิมพ์เล็กทุกตัว:

```sql
-- sql/select-collation.sql

SELECT w AS c_collation FROM (VALUES ('apple'), ('Banana'), ('cherry'), ('Apple')) t(w) ORDER BY w COLLATE "C";
```

```text
(4 rows)

(4 rows)
```

### OFFSET ลึกช้า keyset paging ไม่ช้า

`OFFSET n` ข้าม row โดยไม่อ่านไม่ได้: เซิร์ฟเวอร์สร้าง `n + limit` row แรกแล้วทิ้ง `n` ตัว ต้นทุนโตตามเลขหน้า keyset ("seek") paging ขอ row หลัง key ล่าสุดที่คุณเห็นแทน บน 200,000 row หน้า 15,001 ทั้งสองวิธี (plan แสดง row ที่อ่านจริง):

```sql
-- sql/offset-vs-keyset.sql
CREATE TABLE events (id int PRIMARY KEY, payload text);
INSERT INTO events SELECT g, md5(g::text) FROM generate_series(1, 200000) g;
ANALYZE events;
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, SUMMARY ON)
SELECT id FROM events ORDER BY id LIMIT 10 OFFSET 150000;
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, SUMMARY ON)
SELECT id FROM events WHERE id > 150000 ORDER BY id LIMIT 10;
```


### การจับคู่รูปแบบและ index

คำแนะนำที่ว่า `ILIKE '%text%'` "ใช้ index ธรรมดาไม่ได้" เป็นจริง และทางแก้คือ trigram index บน 200,000 row เดิม พบ 4 row จาก 200,000 กับ `ILIKE` บน `'%A3F9C%'` (ข้อมูลเป็น hex ตัวพิมพ์เล็ก จึงทำให้ `ILIKE` มีความหมาย): แม้มี B-tree ธรรมดาบน column PostgreSQL ก็อ่านทั้ง table แต่เมื่อมี GIN index ของ `pg_trgm` มันอ่าน heap block ห้าบล็อก:

```sql
-- sql/ilike-trigram.sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX events_payload_btree ON events (payload);
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, SUMMARY ON)
SELECT id FROM events WHERE payload ILIKE '%A3F9C%';
CREATE INDEX events_payload_trgm ON events USING gin (payload gin_trgm_ops);
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, SUMMARY ON)
SELECT id FROM events WHERE payload ILIKE '%A3F9C%';
```

## Mental Model

`SELECT` คือ pipeline: FROM (row ไหนมีอยู่) แล้ว WHERE (ตัวไหนผ่าน) แล้ว select list แล้ว ORDER BY แล้ว LIMIT/OFFSET แต่ละขั้นเห็นเฉพาะสิ่งที่ขั้นก่อนหน้าส่งให้ นั่นคือเหตุผลที่การเปรียบเทียบกับ NULL ทิ้ง row แบบเงียบ ๆ (ขั้น WHERE เก็บเฉพาะ *true*) ทำไม LIMIT ที่ไม่เรียงจึงไม่แน่นอน (ไม่เคยกำหนดลำดับ) และทำไม OFFSET ลึกจึงแพง (ขั้นก่อนหน้าต้องสร้าง row เหล่านั้นก่อน OFFSET จะทิ้งได้)

## เคล็ดลับและข้อควรระวัง

- `NULL` ใช้ตรรกะสามค่า: การเปรียบเทียบกับ `NULL` ไม่จริงไม่เท็จแต่ไม่ทราบ row เหล่านั้นจึงถูก `WHERE` ตัดออก ใช้ `IS NULL` (หรือ `IS DISTINCT FROM`) แทน `= NULL` เสมอ
- `LIMIT` ที่ไม่มี `ORDER BY` คืนส่วนย่อยตามอำเภอใจ — เซิร์ฟเวอร์คืน row ลำดับใดก็ได้ และลำดับนั้นเปลี่ยนได้ระหว่างการรัน จับคู่ `LIMIT` กับ `ORDER BY` ที่แน่นอนพร้อม tiebreaker ที่ไม่ซ้ำเสมอ
- `ILIKE '%x%'` ใช้ B-tree ธรรมดาไม่ได้ GIN index ของ `pg_trgm` ทำให้เร็ว (ราว 100 ms เหลือ 0.2 ms ข้างบน) `lower(col) = ...` ต้องใช้ expression index
- ควรใช้ keyset paging แทน `OFFSET` ลึกกับ table ใหญ่
- เลือกเฉพาะ column ที่ต้องการ ทำให้ชุดผลลัพธ์เล็กและโค้ดทนต่อการเปลี่ยน schema

<Callout title="เรียงก่อนแบ่งหน้า">
การแบ่งหน้ามีความหมายเฉพาะบนการเรียงที่คงที่ ถ้าสอง row เสมอกันบน column ที่เรียง ให้เพิ่ม tiebreaker เช่น `ORDER BY born DESC, id` เพื่อไม่ให้ row เดียวกันโผล่ในสองหน้า

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| ลิสต์ column ชัดเจน | API คงที่ ข้อมูลผ่านเครือข่ายน้อยลง ไม่รั่ว column อ่อนไหว | ต้องแก้ query เมื่อ column ที่ต้องการเปลี่ยน |
| `SELECT *` | เขียนเร็ว สะดวกสำหรับ prototype หรือสำรวจข้อมูล | พังแบบเงียบ ๆ เมื่อมีคนเพิ่ม/ลบ/เปลี่ยนชื่อ column ทีหลัง และอาจรั่ว column ที่ไม่ควรเปิดเผย |
| กรองด้วย `WHERE` ใน SQL | ถูกผลักลงฐานข้อมูล ใช้ index ได้ มีเฉพาะ row ที่ต้องการข้ามเครือข่าย | ต้องเข้าใจ SQL และวางแผน index ให้ตรงกับรูปแบบตัวกรอง |
| ดึงทุกอย่างแล้วกรองในโค้ดแอป | ตรรกะฝั่งแอปง่าย ไม่ต้องเขียน SQL ซับซ้อน | สิ้นเปลืองแบนด์วิดท์ พลาดโอกาสใช้ index และช้าลงเมื่อ table โต |
| แบ่งหน้าด้วย `LIMIT`/`OFFSET` | เรียบง่าย กระโดดไปหน้าใดก็ได้ | ต้นทุนโตตาม offset (19 ms ที่ 150,000 row) |
| Keyset paging | ต้นทุนต่อหน้าคงที่ | ต้องมี key เรียงที่ไม่ซ้ำและมี index กระโดดหน้าแบบสุ่มไม่ได้ |

## Common Misconceptions

- **"`WHERE col <> 1` คืนทุก row ที่ไม่ใช่ 1"** ไม่รวม row ที่ `col` เป็น NULL (พิสูจน์ข้างบน)
- **"`LIMIT 10` ให้ 10 row แรก"** ให้ 10 row ตัวไหนไม่ระบุถ้าไม่มี `ORDER BY`
- **"`BETWEEN` ไม่รวมขอบบน"** รวมทั้งสองปลาย
- **"`ILIKE` คือ `LIKE` ที่ช้ากว่า"** มันยังใช้ index เดียวกับ `LIKE` ไม่ได้ด้วย trigram index ทำให้เร็วทั้งคู่
- **"การเรียงเหมือนกันทุกที่"** มันตาม collation: `apple, Apple, Banana` ใน `en_US.utf8`, `Apple, Banana, apple` ใน `"C"`
