สองหน้าที่ปฏิบัติการสุดท้ายคือสิ่งที่หวังว่าจะไม่ต้องใช้และข้ามไม่ได้ **Backup** ให้คุณสร้างใหม่หลังดิสก์พัง deploy พลาด หรือ `DELETE` ที่ผิดพลาด **Security** ควบคุมว่าใครเชื่อมต่อได้ ใครเห็นอะไรได้ และข้อมูลเดินทางผ่านเครือข่ายอย่างไร ฐานข้อมูลที่เร็วและพร้อมใช้งานสูงยังเป็นภาระถ้ากู้คืนไม่ได้ หรือถ้าใครบนอินเทอร์เน็ตอ่านมันได้

บทเรียนนี้ครอบคลุมทั้งสองตระกูลของ backup ที่ PostgreSQL มี แล้วเดินลงตามชั้นของการควบคุมการเข้าถึงจากขอบเครือข่ายถึงแต่ละ row ทุกอย่างรันจริงบน **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) ส่วน backup และ network security ใช้คอนเทนเนอร์เดียวที่เริ่มด้วย `--network none` (ไม่มีเครือข่ายเลย; การเชื่อมต่อผ่าน loopback ของมันเอง) และ volume ที่ตั้งชื่อ `postgresql-b3-*` ลบทั้งหมดเมื่อจบ ส่วน role และ row-level security เป็น fence `sql` ที่รันในฐานข้อมูลเปล่าหนึ่งตัว `<your-password>` แทนค่าใดก็ได้ที่คุณเลือก

## Backup สองชนิด

backup ของ PostgreSQL มีสองแบบที่เหมาะกับความต้องการต่างกัน

| ชนิด     | เครื่องมือ                          | สิ่งที่มันจับ                        | เหมาะกับ                          |
|----------|-------------------------------|-----------------------------------------|-----------------------------------|
| Logical  | `pg_dump` / `pg_restore`      | SQL หรือ archive ของฐานข้อมูลหนึ่งตัว       | ฐานข้อมูลเดี่ยว การย้าย version   |
| Physical | base backup + WAL archiving   | ไฟล์ของทั้ง cluster แบบ byte ต่อ byte| cluster ใหญ่ point-in-time recovery |

แล็บ: ฐานข้อมูลหนึ่งตัวที่เปิด archiving `archive_command` คัดลอก WAL segment ที่เสร็จแล้วแต่ละอันไปยัง volume ที่อยู่รอดกว่าเซิร์ฟเวอร์ `summarize_wal` (จำเป็นสำหรับ incremental backup) เปิดอยู่ด้วย

```bash
# scripts/backup-lab.sh
docker volume create postgresql-b3-pgdata
docker volume create postgresql-b3-archive
docker volume create postgresql-b3-backup
# the archive and backup volumes must be writable by the postgres user
docker run --rm --user root -v postgresql-b3-archive:/archive -v postgresql-b3-backup:/backup \
  postgres:18.6 chown postgres:postgres /archive /backup

docker run -d --name postgresql-b3-pg --network none --memory 768m --cpus 4 \
  -e POSTGRES_PASSWORD=<your-password> \
  -v postgresql-b3-pgdata:/var/lib/postgresql -v postgresql-b3-archive:/archive -v postgresql-b3-backup:/backup \
  postgres:18.6 \
  -c archive_mode=on -c 'archive_command=test ! -f /archive/%f && cp %p /archive/%f' -c summarize_wal=on
```


### Logical backup

logical backup รัน `pg_dump` ซึ่งอ่านฐานข้อมูลและเขียนคำสั่งที่จำเป็นเพื่อสร้างมันใหม่ มันพกพาข้ามเครื่องและแม้แต่ข้าม major version จึงเหมาะกับการย้ายหรือ clone ฐานข้อมูลเดี่ยว ([docs](https://www.postgresql.org/docs/18/app-pgdump.html)) มันจับฐานข้อมูลเดียวเท่านั้น; role และวัตถุระดับ cluster อื่นมาจาก `pg_dumpall --globals-only` รูปแบบ custom ถูกบีบอัดและให้ `pg_restore` เลือกส่วนและรันขนานได้; ฐานข้อมูลเดียวกันเป็น SQL ธรรมดาใหญ่กว่าสี่เท่าครึ่งที่นี่

```text
$ docker exec --user postgres postgresql-b3-pg pg_dump --format=custom --file=/backup/shop.dump shop

$ docker exec --user postgres postgresql-b3-pg sh -c "pg_dump shop | wc -c; ls -l /backup/shop.dump | awk '{print $5, $9}'"    # plain SQL bytes, then the custom-format file
4559583
1006636 /backup/shop.dump

$ docker exec --user postgres postgresql-b3-pg pg_restore --list /backup/shop.dump | head -12
;
; Archive created at 2026-09-30 08:42:43 UTC
;     dbname: shop
;     TOC Entries: 9
;     Compression: gzip
;     Dump Version: 1.16-0
;     Format: CUSTOM
;     Integer: 4 bytes
;     Offset: 8 bytes
;     Dumped from database version: 18.6 (Debian 18.6-1.pgdg13+2)
;     Dumped by pg_dump version: 18.6 (Debian 18.6-1.pgdg13+2)
;

# --create names the database to CONNECT to first; the database restored is the one in the dump

$ docker exec --user postgres postgresql-b3-pg pg_restore --dbname=shop_restored --create /backup/shop.dump    # shop_restored does not exist yet
pg_restore: error: connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed: FATAL:  database "shop_restored" does not exist

$ docker exec --user postgres postgresql-b3-pg createdb shop_restored

$ docker exec --user postgres postgresql-b3-pg pg_restore --dbname=shop_restored --jobs=2 /backup/shop.dump

$ docker exec --user postgres postgresql-b3-pg psql -d shop -Atc "SELECT count(*), sum(amount) FROM orders"
200000|9900000

$ docker exec --user postgres postgresql-b3-pg psql -d shop_restored -Atc "SELECT count(*), sum(amount) FROM orders"
200000|9900000

# restoring INTO the cluster under the dump's own name: drop the original, then --create with a maintenance database

$ docker exec --user postgres postgresql-b3-pg dropdb shop

$ docker exec --user postgres postgresql-b3-pg pg_restore --dbname=postgres --create /backup/shop.dump

$ docker exec --user postgres postgresql-b3-pg psql -d shop -Atc "SELECT count(*), sum(amount) FROM orders"
200000|9900000
```

สองบทเรียนใน transcript dump กับสำเนาที่กู้คืนตรงกันทั้ง count และ sum ซึ่งคือการตรวจที่การซ้อมกู้คืนควรทำ และ `--create` ไม่ได้แปลว่า "กู้คืนเข้าฐานข้อมูลใหม่ชื่อที่ฉันให้": `--dbname` ระบุฐานข้อมูลที่ *เชื่อมต่อก่อน* (ต้องมีอยู่) และฐานข้อมูลที่ถูกสร้างคือชื่อที่อยู่ใน dump ความพยายามแรกล้มเพราะ `shop_restored` ไม่มีอยู่ รูปแบบที่ใช้ได้คือ `createdb` + กู้คืนโดยไม่มี `--create` หรือ `--dbname=postgres --create` หลัง drop ต้นฉบับ

### Physical backup และ point-in-time recovery

สำหรับ cluster ใหญ่หรือยุ่ง การ dump แบบ logical ช้าเกินไป แทนที่จะทำเช่นนั้น คุณทำ **base backup** — สำเนาระดับ byte ของไฟล์ข้อมูล — และ archive write-ahead log ต่อเนื่อง การ replay WAL บน base backup ให้คุณกู้คืนไปยังช่วงเวลาใดก็ได้ เรียกว่า **point-in-time recovery** (PITR, [docs](https://www.postgresql.org/docs/18/continuous-archiving.html))

export const backupDiagram = `flowchart LR
  PG[(Primary cluster)] -->|pg_basebackup| Base[Base backup]
  PG -->|archive_command| WAL[Archived WAL segments]
  Base --> Restore[Restore]
  WAL -->|replay to a chosen time| Restore
  Restore --> Recovered[(Recovered cluster)]`;

<Mermaid code={backupDiagram} title="Base backup บวม WAL ที่ archive ไว้ทำให้ทำ point-in-time recovery ได้" />

`pg_basebackup` ทำ base backup และ `pg_verifybackup` ตรวจมันกับ manifest ที่มันเขียน PostgreSQL 17 เพิ่ม backup แบบ **incremental**: หลัง full backup อันที่สองคัดลอกเฉพาะ block ที่เปลี่ยน (สิ่งที่ `summarize_wal` บันทึก) และ `pg_combinebackup` รวมสายกลับเป็น full backup ([release notes](https://www.postgresql.org/docs/17/release-17.html), [docs](https://www.postgresql.org/docs/18/app-pgcombinebackup.html))


incremental backup ขนาด 30 MB เทียบกับ 88 MB ของ full หลังเพิ่ม 50 003 row ใน table 200 000 row ผลรวมที่ได้ verify ได้เหมือน base backup ใด ๆ

ทีนี้ภัยพิบัติ มี base backup อยู่ เพิ่มสาม row หลังมัน และมีคนรัน `DELETE FROM orders` โดยไม่มี `WHERE` สองวินาทีก่อนความผิดพลาดเราจดเวลาไว้ `pg_switch_wal()` ปิด WAL segment ปัจจุบันเพื่อให้ถูก archive และ `pg_stat_archiver` กับรายการ archive แสดงว่า archive ได้รับ segment (archive แล้ว 13 ล้ม 0):

การกู้คืนคือ data directory ใหม่ จึงเกิดห่างจากเซิร์ฟเวอร์ที่เสียหาย คัดลอก base backup เข้า directory ว่าง สร้างไฟล์ `recovery.signal` (ที่บอกเซิร์ฟเวอร์ให้เริ่มใน archive recovery) และให้การตั้งค่าสามอย่าง: `restore_command` (วิธีดึง segment ที่ archive ไว้; `%f` คือชื่อไฟล์ และ `%p` คือ path ที่จะคัดลอกไป) `recovery_target_time` และ `recovery_target_action = 'promote'` (เปิดให้เขียนเมื่อถึงเป้าหมาย) log แสดงสิ่งที่ PostgreSQL ทำ:

```text
# restore: copy the base backup into an empty data directory, ask for recovery, and say where to fetch WAL and when to stop

# appended to postgresql.auto.conf in the restored data directory:
restore_command = 'cp /archive/%f %p'
recovery_target_time = '2026-09-30 08:42:49.102022+00'
```

มันดึง segment 7 ถึง B จาก archive replay และหยุด *ก่อน commit ของ transaction 773* คือ `DELETE` ที่เวลา commit อยู่หลังเป้าหมายของเรา เซิร์ฟเวอร์ที่กู้คืนไม่อยู่ใน recovery แล้ว และ `orders` มี 250 003 row: 200 000 จาก backup บวม 3 กับ 50 000 ที่เขียนทีหลัง มีแต่ความผิดพลาดที่หายไป นั่นคือประเด็นของ PITR: backup อย่างเดียวจะได้ 200 000 row และเสียงานที่ทำทีหลัง

สามข้อควรระวัง `archive_command` ต้องรายงานความล้มเหลวตรงไปตรงมา (`test ! -f ... && cp ...` ปฏิเสธการเขียนทับไฟล์ที่มีอยู่); ถ้ามันล้มต่อเนื่อง WAL กองบน primary จนดิสก์เต็ม backup และ WAL ของมันต้องเก็บที่ที่ความล้มเหลวของ primary เอาไปด้วยไม่ได้ และทั้งหมดนี้ไม่ใช่ backup จนกว่าจะกู้คืนจากมันสำเร็จ ซึ่งคือสิ่งที่ transcript นี้ทำ

## Security เป็นชั้น

การควบคุมการเข้าถึงใน PostgreSQL มองเป็นชุดประตูที่ request ผ่านได้ดีที่สุด: เครือข่ายก่อน แล้ว authentication แล้ว privilege ของ role และสุดท้ายกฎระดับ row แต่ละชั้นหยุด request ที่ชั้นก่อนหน้าปล่อยผ่านมาได้

export const securityDiagram = `flowchart LR
  Client[Client] -->|encrypted with TLS| HBA["pg_hba.conf - who may connect"]
  HBA --> Auth[Authenticate the role]
  Auth --> Priv["Role privileges - GRANT and REVOKE"]
  Priv --> RLS[Row-level security policy]
  RLS --> Data[(Table rows)]`;

### ประตูเครือข่าย: pg_hba.conf และ TLS

ประตูแรกคือ `pg_hba.conf` (host-based authentication) แต่ละบรรทัดบอกว่า role ไหนเชื่อมต่อฐานข้อมูลไหนจากที่อยู่ไหนได้ และต้องพิสูจน์ตัวตนอย่างไร กฎอ่านจากบนลงล่างและ **อันแรกที่ตรงชนะ** ([docs](https://www.postgresql.org/docs/18/auth-pg-hba-conf.html)) รหัสผ่านถูกเก็บเป็น SCRAM verifier โดย default (`password_encryption = scram-sha-256`); ค่าที่เก็บขึ้นต้นด้วย `SCRAM-SHA-256$`:

```text
-- database: script
SHOW password_encryption;
CREATE ROLE app LOGIN PASSWORD '<your-password>';
SELECT rolname, left(rolpassword, 14) AS stored_as FROM pg_authid WHERE rolname = 'app';
-- database: psql output
 password_encryption 
---------------------
 scram-sha-256
(1 row)

CREATE ROLE
 rolname |   stored_as    
---------+----------------
 app     | SCRAM-SHA-256$
(1 row)

# 1. first match wins: the reject line for app comes before the general rule

# pg_hba.conf (reject before allow):
local   all   all                    trust
host    all   app   127.0.0.1/32      reject
host    all   all   127.0.0.1/32      scram-sha-256
```

### Role และ privilege: GRANT และ REVOKE

เมื่อเชื่อมต่อแล้ว สิ่งที่ role ทำได้ถูกควบคุมด้วย privilege คุณสร้าง role แล้ว `GRANT` สิทธิ์เฉพาะและ `REVOKE` หลักการนำทางคือ **least privilege**: ให้แต่ละ role แค่สิ่งที่ต้องการ fence ด้านล่างใช้สาม role ที่ไม่มี login (จึง switch เข้าได้ด้วย `SET ROLE`): เจ้าของ table, role รายงาน และแอป

```sql
-- sql/setup.sql
CREATE ROLE shop_owner NOLOGIN;      -- owns the tables
CREATE ROLE shop_reporting NOLOGIN;  -- read-only reports
CREATE ROLE shop_app NOLOGIN;        -- the application
GRANT CREATE ON SCHEMA public TO shop_owner;

SET ROLE shop_owner;
CREATE TABLE orders (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id bigint NOT NULL,
  item      text NOT NULL,
  amount    numeric NOT NULL
);
INSERT INTO orders (tenant_id, item, amount) VALUES (1, 'lamp', 30), (1, 'desk', 200), (2, 'chair', 80);
RESET ROLE;
```

ตั้งแต่ PostgreSQL 15 role ธรรมดาสร้างวัตถุใน schema `public` โดย default ไม่ได้อีก role ของแอปสร้าง table ไม่ได้แม้แต่ตารางเดียวจนกว่าจะมีคนให้สิทธิ์:

```sql
-- @expect-error 42501
SET ROLE shop_app;
CREATE TABLE sneaky (x int);
RESET ROLE;
```

```text

                     ^
RESET
```

ทีนี้ role รายงานแบบอ่านอย่างเดียวและ role ของแอปได้สิ่งที่ต้องการพอดี และ role รายงานเปลี่ยนอะไรไม่ได้:

```sql
-- sql/grants.sql
GRANT USAGE ON SCHEMA public TO shop_reporting, shop_app;
GRANT SELECT ON orders TO shop_reporting;
GRANT SELECT, INSERT, UPDATE ON orders TO shop_app;

SET ROLE shop_reporting;
SELECT count(*) AS reporting_sees FROM orders;
RESET ROLE;
```

### Row-level security

privilege ควบคุมทั้ง table **Row-level security** (RLS) ละเอียดกว่า ให้ policy ตัดสินว่า role เห็นหรือเปลี่ยน *row* ไหนได้ — รากฐานของระบบ multi-tenant ที่แต่ละ tenant ต้องเห็นเฉพาะข้อมูลของตัวเอง ([docs](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)) policy ด้านล่างเทียบ `tenant_id` ของแต่ละ row กับค่าที่แอปเลือกสำหรับ session ของมัน

```sql
-- sql/rls.sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;   -- run as the owner in real life; the superuser session here is equivalent
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id')::bigint);
```

เมื่อไม่มีค่าตั้ง query แรกไม่ได้คืนว่างเงียบ ๆ แต่ล้ม:

```sql
-- @expect-error 42704
SET ROLE shop_app;
SELECT count(*) FROM orders;
RESET ROLE;
```

```text
SET
ERROR:  unrecognized configuration parameter "app.tenant_id"
RESET
```

เมื่อ `app.tenant_id = 1` role ของแอปเห็นเฉพาะ row ของ tenant 1 และ insert row ของ tenant อื่นไม่ได้ (เงื่อนไขของ policy ใช้กับ row ใหม่ด้วย):

```sql
-- sql/rls-tenant.sql
SET app.tenant_id = 1;
SET ROLE shop_app;
SELECT id, item FROM orders ORDER BY id;
RESET ROLE;
```

```text

----+------

  2 | desk
(2 rows)

RESET
```

```sql
-- @expect-error 42501
SET app.tenant_id = 1;
SET ROLE shop_app;
INSERT INTO orders (tenant_id, item, amount) VALUES (2, 'sneaky', 1);
RESET ROLE;
```



## Mental Model

backup คือไทม์แมชชีน และ WAL archive คือฟิล์มที่ฉายระหว่าง snapshot dump คือภาพถ่ายของห้องหนึ่ง base backup บวม WAL คือการบันทึกทั้งอาคารที่คุณย้อนไปวินาทีใดก็ได้ security คือชุดประตู แต่ละบานแคบกว่าบานก่อน: เส้นเครือข่ายตัดสินว่าใครเคาะได้ role ตัดสินว่าเข้าห้องไหนได้ และ row-level security ตัดสินว่ามองชั้นวางไหนได้ ประตูถูกตรวจตามลำดับ และกฎแรกที่ตรงตัดสิน

## เคล็ดลับและข้อควรระวัง

- backup จะเป็นจริงก็ต่อเมื่อคุณกู้คืนสำเร็จแล้ว ตั้งเวลาซ้อมกู้คืนเข้าฐานข้อมูลทิ้งขว้างเป็นประจำและเทียบ count เหมือนที่แล็บทำ
- logical dump พกพาและเหมาะกับฐานข้อมูลเดี่ยว; physical base backup บวม WAL archiving คือสิ่งที่ต้องใช้กับ cluster ใหญ่และ point-in-time recovery `pg_dump` ไม่รวม role; `pg_dumpall --globals-only` รวม
- จดเวลาเป้าหมายกู้คืนที่แน่นอนก่อนการทำงานเสี่ยง หรือสร้าง restore point ที่มีชื่อด้วย `pg_create_restore_point()`
- ใช้ least privilege ทุกที่ role ของแอปไม่ควรเป็นเจ้าของ schema หรือ drop table ได้ และรายงานควรอ่านอย่างเดียว
- อย่าใช้ `trust` authentication บนที่อยู่ใดที่เข้าถึงได้จากนอกโฮสต์ — มันให้ใครก็ได้เชื่อมต่อเป็น role ใดก็ได้โดยไม่ต้องใช้รหัสผ่าน
- บังคับ TLS สำหรับการเชื่อมต่อที่ข้ามเครือข่ายด้วย `hostssl` และจำว่ากฎ `pg_hba.conf` จับคู่จากบนลงล่าง อันแรกที่ตรงชนะ
- เชื่อมต่อแอปด้วย role ที่ไม่เป็นเจ้าของ table และไม่มี `BYPASSRLS` ไม่งั้น RLS จะไม่ใช้กับมัน

<Callout title="ป้องกันเป็นชั้นลึก (Defence in depth)">
ไม่มีการควบคุมเดียวที่พอ ประตูเครือข่ายกันคนแปลกหน้า authentication พิสูจน์ตัวตน privilege ของ role จำกัดการกระทำ และ row-level security จำกัดสิ่งที่มองเห็น backup อยู่ใต้ทั้งหมดเป็นตาข่ายนิรภัยสุดท้าย ปฏิบัติเหมือนแต่ละชั้นจะล้มเป็นบางครั้ง และทำให้แน่ใจว่าชั้นถัดไปยังปกป้องคุณ
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| Logical backup (`pg_dump`) | พกพา เลือกได้ archive 1 MB สำหรับ table 200 000 row | ทีละฐานข้อมูล กู้คืนด้วยการ replay SQL ไม่มี point-in-time |
| Physical backup + WAL archive | ช่วงเวลาใดก็ได้ (การกู้คืนหยุดก่อน `DELETE`) ทั้ง cluster | major version เดียวกัน ชิ้นส่วนเคลื่อนไหวมากขึ้น archive ห้ามล้ม |
| Incremental backup | 30 MB แทน 88 MB | ต้องมี `summarize_wal` และสายที่ต้องรวมก่อนกู้คืน |
| RLS กับ policy เข้มงวด | การแยกที่ฐานข้อมูลบังคับ | เจ้าของและ role `BYPASSRLS` ข้ามมัน; ค่าตั้งที่หายทำให้ error เว้นแต่เขียน policy ให้ fail closed |
| พึ่ง replication อย่างเดียวเพื่อความคงทน | failover เร็ว high availability | replica ไม่ใช่ backup — มันคัดลอกความผิดพลาดและการลบด้วย |

## Common Misconceptions

- **"มี backup แล้ว ฉันปลอดภัย"** มีแต่การกู้คืนที่พิสูจน์ แล็บรันหนึ่งครั้งและเทียบ count
- **"pg_restore --create กู้คืนเข้าฐานข้อมูลที่ฉันระบุด้วย --dbname"** มันเชื่อมต่อที่นั่นและสร้างฐานข้อมูลชื่อที่อยู่ใน dump
- **"Replication คือ backup"** `DELETE` จะไปถึงทุก replica ภายในมิลลิวินาที
- **"RLS ปกป้องทุก connection"** ไม่ใช่เจ้าของ ไม่ใช่ superuser ไม่ใช่ role `BYPASSRLS`; เจ้าของเห็น 3 row เทียบ 2 ของ policy
- **"GRANT SELECT ON ALL TABLES ครอบคลุม table อนาคต"** table `refunds` ใหม่อ่านไม่ได้จน `ALTER DEFAULT PRIVILEGES`
