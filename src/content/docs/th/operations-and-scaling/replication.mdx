เซิร์ฟเวอร์เดียวคือจุดล้มเหลวจุดเดียว ถ้าดิสก์พังหรือเครื่อง reboot ฐานข้อมูลของคุณหายไปจนกว่าจะมีคนแก้ **Replication** ขจัดความเสี่ยงนี้ด้วยการเก็บสำเนาข้อมูลตั้งแต่หนึ่งชุดขึ้นไปบนเครื่องอื่น ที่อัปเดตต่อเนื่องเมื่อต้นฉบับเปลี่ยน สำเนาเหล่านั้นยังให้คุณกระจายทราฟฟิกอ่านไปหลายเซิร์ฟเวอร์ได้

PostgreSQL มีสองแบบ: **streaming replication** ที่คัดลอกทั้ง cluster แบบ byte ต่อ byte และ **logical replication** ที่คัดลอกบาง table แบบ row ต่อ row ทั้งสองแก้ปัญหาต่างกัน บทเรียนนี้จึงครอบคลุมทั้งคู่ ([docs](https://www.postgresql.org/docs/18/warm-standby.html))

ทุกอย่างด้านล่างรันจริงบน **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) แล็บคือสองคอนเทนเนอร์บนเครือข่าย Docker ที่สร้างด้วย `--internal` จึงคุยกันเองได้และไม่คุยกับใครอื่น คอนเทนเนอร์ volume และเครือข่ายทั้งหมดตั้งชื่อ `postgresql-b3-*` และถูกลบเมื่อบทเรียนเสร็จ รหัสผ่าน `<your-password>` แทนค่าใดก็ได้ที่คุณเลือก ส่วนที่อยู่และ process id ในผลลัพธ์มาจากการรันนั้น คำสั่งและผลลัพธ์ถูกวางตามที่ตอบกลับมา ไม่มีอะไรในหน้านี้เป็นแค่ภาพร่าง

<Callout title="ความปลอดภัยของแล็บ">
Docker Desktop แบ่งหน่วยความจำให้ทุกคอนเทนเนอร์ร่วมกัน รันแล็บนี้เมื่อไม่มีอะไรหนักอื่นรันอยู่ และลบมัน (บล็อกสุดท้ายของบทเรียน) เมื่อเสร็จ ไม่มีอะไรที่นี่เปิดพอร์ตไปยังเครื่องโฮสต์ของคุณ

## Write-ahead log คือแหล่งความจริง

ก่อนการเปลี่ยนแปลงแตะไฟล์ table PostgreSQL บันทึกมันลงใน **write-ahead log** (WAL): สตรีมแบบ append-only ของทุกการแก้ไข log นี้มีไว้กู้คืนหลัง crash แต่ก็เป็นสิ่งที่ replica ต้องการพอดี ถ้าเซิร์ฟเวอร์ที่สอง replay record WAL เดียวกันตามลำดับเดียวกัน มันจะได้สำเนาข้อมูลที่เหมือนกันทุกประการ

streaming replication ทำเช่นนั้นเป๊ะ primary ส่ง WAL ไปยังแต่ละ replica ผ่านการเชื่อมต่อเครือข่าย และแต่ละ replica apply record เหล่านั้นต่อเนื่องเพื่อให้ตามทัน

export const streamDiagram = `flowchart LR
  C[Client write] --> P[(Primary)]
  P -->|append| W[Write-ahead log]
  W -->|stream WAL| R1[(Replica 1 - read only)]
  W -->|stream WAL| R2[(Replica 2 - read only)]
  RC1[Read query] --> R1
  RC2[Read query] --> R2`;

replica เป็น read-only: มัน apply การเปลี่ยนแปลงของ primary และตอบ `SELECT` แต่ปฏิเสธการเขียน จึงเหมาะกับการยกงานรายงาน วิเคราะห์ หรือ workload หนักฝั่งอ่านออกจาก primary

## ตั้งค่า streaming replication

บน PostgreSQL 18 ค่าที่ streaming replication ต้องการเป็นค่า default อยู่แล้ว primary เริ่มด้วย `wal_level = replica` ที่ว่างให้ WAL sender 10 ตัวและ replication slot 10 อัน และ `hot_standby = on` ส่วน `wal_keep_size` เป็น 0 แปลว่า WAL เก่าไม่ถูกเก็บให้ replica เว้นแต่คุณใช้ slot สิ่งที่ไม่เปิดโดย default คือประตู: คุณต้องมี role ที่มี attribute `REPLICATION` และบรรทัด `pg_hba.conf` สำหรับชื่อฐานข้อมูลพิเศษ `replication` บรรทัด `host all all all` ไม่ครอบคลุม เพราะ `all` ไม่รวม `replication`

```text
# 1. one internal network (no route out), one named volume, one primary

$ docker network create --internal postgresql-b3-net

$ docker run -d --name postgresql-b3-primary --network postgresql-b3-net -e POSTGRES_PASSWORD=<your-password> -v postgresql-b3-primary-data:/var/lib/postgresql postgres:18.6

-- primary: script
SELECT name, setting FROM pg_settings
WHERE name IN ('wal_level', 'max_wal_senders', 'max_replication_slots', 'wal_keep_size', 'hot_standby')
ORDER BY name;
-- primary: psql output

-----------------------+---------
```

```bash
# scripts/replication-lab.sh
docker network create --internal postgresql-b3-net

docker run -d --name postgresql-b3-replica --network postgresql-b3-net \

```

replica ถูกสร้างโดยทำ base backup ของ primary แล้วชี้มันไปที่ primary เพื่อ stream WAL ต่อเนื่อง เครื่องมือที่คัดลอกสถานะเริ่มต้นคือ `pg_basebackup` ([docs](https://www.postgresql.org/docs/18/app-pgbasebackup.html)) สามแฟล็กที่สำคัญ: `-X stream` เปิดการเชื่อมต่อที่สองเพื่อ stream WAL ที่เกิดระหว่างการคัดลอก backup จึงสอดคล้องกัน `-R` เขียนรายละเอียดการเชื่อมต่อเพื่อให้เซิร์ฟเวอร์ใหม่เริ่มเป็น standby และ `application_name` ใน connection string ตั้งชื่อ standby นี้ ซึ่งสำคัญกับ synchronous replication image ของ Docker เก็บ PGDATA ใน `/var/lib/postgresql/18/docker` และ volume ถูก mount สูงกว่ามันหนึ่งระดับ

## Replication lag

asynchronous replication ไม่ทันที เพื่อให้ช่องว่างมองเห็นได้ ให้หยุดการ replay WAL บน replica (`pg_wal_replay_pause()`) เขียนบน primary และอ่านจากทั้งสอง replica ได้รับ WAL ใหม่แต่ยังไม่ apply:

```text
-- replica: script
SELECT pg_wal_replay_pause();
-- replica: psql output
 pg_wal_replay_pause 
---------------------
 
(1 row)

-- primary: script
INSERT INTO accounts (owner, balance) VALUES ('Grace', 300);
-- primary: psql output
INSERT 0 1

-- replica: script
SELECT count(*) AS rows_on_replica FROM accounts;
SELECT pg_last_wal_receive_lsn() AS received, pg_last_wal_replay_lsn() AS replayed;
-- replica: psql output
 rows_on_replica 
-----------------
               2
(1 row)

 received  | replayed  
-----------+-----------
 0/3000248 | 0/3000000
(1 row)

-- primary: script
SELECT application_name, state, pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_lag_bytes
FROM pg_stat_replication;
-- primary: psql output
 application_name |   state   | replay_lag_bytes 
------------------+-----------+------------------
 replica1         | streaming |              584
(1 row)

-- replica: script
SELECT pg_wal_replay_resume();
-- replica: psql output
 pg_wal_replay_resume 
----------------------
 
(1 row)

-- replica: script
SELECT count(*) AS rows_on_replica FROM accounts;
-- replica: psql output
 rows_on_replica 
-----------------
               3
(1 row)
```

replica ยังคืนสองแถวขณะที่ primary มีสาม และตำแหน่ง receive กับ replay ต่างกัน 584 byte หลัง `pg_wal_replay_resume()` มันตามทัน ในชีวิตจริงช่องว่างไม่ใช่ปุ่ม pause แต่คือดิสก์ช้า query ยาวบน replica หรือเครือข่ายสะดุด คอลัมน์ `write_lag`, `flush_lag` และ `replay_lag` ของ `pg_stat_replication` วัดมันเป็นเวลา

## Synchronous เทียบกับ asynchronous

ทางเลือกใหญ่ใน streaming replication คือ *เมื่อไร* ที่ primary ถือว่าการเขียนเสร็จ

| โหมด         | Primary ยืนยัน commit เมื่อ...                 | ข้อแลกเปลี่ยน                                  |
|--------------|---------------------------------------------------|--------------------------------------------|
| Asynchronous | WAL ถูกเขียนในเครื่อง                        | เร็ว แต่ replica อาจตามหลัง         |
| Synchronous  | อย่างน้อยหนึ่ง standby ที่ระบุชื่อเก็บ WAL ด้วย | ไม่เสียข้อมูลตอน failover แต่เขียนช้ากว่า |

Asynchronous เป็น default และเป็นตัวเลือกทั่วไป การเขียนไม่รอเครือข่าย primary จึงเร็ว — แต่ replica ตามหลังได้เล็กน้อย เรียก **replication lag** query ที่ส่งไป replica ที่ตามหลังอาจยังไม่เห็น commit ล่าสุด

Synchronous replication ทำให้ primary รอ standby ตอบรับแต่ละ commit คุณเปิดมันโดยระบุ standby ที่ต้องยืนยัน และชื่อต้องตรงกับ `application_name` ของ standby (เราตั้งเป็น `replica1` ตอน clone):

```conf
# postgresql.conf (or ALTER SYSTEM) on the primary
synchronous_standby_names = 'replica1'   # must equal the standby's application_name
```

ถ้าชื่อไม่ตรงกับ standby ที่เชื่อมต่อใด ทุก commit จะรอตลอดไป การตั้งค่านี้จึงควรทดสอบ ด้านล่าง standby ถูกหยุด และ client insert หนึ่งแถว statement ของมันเสร็จ แต่ commit ไม่: `pg_stat_activity` ของผู้ดูแลแสดง client อยู่ใน wait event `SyncRep` ทางออกมีแค่ เอา standby กลับมา ลบการตั้งค่า หรือยกเลิกการรอ:

## Replication ยับยั้ง vacuum

standby ที่รัน query ยาวอาจขัดแย้งกับการเก็บกวาดของ primary เมื่อ `hot_standby_feedback = on` (และลด `wal_receiver_status_interval` เป็น 1 วินาทีเพื่อให้เดโมเร็ว) standby รายงาน snapshot เก่าสุดของมันไปยัง primary ซึ่งจะปฏิเสธการลบ row ที่ snapshot นั้นอาจยังต้องใช้ รายงานหนึ่งรันบน replica สิบวินาทีขณะที่ primary update หนึ่ง row 1 000 ครั้งและ vacuum:

## Failover

ถ้า primary ตาย ต้อง **promote** replica หนึ่งให้เป็น primary ใหม่เพื่อให้การเขียนกลับมา การ promote บอก replica ให้หยุดตามและเริ่มรับการเขียน: `pg_promote()` ใน SQL หรือ `pg_ctl promote` จาก shell นี่คือบน replica ในแล็บ:

```text
-- primary: script
SELECT pg_walfile_name(pg_current_wal_lsn()) AS primary_wal_file;
-- primary: psql output

--------------------------

(1 row)

-- replica: script

-- replica: psql output

------------

(1 row)

-- replica: script

INSERT INTO accounts (owner, balance) VALUES ('after-promote', 1) RETURNING id, owner;
SELECT pg_walfile_name(pg_current_wal_lsn()) AS promoted_wal_file;
-- replica: psql output

-----------------

(1 row)

 id |     owner     
----+---------------

(1 row)

INSERT 0 1
    promoted_wal_file     
--------------------------

(1 row)

-- primary: script

-- primary: psql output

(1 row)
```

หลัง promote replica รับการเขียน และชื่อไฟล์ WAL เปลี่ยนจาก `000000010...` เป็น `000000020...`: แปดตัวแรกคือ **timeline** ที่ PostgreSQL เพิ่มทุกครั้งที่ promote เพื่อไม่ให้ประวัติปะปน primary เก่าที่ยังรันอยู่ไม่รู้เรื่อง: row ที่เขียนหลัง promote (`after-promote`) มีเฉพาะบนตัวใหม่ ถ้า client เขียนทั้งสองที่ คุณจะมีสอง primary ที่แยกทางกัน (**split brain**) เหตุผลที่การ deploy จริงต้องมีอะไรมา fence primary เก่า เครื่องมือ failover เช่น [Patroni](https://github.com/patroni/patroni) ที่อธิบายตัวเองว่าเป็น Python template สำหรับสร้าง cluster PostgreSQL high availability และประสานการเลือก leader ผ่าน ZooKeeper, etcd, Consul หรือ Kubernetes มีไว้ตัดสินใจนั้นอย่างปลอดภัย ตัว promote เองยังเป็นขั้นตอนเดียวเหมือนเดิม

## Logical replication: คัดลอกบาง table

streaming replication คัดลอก *ทั้ง cluster* และไหลทางเดียวไปยัง standby แบบ read-only บางครั้งคุณอยากได้น้อยกว่านั้น — แค่ไม่กี่ table — หรืออยากคัดลอกข้าม major version เช่นตอน upgrade นั่นคือ **logical replication** สร้างบนโมเดล publish-and-subscribe ([docs](https://www.postgresql.org/docs/18/logical-replication.html))

ที่ต้นทางคุณสร้าง **publication** ระบุ table ที่จะแชร์ ที่ปลายทางคุณสร้าง **subscription** ที่เชื่อมต่อและคัดลอกมัน

export const logicalDiagram = `flowchart LR
  S[(Source database)] -->|CREATE PUBLICATION| Pub[Publication: orders]
  Pub -->|row changes| Sub[Subscription]
  Sub --> D[(Destination database - writable)]`;

<Mermaid code={logicalDiagram} title="Logical replication publish บาง table ไปยัง subscriber" />

logical replication ต้องการ `wal_level = logical` ที่ต้นทาง ซึ่งเปลี่ยนสิ่งที่เข้า WAL และต้อง restart บนเซิร์ฟเวอร์ default publication ถูกสร้างอยู่ดี แต่พร้อมคำเตือน และการเขียนไปยัง table ที่ไม่มี **replica identity** ล้มเหลว:

```text
$ docker rm -f postgresql-b3-replica && docker volume rm postgresql-b3-replica-data
```


## Reading AI-generated code

ผู้ช่วย AI ถูกขอให้ตั้ง logical replication ของ table `orders` และเขียนสอง statement พร้อมคอมเมนต์ที่มั่นใจ:

<SpotTheBug lang="sql" code={`-- AI comment: "publish orders; a subscriber will pick up every change"
CREATE TABLE orders (id int, item text NOT NULL, qty int NOT NULL);
CREATE PUBLICATION shop_pub FOR TABLE orders;`}>

ทั้งสอง statement รันโดยไม่มี error บนเซิร์ฟเวอร์ default และคอมเมนต์ผิดสองครั้ง `wal_level` เป็น `replica` โดย default จึงไม่มีอะไรถูก decode ให้ subscriber: PostgreSQL พิมพ์ `WARNING: "wal_level" is insufficient to publish logical changes` ตอน `CREATE PUBLICATION` ซึ่งพลาดง่ายใน log ของ migration แย่กว่านั้น table ไม่มี primary key `UPDATE` แรกจึงล้มด้วย `cannot update table "orders" because it does not have a replica identity and publishes updates` ทั้งสองปรากฏในบล็อกแรกของ transcript logical replication ข้างบน: publication ถูกสร้างพร้อมคำเตือน `INSERT` ใช้ได้ และ `UPDATE` ล้ม วิธีแก้คือ `wal_level = logical` (restart) primary key (หรือ `REPLICA IDENTITY FULL` เมื่อไม่มี key) และนิยาม table เดียวกันบน subscriber ก่อน `CREATE SUBSCRIPTION` หลังเพิ่ม primary key `UPDATE` เดียวกันสำเร็จในแล็บ

</SpotTheBug>

## Mental Model

standby คือเซิร์ฟเวอร์ที่สองที่อ่านไดอารี่เล่มเดียวกับที่ primary กำลังเขียน physical replication คัดลอกทุกบรรทัดตรงตัวและ standby เขียนลงไปไม่ได้เลย logical replication อ่านไดอารี่เฉพาะบทที่เลือกและแสดงซ้ำในสมุดอีกเล่มที่เป็นอิสระ synchronous replication แปลว่า "อย่าบอก client ว่าสำเร็จจนกว่าผู้อ่านคนที่สองมีบรรทัดนั้น" ทุกคำถามด้านการออกแบบคือ: ผู้อ่านคนที่สองตามหลังได้นานเท่าไร และเกิดอะไรเมื่อเขาหายไป

## เคล็ดลับและข้อควรระวัง

- replica มีไว้อ่านและความพร้อมใช้งาน ส่งทุกการเขียนไป primary; replica จะปฏิเสธ (`read-only transaction`)
- กับ asynchronous replication คาดว่าจะมี lag ถ้าการอ่านต้องสะท้อนการเขียนที่เพิ่งเกิด ส่งไป primary รอให้ replica ตามทัน หรือใช้ `remote_apply` สำหรับ transaction นั้น
- synchronous replication แลก latency และความพร้อมใช้งานกับความปลอดภัย ตั้งชื่อ standby ให้ถูก ทดสอบว่าเกิดอะไรเมื่อมันล่ม และใช้เมื่อเสีย transaction ที่ยืนยันแล้วแม้แต่หนึ่งรายการก็รับไม่ได้ ไม่ใช่ default ทั่วไป
- streaming replication คัดลอกทั้ง cluster และต้องตรง version; logical replication คัดลอก table ที่เลือกและข้าม major version ได้ จึงเด่นสำหรับ upgrade
- logical replication ต้องมี replica identity — มักเป็น primary key — บนทุก table ที่ publish และต้องรักษา schema ให้ตรงกันด้วยมือ
- เฝ้าดู `pg_replication_slots` slot ที่ไม่มีใครใช้ทำให้ดิสก์เต็มในที่สุด เว้นแต่ตั้ง `max_slot_wal_keep_size`

<Callout title="หนึ่ง log สองการใช้งาน">
write-ahead log ถูกประดิษฐ์เพื่อให้ PostgreSQL กู้คืนหลัง crash ได้ด้วยการ replay การเปลี่ยนแปลงล่าสุด replication นำ log เดียวกันมาใช้ซ้ำ: replica ก็คือเซิร์ฟเวอร์อีกตัวที่ replay WAL ของ primary ตลอดไปและผ่านเครือข่าย เข้าใจ WAL คือเข้าใจ replication
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| Synchronous replication | ไม่เสียข้อมูลตอน failover เพราะ standby มี WAL ก่อน commit ตอบรับ | ทุกการเขียนรอ round trip เครือข่าย; ถ้า standby ติดต่อไม่ได้ การเขียนค้าง (รอ 3 วินาทีข้างบนจนยกเลิก) |
| Asynchronous replication | เขียนเร็ว เพราะ primary ไม่รอ replica | replica ตามหลังได้ (2 แถวเทียบ 3 ข้างบน) และมีโอกาสเล็กน้อยที่ข้อมูลหายตอน failover |
| Logical replication | table ที่เลือก subscriber ที่เขียนได้ ข้าม major version | DDL ไม่ถูก replicate ต้องมี replica identity slot ที่ไม่มีใครใช้เก็บ WAL (26 MB ข้างบน) |
| `hot_standby_feedback` | query บน replica ถูกยกเลิกน้อยลง | primary vacuum สิ่งที่ standby ยังต้องใช้ไม่ได้ (dead tuple 1 000 ข้างบน) |

## Common Misconceptions

- **"replica คือ backup"** มันคัดลอกความผิดพลาดด้วย: `DROP TABLE` บน primary ไปถึง replica ภายในมิลลิวินาที replica คือความพร้อมใช้งาน ไม่ใช่การกู้คืน
- **"synchronous replication แปลว่า replica แสดงการเขียนของฉันเสมอ"** มีแต่ `remote_apply`; `on` แปลว่า WAL ถูก flush ที่นั่น ไม่ใช่ replay แล้ว
- **"promote replica ปลอดภัยขณะ primary เก่ายังอยู่"** ทั้งสองรับการเขียนและ timeline แยกทางกัน
- **"logical replication replicate schema"** ไม่ใช่; row ของ column ใหม่ทำให้ apply worker ค้าง
- **"streaming replication ต้องตั้งค่ามาก"** บน PostgreSQL 18 ค่า default พอ; ชิ้นที่ขาดคือ role และบรรทัด `pg_hba.conf`
