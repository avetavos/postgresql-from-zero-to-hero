ปัญหา production จำนวนมากอย่างน่าประหลาดใจย้อนกลับไปที่ข้อเท็จจริงข้อเดียว: ใน PostgreSQL ทุก client connection มี process ระดับระบบปฏิบัติการของตัวเองบนเซิร์ฟเวอร์ไม่กี่ connection แทบไม่มีต้นทุน แต่ไม่กี่พัน connection กินหน่วยความจำและ overhead การจัดตารางเวลามหาศาล และเซิร์ฟเวอร์ช้าลงมากก่อนจะหมดงานที่มีประโยชน์ให้ทำ

**Connection pooling** แก้ปัญหานี้โดยวางตัวกลางเล็ก ๆ ระหว่างแอปกับฐานข้อมูล pooler เก็บ server connection จริงจำนวนพอประมาณเปิดไว้และแจกให้ client ตามต้องการ ฐานข้อมูลจึงจัดการกับ connection ไม่กี่อันเสมอไม่ว่ามี client กี่ตัว

ทุกอย่างด้านล่างรันจริงบน **PostgreSQL 18.6** และ **PgBouncer 1.26.0** (aarch64, Docker Desktop บน Mac, กันยายน 2026) แล็บคือสามคอนเทนเนอร์บนเครือข่าย Docker `--internal` — ฐานข้อมูลที่จำกัด 768 MB และ 4 CPU คอนเทนเนอร์ client สำหรับ `psql` และ `pgbench` และ PgBouncer — ตั้งชื่อ `postgresql-b3-*` ทั้งหมดและลบเมื่อจบ โปรเจกต์ PgBouncer ไม่เผยแพร่ image ทางการ แล็บจึง build เองจาก apt repository ของ PostgreSQL `<your-password>` แทนค่าใดก็ได้ที่คุณเลือก ตัวเลข throughput มาจาก Mac เครื่องนี้ และมีแค่สัดส่วนที่ติดตัวไป การทดลองกำหนดขนาด pool วัดซ้ำสามครั้งเพื่อแสดง noise

## ทำไม connection ถึงหนัก

เมื่อ client เชื่อมต่อ postmaster ของ PostgreSQL fork backend process เฉพาะเพื่อรับใช้มัน process นั้นถือหน่วยความจำสำหรับ cache, sort buffer และการจัดการภายใน และระบบปฏิบัติการต้องจัดตารางเวลามันร่วมกับ backend อื่นทุกตัว connection ที่ว่างอยู่ก็ยังครอบครอง process 60 client เชื่อมต่อตรงแล้วนั่งเฉย ๆ:

## Pooler ตรงกลาง

pooler เช่น **PgBouncer** อยู่ระหว่าง client กับเซิร์ฟเวอร์ client เชื่อมต่อกับ pooler ซึ่งคุยด้วยถูก และ pooler เก็บชุดเล็ก ๆ ของ connection จริงไปยัง PostgreSQL เมื่อ client ต้องการฐานข้อมูล pooler ให้ยืม server connection แล้วเอาคืนเพื่อให้ client อื่นใช้ซ้ำ

  Cli[Thousands of clients] -->|cheap client connections| Pool[PgBouncer pooler]
  Pool -->|few reused server connections| PG[(PostgreSQL)]`;

<Mermaid code={poolDiagram} title="หลาย client แชร์ server connection ไม่กี่อันผ่าน pooler" />

บล็อกสุดท้ายข้างบนคือ 200 client เดิม ตอนนี้ผ่าน PgBouncer ด้วย pool ขนาด 10 ระหว่างการรัน `SHOW POOLS` ใน admin console แสดง 16 client อยู่ใน transaction จริง 184 รอคิว 10 server connection ทำงาน และ `pg_stat_activity` บนฐานข้อมูลยืนยัน server connection พอดี 10 ทั้ง 200 client ได้รับบริการที่ราว 56 000 transaction ต่อวินาที latency เฉลี่ย 3.5 ms ไม่มี client ใดถือ server connection ขณะว่าง

## โหมด pooling

PgBouncer มีสามโหมดที่ต่างกันที่ *นานแค่ไหน* ที่ client ถือ server connection ที่ยืมไป ([docs](https://www.pgbouncer.org/config.html))

| โหมด        | Server connection ถูกคืนหลัง... | หมายเหตุ                                              |
|-------------|-----------------------------------------|----------------------------------------------------|
| Session     | client ตัดการเชื่อมต่อ                  | ปลอดภัยที่สุด แต่ถือ connection ตลอด session |
| Transaction | แต่ละ transaction commit หรือ rollback  | ตัวเลือกที่พบบ่อย; reuse ดีมากแต่มีข้อควรระวัง         |
| Statement   | แต่ละ statement                         | ก้าวร้าวที่สุด; ห้าม transaction หลาย statement |

**Transaction mode** เป็นตัวเลือกยอดนิยม server connection ถูกยืมเฉพาะช่วงหนึ่ง transaction ระหว่าง transaction จึงว่างให้คนอื่น ให้การใช้ซ้ำยอดเยี่ยมกับทราฟฟิกเว็บทั่วไปที่แต่ละ request เป็น transaction สั้น ๆ ข้อควรระวังคือทุกอย่างที่ผูกกับ *session* ไม่ใช่ transaction พังได้ เพราะ transaction ถัดไปอาจไปตกที่ server connection อื่น ตารางความสามารถของ PgBouncer ระบุว่าอะไรใช้ไม่ได้ใน transaction mode "by design": `SET`/`RESET`, `LISTEN`, cursor `WITH HOLD`, `PREPARE`/`DEALLOCATE`, `LOAD` และ advisory lock ระดับ session ([docs](https://www.pgbouncer.org/features.html))

## pgbouncer.ini ขั้นต่ำ

PgBouncer ตั้งค่าด้วยไฟล์ INI เล็ก ๆ สิ่งจำเป็นคือมันเป็นหน้าด่านให้ฐานข้อมูลใด ฟังที่ไหน และโหมด pooling นี่คือไฟล์ที่แล็บใช้; รายการ `shopN` คือฐานข้อมูลเดียวกันที่ขนาด pool ต่างกัน สำหรับการทดลองด้านล่าง `userlist.txt` เก็บ SCRAM verifier ของ role `app` และ `admin_users` ให้ `app` เปิด admin console (ฐานข้อมูลจำลอง `pgbouncer`)

```ini
[databases]
shop   = host=postgresql-b3-db port=5432 dbname=shop
shop1  = host=postgresql-b3-db port=5432 dbname=shop pool_size=1
shop1b = host=postgresql-b3-db port=5432 dbname=shop pool_size=1
shop2  = host=postgresql-b3-db port=5432 dbname=shop pool_size=2
shop4  = host=postgresql-b3-db port=5432 dbname=shop pool_size=4
shop30 = host=postgresql-b3-db port=5432 dbname=shop pool_size=30
shop60 = host=postgresql-b3-db port=5432 dbname=shop pool_size=60

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt
admin_users = app
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 10
max_prepared_statements = 0
ignore_startup_parameters = extra_float_digits
```

`max_client_conn` คือจำนวน client ที่เชื่อมต่อ PgBouncer ได้ ส่วน `default_pool_size` คือจำนวน connection จริงไป PostgreSQL ที่มันเก็บต่อฐานข้อมูลและผู้ใช้ (`pool_size=` ต่อฐานข้อมูลเขียนทับมัน) แล็บ build และเริ่มทุกอย่างแบบนี้:

```dockerfile
# Dockerfile: PgBouncer from the PostgreSQL apt repository that the postgres image already uses
FROM postgres:18.6
RUN apt-get update && apt-get install -y --no-install-recommends pgbouncer && rm -rf /var/lib/apt/lists/*
USER postgres
```

```bash
# scripts/pooling-lab.sh
docker network create --internal postgresql-b3-net
docker volume create postgresql-b3-db-data
docker run -d --name postgresql-b3-db --network postgresql-b3-net --memory 768m --cpus 4 \
  -e POSTGRES_PASSWORD=<your-password> -v postgresql-b3-db-data:/var/lib/postgresql postgres:18.6
docker run -d --name postgresql-b3-client --network postgresql-b3-net --memory 1g --cpus 2 \
  --entrypoint sleep postgres:18.6 infinity

docker build -t postgresql-b3-pgbouncer:local .
docker create --name postgresql-b3-pgbouncer --memory 128m -p 127.0.0.1:6432:6432 \
  --entrypoint pgbouncer postgresql-b3-pgbouncer:local /etc/pgbouncer/pgbouncer.ini
docker network connect postgresql-b3-net postgresql-b3-pgbouncer
docker cp pgbouncer.ini postgresql-b3-pgbouncer:/etc/pgbouncer/pgbouncer.ini
docker cp userlist.txt  postgresql-b3-pgbouncer:/etc/pgbouncer/userlist.txt
docker start postgresql-b3-pgbouncer
```

## อะไรพังใน transaction mode

เพราะ client ไม่ถือ server connection ระหว่าง transaction สถานะ session อาจรั่วระหว่าง client หรือหายไป สามกรณี รันบน alias `shop1` ที่ pool มี server connection เดียวพอดี ทุก client จึงแชร์มันแน่นอน (กับ pool ที่ใหญ่กว่า bug เดียวกันเกิดเป็นช่วง ๆ ซึ่งแย่กว่า)

```text
# each command is a separate client connection; the database alias shop1 has pool_size=1, so every client shares ONE server connection

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client psql -h postgresql-b3-pgbouncer -p 6432 -U app -d shop1 -c "SET app.tenant = 'alice'"
SET

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client psql -h postgresql-b3-pgbouncer -p 6432 -U app -d shop1 -c "SHOW app.tenant"    # a different client
 app.tenant 
------------
 alice
(1 row)

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client psql -h postgresql-b3-db -U app -d shop -c "SHOW app.tenant"    # a direct connection, for comparison
ERROR:  unrecognized configuration parameter "app.tenant"

# the transaction-local version: shop1b is a separate one-connection pool

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client psql -h postgresql-b3-pgbouncer -p 6432 -U app -d shop1b   (script below)
BEGIN
 set_config 
------------
 bob
(1 row)

 app.tenant 
------------
 bob
(1 row)

COMMIT

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client psql -h postgresql-b3-pgbouncer -p 6432 -U app -d shop1b -c "SELECT current_setting('app.tenant', true) AS tenant_seen_by_next_client"
 tenant_seen_by_next_client 
----------------------------
 
(1 row)

# session-level advisory locks

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client psql -h postgresql-b3-pgbouncer -p 6432 -U app -d shop1 -c "SELECT pg_advisory_lock(42)"
 pg_advisory_lock 
------------------
 
(1 row)

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client psql -h postgresql-b3-pgbouncer -p 6432 -U app -d shop1 -c "SELECT pg_try_advisory_lock(42) AS another_client_gets_it"
 another_client_gets_it 
------------------------
 t
(1 row)

$ docker exec -e PGPASSWORD=<your-password> postgresql-b3-client psql -h postgresql-b3-db -U app -d shop -c "SELECT pg_try_advisory_lock(42) AS direct_client_gets_it"
 direct_client_gets_it 
-----------------------
 f
(1 row)

-- database: script
SELECT locktype, objid, mode, granted FROM pg_locks WHERE locktype = 'advisory';
-- database: psql output
 locktype | objid |     mode      | granted 
----------+-------+---------------+---------
 advisory |    42 | ExclusiveLock | t
(1 row)
```

**`SET` รั่ว** client หนึ่งรัน `SET app.tenant = 'alice'` แล้วตัดการเชื่อมต่อ; client อื่นที่เพิ่งเชื่อมต่ออ่านได้ `alice` การเชื่อมต่อตรงไม่รู้เรื่องอะไร รูปแบบที่ปลอดภัยคือ `SET LOCAL` หรือ `set_config(name, value, true)` ใน transaction: ค่าอยู่จนกว่า transaction จบ และ client ถัดไปเห็นค่าว่าง

**Advisory lock เป็นของ server connection** client หนึ่งถือ `pg_advisory_lock(42)` แล้วจากไป client ที่สองขอ lock เดียวกันและได้ (`t`) เพราะมันคือ backend เดียวกัน ขณะที่การเชื่อมต่อตรงถูกปฏิเสธ (`f`) และ `pg_locks` แสดงหนึ่ง lock ที่ไม่มีเจ้าของชัดเจน ใช้ `pg_advisory_xact_lock` ใน transaction mode

**Prepared statement** prepared statement ระดับโปรโตคอลคือสิ่งที่ driver ส่วนใหญ่ใช้โดย default และ prepared statement อยู่บน server connection เดียว ก่อน PgBouncer 1.21 นั่นทำให้ใช้ใน transaction mode ไม่ได้; ตั้งแต่นั้น PgBouncer ติดตามมันและ prepare ใหม่บน server connection ที่ client ไปตก ถ้าคุณให้ที่ว่างด้วย `max_prepared_statements` ([docs](https://www.pgbouncer.org/features.html)) ค่า default ใน 1.26 คือ 200 ไฟล์ในแล็บตั้งเป็น 0 เพื่อแสดงความล้มเหลว `pgbench -M prepared` ใช้ extended query flow ระดับโปรโตคอล:

```text
# max_prepared_statements = 0: protocol-level prepared statements are not supported in transaction mode
```

## เชื่อมต่อผ่าน pooler

จากมุมมองของแอป pooler ดูเหมือน PostgreSQL คุณชี้ driver ไปที่ host และพอร์ตของ pooler — `6432` ข้างบนแทน `5432` — และไม่มีอะไรอื่นเปลี่ยน ยกเว้นกฎ transaction-mode ข้างบน โปรแกรมด้านล่างแต่ละอันเปิด client connection 10 อัน รัน 20 worker ที่รัน query แบบมี parameter เดียวกันสามครั้ง และถูกรันสองครั้งกับ pool แค่ 2 server connection เพื่อบังคับให้ client ต้องแชร์: ครั้งแรกด้วย `max_prepared_statements = 0` แล้วด้วย `100`

## Mental Model

pooler คือคิวแท็กซี่ client คือผู้โดยสาร server connection คือรถ และ transaction คือหนึ่งเที่ยว ใน transaction mode ผู้โดยสารถือรถเฉพาะตลอดเที่ยว รถยี่สิบคันจึงรับใช้ผู้โดยสารหลายพันคน — แต่ทุกอย่างที่คุณทิ้งไว้ในรถ (`SET`, session lock, prepared statement ที่ไม่มีการรองรับ) ไม่ใช่ของคุณอีกแล้วเมื่อจบเที่ยว

## เคล็ดลับและข้อควรระวัง

- transaction mode เป็นคำแนะนำปกติเพราะให้ connection reuse ดีที่สุดสำหรับ request เว็บสั้น ๆ ใช้ session mode เมื่อต้องการความต่อเนื่องของ session จริง ๆ เท่านั้น
- ใน transaction mode หลีกเลี่ยงฟีเจอร์ที่ข้าม transaction บน connection เดียว — `SET` ระดับ session, advisory lock ระดับ session และ `LISTEN`/`NOTIFY` prepared statement ใช้ได้ใน PgBouncer 1.21 ขึ้นไปเมื่อ `max_prepared_statements` ไม่ใช่ศูนย์
- pooler ไม่ทดแทน connection pool ของ driver เอง รันทั้งสองได้ แต่กำหนดขนาดให้ driver ไม่ขอมากกว่าที่ pooler ให้ได้
- ตั้ง `default_pool_size` ตามความสามารถของเซิร์ฟเวอร์ (จำนวน core ไม่ใช่ client) และจำไว้ว่า server connection ของ pooler เองก็นับรวมใน `max_connections` ด้วย
- ใช้ `SHOW POOLS` และ `SHOW STATS` บน admin console เพื่อดู client ที่รอ (`cl_waiting`) ก่อนผู้ใช้จะบอกคุณ
- อย่าใส่ credential ของฐานข้อมูลลงใน image; แล็บใช้รหัสผ่านใช้แล้วทิ้งบนเครือข่ายภายใน

<Callout title="ว่างคือศัตรู">
ข้อมูลเชิงลึกหลักของ pooling คือ connection ของแอปส่วนใหญ่ว่างเกือบตลอดเวลา แต่แต่ละ connection PostgreSQL ที่ว่างก็ยังเสียหนึ่ง process pooler ทำให้ช่วงว่างเหล่านั้นแชร์ได้ คุณไม่ได้เพิ่มความจุให้ฐานข้อมูล — คุณหยุด client ไม่ให้กักตุนมันขณะที่ไม่มีอะไรทำ
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| Transaction-mode pooling (PgBouncer) | client ต่อ PostgreSQL connection จริงได้มากกว่าเยอะ (200 client บน 10) | ฟีเจอร์ระดับ session (`SET`, session advisory lock, `LISTEN`) พัง; prepared statement ต้องมี `max_prepared_statements` และ PgBouncer ที่ใหม่พอ |
| Session-mode pooling / ไม่มี pooler | รองรับฟีเจอร์ระดับ session เต็มที่ การเชื่อมต่อตรงไปตรงมา | PostgreSQL connection แพงและจำกัด (ราว 3 MB ต่ออัน เพดานแข็งที่ `max_connections`) |
| pool ที่ใหญ่ขึ้น | client รอน้อยลง | เกินจำนวน CPU แล้ว server connection มากขึ้นไม่เพิ่ม throughput (30 เทียบ 60 ข้างบน) |

## Common Misconceptions

- **"pooler ทำให้ฐานข้อมูลเร็วขึ้น"** มันจำกัดจำนวน connection; throughput ที่ยอดบนเท่าเดิมโดยประมาณทั้งมีและไม่มีมัน
- **"เพิ่ม max_connections แก้ 'too many clients'"** มันสร้าง process มากขึ้นที่ราว 3 MB ต่ออันและการแย่งกันมากขึ้น pooler แก้ได้
- **"prepared statement ใช้กับ PgBouncer ไม่ได้"** จริงก่อน 1.21; เมื่อ `max_prepared_statements` มากกว่าศูนย์ มันใช้ได้
- **"transaction mode ปลอดภัยถ้าโค้ดเปิด transaction"** เฉพาะเมื่อไม่มีอะไรพึ่งสถานะ session; `SET` ธรรมดานอก `BEGIN` รั่วไปยัง client อื่น
- **"ขนาด pool ควรเท่าจำนวน client"** ควรตามความจุของเซิร์ฟเวอร์; 60 server connection ไม่ดีกว่า 30
