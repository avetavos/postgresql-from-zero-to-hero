join นำสอง table มาจับคู่ row ตามกฎที่คุณเขียนใน clause `ON` เพราะหนังสือเก็บ `id` ของผู้เขียน คุณจึงสั่งให้ PostgreSQL เดินตามลิงก์นั้นและสร้าง row ที่มี column จากทั้งสอง table พร้อมกันได้ ตัวเลือกจริงเพียงอย่างเดียวคือจะทำอย่างไรกับ row ที่ไม่มีคู่อีกฝั่ง และนั่นคือสิ่งที่แยกชนิดของ join ออกจากกัน

ทุกอย่างด้านล่างรันบน **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) fence `sql` รันจากบนลงล่างในฐานข้อมูลเปล่าหนึ่งตัว ผลลัพธ์คัดลอกจาก `psql` และตัวเลขเวลาใน plan มาจาก Mac เครื่องนี้

## ชุดข้อมูล

นี่คือชุดข้อมูลมาตรฐานของคอร์ส ทุกบทเรียนใน module นี้เริ่มจากสาม table เดียวกัน คุณจึงวางบล็อกนี้ในฐานข้อมูลเปล่าแล้วได้ผลลัพธ์ตรงกับที่แสดงเป๊ะ Sela Vance ไม่มีหนังสือ และ *Unlinked Draft* ไม่มีผู้เขียน: row ที่ไม่มีคู่สองแบบที่ทำให้ join น่าสนใจ

```sql
-- sql/setup.sql
CREATE TABLE authors (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  born int
);
CREATE TABLE books (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title       text NOT NULL,
  author_id   bigint REFERENCES authors (id),
  published   int,
  copies_sold int NOT NULL DEFAULT 0
);
CREATE TABLE sales (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  book_id bigint REFERENCES books (id),
  region  text NOT NULL,
  copies  int NOT NULL
);
INSERT INTO authors (name, born) VALUES ('Mara Linde', 1968), ('Owen Pryce', 1975), ('Sela Vance', 1990);
INSERT INTO books (title, author_id, published, copies_sold) VALUES
  ('Quiet Harbors', 1, 2003, 450), ('The Glass Orchard', 1, 2018, 1250), ('Tidal Notes', 2, 2011, 600), ('Unlinked Draft', NULL, 2020, 0);
INSERT INTO sales (book_id, region, copies) VALUES
  (2, 'East', 900), (3, 'West', 400), (1, 'West', 400), (3, 'East', 200), (2, 'West', 150), (1, 'East', 50);
```

## INNER JOIN: เฉพาะ row ที่ตรงกัน

`INNER JOIN` คืนหนึ่ง row ที่รวมกันสำหรับทุกคู่ที่เงื่อนไข `ON` เป็นจริง row ฝั่งใดที่หาคู่ไม่เจอจะถูกทิ้ง นี่คือ join ที่คุณใช้บ่อยที่สุด

## RIGHT และ FULL OUTER JOIN

`RIGHT JOIN` เป็นภาพสะท้อน: เก็บทุก row จาก table ฝั่งขวาและเติม `NULL` ฝั่งซ้ายเมื่อไม่มีคู่ `A RIGHT JOIN B` ให้ row เดียวกับ `B LEFT JOIN A` หลายคนจึงเขียนแต่ `LEFT JOIN` ส่วน `FULL OUTER JOIN` เก็บ row ที่ไม่มีคู่จากทั้งสองฝั่งพร้อมกัน

## ไม่มี ON: syntax error หรือ cross join

`JOIN` ที่ไม่มี `ON` หรือ `USING` ไม่ใช่ cross join แบบเงียบใน PostgreSQL แต่เป็น syntax error:

```sql
-- @expect-error 42601
SELECT * FROM authors JOIN books;
```

```text
ERROR:  syntax error at or near ";"
LINE 1: SELECT * FROM authors JOIN books;
                                        ^
```

แบบเงียบคือ comma join `FROM a, b` ที่ไม่มี `WHERE` จับคู่ทุก row ซ้ายกับทุก row ขวา (3 ผู้เขียน × 4 หนังสือ = 12) เท่ากับที่ `CROSS JOIN` ตรง ๆ คืน ส่วน join ที่ถูกต้องคืน 3:

```sql
-- sql/comma-cross.sql
SELECT count(*) AS comma_join FROM authors, books;
SELECT count(*) AS cross_join FROM authors CROSS JOIN books;
SELECT count(*) AS proper_join FROM authors a JOIN books b ON b.author_id = a.id;
```

```text
 comma_join 
------------
         12
(1 row)

 cross_join 
------------
         12
(1 row)

 proper_join 
-------------
           3
(1 row)
```

## ON เทียบกับ WHERE ใน outer join

สำหรับ inner join เงื่อนไขใน `ON` กับเงื่อนไขเดียวกันใน `WHERE` ให้ row เท่ากัน แต่ outer join ไม่ใช่ `ON` ตัดสินว่า row ไหน *ตรงกัน* ส่วน `WHERE` ทำงานทีหลังและลบ row ออกจากผลลัพธ์ รวมถึง row ที่ถูกเติม `NULL` ซึ่ง `LEFT JOIN` เพิ่งอุตส่าห์เก็บไว้

```sql
-- sql/on-vs-where.sql
-- filter in ON: every author survives, the filter only limits which books match
SELECT a.name, b.title
FROM authors a
LEFT JOIN books b ON b.author_id = a.id AND b.published > 2010
ORDER BY a.name, b.title;

-- same filter in WHERE: the NULL-extended rows are thrown away, it is an INNER JOIN now
SELECT a.name, b.title
FROM authors a
LEFT JOIN books b ON b.author_id = a.id
WHERE b.published > 2010
ORDER BY a.name, b.title;
```

```text
    name    |       title       
------------+-------------------
 Mara Linde | The Glass Orchard
 Owen Pryce | Tidal Notes
 Sela Vance | 
(3 rows)

    name    |       title       
------------+-------------------
 Mara Linde | The Glass Orchard
 Owen Pryce | Tidal Notes
(2 rows)
```

Sela Vance อยู่ในผลลัพธ์แรกและหายไปในผลลัพธ์ที่สอง เวอร์ชัน `WHERE` เปลี่ยน `LEFT JOIN` เป็น `INNER JOIN` เงียบ ๆ เพราะ `NULL > 2010` ไม่เป็นจริง นี่คือ bug ที่หัวข้อ *Reading AI-generated code* ด้านล่างพูดถึง

## USING และเหตุที่ NATURAL JOIN เป็นกับดัก

เมื่อ column ที่ join มีชื่อเดียวกันในทั้งสอง table `USING (col)` เป็นทางลัดของ `ON a.col = b.col` และแสดง column นั้นครั้งเดียวใน `SELECT *` ส่วน `NATURAL JOIN` ไปไกลกว่านั้นและ join บน **ทุก** column ที่ชื่อเหมือนกันในทั้งสอง table โดยไม่มีทางบอกว่าอันไหน ในชุดข้อมูลของเรา `authors.id` และ `books.id` ต่างชื่อ `id` `NATURAL JOIN` จึงเทียบ id ของผู้เขียนกับ id ของ *หนังสือ* และจับคู่ Owen Pryce กับ *The Glass Orchard* ผู้เขียนกับหนังสือที่ไม่เกี่ยวกัน:

```sql
-- sql/using-natural.sql
-- USING: the joined column appears once in SELECT *
SELECT *
FROM books
JOIN (SELECT id AS author_id, name FROM authors) AS a USING (author_id)
ORDER BY books.id;

-- NATURAL JOIN: matches on EVERY same-named column. authors and books both have "id"
SELECT a.name, b.title
FROM authors a NATURAL JOIN books b
ORDER BY a.name;
```

```text
 author_id | id |       title       | published | copies_sold |    name    
-----------+----+-------------------+-----------+-------------+------------
         1 |  1 | Quiet Harbors     |      2003 |         450 | Mara Linde
         1 |  2 | The Glass Orchard |      2018 |        1250 | Mara Linde
         2 |  3 | Tidal Notes       |      2011 |         600 | Owen Pryce
(3 rows)

    name    |       title       
------------+-------------------
 Mara Linde | Quiet Harbors
 Owen Pryce | The Glass Orchard
 Sela Vance | Tidal Notes
(3 rows)
```

ยิ่งนานยิ่งแย่ เพราะเงื่อนไข join ขึ้นกับชื่อ column ใน table ณ ตอนนี้ เพิ่ม column `author_id` ให้ `authors` (migration ธรรมดามาก) แล้ว `NATURAL JOIN` เดิมต้องการให้ `id` *และ* `author_id` ตรงกัน: ผลลัพธ์หดจาก 3 row เหลือ 1 โดยไม่มี error:

```sql
-- sql/natural-drift.sql
-- someone adds a column to both tables, and the NATURAL JOIN silently changes meaning
BEGIN;
ALTER TABLE authors ADD COLUMN author_id bigint;
UPDATE authors SET author_id = id;
SELECT * FROM books NATURAL JOIN authors ORDER BY books.id;
ROLLBACK;
```

```text
BEGIN
ALTER TABLE
UPDATE 3

----+-----------+---------------+-----------+-------------+------------+------
  1 |         1 | Quiet Harbors |      2003 |         450 | Mara Linde | 1968
(1 row)

ROLLBACK
```

เขียน `ON` ให้ชัด มันเสียแค่ไม่กี่ตัวอักษรและไม่เปลี่ยนความหมายลับหลังคุณ ([เอกสาร PostgreSQL เรื่อง joined tables](https://www.postgresql.org/docs/18/queries-table-expressions.html#QUERIES-JOIN))

## NULL ไม่เท่ากับ NULL ใน ON

เงื่อนไข join เป็น boolean expression ธรรมดา `NULL = NULL` ไม่เป็นจริง สอง row ที่ `author_id` เป็น `NULL` จึงไม่จับคู่กันเองใน self-join ส่วนการเทียบแบบ null-safe `IS NOT DISTINCT FROM` จับคู่ได้:

```sql
-- sql/null-in-on.sql
SELECT count(*) AS with_equals
FROM books x JOIN books y ON x.author_id = y.author_id;

SELECT count(*) AS with_not_distinct
FROM books x JOIN books y ON x.author_id IS NOT DISTINCT FROM y.author_id;
```

```text
 with_equals 
-------------
           5
(1 row)

 with_not_distinct 
-------------------
                 6
(1 row)
```

ตัวเลข 5 คือสี่คู่ (1,1) บวกหนึ่งคู่ (2,2) ส่วน row ที่เพิ่มใน query ที่สองคือ *Unlinked Draft* จับคู่กับตัวเอง

## LATERAL: subquery ที่มองเห็น row ทางซ้าย

ปกติแต่ละรายการใน `FROM` เป็นอิสระต่อกัน subquery ที่ระบุ `LATERAL` อ้างถึง column ของรายการก่อนหน้าได้ จึงรันหนึ่งครั้งต่อ row ซ้าย ([docs](https://www.postgresql.org/docs/18/queries-table-expressions.html#QUERIES-LATERAL)) ทำให้ "top N ต่อกลุ่ม" เป็น query สั้น ๆ ตรงนี้คือยอดขายสูงสุดของแต่ละเล่ม `LEFT JOIN LATERAL ... ON true` เก็บ *Unlinked Draft* ที่ไม่มียอดขายไว้:

```sql
-- sql/lateral.sql
-- the biggest sale for each book; LEFT JOIN LATERAL ... ON true keeps books with no sales
SELECT b.title, s.region, s.copies
FROM books b
LEFT JOIN LATERAL (
  SELECT region, copies
  FROM sales
  WHERE sales.book_id = b.id
  ORDER BY copies DESC
  LIMIT 1
) AS s ON true
ORDER BY b.id;
```

```text
       title       | region | copies 
-------------------+--------+--------
 Quiet Harbors     | West   |    400
 The Glass Orchard | East   |    900
 Tidal Notes       | West   |    400
 Unlinked Draft    |        |       
(4 rows)
```

`LIMIT 1` ใน subquery คือหัวใจ: join ธรรมดาบอกไม่ได้ว่า "เอาเฉพาะ row แรกของฝั่งขวา ต่อหนึ่ง row ซ้าย"

## Semi join และ anti join

"ผู้เขียนที่มีหนังสืออย่างน้อยหนึ่งเล่ม" และ "ผู้เขียนที่ไม่มีหนังสือ" ไม่ใช่ join จริง ๆ เพราะคุณไม่ต้องการ column จาก table อื่น มันคือตัวกรอง เขียนด้วย `EXISTS` และ `NOT EXISTS` (หรือ `IN` สำหรับอันแรก) planner แปลงเป็น *semi* และ *anti* join ภายใน และต่างจาก join ธรรมดา semi join ไม่คืน row ซ้ายซ้ำสองครั้ง (Mara Linde มีสองเล่มแต่ปรากฏครั้งเดียว):

```sql
-- sql/semi-anti.sql
SELECT name FROM authors a
WHERE EXISTS (SELECT 1 FROM books b WHERE b.author_id = a.id);

SELECT name FROM authors a
WHERE NOT EXISTS (SELECT 1 FROM books b WHERE b.author_id = a.id);
```

```text
    name    
------------
 Mara Linde
 Owen Pryce
(2 rows)

    name    
------------
 Sela Vance
(1 row)
```

## Mental Model

join คือ cross product ที่ผ่านตัวกรอง: ในเชิงแนวคิดทุก row ซ้ายถูกจับคู่กับทุก row ขวา และเงื่อนไข `ON` เก็บคู่ที่ผ่าน outer join เพิ่มหนึ่งขั้นตอน *หลัง* การทดสอบนั้น: row ซ้าย (หรือขวา หรือทั้งคู่) ที่จบโดยไม่มีคู่จะถูกเพิ่มกลับพร้อม `NULL` ส่วน `WHERE` ทำงานหลังทั้งหมดนั้น ส่วนที่เหลือในบทนี้ (`USING`, `LATERAL`, semi join) คือรูปแปรของการเลือกว่าคู่ไหนถูกเก็บ และอัลกอริทึม (nested loop, hash, merge) คือสามวิธีคำนวณผลลัพธ์เดียวกันโดยไม่ต้องสร้าง product เต็มรูป

## เคล็ดลับและข้อควรระวัง

- `JOIN` ที่ไม่มี `ON` หรือ `USING` เป็น syntax error (`42601`) cross join โดยไม่ตั้งใจมาจากการลิสต์ table ด้วย comma (`FROM a, b`) แล้วลืม `WHERE`: สิบกับสิบ row ให้หนึ่งร้อย row
- ตั้ง alias สั้น ๆ ให้แต่ละ table เช่น `a` และ `b` แล้วใส่ prefix ทุก column ทำให้ query อ่านง่ายและไม่กำกวมเมื่อสอง table มี column ชื่อเดียวกันอย่าง `id`
- `NULL` ในผลลัพธ์ outer join แปลว่า "ไม่พบ row ที่ตรงกัน" ไม่ใช่ "ค่าเป็นศูนย์หรือว่าง" ทดสอบด้วย `IS NULL` ห้าม `= NULL`
- ใส่ตัวกรองที่อธิบายฝั่ง *ทางเลือก* ใน `ON` และตัวกรองของฝั่งที่คุณเก็บไว้ใน `WHERE`
- ใช้ `EXISTS` / `NOT EXISTS` เมื่อต้องแค่ทดสอบว่ามีอยู่: ไม่มีค่าซ้ำ ไม่มี column ที่ต้องทิ้ง

<Callout title="เลือกฝั่งที่ต้องการเก็บ">
ตัดสินใจว่า table ไหนต้องปรากฏในผลลัพธ์เสมอ วางไว้ก่อน แล้ว `LEFT JOIN` อีก table เข้าไป "ผู้เขียนทุกคน พร้อมหนังสือถ้ามี" คือ `LEFT JOIN` จาก `authors` "เฉพาะผู้เขียนที่มีหนังสือ" คือ `INNER JOIN` (หรือ `EXISTS`) ประโยคภาษาอังกฤษมักบอกชนิด join ให้เอง
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| join table ที่ normalize ตอน query | ข้อมูลไม่ซ้ำและเป็นปัจจุบันเสมอ | query ซับซ้อนกว่า และ join ถูกคำนวณใหม่ทุกครั้ง |
| Denormalize / คัดลอกข้อมูลไว้ล่วงหน้า | อ่านเร็วกว่าเพราะไม่มี join ตอน query | เสี่ยงข้อมูลเก่าหรือไม่สอดคล้อง ต้องซิงก์สำเนาเอง |
| `NATURAL JOIN` / `USING` | เขียนสั้น | `NATURAL` เปลี่ยนความหมายเงียบ ๆ เมื่อเพิ่มหรือเปลี่ยนชื่อ column |
| `EXISTS` แทน join สำหรับทดสอบการมีอยู่ | ไม่ทำ row ซ้ายซ้ำ planner ใช้ semi join | คืน column จาก table อื่นไม่ได้ |
| บังคับอัลกอริทึม join ด้วย `enable_*` | ใช้วินิจฉัย plan ได้ | ไม่ใช่วิธีแก้: มัน override planner ทั้ง session |

## Common Misconceptions

- **"JOIN ที่ไม่มี ON คือ cross join แบบเงียบ"** เป็น syntax error ใน PostgreSQL cross join แบบเงียบคือ `FROM a, b` ที่ไม่มี `WHERE`
- **"ON กับ WHERE ใช้แทนกันได้"** ใช้ได้เฉพาะ inner join ใน `LEFT JOIN` การใส่ `WHERE` บน table ขวาเปลี่ยนมันเป็น inner join (2 row แทน 3 ข้างบน)
- **"NATURAL JOIN join ด้วย foreign key"** มัน join บนทุก column ชื่อเดียวกัน ที่นี่คือ `id` กับ `id` จับคู่ row ที่ไม่เกี่ยวกัน
- **"NULL = NULL จับคู่ใน join"** ไม่เคยจับคู่ ใช้ `IS NOT DISTINCT FROM` เมื่อหมายถึงอย่างนั้น
- **"hash join เร็วที่สุดเสมอ"** planner เลือกตาม cost: nested loop ใช้ 0.17 ms กับลูกค้าหนึ่งคน และการบังคับ merge join ใช้ 120 ms เทียบกับ hash join 68 ms สำหรับทั้งหมด
