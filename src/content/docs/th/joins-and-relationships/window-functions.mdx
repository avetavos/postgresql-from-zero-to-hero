`GROUP BY` ยุบหลาย row เป็น row สรุปหนึ่ง row และบางครั้งนั่นผิดพอดี: คุณอยากได้ทั้งสรุป *และ* รายละเอียดเดิมข้าง ๆ กัน window function ทำอย่างนั้น window function มองชุด row ที่เกี่ยวข้องกับ row ปัจจุบัน — *window* ของมัน — แล้วคำนวณค่า แต่ทุก row ยังอยู่ในผลลัพธ์ วิธีนี้เพิ่ม rank, ยอดสะสม หรือค่าเฉลี่ยต่อกลุ่มเป็น column เพิ่มได้โดยไม่เสียรายละเอียด

ทุกอย่างด้านล่างรันบน **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) คัดลอกจาก `psql` fence `sql` รันจากบนลงล่างในฐานข้อมูลเปล่าหนึ่งตัว ตัวเลขเวลามาจาก Mac เครื่องนี้

## clause OVER

เปลี่ยนฟังก์ชันธรรมดาให้เป็น window function ด้วยการเพิ่ม clause `OVER` ข้างใน `PARTITION BY` แบ่ง row เป็นกลุ่ม (เหมือน `GROUP BY` แต่ไม่ยุบ) และ `ORDER BY` กำหนดลำดับในแต่ละ partition เริ่มจาก aggregate ธรรมดาบน window: แต่ละยอดขายข้างยอดรวมของ region

    ```sql
           sum(s.copies) OVER (PARTITION BY s.region) AS region_total
    FROM sales AS s
    JOIN books AS b ON b.id = s.book_id
    ```

```sql
-- sql/share-of-region.sql
SELECT s.region, b.title, s.copies,

FROM sales AS s
JOIN books AS b ON b.id = s.book_id
ORDER BY s.region, s.copies DESC, b.title;
```

## ROW_NUMBER, RANK และ DENSE_RANK

ฟังก์ชันให้เลขทั้งสามต่างกันที่การจัดการกับ row เสมอ ตรงนี้อยู่เคียงกันบน window เดียวกัน clause `WINDOW w AS (...)` ตั้งชื่อให้ครั้งเดียวจึงไม่ต้องเขียนซ้ำ:

## ยอดสะสมและ default frame

window ที่มี `ORDER BY` มี **frame**: ส่วนย่อยของ partition ที่ฟังก์ชันมองเห็น ถ้าไม่เขียน frame ค่าเริ่มต้นคือ `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` ซึ่งรวมทุก *peer* ของ row ปัจจุบัน คือทุก row ที่เรียงเท่ากับมัน เมื่อค่าเรียงไม่ซ้ำ มันทำตัวเป็น "ทุกอย่างถึง row นี้" เมื่อมีเสมอ มันไม่เป็นอย่างนั้น:

```sql
-- sql/running-total-default.sql
-- default frame: RANGE ... CURRENT ROW, which includes all peers (rows with an equal ORDER BY value)
SELECT s.region, b.title, s.copies,
       sum(s.copies) OVER (PARTITION BY s.region ORDER BY s.copies DESC) AS running_default
FROM sales AS s
JOIN books AS b ON b.id = s.book_id
ORDER BY s.region, s.copies DESC, b.title;
```

```text
 region |       title       | copies | running_default 
--------+-------------------+--------+-----------------
 East   | The Glass Orchard |    900 |             900
 East   | Tidal Notes       |    200 |            1100
 East   | Quiet Harbors     |     50 |            1150
 West   | Quiet Harbors     |    400 |             800
 West   | Tidal Notes       |    400 |             800
 West   | The Glass Orchard |    150 |             950
(6 rows)
```

West แสดง **800, 800, 950** ไม่ใช่ 400, 800, 950: สอง row ที่ 400 เป็น peer กัน แต่ละตัวจึง "เห็น" อีกตัวอยู่แล้ว นั่นคือยอดสะสมที่ผิดแบบเงียบ ๆ เขียน frame ให้ชัดด้วย `ROWS` และเพิ่มตัวตัดสินเสมอเพื่อให้ลำดับถูกกำหนด:

`ROWS`, `RANGE` และ `GROUPS` วัด frame ต่างกัน บนหกยอดขายที่เรียงตาม `copies` frame ย้อนหลังหนึ่งขั้นให้สามผลรวมที่ต่างกันสำหรับ row เดียวกัน: `ROWS` นับ row จริง, `RANGE` นับตามระยะของค่า (ที่นี่: row ที่ `copies` ต่ำกว่า row ปัจจุบันไม่เกิน 100), `GROUPS` นับเป็นกลุ่มของ peer ([docs](https://www.postgresql.org/docs/18/sql-expressions.html#SYNTAX-WINDOW-FUNCTIONS)):

```sql
-- sql/frames.sql
-- the same 6 rows, ordered by copies, under the three frame modes
SELECT copies,
       sum(copies) OVER (ORDER BY copies ROWS   BETWEEN 1 PRECEDING AND CURRENT ROW) AS rows_frame,
       sum(copies) OVER (ORDER BY copies RANGE  BETWEEN 100 PRECEDING AND CURRENT ROW) AS range_frame,
       sum(copies) OVER (ORDER BY copies GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW) AS groups_frame
FROM sales
ORDER BY copies, id;
```

```text
 copies | rows_frame | range_frame | groups_frame 
--------+------------+-------------+--------------
     50 |         50 |          50 |           50
    150 |        200 |         200 |          200
    200 |        350 |         350 |          350
    400 |        600 |         800 |         1000
    400 |        800 |         800 |         1000
    900 |       1300 |         900 |         1700
(6 rows)
```

### first_value และ last_value

default frame เดียวกันจับ `last_value` ด้วย เมื่อมี `ORDER BY` และไม่มี frame frame หยุดที่ row ปัจจุบัน (และ peer ของมัน) "ค่าสุดท้าย" จึงเป็นค่าปัจจุบัน:

```sql
-- sql/last-value-trap.sql
SELECT region, copies,
       last_value(copies) OVER (PARTITION BY region ORDER BY copies DESC) AS last_default,
       last_value(copies) OVER (
         PARTITION BY region ORDER BY copies DESC
         ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS last_real,
       first_value(copies) OVER (PARTITION BY region ORDER BY copies DESC) AS first_val
FROM sales
ORDER BY region, copies DESC, id;
```

```text
 region | copies | last_default | last_real | first_val 
--------+--------+--------------+-----------+-----------
 East   |    900 |          900 |        50 |       900
 East   |    200 |          200 |        50 |       900
 East   |     50 |           50 |        50 |       900
 West   |    400 |          400 |       150 |       400
 West   |    400 |          400 |       150 |       400
 West   |    150 |          150 |       150 |       400
(6 rows)
```

`last_default` เท่ากับ `copies` ทุก row ส่วน `last_real` ที่ใช้ `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` คือยอดขายน้อยที่สุดของ region จริง ๆ (50 และ 150)

## LAG, LEAD, NTILE และพวกเดียวกัน

`lag` และ `lead` อ่าน column จาก row ก่อนหน้าและถัดไปของ window: ไม่ต้อง self-join row แรกและสุดท้ายไม่มีอะไรให้อ่าน จึงได้ `NULL`:

```sql
-- sql/lag-lead.sql
SELECT title, published,
       lag(title)  OVER (ORDER BY published) AS previous_title,
       lead(title) OVER (ORDER BY published) AS next_title,
       published - lag(published) OVER (ORDER BY published) AS years_since_previous
FROM books
ORDER BY published;
```

```text
       title       | published |  previous_title   |    next_title     | years_since_previous 
-------------------+-----------+-------------------+-------------------+----------------------
 Quiet Harbors     |      2003 |                   | Tidal Notes       |                     
 Tidal Notes       |      2011 | Quiet Harbors     | The Glass Orchard |                    8
 The Glass Orchard |      2018 | Tidal Notes       | Unlinked Draft    |                    7
 Unlinked Draft    |      2020 | The Glass Orchard |                   |                    2
(4 rows)
```

`ntile(n)` ตัด row ที่เรียงแล้วเป็น `n` ถัง และ `percent_rank()` ให้ตำแหน่งสัมพัทธ์ของ row (0 สำหรับตัวแรก 1 สำหรับตัวสุดท้าย):

```sql
-- sql/ntile-percent.sql
SELECT title, copies_sold,
       ntile(2)       OVER (ORDER BY copies_sold DESC) AS half,
       percent_rank() OVER (ORDER BY copies_sold)      AS pct_rank
FROM books
ORDER BY copies_sold DESC;
```

```text

-------------------+-------------+------+--------------------
 The Glass Orchard |        1250 |    1 |                  1
 Tidal Notes       |         600 |    1 | 0.6666666666666666
 Quiet Harbors     |         450 |    2 | 0.3333333333333333
 Unlinked Draft    |           0 |    2 |                  0
(4 rows)
```

## Window เก็บ row; GROUP BY ยุบ row

window function ถูกประเมินหลัง `WHERE`, `GROUP BY` และ `HAVING` ก่อน `ORDER BY` และ `LIMIT` เล็กน้อย ผลที่ตามมาคือกรองด้วย window function ใน `WHERE` ไม่ได้ เพราะ ณ จุดนั้นมันยังไม่มีอยู่:

```sql
-- @expect-error 42P20
SELECT region, copies FROM sales
WHERE rank() OVER (PARTITION BY region ORDER BY copies DESC) = 1;
```

```text
ERROR:  window functions are not allowed in WHERE
LINE 2: WHERE rank() OVER (PARTITION BY region ORDER BY copies DESC)...
              ^
```

เพื่อกรองด้วย rank ("อันดับหนึ่งต่อกลุ่ม" แบบคลาสสิก) ให้คำนวณใน subquery หรือ CTE แล้วกรองข้างนอก:

```sql
-- sql/top-n-per-group.sql
SELECT region, title, copies
FROM (
  SELECT s.region, b.title, s.copies,
         row_number() OVER (PARTITION BY s.region ORDER BY s.copies DESC, b.title) AS rn
  FROM sales s JOIN books b ON b.id = s.book_id
) AS ranked
WHERE rn = 1
ORDER BY region;
```

```text
 region |       title       | copies 
--------+-------------------+--------
 East   | The Glass Orchard |    900
 West   | Quiet Harbors     |    400
(2 rows)
```

## Mental Model

window function คำนวณค่าให้แต่ละ row โดยมองที่ *frame* ของ row รอบ ๆ แล้ววางค่ากลับข้าง row นั้น สามการตั้งค่ากำหนดสิ่งที่มันเห็น: `PARTITION BY` (row ไหนเกี่ยวข้องกัน), `ORDER BY` (ลำดับใด) และ frame (มองไกลแค่ไหนในลำดับนั้น) frame มีค่าเริ่มต้นโดยนัย และค่านั้นคือ `RANGE ... CURRENT ROW` ที่รวม peer เมื่อไรที่ได้ตัวเลขผิดจาก window function ผู้ต้องสงสัยอันดับแรกคือ frame

## เคล็ดลับและข้อควรระวัง

- `OVER` ของ window function คือสิ่งที่ทำให้มันเป็น window function: `sum(x)` เดี่ยว ๆ คือ aggregate, `sum(x) OVER (...)` คือ window
- ใช้ window function ใน `WHERE` (`42P20`), `GROUP BY` หรือ `HAVING` ไม่ได้ ห่อ query ใน subquery หรือ CTE แล้วกรองข้างนอก
- เมื่อมี `ORDER BY` และไม่มี frame ชัดเจน frame คือ `RANGE ... CURRENT ROW` (รวม peer) เขียน `ROWS BETWEEN ...` สำหรับยอดสะสมและ `last_value`
- `row_number()` บน row ที่เสมอกันเป็นแบบสุ่ม เพิ่มตัวตัดสินใน `ORDER BY` ของ window ถ้าต้องการเลขที่เสถียร
- `PARTITION BY ... ORDER BY` มีต้นทุนเป็น sort ตรวจ `EXPLAIN` บน table ใหญ่ ระวัง `external merge` และดูว่า index ให้ลำดับได้ไหม

<Callout title="Window หรือ GROUP BY?">
ต้องการหนึ่ง row ต่อกลุ่ม? `GROUP BY` ต้องการทุก row พร้อมสิ่งที่คำนวณทั้งกลุ่ม (rank, ยอดสะสม, สัดส่วนของกลุ่ม, row ก่อนหน้า)? window function ต้องการทั้งสอง? aggregate ก่อนใน subquery แล้ว window ทับผลลัพธ์
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| Window function | เก็บทุก row; ไม่ต้อง self-join สำหรับ rank, ยอดสะสม, lag | ต้อง sort ต่อ `PARTITION BY`/`ORDER BY` ที่ต่างกัน (sort ราว 460 ms จาก 560 ms ข้างบน); default frame ทำให้ประหลาดใจ |
| `GROUP BY` + join กลับ | ใช้ได้ทุกที่ ชัดเจน | สองรอบและ join เพื่อแปะยอดรวมกลับ |
| correlated subquery ต่อ row | อ่านง่ายสำหรับตัวเลขเดียว | รันซ้ำต่อ row (ดูบท subquery) |
| จัดอันดับฝั่งแอป | ยืดหยุ่น | ดึงทุก row ผ่านเครือข่าย |

## Common Misconceptions

- **"SUM() OVER (ORDER BY x) คือยอดสะสมทีละ row"** เมื่อ `x` ซ้ำ มันคือยอดสะสมบน peer: 800, 800, 950 ข้างบน
- **"last_value ให้ row สุดท้ายของ partition"** เฉพาะเมื่อ frame ไปถึงจุดสิ้นสุด โดยค่าเริ่มต้นมันคืน row ปัจจุบัน
- **"row_number() ตัดสินเสมอได้อย่างเสถียร"** ลำดับของ row ที่เสมอกันไม่ถูกกำหนด นอกจากเพิ่มตัวตัดสิน
- **"Window function ฟรี"** แต่ละ window ที่ต่างกันต้อง sort ตัวอย่าง 500 000 row spill ลงดิสก์ที่ `work_mem` ค่าเริ่มต้น
- **"กรองด้วย rank ใน WHERE ได้"** มันถูกประเมินหลัง `WHERE` ใช้ subquery หรือ CTE
