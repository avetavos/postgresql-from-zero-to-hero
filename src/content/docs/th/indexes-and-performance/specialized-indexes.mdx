B-tree รองรับ equality, range, การเรียงลำดับ และ (ด้วย operator class ที่ถูก) การ match แบบ prefix ซึ่งครอบคลุม query ส่วนใหญ่ แต่ข้อมูลและรูปแบบ query บางอย่างต้องการโครงสร้างอื่น PostgreSQL มาพร้อม index access method อื่นอีกหลายแบบ และ *ตัวแปร* ของ index ที่ใช้ได้กับทุก access method บทนี้เป็นทัวร์ของพวกมัน และสำหรับแต่ละแบบจะแสดงขนาดและ plan บน row จริง คุณจึงเห็นว่าเมื่อไรมันคุ้มค่า

ทุกอย่างด้านล่างรันบน **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) fence `sql` รันจากบนลงล่างในฐานข้อมูลเปล่าหนึ่งตัว ทุกขนาดและ plan คัดลอกจาก `psql` และเวลาเป็นการรันครั้งเดียวจาก Mac เครื่องนี้

## ชุดข้อมูล

table เดียวของหนังสือ 300 000 เล่ม มีเอกสาร JSON `metadata`, ISBN, `created_at` ที่เรียงตามเวลา และแฟลก `in_print` (หนังสือ 5 % หมดพิมพ์) ตั้ง `autovacuum_enabled = off` เฉพาะ table นี้เพื่อให้การสาธิต visibility map ตอนท้ายทำงานเหมือนเดิมทุกครั้ง extension `btree_gist` ต้องใช้กับ exclusion constraint ทีหลัง

```sql
-- sql/setup.sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE books (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  isbn       text        NOT NULL,
  title      text        NOT NULL,
  author_id  int         NOT NULL,
  created_at timestamptz NOT NULL,
  in_print   boolean     NOT NULL,
  metadata   jsonb       NOT NULL
) WITH (autovacuum_enabled = off);  -- keeps the visibility-map demo repeatable
INSERT INTO books (isbn, title, author_id, created_at, in_print, metadata)
SELECT md5(g::text),
       (ARRAY['Amber', 'Birch', 'Cedar', 'Dune', 'Ember', 'Fjord', 'Glen', 'Harbor'])[1 + h % 8] || ' Notes ' || g,
       1 + g % 500,
       timestamptz '2020-01-01 00:00:00+00' + g * interval '5 minutes',
       g % 20 <> 0,
       jsonb_build_object(
         'genre',  (ARRAY['fiction', 'poetry', 'history', 'science', 'travel', 'cooking', 'art', 'sport'])[1 + (h / 8) % 8],
         'rating', 1 + (h / 64) % 5,
         'pages',  100 + (h / 320) % 700,
         'tags',   jsonb_build_array('t' || (h / 224000) % 50, 't' || h % 97))
FROM (SELECT g, ('x' || substr(md5(g::text || 'h'), 1, 7))::bit(28)::int AS h
      FROM generate_series(1, 300000) AS g) AS s;
ANALYZE books;
SELECT count(*) AS books,
       pg_size_pretty(pg_table_size('books')) AS table_size,
       count(*) FILTER (WHERE metadata @> '{"genre": "poetry", "rating": 5}') AS poetry_5
FROM books;
```

## GIN: สำหรับค่าที่มีหลายรายการ

**Generalized Inverted Index** (GIN) สร้างมาสำหรับ column ที่แต่ละ row เก็บรายการที่ค้นได้ *หลายอย่าง*: สมาชิกของ array, key และ value ของเอกสาร `jsonb` หรือคำ ("lexeme") ของเอกสาร full-text GIN แมปแต่ละรายการไปยัง row ที่มีมัน "หา row ที่มี X ทั้งหมด" จึงเป็นการค้นหาแทนการ scan เมื่อไม่มี index query แบบ containment อ่านทุก row:

```sql
-- sql/gin-baseline.sql
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF)
SELECT count(*) FROM books
WHERE metadata @> '{"genre": "poetry", "rating": 5, "tags": ["t3"]}';
```

## GiST: สำหรับข้อมูลเรขาคณิต ช่วง และเพื่อนบ้านใกล้สุด

**Generalized Search Tree** (GiST) index ค่าที่ซ้อนทับกันหรือมี "ระยะทาง": รูปทรงเรขาคณิต, range และการค้นหาเพื่อนบ้านใกล้สุด สำหรับ table การจองห้อง (200 000 row แต่ละอันเป็น `tstzrange`) "การจองใดซ้อนทับวันนี้?" คือ query `&&` (overlap) B-tree ตอบไม่ได้ และเมื่อไม่มี index มันคือการ scan:

```sql
-- sql/gist-setup.sql
CREATE TABLE rooms (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room_id       int NOT NULL,
  booked_during tstzrange NOT NULL
);
INSERT INTO rooms (room_id, booked_during)
SELECT g % 1000,
       tstzrange(timestamptz '2024-01-01 00:00+00' + (g / 1000) * interval '1 day',
                 timestamptz '2024-01-01 00:00+00' + (g / 1000) * interval '1 day' + interval '20 hours')
FROM generate_series(0, 199999) AS g;
ANALYZE rooms;
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF)
SELECT count(*) FROM rooms WHERE booked_during && tstzrange('2024-03-01 00:00+00', '2024-03-02 00:00+00');
```

GiST ยังเป็นกลไกของ **exclusion constraint** ซึ่งขยาย `UNIQUE` จาก "ไม่ซ้ำกัน" เป็น "ไม่ซ้อนทับกัน" ด้วย `btree_gist` คุณรวม equality บนห้องกับ overlap บนช่วงเวลา และฐานข้อมูลเองปฏิเสธการจองซ้อน:

```sql
-- sql/exclusion-constraint.sql
CREATE TABLE room_bookings (
  room_id       int NOT NULL,
  booked_during tstzrange NOT NULL,
  EXCLUDE USING gist (room_id WITH =, booked_during WITH &&)
);
INSERT INTO room_bookings VALUES (5, tstzrange('2024-03-01 09:00+00', '2024-03-01 11:00+00'));
INSERT INTO room_bookings VALUES (6, tstzrange('2024-03-01 10:00+00', '2024-03-01 12:00+00'));
```

INSERT 0 1
```

-- @expect-error 23P01

```

## BRIN: สำหรับ table ใหญ่ที่เรียงตามธรรมชาติ

**Block Range Index** (BRIN) เก็บเพียงค่าต่ำสุดและสูงสุดของ column ต่อ block range ของ table (ค่าเริ่มต้น 128 page) ใช้ได้เฉพาะเมื่อค่าใน column สัมพันธ์กับลำดับทางกายภาพของ row ซึ่งเป็นกรณีของ table แบบ append-only ที่มี timestamp ตรงนี้ `created_at` เพิ่มตาม row id:

```sql
-- sql/brin-baseline.sql
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF)
SELECT count(*) FROM books WHERE created_at >= '2021-06-01 00:00+00' AND created_at < '2021-06-08 00:00+00';
```

```text

         Workers Launched: 2
         ->  Partial Aggregate (actual time=9.809..9.810 rows=1.00 loops=3)
               ->  Parallel Seq Scan on books (actual time=4.016..9.782 rows=672.00 loops=3)
                     Filter: ((created_at >= '2021-06-01 00:00:00+00'::timestamp with time zone) AND (created_at < '2021-06-08 00:00:00+00'::timestamp with time zone))

FROM pg_class
WHERE relname IN ('books', 'books_created_btree', 'books_created_brin')
ORDER BY pg_relation_size(oid) DESC;
DROP INDEX books_created_btree;  -- keep only BRIN to see its plan

**24 kB เทียบกับ 6 600 kB** ของ B-tree (และ 59 MB ของ table): index BRIN เล็กกว่าราว 275 เท่า plan ของ BRIN คือ `Bitmap Heap Scan` ที่ `Heap Blocks: lossy=256`: index บอกเพียง "ช่วงเหล่านี้อาจมี row ที่ตรง" และ PostgreSQL ตรวจ row ในช่วงเหล่านั้นซ้ำ (`Rows Removed by Index Recheck: 8016`) มันตอบข้อมูลหนึ่งสัปดาห์ใน 0.9 ms เทียบกับ 13.9 ms ของ sequential scan

BRIN พึ่งพา correlation ระหว่าง column กับลำดับทางกายภาพทั้งหมด ซึ่ง `pg_stats` รายงาน:

-- sql/brin-correlation.sql

FROM pg_stats
WHERE tablename = 'books' AND attname IN ('id', 'created_at', 'isbn')
ORDER BY attname;
```

## Hash: สำหรับ equality เท่านั้น

**Hash index** เก็บ hash ของ key รองรับเฉพาะ `=`; ใช้กับ range หรือ `ORDER BY` ไม่ได้ จุดขายคือขนาดสำหรับ key ยาว สำหรับ ISBN 32 ตัวอักษร:

```sql
-- sql/hash-index.sql
CREATE INDEX books_isbn_hash  ON books USING hash (isbn);
CREATE INDEX books_isbn_btree ON books (isbn);
SELECT relname, pg_size_pretty(pg_relation_size(oid)) AS size
FROM pg_class WHERE relname IN ('books_isbn_hash', 'books_isbn_btree') ORDER BY 2 DESC;
DROP INDEX books_isbn_btree;
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE isbn = md5('777');
-- a range / ORDER BY cannot use a hash index
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE isbn > md5('777') ORDER BY isbn LIMIT 5;
```

## Partial index: index เฉพาะ row ที่ query

**partial index** มี clause `WHERE` และมีเฉพาะ row ที่เข้าเงื่อนไข ถ้าคุณค้นหาแต่หนังสือที่หมดพิมพ์ (5 % ของ table) partial index มีขนาดเป็นเศษเสี้ยวของ index เต็ม และดูแลถูกกว่า:

```sql
-- sql/partial-index.sql
CREATE INDEX books_author_full ON books (author_id);
CREATE INDEX books_out_of_print_idx ON books (author_id) WHERE NOT in_print;
SELECT relname, pg_size_pretty(pg_relation_size(oid)) AS size
FROM pg_class WHERE relname IN ('books_author_full', 'books_out_of_print_idx') ORDER BY pg_relation_size(oid) DESC;
DROP INDEX books_author_full;  -- now only the partial index exists
-- the WHERE of the query implies the index predicate: usable
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE NOT in_print AND author_id = 21;
-- it does not: not usable
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE in_print AND author_id = 21;
```

## Expression index: index ค่าที่คำนวณ

**expression index** เก็บผลของฟังก์ชันหรือ expression แก้กรณีที่ query ครอบ column ด้วยฟังก์ชันจน index ธรรมดาไม่มีประโยชน์:

```sql
-- sql/expression-index.sql
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE lower(title) = 'harbor notes 1234';
CREATE INDEX books_lower_title_idx ON books (lower(title));
ANALYZE books;
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE lower(title) = 'harbor notes 1234';
-- a different expression is a different question
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT * FROM books WHERE title ILIKE 'harbor notes 1234';
```

## Covering index: ตอบ query จาก index อย่างเดียว

**Index Only Scan** ตอบ query จาก index โดยไม่แตะ table ถ้าทุก column ที่ต้องการอยู่ใน index `INCLUDE` เพิ่ม column ที่ไม่ใช่ key เข้าไปในใบของ index เพื่อจุดประสงค์นี้ พวกมันถูกเก็บแต่ไม่ใช้เรียงลำดับ

มีข้อแม้ที่ `Heap Fetches` แสดง entry ของ index ไม่บอกว่า row มองเห็นได้สำหรับ transaction ของคุณ visibility map บอก และมีแต่ `VACUUM` ที่สร้างมัน ก่อน `VACUUM` planner ไม่เลือก index-only scan เลย (ใช้ bitmap heap scan 1.35 ms); เมื่อบังคับ มันต้องไปที่ heap ทั้ง 600 row (`Heap Fetches: 600`); หลัง `VACUUM` การไปที่ heap หายไป:

```sql
-- sql/covering-index.sql
CREATE INDEX books_author_incl ON books (author_id) INCLUDE (title);
-- before VACUUM the visibility map is empty: the planner avoids index-only scans
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT author_id, title FROM books WHERE author_id = 7;
-- force one to count the heap visits it would need (teaching switch)
BEGIN;
SET LOCAL enable_bitmapscan = off;
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT author_id, title FROM books WHERE author_id = 7;
ROLLBACK;
VACUUM books;
EXPLAIN (ANALYZE, BUFFERS OFF, COSTS OFF) SELECT author_id, title FROM books WHERE author_id = 7;
```

## Mental Model

index แต่ละชนิดคือโครงสร้างข้อมูลที่ตอบคำถามตระกูลหนึ่งได้ถูก B-tree: "อะไรมาก่อน หลัง หรือเท่ากับสิ่งนี้?" GIN: "row ไหนมีรายการนี้?" GiST: "ค่าไหนซ้อนทับหรืออยู่ใกล้สิ่งนี้?" BRIN: "ส่วนไหนของ table อาจมีค่านี้?" เล็กเพราะเก็บเพียง min และ max ต่อส่วน และมีประโยชน์เฉพาะเมื่อ table เรียงทางกายภาพตาม column Hash: "key ตรงนี้เป๊ะมีอยู่ไหม?" ตัวแปร (partial, expression, covering) เปลี่ยน *row ไหน* หรือ *ค่าอะไร* ที่ถูก index ไม่ใช่คำถามที่โครงสร้างตอบได้ index ถูกใช้เฉพาะเมื่อ query ถามคำถามที่ index สร้างมาตอบ

## เคล็ดลับและข้อควรระวัง

- เลือก access method ให้ตรงกับรูปแบบ query: GIN สำหรับ "มีรายการนี้", GiST สำหรับ "ซ้อนทับหรืออยู่ใกล้", BRIN สำหรับ "ใหญ่และเรียงทางกายภาพ", Hash สำหรับ "equality อย่างเดียว" และ B-tree สำหรับทุกอย่างอื่น
- BRIN ลองบน column เวลาแบบ append-only ได้ปลอดภัย ตรวจ `pg_stats.correlation` ก่อน (ใกล้ 1.0 หรือ -1.0) หลัง update หรือ delete หนัก ๆ ที่เอาพื้นที่ว่างกลับมาใช้ correlation อาจเสื่อม
- สำหรับ `jsonb` เลือก `jsonb_path_ops` เมื่อใช้แค่ `@>` (เล็กกว่า เร็วกว่า); เก็บ class มาตรฐานไว้ถ้าต้องการ `?`
- partial index ถูกใช้เฉพาะเมื่อ `WHERE` ของ query บ่งชี้ predicate; expression index เฉพาะเมื่อ query ใช้ expression ซ้ำ
- index-only scan ต้องการ `VACUUM` เพื่อสร้าง visibility map; ตรวจ `Heap Fetches`
- ทุก index ที่เพิ่มทำให้การเขียนช้าลงและกินดิสก์ วัดก่อนเพิ่ม

<Callout title="เลือกโครงสร้างให้ตรงกับคำถาม">
ถามว่า query ทำอะไร ไม่ใช่ column คืออะไร column `jsonb` ที่ query ด้วย `->>` แบบ equality ต้องการ B-tree expression index; column เดียวกันที่ query ด้วย `@>` ต้องการ GIN timestamp บน table แบบ append-only ต้องการ BRIN ถ้าขนาดสำคัญที่สุด และ B-tree ถ้าต้องการค้นหาแบบตรงเป๊ะด้วย
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| GIN (`jsonb_ops`) | `@>`, `?` บน jsonb, array, full text; 25.8 ms เหลือ 5.2 ms ที่นี่ | index 5 MB เขียนช้าลง; ไร้ประโยชน์กับ expression `->>` |
| GIN (`jsonb_path_ops`) | เล็กกว่า (3.7 MB) และ `@>` เร็วกว่า | ไม่มี query key-existence (`?`) |
| GiST | overlap, เพื่อนบ้านใกล้สุด, exclusion constraint; 13.1 ms เหลือ 0.53 ms ที่นี่ | index 9.8 MB; ต้องใช้ชนิด range ที่ตรงกัน |
| BRIN | 24 kB แทน 6.6 MB | เฉพาะ column ที่เรียงทางกายภาพ; lossy ต้องตรวจ row ซ้ำ |
| Hash | ครึ่งหนึ่งของ B-tree บน key ยาว | equality อย่างเดียว ไม่มีการเรียง |
| Partial | 120 kB แทน 2 MB | รองรับเฉพาะ query ที่บ่งชี้ predicate |
| Expression | ทำให้ `lower(title) = ...` เร็วขึ้นราว 600 เท่า | query ต้องใช้ expression เดิมเป๊ะ |
| Covering (`INCLUDE`) | Index Only Scan, 0.085 ms | index ใหญ่ขึ้น; ต้อง `VACUUM` จึงทำงาน |

## Common Misconceptions

- **"GIN index บน column jsonb เร่งทุกตัวกรองบนมัน"** เฉพาะ operator ที่ใช้กับ column เอง; `metadata->>'genre' = ...` ละเลยมัน (15.6 ms)
- **"BRIN คือ B-tree ที่เล็กกว่า"** มันตอบคำถามต่างกัน: เมื่อเรียงสุ่มมันตัดอะไรไม่ได้ (23.5 ms ช้ากว่า scan)
- **"Hash index ไม่ปลอดภัย"** ไม่ใช่ตั้งแต่ PostgreSQL 10 แค่รองรับเฉพาะ equality
- **"index-only scan ไม่แตะ table เลย"** แตะจนกว่า `VACUUM` จะทำเครื่องหมาย page ว่า all-visible (`Heap Fetches: 600` แล้ว 0)
- **"index เดียวบน `lower(title)` รองรับ `ILIKE` ด้วย"** รองรับเฉพาะ expression เดียวกัน
