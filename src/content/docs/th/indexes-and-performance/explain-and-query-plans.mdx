เมื่อ query ช้า การเดาเป็นการเสียเวลา PostgreSQL บอกคุณได้เป๊ะว่ามันตั้งใจรัน query อย่างไร และรันจริงอย่างไร เครื่องมือคือ `EXPLAIN` และการอ่านผลของมันเป็นทักษะด้านประสิทธิภาพที่มีประโยชน์ที่สุดอย่างเดียวที่คุณเรียนได้

ทุกอย่างด้านล่างรันบน **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) ทุก plan คัดลอกมาจาก `psql` ไม่ได้พิมพ์เอง และตัวเลขเวลามาจาก Mac เครื่องนี้ (รันครั้งเดียว ความต่างเล็ก ๆ คือสัญญาณรบกวน)

## planner เลือก plan

คุณเขียนว่า *ต้องการอะไร*; **query planner** ตัดสินว่า *ทำอย่างไร* สำหรับ query หนึ่งมี plan ที่เป็นไปได้มากมาย (scan ทั้ง table, ใช้ index นี้, ใช้ index นั้น, รวมสองอัน) และ planner ประมาณ cost ของแต่ละอัน แล้วเลือกอันที่ถูกที่สุด

export const plannerFlow = `flowchart LR
  Q["Your SQL query"] --> P["Query planner"]
  P --> E1["Estimate: Seq Scan cost"]
  P --> E2["Estimate: Index Scan cost"]
  P --> E3["Estimate: Bitmap Scan cost"]
  E1 --> C["Pick the cheapest plan"]
  E2 --> C
  E3 --> C
  C --> X["Execute chosen plan"]`;

<Mermaid code={plannerFlow} title="planner เลือก plan อย่างไร" />

การประมาณ cost เหล่านั้นขึ้นกับสถิติของข้อมูลคุณ: table มีกี่ row, column มีกี่ค่าที่ไม่ซ้ำ, แต่ละค่าพบบ่อยแค่ไหน ถ้าสถิติเก่าหรือหยาบเกินไป planner เดาผิด ทั้งสองกรณีปรากฏด้านล่าง

## ชุดข้อมูล

plan มีความหมายเฉพาะบนปริมาณข้อมูลที่สมจริง บทนี้จึงสร้าง table `orders` 500 000 row: ลูกค้า 10 000 คน สามสถานะ (เอียงโดยตั้งใจ) หนึ่ง order ทุก 90 วินาทีตั้งแต่ 1 มกราคม 2024 และ `city` ที่กำหนด `country` เสมอ มี index บน `customer_id`, `created_at` และ `status`

```sql
-- sql/setup.sql
CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id int NOT NULL,
  status      text NOT NULL,
  created_at  timestamptz NOT NULL,
  amount      numeric(10, 2) NOT NULL,
  city        int NOT NULL,
  country     int NOT NULL
);
INSERT INTO orders (customer_id, status, created_at, amount, city, country)
SELECT 1 + (g::bigint * 7919) % 10000,
       CASE WHEN g % 200 = 0 THEN 'refunded' WHEN g % 12 = 0 THEN 'pending' ELSE 'paid' END,
       timestamptz '2024-01-01 00:00:00+00' + g * interval '90 seconds',
       (g % 500) + 0.99,
       g % 100,
       (g % 100) % 10
FROM generate_series(1, 500000) AS g;
CREATE INDEX orders_customer_id_idx ON orders (customer_id);
CREATE INDEX orders_created_at_idx  ON orders (created_at);
CREATE INDEX orders_status_idx      ON orders (status);
ANALYZE orders;
SELECT status, count(*) FROM orders GROUP BY status ORDER BY 2 DESC;
```

## EXPLAIN: plan ที่ประมาณการ

`EXPLAIN` ธรรมดาวาง plan แต่ไม่รัน query จึงทันทีและปลอดภัยกับทุกอย่าง:

```sql
-- sql/explain-estimate.sql
EXPLAIN SELECT * FROM orders WHERE customer_id = 42;
```

```text
                                      QUERY PLAN                                      
--------------------------------------------------------------------------------------
 Bitmap Heap Scan on orders  (cost=4.81..189.92 rows=50 width=39)
   Recheck Cond: (customer_id = 42)
   ->  Bitmap Index Scan on orders_customer_id_idx  (cost=0.00..4.80 rows=50 width=0)
         Index Cond: (customer_id = 42)
(4 rows)
```

อ่าน node แบบนี้: `cost=4.81..189.92` คือ cost ที่ประมาณสำหรับคืน row แรก แล้วคืนทุก row ในหน่วยที่กำหนดเอง (การอ่าน page แบบ sequential หนึ่งครั้งคือ 1.0 จาก `seq_page_cost`); `rows=50` คือจำนวน row ที่ planner คาดว่าจะออกมา; `width=39` คือขนาดเฉลี่ยของ row เป็น byte plan เป็นต้นไม้ อ่านจากด้านในออกมา: node ที่เยื้องลึกที่สุด (`Bitmap Index Scan`) ทำงานก่อนและป้อนให้ parent (`Bitmap Heap Scan`)

## EXPLAIN ANALYZE: เกิดอะไรขึ้นจริง

`EXPLAIN ANALYZE` รัน query จริงและเพิ่มตัวเลขที่วัดได้ข้างค่าประมาณ ตั้งแต่ PostgreSQL 18 มันแสดงการใช้ buffer เป็นค่าเริ่มต้น เวอร์ชันเก่าต้องเขียน `BUFFERS` เอง ([release notes](https://www.postgresql.org/docs/18/release-18.html)):

```text
                                                             QUERY PLAN                                                             
------------------------------------------------------------------------------------------------------------------------------------

   Heap Blocks: exact=50
   Buffers: shared hit=50 read=3
   ->  Bitmap Index Scan on orders_customer_id_idx  (cost=0.00..4.80 rows=50 width=0) (actual time=0.041..0.041 rows=50.00 loops=1)
         Index Cond: (customer_id = 42)
         Index Searches: 1
         Buffers: shared read=3
 Planning:
   Buffers: shared hit=135
 Planning Time: 0.284 ms
 Execution Time: 0.304 ms
(12 rows)
```

ทีละบรรทัด:

- `actual time=0.054..0.267`: มิลลิวินาทีจนถึง row แรกและจนถึง row สุดท้าย ต่อ loop `rows=50.00` คือ row *จริง* ต่อ loop แสดงทศนิยมตั้งแต่ PostgreSQL 18 (ค่าเฉลี่ยเมื่อ node วน loop) ค่าประมาณคือ `rows=50` plan นี้ประมาณได้ดี
- `loops=1`: node นี้รันกี่ครั้ง ใน nested loop ตัวเลขของ node ด้านในเป็น *ต่อ loop* จึงต้องคูณ
- `Recheck Cond` และ `Heap Blocks: exact=50`: bitmap บอกว่า page ไหนมี row ที่ตรง executor ใช้เงื่อนไขซ้ำบน 50 page นั้น
- `Buffers: shared hit=50 read=3`: block ขนาด 8 kB ที่พบใน `shared_buffers` (hit) เทียบกับที่ดึงจากระบบปฏิบัติการหรือดิสก์ (read) เป็นตัววัด I/O ที่ตรงไปตรงมา
- `Index Searches: 1`: PG 18 แสดงว่ามีการลงไปใน index กี่ครั้ง
- `Planning: Buffers` และ `Planning Time`: ต้นทุนของการสร้าง plan เอง แยกจาก `Execution Time`

การส่ง statement เดียวกันจากโค้ดแอปคืน plan เป็น row ธรรมดา หนึ่งบรรทัดข้อความต่อหนึ่ง row แต่ละ driver รันหนึ่งครั้งกับชุดข้อมูลและรายงานจำนวนบรรทัดของ plan, ต้นบรรทัดแรก และบรรทัดสุดท้าย:

### ตัวเลือกอื่น

`EXPLAIN (COSTS OFF)` ตัดตัวเลข cost เมื่อสนใจแค่รูปร่าง `VERBOSE` เพิ่มรายการ column ที่ออกและชื่อที่มี schema และ `SETTINGS` แสดง setting ของ planner ที่ต่างจากค่าเริ่มต้น ทำให้ plan ที่แปะไว้ทำซ้ำได้ ตรงนี้ `random_page_cost` ที่ลดลง (ค่าที่มักแนะนำสำหรับ SSD ดู[การตั้งค่า planner](https://www.postgresql.org/docs/18/runtime-config-query.html)) เปลี่ยน query เดิมจาก bitmap scan เป็น index scan ธรรมดา:

```sql
-- sql/explain-options.sql
BEGIN;
SET LOCAL random_page_cost = 1.1;
EXPLAIN (COSTS OFF, SETTINGS, VERBOSE) SELECT id, amount FROM orders WHERE customer_id = 42;
ROLLBACK;
```

```text
BEGIN
SET
                        QUERY PLAN                        
----------------------------------------------------------
 Index Scan using orders_customer_id_idx on public.orders
   Output: id, amount
   Index Cond: (orders.customer_id = 42)
 Settings: random_page_cost = '1.1'
(4 rows)

ROLLBACK
```

`EXPLAIN` ยังพิมพ์บล็อก `JIT:` ได้เมื่อ server คอมไพล์ expression เป็น machine code ซึ่งทำเฉพาะ query ที่ cost ที่ประมาณสูงกว่า `jit_above_cost` (ค่าเริ่มต้น 100000) image นี้มี JIT ใช้ได้ เมื่อบังคับ threshold เป็น 0 บน query ที่ถูก บล็อกจะปรากฏและเวลาคอมไพล์เป็นส่วนของยอดรวม:

## แยกชนิดของ scan

table เดียวกันให้ node scan ต่างกันเมื่อ query เปลี่ยน สี่ชนิดที่ต้องจำได้:

**Seq Scan** อ่านทั้ง table แล้วกรอง ชนะเมื่อ row ส่วนใหญ่เข้าเงื่อนไข **Index Scan** เดิน index และดึงแต่ละ row ที่ตรงจาก table **Bitmap Heap Scan** รวบรวมตำแหน่ง row ที่ตรงทั้งหมดจาก index ก่อน แล้วดึง page ตามลำดับทางกายภาพ: จุดกึ่งกลางสำหรับหลักร้อยถึงหลักพัน row **Index Only Scan** ตอบจาก index อย่างเดียว เมื่อ query ต้องการเฉพาะ column ที่ index

order หนึ่งชั่วโมงและหนึ่งวันใช้ Index Scan ทั้งคู่ และน่าแปลกที่ 175 680 row (หกเดือน 35 % ของ table) ก็ใช้ใน 15 ms:

```sql
-- sql/scan-types.sql
-- the same table, three time windows: 1 hour, 1 day, about half of the table
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF)
SELECT * FROM orders WHERE created_at >= '2024-06-01 00:00+00' AND created_at < '2024-06-01 01:00+00';
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF)
SELECT * FROM orders WHERE created_at >= '2024-06-01 00:00+00' AND created_at < '2024-06-02 00:00+00';
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF)
SELECT * FROM orders WHERE created_at >= '2024-06-01 00:00+00' AND created_at < '2024-12-01 00:00+00';
```

ทำไม scan หนึ่งในสามของ table ยังเลือก index? เพราะ `created_at` สัมพันธ์กับลำดับ row ทางกายภาพอย่างสมบูรณ์ (table ถูกเติมตามลำดับเวลา) index scan จึงอ่าน heap page ต่อกันไป planner รู้เรื่องนี้จากสถิติ:

```sql
-- sql/correlation.sql
SELECT attname, round(correlation::numeric, 3) AS correlation
FROM pg_stats
WHERE tablename = 'orders' AND attname IN ('created_at', 'customer_id', 'status')
ORDER BY attname;
```

```text

-------------+-------------

 customer_id |       0.000
 status      |       0.842
(3 rows)
```

`created_at` มี correlation 1.000; `customer_id` เป็น 0.000 คือสุ่ม สำหรับ column สุ่ม หนึ่งพัน row ที่ตรงกระจายอยู่ในหนึ่งพัน page และ planner เลือก Bitmap Heap Scan (2.4 ms ด้านล่าง) จนกระทั่ง `VACUUM` สร้าง visibility map และ query เดียวกันกลายเป็น **Index Only Scan** ที่ `Heap Fetches: 0` (0.044 ms):

```sql
-- sql/index-only-scan.sql
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF)
SELECT customer_id FROM orders WHERE customer_id BETWEEN 1 AND 20;
VACUUM orders;
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF)
SELECT customer_id FROM orders WHERE customer_id BETWEEN 1 AND 20;
```

## ทำไม planner บางครั้งละเลย index

ความประหลาดใจที่พบบ่อย: คุณสร้าง index แต่ `EXPLAIN` ยังแสดง `Seq Scan` มักเป็นกรณีที่ planner *ถูก* ไม่ใช่ผิด column `status` เดียวกันที่มี index ให้ทั้งสองคำตอบ:

```sql
-- sql/selectivity.sql
-- 0.5 % of the rows versus 91 % of the rows
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF) SELECT * FROM orders WHERE status = 'refunded';
```

## Mental Model

`EXPLAIN` คือ plan ของ planner; `EXPLAIN ANALYZE` เพิ่มสิ่งที่ executor เห็น ระยะห่างระหว่างสองตัวเลข `rows=` คือสุขภาพของสถิติ query ช้าเกือบทุกตัวเป็นหนึ่งในสามอย่าง: scan ที่อ่านมากกว่าที่คืนมาก, ค่าประมาณผิดที่เลือกกลยุทธ์ผิด หรือเงื่อนไขที่ซ่อน column จาก index plan บอกว่าเป็นอันไหน ถ้าคุณอ่านจากด้านในออกมาและเทียบค่าประมาณกับค่าจริง

## เคล็ดลับและข้อควรระวัง

- `EXPLAIN ANALYZE` รัน query จริง สำหรับ `SELECT` ไม่เป็นไร แต่สำหรับ `UPDATE` หรือ `DELETE` มันเปลี่ยนข้อมูลคุณ: ห่อใน transaction ที่ `ROLLBACK`
- plan มีความหมายเฉพาะบนข้อมูลที่สมจริง query ที่ seq-scan table ทดสอบ 100 row อาจ index-scan table เดียวกันเมื่อมีล้าน row ทดสอบกับปริมาณที่เป็นตัวแทน
- เทียบ `rows` ที่ประมาณกับ `rows` จริงเสมอ ความต่างมากชี้ไปที่สถิติเก่า (`ANALYZE`) หรือ column ที่สัมพันธ์กัน (`CREATE STATISTICS`)
- อ่าน plan จากด้านในออกมา และคูณตัวเลขต่อ loop ด้วย `loops`
- `SET enable_seqscan = off` (และพวกเดียวกัน) พิสูจน์สิ่งที่ planner หลีกเลี่ยง; อย่าเอาไปใช้จริง
- อย่าเทียบตัวเลข `cost=` ข้าม query ต่างกัน: มีความหมายเฉพาะการเลือกระหว่าง plan ของ query เดียวกัน

<Callout title="ให้ EXPLAIN แทนที่การเดา">
ก่อนเพิ่ม index หรือเขียน query ใหม่ ให้รัน `EXPLAIN (ANALYZE, BUFFERS)` (บน PostgreSQL 18 `EXPLAIN ANALYZE` รวม buffer อยู่แล้ว) และอ่านสิ่งที่ PostgreSQL ทำจริง plan บอกชนิด scan, เวลาหมดไปที่ไหน และค่าประมาณตรงกับความจริงหรือไม่ เปลี่ยนงานด้านประสิทธิภาพจากการเดาเป็นการวัด
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| `EXPLAIN` | ทันที ปลอดภัยกับทุก query เพราะไม่มีอะไรรัน | ได้แค่ค่าประมาณจากสถิติ ไม่มีตัวเลขจริง |
| `EXPLAIN ANALYZE` | เวลาจริง จำนวน row จริง การใช้ buffer (ค่าเริ่มต้นใน PG 18) | รัน query จริง: `UPDATE`/`DELETE` เปลี่ยนข้อมูลจริง |
| `EXPLAIN (ANALYZE, BUFFERS OFF)` | output น้อยลงเมื่อสนใจแค่เวลา | เสียข้อมูล cache-เทียบ-ดิสก์ |
| สวิตช์ `enable_*` | แสดง plan ทางเลือกที่ planner ปฏิเสธ | มีผลทั้ง session; ซ่อนปัญหาจริงถ้าทิ้งไว้ |
| `CREATE STATISTICS` | แก้ค่าประมาณสำหรับ column ที่สัมพันธ์กัน | งานเพิ่มตอน `ANALYZE`; ช่วยเฉพาะ query ที่กรอง column เหล่านั้นด้วยกัน |

## Common Misconceptions

- **"index ถูกใช้เสมอถ้ามีอยู่"** `paid` (91 % ของ row) ละเลย index อย่างถูกต้อง: การบังคับใช้ช้ากว่า (51.4 ms เทียบกับ 43.7 ms)
- **"seq scan แปลว่าขาด index"** บางครั้งมันคือ plan ที่ถูกที่สุด (table เล็ก เงื่อนไขไม่ selective)
- **"index scan เร็วเสมอ"** 175 680 row ด้วย index scan ใช้ 15 ms ถูกหรือไม่ขึ้นกับ correlation ระหว่างลำดับ index และลำดับ heap
- **"`WHERE col::date = ...` ใช้ index บน `col`"** ไม่ใช้ ช่วงบน column เปล่าใช้ (15.9 ms เทียบกับ 0.69 ms)
- **"EXPLAIN ANALYZE บน UPDATE คือการลองแห้ง"** มัน update จริง มีแต่ rollback ที่คืนข้อมูล
