index คือโครงสร้างข้อมูลแยกที่ให้ PostgreSQL หา row ได้โดยไม่ต้องอ่านทั้ง table PostgreSQL รองรับ index หลายชนิด แต่มีหนึ่งชนิดที่เป็นค่าเริ่มต้นและเป็นคำตอบที่ถูกสำหรับกรณีส่วนใหญ่: **B-tree** บทนี้สร้างหนึ่งตัว ให้ดู plan เปลี่ยน และพูดตรง ๆ เรื่องต้นทุน

ทุกอย่างด้านล่างรันบน **PostgreSQL 18.6** (`postgres:18.6`, aarch64, Docker Desktop บน Mac, กันยายน 2026) fence `sql` รันจากบนลงล่างในฐานข้อมูลเปล่าหนึ่งตัว plan คัดลอกจาก `psql` และเวลาทุกตัวมาจาก Mac เครื่องนี้ (รันครั้งเดียว ความต่างเล็ก ๆ ถือเป็นสัญญาณรบกวน)

## ชุดข้อมูล

บทนี้ต้องการ table ใหญ่พอให้ index มีความหมาย จึงสร้างข้อมูลเอง: หนังสือ 200 000 เล่ม แต่ละเล่มมี `isbn` ไม่ซ้ำ, `title`, ผู้เขียนหนึ่งใน 20 คน, ปีที่ตีพิมพ์ระหว่าง 1950 ถึง 2024 และยอดขาย

```sql
-- sql/setup.sql
CREATE TABLE books (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  isbn        text NOT NULL,
  title       text NOT NULL,
  author_id   int  NOT NULL,
  published   int  NOT NULL,
  copies_sold int  NOT NULL DEFAULT 0
);
INSERT INTO books (isbn, title, author_id, published, copies_sold)
SELECT md5(g::text),
       'The ' || substr(md5((g * 3)::text), 1, 12),
       1 + g % 20,
       1950 + ('x' || substr(md5((g * 5)::text), 1, 6))::bit(24)::int % 75,
       (g * 7919) % 5000
FROM generate_series(1, 200000) AS g;
ANALYZE books;
SELECT count(*) AS books, count(DISTINCT author_id) AS authors, pg_size_pretty(pg_table_size('books')) AS table_size
FROM books;
```

## การสร้าง index

รูปแบบพื้นฐานระบุ table และ column ที่จะ index ก่อนอื่น query เมื่อยังไม่มี index `md5('12345')` เป็นค่าคงที่ PostgreSQL จึงคำนวณให้ก่อนวาง plan:

```sql
-- sql/before-index.sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM books WHERE isbn = md5('12345');
```


`Seq Scan`: อ่านทั้ง 2 470 page (`Buffers: shared hit=2470`) และทิ้ง 199 999 row (`Rows Removed by Filter`) 9.1 ms เพื่อได้ row เดียว ทีนี้สร้าง unique index บน `isbn` PostgreSQL ตั้งชื่อให้ถ้าคุณไม่ใส่ (`CREATE INDEX ON books (title)`) แต่การตั้งชื่อเองช่วยให้หาใน plan และ drop ทีหลังง่ายขึ้น

## B-tree ทำอะไรได้

B-tree เก็บ key เรียงลำดับในต้นไม้สมดุล จึงรองรับทุกอย่างที่ตามลำดับนั้น: equality, range (`<`, `<=`, `>`, `>=`, `BETWEEN`), `IN`, `IS NULL` และที่สำคัญคือ `ORDER BY` กับ `LIMIT` เพราะ row ออกมาเรียงแล้ว เพิ่ม index บน `title` และขอห้า title แรก:

```sql
-- sql/title-index.sql
CREATE INDEX books_title_idx ON books (title);
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM books ORDER BY title LIMIT 5;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM books WHERE title BETWEEN 'The 3f9' AND 'The 3fa';
```

```text
CREATE INDEX
                                                                QUERY PLAN                                                                
------------------------------------------------------------------------------------------------------------------------------------------
 Limit  (cost=0.42..0.84 rows=5 width=70) (actual time=0.034..0.044 rows=5.00 loops=1)
   Buffers: shared hit=5 read=3
   ->  Index Scan using books_title_idx on books  (cost=0.42..16860.37 rows=200000 width=70) (actual time=0.033..0.040 rows=5.00 loops=1)
         Index Searches: 1
         Buffers: shared hit=5 read=3
 Planning:
   Buffers: shared hit=119 read=1
 Planning Time: 0.330 ms
 Execution Time: 0.063 ms
(9 rows)

                                                         QUERY PLAN                                                         
----------------------------------------------------------------------------------------------------------------------------
 Index Scan using books_title_idx on books  (cost=0.42..8.44 rows=1 width=70) (actual time=0.036..0.109 rows=50.00 loops=1)
   Index Cond: ((title >= 'The 3f9'::text) AND (title <= 'The 3fa'::text))
   Index Searches: 1
   Buffers: shared hit=51 read=2
 Planning:
   Buffers: shared hit=6
 Planning Time: 0.057 ms
 Execution Time: 0.115 ms
(8 rows)
```

plan ของ `ORDER BY title LIMIT 5` ไม่มี node `Sort`: มันอ่านห้า entry แรกของ index แล้วหยุด (0.06 ms ถ้าไม่มี index PostgreSQL ต้องอ่านและ sort ทั้ง 200 000 row) query แบบ range (`BETWEEN 'The 3f9' AND 'The 3fa'`) ก็เป็น `Index Scan` เช่นกัน: ลงไปที่ match แรก เดิน entry ที่เรียงแล้ว และคืน 50 row ใน 0.1 ms

| การดำเนินการ | B-tree รองรับหรือไม่? |
|---|---|
| `=`, `IN`, `IS NULL` | ใช่ |
| `<`, `<=`, `>`, `>=`, `BETWEEN` | ใช่ |
| `ORDER BY` / `LIMIT` บน column ที่ index | ใช่ ไม่ต้อง sort แยก |
| `LIKE 'The 3f%'` (prefix) | เฉพาะเมื่อมี operator class ที่ถูกหรือ collation `C` ดูหัวข้อ *Reading AI-generated code* ด้านล่าง |
| `LIKE '%3f'` (suffix / contains), `ILIKE` | ไม่: ใช้ trigram (`pg_trgm`) GIN index ดูบทถัดไป |
| `lower(title) = ...` | ไม่ได้กับ index บน `title` ธรรมดา ต้องใช้ expression index |

กรณี prefix ขึ้นกับ collation ของฐานข้อมูล ของเราคือ:

```sql
-- sql/collation.sql
SELECT datcollate FROM pg_database WHERE datname = current_database();
```

```text

------------
 en_US.utf8
(1 row)
```

## Composite index และกฎ left-prefix

index ครอบหลาย column ได้ โดยเรียงลำดับ `(author_id, published)` เรียงตาม `author_id` ก่อน และตาม `published` ภายในผู้เขียนแต่ละคน เหมาะกับ query ที่ใช้ทั้งสอง ก่อนอื่น baseline ของ query บน `published` อย่างเดียว (2 762 จาก 200 000 row) แล้วค่อย index:

```sql
-- sql/composite-baseline.sql
SELECT count(DISTINCT author_id) AS distinct_authors, count(DISTINCT published) AS distinct_years FROM books;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM books WHERE published = 2000;
```

```text

------------------+----------------
               20 |             75
(1 row)

------------------------------------------------------------------------------------------------------------
 Seq Scan on books  (cost=0.00..4970.00 rows=2647 width=70) (actual time=0.018..8.079 rows=2762.00 loops=1)
   Filter: (published = 2000)
   Rows Removed by Filter: 197238
   Buffers: shared hit=2470
 Planning:
   Buffers: shared hit=43
 Planning Time: 0.282 ms
 Execution Time: 8.181 ms
(8 rows)
```

```sql
-- sql/composite-index.sql
CREATE INDEX books_author_published_idx ON books (author_id, published);
-- both columns: the ideal case
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM books WHERE author_id = 6 AND published = 2000;
-- only the second column: PostgreSQL 18 skip scan
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM books WHERE published = 2000;
```

plan แรกคือกรณีตำรา: ทั้งสอง column เป็น equality บน index จึงลงหนึ่งครั้ง (`Index Searches: 1`) และดึง 143 row ใน 0.3 ms

query ที่สองกรองเฉพาะ column **ที่สอง** กฎที่เคยพูดกันว่า query แบบนี้ใช้ index ไม่ได้ เปลี่ยนใน PostgreSQL 18 ตอนนี้มันใช้ **skip scan** ได้: เพราะ `author_id` มีค่าไม่ซ้ำเพียง 20 ค่า executor ค้น index หนึ่งครั้งต่อผู้เขียนสำหรับ `published = 2000` (`Index Searches: 22` สำหรับผู้เขียนที่ไม่ซ้ำ 20 คน) แล้วรวมผล 2.5 ms เทียบกับ `Seq Scan` 8 ms ข้างบน ([docs](https://www.postgresql.org/docs/18/indexes-multicolumn.html), [release notes](https://www.postgresql.org/docs/18/release-18.html))

skip scan คุ้มเฉพาะเมื่อ column นำหน้ามี **ค่าไม่ซ้ำน้อย** ให้ column นำหน้าเป็น `isbn` ที่มีค่าไม่ซ้ำ 200 000 แล้ว planner กลับไปใช้ sequential scan:

```sql
-- sql/composite-high-cardinality.sql
-- same idea, but the leading column now has 200 000 distinct values
DROP INDEX books_author_published_idx;
CREATE INDEX books_isbn_published_idx ON books (isbn, published);
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM books WHERE published = 2000;
DROP INDEX books_isbn_published_idx;
```

```text
DROP INDEX
CREATE INDEX
                                                 QUERY PLAN                                                 
------------------------------------------------------------------------------------------------------------
 Seq Scan on books  (cost=0.00..4970.00 rows=2647 width=70) (actual time=0.013..8.087 rows=2762.00 loops=1)
   Filter: (published = 2000)
   Rows Removed by Filter: 197238
   Buffers: shared hit=2470
 Planning:
   Buffers: shared hit=118 read=1
 Planning Time: 0.363 ms
 Execution Time: 8.211 ms
(8 rows)

DROP INDEX
```

กฎที่ใช้ได้จริงสำหรับ PostgreSQL 18 คือ: วาง column ที่คุณกรองด้วย `=` เสมอไว้ก่อน และมอง query "column ที่สองอย่างเดียว" ว่าเร็วเฉพาะเมื่อ column แรกมีค่าไม่ซ้ำน้อย (status, type, region) ก่อน 18 มันช้าเสมอ

## Unique index

unique index บังคับกฎด้วย การ insert row ที่สองที่มี `isbn` เดียวกันล้ม:

```sql
-- @expect-error 23505
INSERT INTO books (isbn, title, author_id, published) VALUES (md5('12345'), 'A Duplicate Isbn', 1, 2000);
```

```text
ERROR:  duplicate key value violates unique constraint "books_isbn_key"
DETAIL:  Key (isbn)=(827ccb0eea8a706c4c34a16891f84e7b) already exists.
```

`NULL` หลายตัวอนุญาตใน column unique โดยค่าเริ่มต้น เพราะ `NULL` ไม่เท่ากับ `NULL`; `UNIQUE NULLS NOT DISTINCT` (PostgreSQL 15+) เปลี่ยนเรื่องนี้:

```sql
-- sql/unique-nulls.sql
CREATE TABLE codes (code text UNIQUE);
INSERT INTO codes VALUES (NULL), (NULL);
SELECT count(*) AS null_rows FROM codes WHERE code IS NULL;
CREATE TABLE codes_strict (code text UNIQUE NULLS NOT DISTINCT);
INSERT INTO codes_strict VALUES (NULL);
```

```text
CREATE TABLE
INSERT 0 2
 null_rows 
-----------
         2
(1 row)

CREATE TABLE
INSERT 0 1
```

```sql
-- @expect-error 23505
INSERT INTO codes_strict VALUES (NULL);
```

```text
ERROR:  duplicate key value violates unique constraint "codes_strict_code_key"
DETAIL:  Key (code)=(null) already exists.
```

constraint `UNIQUE` หรือ `PRIMARY KEY` สร้าง unique index ให้คุณ: นั่นคือ `books_pkey` ในรายการขนาดข้างบน

## สร้าง index บน table ที่ใช้งานอยู่

`CREATE INDEX` ธรรมดาถือ lock ที่บล็อกการเขียนลง table (การอ่านยังทำได้) จนกว่าจะ build เสร็จ บน table ใหญ่อาจเป็นนาที นี่คือกรณีสอง session: session A สร้าง index, session B ลอง `UPDATE` หลังจากนั้น 0.1 วินาที และรอจน build จบ:

```text
-- session A: script
\timing on
CREATE INDEX books_expr_plain ON books (md5(title || isbn || title));
-- session A: psql output
Timing is on.
CREATE INDEX
Time: 247.257 ms

-- session B (starts 0.1 s later): script
\o /dev/null
SELECT pg_sleep(0.1);
\o
\timing on
UPDATE books SET copies_sold = copies_sold + 1 WHERE id = 1;
-- session B: psql output
Timing is on.
UPDATE 1
Time: 145.352 ms
```

`CREATE INDEX CONCURRENTLY` build โดยไม่บล็อกการเขียน แลกกับงานที่มากขึ้นและการ scan table สองรอบ `UPDATE` เดียวกันที่รันระหว่าง build แบบ concurrent เสร็จใน 2 ms ([docs](https://www.postgresql.org/docs/18/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY)):

```text
-- session A: script
\timing on
CREATE INDEX CONCURRENTLY books_expr_conc ON books (md5(title || isbn || title));
-- session A: psql output
Timing is on.
CREATE INDEX
Time: 272.840 ms

-- session B (same script as above): psql output
Timing is on.
UPDATE 1
Time: 1.990 ms
```

ข้อควรระวัง: ถ้า build แบบ concurrent ล้มเหลว มันทิ้ง index ที่ **invalid** ไว้ ตรงนี้เราเพิ่ม row ที่ title ซ้ำกับที่มีอยู่ แล้วลอง build unique index บน `title`:

```sql
-- @expect-error 23505
INSERT INTO books (isbn, title, author_id, published) VALUES ('dup-title-isbn', (SELECT title FROM books WHERE id = 1), 1, 2000);
CREATE UNIQUE INDEX CONCURRENTLY books_title_uniq ON books (title);
```

```text
INSERT 0 1
ERROR:  could not create unique index "books_title_uniq"
DETAIL:  Key (title)=(The eccbc87e4b5c) is duplicated.
```

```sql
-- sql/invalid-index.sql
SELECT indexrelid::regclass AS index, indisvalid, indisready
FROM pg_index
WHERE indrelid = 'books'::regclass
ORDER BY 1;
DROP INDEX books_title_uniq;
DELETE FROM books WHERE isbn = 'dup-title-isbn';
```

```text
      index       | indisvalid | indisready 
------------------+------------+------------
 books_pkey       | t          | t
 books_isbn_key   | t          | t
 books_title_idx  | t          | t
 books_title_uniq | f          | f
(4 rows)

DROP INDEX
DELETE 1
```

`books_title_uniq` ยังอยู่ (และยังเพิ่มต้นทุนตอนเขียน!) แต่ `indisvalid` เป็น `f` จึงไม่มี query ใดใช้ drop แล้วลองใหม่ `pg_index.indisvalid = false` คือ query ที่ต้องจำหลัง `CONCURRENTLY` ที่ล้มเหลว

## ต้นทุนของ index ตอนเขียน

ทุก `INSERT` ต้องเพิ่ม entry ให้ทุก index 200 000 row เดียวกัน insert ลงสาม table รูปร่างเดียวกันที่มี index แบบ column เดียว 0, 1 และ 5 ตัว:

```sql
-- sql/write-cost.sql
CREATE TABLE w0 (a int, b int, c int, d text, e text);
CREATE TABLE w1 (a int, b int, c int, d text, e text);
```

## Mental Model

index คือสำเนาที่เรียงลำดับของบาง column แต่ละ entry ชี้ไปที่ row ใน table อะไรก็ตามที่ตอบได้ด้วย "หาตำแหน่งนี้ในลำดับ แล้วเดินตามไป" เร็ว: equality, range, prefix (เมื่อลำดับตรงกัน), `ORDER BY`, `MIN`/`MAX` อย่างอื่นถอยกลับไปอ่าน table ทุกการเขียนต้องอัปเดตทุก index index จึงเป็นการแลกเปลี่ยน: อ่านถูกลง เขียนช้าลงและใช้ดิสก์มากขึ้น

## เคล็ดลับและข้อควรระวัง

- index column ที่คุณ filter, join และ sort โดยเรียงตามความสำคัญนั้น primary key และ unique constraint ถูก index อยู่แล้ว
- column foreign key **ไม่** ถูก index อัตโนมัติ: index ถ้าคุณ join ด้วยหรือลบจาก table แม่ ([docs](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-FK))
- สำหรับ composite index วาง column ที่เปรียบเทียบด้วย `=` เสมอไว้ก่อน ตั้งแต่ PostgreSQL 18 query ที่ข้าม column นำหน้ายังใช้ index ผ่าน skip scan ได้ แต่เฉพาะเมื่อ column นั้นมีค่าไม่ซ้ำน้อย
- ตรวจ `EXPLAIN` ก่อนและหลัง planner ละเลย index เมื่อการ scan ถูกกว่า (table เล็ก หรือ query คืน row เป็นสัดส่วนมาก)
- สร้างบน table ที่ใช้งานอยู่ด้วย `CREATE INDEX CONCURRENTLY` และตรวจ `indisvalid` ทีหลัง
- ดู `pg_stat_user_indexes.idx_scan` หา index ที่ไม่เคยถูกใช้ แต่ละตัวทำให้ทุกการเขียนช้าลง

<Callout title="Index ไม่ฟรี">
index ทำให้การอ่านบน column นั้นเร็วขึ้นและทำให้ทุกการเขียนช้าลง อีกทั้งกินดิสก์ (ที่นี่ index ของ `isbn` ใหญ่เกินครึ่งของ table ห้า index ทำให้ bulk insert ช้าลงราว 5.2 เท่า) เพิ่ม index สำหรับ query ที่รันจริง และลบตัวที่ไม่มีใครใช้
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| เพิ่ม B-tree index | จาก 9.1 ms เหลือ 0.06 ms ตอน lookup; ไม่ต้อง sort สำหรับ `ORDER BY ... LIMIT` | 11 MB สำหรับ index `isbn`; เขียนช้าลง (5 index: 384 ms เป็น 1 994 ms สำหรับ insert 200 000) |
| Composite `(a, b)` แทนสอง index | index เดียวรองรับ `a`, `a AND b` และ (PG 18, `a` ไม่ซ้ำน้อย) `b` | index ใหญ่ขึ้น; ไร้ประโยชน์กับ `b` อย่างเดียวเมื่อ `a` มีค่าไม่ซ้ำมาก |
| `text_pattern_ops` | ทำให้ `LIKE 'prefix%'` ใช้ index ได้ | ต้องมี index ที่สองถ้าต้องการ ordering/range ปกติบน column เดียวกัน |
| `CREATE INDEX CONCURRENTLY` | ไม่บล็อกการเขียน | ช้ากว่า scan table สองรอบ และทิ้ง invalid index ได้เมื่อล้มเหลว |

## Common Misconceptions

- **"B-tree รองรับ `LIKE 'prefix%'` เสมอ"** ไม่ใช่ใต้ `en_US.utf8`: index ธรรมดาได้ `Seq Scan`, `text_pattern_ops` ได้ `Index Scan`
- **"composite index ช่วย query บน column ที่สองไม่ได้"** จริงก่อน PostgreSQL 18 เมื่อค่านำหน้าไม่ซ้ำน้อย skip scan ทำให้ใช้ได้ (`Index Searches: 22`) และเมื่อมากมันไม่ได้ผล
- **"index มากยิ่งดี"** ห้า index ทำให้ insert เดียวกันช้าลง 5.2 เท่า
- **"CREATE INDEX CONCURRENTLY ที่ล้มเหลวไม่ทิ้งอะไรไว้"** มันทิ้ง invalid index ที่ยังเสียต้นทุนตอนเขียน
- **"primary key ต้องมี index เพิ่ม"** `PRIMARY KEY` และ `UNIQUE` สร้างให้แล้ว
