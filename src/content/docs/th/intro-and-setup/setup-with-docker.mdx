วิธีที่เร็วที่สุดในการมี PostgreSQL จริงรันอยู่คือใช้ Docker image `postgres` อย่างเป็นทางการ Docker จะดาวน์โหลดฐานข้อมูลสำเร็จรูป เริ่มมันใน container ที่แยกเดี่ยว และปิดให้เรียบร้อยเมื่อคุณใช้เสร็จ — ไม่ต้องติดตั้งทั้งระบบ ไม่มี service ตกค้าง บทเรียนนี้พาคุณจากศูนย์ไปสู่ฐานข้อมูลที่รันอยู่และเชื่อมต่อได้ในไม่กี่คำสั่ง

คุณต้องมี Docker ติดตั้งและรันอยู่ ทุกอย่างด้านล่างใช้คำสั่ง `docker` และ `docker compose` ธรรมดา

> ทุก transcript ในที่นี้รันบน Mac (Docker Desktop 29.6.1, Docker Compose v5.3.0, aarch64) กับ image `postgres:18.6` กันยายน 2026 เพื่อไม่ชนกับสิ่งอื่นบนเครื่องนี้ การรันจริงใช้ container ชื่อ `postgresql-b1-pg`, named volume `postgresql-b1-pgdata` และ host port `55440` transcript แสดงด้วยชื่อของบทเรียน (`pg`, `pgdata`, `5432`) ในจุดที่เป็นแค่ชื่อ ส่วน output ของ `docker ps` ปล่อยไว้ตามจริง ทุกอย่างถูกลบทิ้งหลังใช้ pgAdmin **ไม่ได้** ถูกสตาร์ต (ไม่ได้ pull image) ไฟล์ compose ตรวจด้วย `docker compose config` และรันเฉพาะ service `postgres`

## คำสั่งเดียวเพื่อรัน Postgres

คำสั่งเดียวนี้จะ pull image หากจำเป็นและเริ่มฐานข้อมูล พร้อมตั้งรหัสผ่าน superuser, publish port มาตรฐาน และเก็บข้อมูลไว้ใน named volume เพื่อให้ข้อมูลรอดจากการ restart container

```bash
# scripts/run-postgres.sh
docker run --name pg \
  -e POSTGRES_PASSWORD=secret \
  -p 5432:5432 \
  -v pgdata:/var/lib/postgresql \
  -d postgres:18.6
```

ทัวร์สั้น ๆ เกี่ยวกับ flag ต่าง ๆ:

- `--name pg` ตั้งชื่อที่จำง่ายให้ container เพื่อให้คำสั่งทีหลังอ้างชื่อนี้ได้
- `-e POSTGRES_PASSWORD=secret` ตั้งรหัสผ่านสำหรับ user `postgres` เริ่มต้น ตัวแปรนี้บังคับ ถ้าไม่ใส่ image จะไม่ยอมเริ่มทำงาน (พิสูจน์ด้านล่าง)
- `-p 5432:5432` แมป PostgreSQL port ของ container ไปยัง port เดียวกันบนเครื่องของคุณ เพื่อให้เครื่องมือบน host เชื่อมต่อกับ `localhost:5432` ได้ วิธีนี้ publish บน **ทุก** interface ของ host ใช้ `-p 127.0.0.1:5432:5432` เพื่อให้เข้าถึงได้จากเครื่องคุณเท่านั้น (transcript ด้านล่างทำแบบนี้)
- `-v pgdata:/var/lib/postgresql` mount named volume หนึ่งระดับเหนือ data directory ตั้งแต่ image `postgres:18` cluster อยู่ในไดเรกทอรีย่อยที่ตั้งชื่อตาม version (`18/docker`) ใต้ mount นั้น จึงต้อง mount volume ที่ `/var/lib/postgresql` **ไม่ใช่** `/var/lib/postgresql/data` แบบบทเรียนเก่า ๆ
- `-d postgres:18.6` รัน image อย่างเป็นทางการ ปักตามรุ่นที่คอร์สนี้ตรวจสอบไว้ ในเบื้องหลัง

### เกิดอะไรขึ้นกับ path mount แบบเก่า

บทเรียนที่เขียนสำหรับ PostgreSQL 17 และเก่ากว่า mount `/var/lib/postgresql/data` บน image 18 container นั้นปฏิเสธที่จะเริ่ม:

```text
$ docker run --rm -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:18.6
Error: in 18+, these Docker images are configured to store database data in a
       format which is compatible with "pg_ctlcluster" (specifically, using
       major-version-specific directory names).  This better reflects how
       PostgreSQL itself works, and how upgrades are to be performed.

       See also https://github.com/docker-library/postgres/pull/1259

       Counter to that, there appears to be PostgreSQL data in:
         /var/lib/postgresql/data (unused mount/volume)

       This is usually the result of upgrading the Docker image without
       upgrading the underlying database using "pg_upgrade" (which requires both
       versions).

       The suggested container configuration for 18+ is to place a single mount
       at /var/lib/postgresql which will then place PostgreSQL data in a
       subdirectory, allowing usage of "pg_upgrade --link" without mount point
       boundary issues.

       See https://github.com/docker-library/postgres/issues/37 for a (long)
       discussion around this process, and suggestions for how to do so.
exit=1
```

ข้อความยาวแต่วิธีแก้บรรทัดเดียว: mount `/var/lib/postgresql` (ดู [docker-library PR ที่ข้อความอ้างถึง](https://github.com/docker-library/postgres/pull/1259) และ [เอกสาร image](https://hub.docker.com/_/postgres))

## docker-compose.yml สำหรับการตั้งค่าที่ทำซ้ำได้

การพิมพ์คำสั่งนั้นทุกครั้งเริ่มน่าเบื่อ และบ่อยครั้งคุณอยากได้ GUI ควบคู่กับฐานข้อมูล `docker-compose.yml` เก็บการตั้งค่าทั้งหมดไว้ในไฟล์เดียว เพื่อให้เริ่มทุกอย่างด้วย `docker compose up` ไฟล์นี้รัน PostgreSQL พร้อม **pgAdmin** ซึ่งเป็น web GUI ที่คุณจะได้ทัวร์ในบทถัดไป

```yaml
services:
  postgres:
    image: postgres:18.6
    environment:
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: appdb
    ports:
      - '5432:5432'
    volumes:
      - pgdata:/var/lib/postgresql

  pgadmin:
    image: dpage/pgadmin4
    environment:
      PGADMIN_DEFAULT_EMAIL: admin@example.com
      PGADMIN_DEFAULT_PASSWORD: secret
    ports:
      - '8080:80'
    depends_on:
      - postgres

volumes:
  pgdata:
```

บันทึกเป็น `docker-compose.yml` แล้วเริ่มทุกอย่างจากไดเรกทอรีนั้น:

```bash
# scripts/compose-up.sh
docker compose up -d
```

ตอนนี้ PostgreSQL อยู่ที่ `localhost:5432` และ pgAdmin อยู่ที่ `http://localhost:8080` ถ้าอยากได้ GUI ที่เบากว่า ให้สลับ service `pgadmin` เป็น image `adminer` ซึ่งให้หน้า admin ไฟล์เดียวบน port ของมันเอง ไม่ว่าแบบไหน service ฐานข้อมูลก็ไม่เปลี่ยน นี่คือ service ฐานข้อมูลที่รันจากไฟล์นั้น (เฉพาะ `postgres` และเปลี่ยน host port เป็น `55440`):

## ชิ้นส่วนต่าง ๆ ประกอบกันอย่างไร

## ตรวจสอบและเชื่อมต่อ

ยืนยันว่า container ขึ้นแล้ว จากนั้นเชื่อมต่อ ถ้ามี `psql` บน host ให้ชี้ไปที่ฐานข้อมูลด้วย connection string ถ้าไม่มี `psql` ในเครื่อง image มีติดมาให้แล้ว:

```bash
# scripts/verify-postgres.sh
docker ps
psql "postgresql://postgres:secret@localhost:5432/postgres"
docker exec -it pg psql -U postgres
```

`docker ps` แสดง image `postgres:18.6` สถานะ `Up` และการแมป port transcript ด้านบน (ส่วนแรก) เชื่อมต่อผ่าน published port จาก container ชั่วคราวอีกตัว ซึ่งก็คือเส้นทางเดียวกับที่เครื่องมือบน host ใช้ `\conninfo` แสดง `Server Port | 55440` และ `Password Used | true` ไม่ว่าแบบไหนคุณจะมาอยู่ที่ prompt `postgres=#` พร้อมรัน SQL

volume คือสิ่งที่พาข้อมูลไป volume เดิม container ใหม่เอี่ยม row ยังอยู่ ลบ volume แล้วก็หาย:

## รหัสผ่านและ `trust`

`POSTGRES_PASSWORD` บังคับ เว้นแต่คุณผ่อนการยืนยันตัวตนอย่างชัดเจน พิสูจน์แล้ว:

```text
$ psql -h <host> -p 55441 -U postgres -w -c "select 1 as no_password_needed"     # POSTGRES_HOST_AUTH_METHOD=trust
 no_password_needed 
--------------------
                  1
(1 row)


$ psql -h <host> -p 55442 -U postgres -w -c "select 1"     # POSTGRES_PASSWORD only, no password supplied
psql: error: connection to server at "host.docker.internal" (192.168.65.254), port 55442 failed: fe_sendauth: no password supplied

$ docker run --rm postgres:18.6    # no POSTGRES_PASSWORD at all
Error: Database is uninitialized and superuser password is not specified.
       You must specify POSTGRES_PASSWORD to a non-empty value for the
       superuser. For example, "-e POSTGRES_PASSWORD=password" on "docker run".

       You may also use "POSTGRES_HOST_AUTH_METHOD=trust" to allow all
       connections without a password. This is *not* recommended.

       See PostgreSQL documentation about "trust":
```

`POSTGRES_HOST_AUTH_METHOD=trust` ให้ทุกคนที่เข้าถึง port ได้เข้ามาโดยไม่ต้องใช้รหัสผ่านจริง ๆ ห้ามใช้นอกเครื่องของคุณ และห้ามใช้ร่วมกับ port ที่ publish บนทุก interface

## Mental Model

Image = สูตร (อ่านอย่างเดียว), container = สำเนาที่รันอยู่หนึ่งชุด (ทิ้งได้), volume = ข้อมูล (คงทน), port mapping = ประตู ปัญหาทุกอย่างในบทนี้คือหนึ่งในสี่สิ่งนี้ผิด: tag ผิด, container ตายตอนเริ่ม, volume อยู่ผิด path หรือประตูเปิดให้ทั้งเครือข่าย

## เคล็ดลับและข้อควรระวัง

- named volume คือสิ่งที่ทำให้ข้อมูลของคุณคงอยู่ ลบ container แล้วข้อมูลยังอยู่ ลบ volume แล้วข้อมูลหายถาวร (พิสูจน์ทั้งสองอย่างด้านบน)
- `5432` คือ port เริ่มต้นของ PostgreSQL และ `postgres` คือ superuser เริ่มต้น เครื่องมือต่าง ๆ สมมติค่าเหล่านี้เว้นแต่จะบอกเป็นอย่างอื่น
- `POSTGRES_DB` สร้างฐานข้อมูลเพิ่มเมื่อเริ่มครั้งแรก (`appdb` ด้านบน) ถ้าไม่ใส่ก็ยังมีฐานข้อมูล `postgres` ในตัวให้ใช้
- `POSTGRES_PASSWORD` (และ `POSTGRES_DB`) มีผลเฉพาะตอน data directory ว่าง การเปลี่ยนค่าแล้ว restart บน volume เดิมไม่มีผลอะไร
- `POSTGRES_PASSWORD` บังคับสำหรับ image อย่างเป็นทางการ ใช้ secret จริงนอกการทดลองในเครื่อง ไม่ใช่ `secret`
- ปัก tag `postgres:18.6` คือเป๊ะ `postgres:18` ตาม minor release ส่วน `postgres:latest` จะกระโดดข้าม major และทำให้ volume พัง

container ถูกออกแบบให้ทิ้งและสร้างใหม่ได้อย่างอิสระ แต่ข้อมูลของคุณไม่ควรเป็นเช่นนั้น การเก็บข้อมูลไว้ใน named volume ให้คุณได้ทั้งสองอย่าง: ทำลายและสร้าง container ใหม่กี่ครั้งก็ได้ ขณะที่ row ยังปลอดภัยบนดิสก์
</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| รันด้วย Docker | เร็ว ทิ้งได้ และตั้งค่าเหมือนกันทุกเครื่อง | มี overhead ของ container และต่างจากการ tune บน production host จริงเล็กน้อย |
| ติดตั้ง PostgreSQL แบบ native | ใกล้เคียงสภาพแวดล้อม production จริงกว่า ไม่มีชั้นเพิ่ม | ติดตั้ง/ถอนยากกว่า และต่างกันไปตามระบบปฏิบัติการ |
| ใช้ image ดีฟอลต์ตามเดิม | ใช้งานได้ทันที ไม่ต้องเขียนอะไรเพิ่ม | ไม่ได้ tune หน่วยความจำหรือ config สำหรับ workload เฉพาะของคุณ |
| เขียน Dockerfile เอง | ปรับ config และ extension ได้ตามต้องการ | ต้องดูแล image และอัปเดตเอง |

## Common Misconceptions

- **"`docker compose down` ลบข้อมูลของฉัน"** ไม่ใช่ ที่ลบคือ `down -v` (หรือ `docker volume rm`) ทั้งสองแสดงไว้ด้านบน
- **"volume ต้อง mount ที่ `/var/lib/postgresql/data`"** จริงจนถึง 17 บน image 18 mount นั้นทำให้ container exit
- **"`latest` ใช้ตอนพัฒนาได้"** ใช้ได้จนกว่า tag จะย้ายไป major ใหม่ แล้ว volume เดิมจะไม่สตาร์ต
- **"รันด้วย superuser เริ่มต้นในเครื่องไม่เป็นไร"** มันซ่อน bug เรื่องสิทธิ์ที่คุณจะเจอจริงบน production สร้าง role ที่จำกัดสิทธิ์ไว้ทดสอบ (บทถัดไป)
- **"`POSTGRES_HOST_AUTH_METHOD=trust` แค่สะดวก"** มันเอาการยืนยันตัวตนออกสำหรับทุกคนที่เข้าถึง port ได้ (พิสูจน์ด้านบน)
